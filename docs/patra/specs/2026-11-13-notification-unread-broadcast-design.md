# 通知服务多实例推送未读数工程设计（#406）

> 状态：设计已确认，待实施
> 日期：2026-11-13
> Issue：GitHub #406「通知服务支持多实例推送未读数：加一层广播，连接在任一实例都能收到」
> 依据：实时推送设计 `docs/patra/specs/2026-10-31-notification-realtime-push-design.md`（第 3 节 C「只跑一个实例」、第 6 节）；信箱设计 `docs/patra/specs/2026-10-31-notification-inbox-design.md`（单消费线程）；提醒邮件设计 `docs/patra/specs/2026-10-31-notification-reminder-mail-design.md`（非目标「多实例」）
> 拍板：用户 2026-11-12～13 在会话中确认：广播走 RabbitMQ fanout；本机直推、广播只给别的实例；信箱单消费线程在本 Issue 里修；停机不等推送发完；mini 继续只跑一台。其余选择标了「我的判断」或「实施者定」，汇总在第 16 节

## 1. 要解决的问题

现状：

- 每条推送连接（`SseEmitter`）只活在建立它的那个实例的内存里。`UnreadCountStreamRegistry` 用一个 `ConcurrentMap` 记「用户 → 连接」。
- 信箱事务提交后，`UnreadCountPushListener` 调 `registry.push(用户)`，只能推到本实例的连接。

跑两台以后：A 的连接在实例 1，回复 A 的那条消息被实例 2 消费，实例 2 的表里没有 A，这次推送就没了。提醒已经写进数据库，丢的是实时性：门户在推送连着时停掉了轮询，A 的铃铛要等下一次推送恰好落在实例 1，或者连接满 30 分钟寿命重连，才会更新。

本 Issue 做三件事：

1. 加一层广播：未读数变了，告诉所有实例「这些用户变了」，每个实例推自己手上的连接。广播只带用户 ID，数字照旧现读库。
2. 通知服务里另外两条「只有一个实例」的假设（信箱单消费线程、提醒邮件单机串行）给出结论，该改的一起改。
3. 集成测试里真起两个实例验证。

## 2. 先讲清几个概念

### 2.1 fanout 交换机，每个实例一条临时队列

RabbitMQ 里，生产者把消息发给交换机，交换机按规则投进绑定的队列，消费者从队列取。

- topic 交换机（现在 `interaction.events` 用的）按路由键匹配。一条队列上有多个消费者时，一条消息只给其中一个，这叫竞争消费，适合「这件活儿派给某一台干」。
- fanout 交换机不看路由键，把消息复制一份投进每一条绑定的队列。

要让每台都收到，就让每个实例各有一条自己的队列，绑到同一个 fanout 交换机上。这条队列只为这个实例存在：

- 非持久（broker 重启就没了）、独占（只有声明它的那条连接能用）、自动删除（实例断开即删）。Spring AMQP 的 `AnonymousQueue` 就是这三样，外加一个随机名字。
- 不配死信：广播丢了不需要补。

实例下线，它的队列跟着消失，不会有消息堆在没人收的队列里。

### 2.2 本机直推，广播只给别的实例

提交后，本实例照旧直接推自己的连接，同时发一条广播。广播也会投进本实例自己的队列；消息里带着发送实例的 ID，收到时看到是自己发的就丢掉。

另一种做法是本机也不直推，全部绕 RabbitMQ 一圈。没选：那样单实例时也依赖 RabbitMQ，RabbitMQ 一抖本机推送也没了，做不到「只有一个实例时行为不变」。Socket.IO 的 Redis 适配器也是「本机直推、跳过自己发的广播」。

### 2.3 为什么广播丢了可以接受

推送里没有只存在于消息里的数据：它只说「你的数变了」，数字每次现读库；每条连接一建立，先推一次当前值。所以丢一次推送，丢的只是「早一点知道」，下一次变化或下一次连上就补齐。

这是状态同步，不是必须逐条送达的事件流。逐条送达的东西（例如 IM 消息）要落库、带递增序号、重连时补拉，推送只当提示；本 Issue 不涉及。

### 2.4 single active consumer（单活跃消费者）

RabbitMQ 队列的一个参数 `x-single-active-consumer`。打开后，多个消费者都可以订阅这条队列，但同一时刻只有一个（最先订阅的）收到消息；它断开或取消订阅时，RabbitMQ 把下一个提升为活跃消费者。效果是「多台都待命，只有一台在干」。

这个参数只能在声明队列时设置。已经存在的队列不能原地加，要删掉重建。

## 3. 目标、非目标、反目标

**目标**（即 Issue 验收标准）

1. 连接在实例 1、消息被实例 2 消费时，A 能实时收到最新未读数。
2. 同一用户在两个实例上都有连接时，两边都能收到。
3. 只有一个实例时行为不变。
4. 信箱单消费线程、提醒邮件单机串行两条假设有明确结论（第 7、8 节）；顺带核对的其他假设见第 9 节。
5. 相关单测和集成测试通过。

**非目标**

- 不改 SSE 协议，不换 WebSocket；不把连接表放进 Redis，连接对象只能留在持有它的实例上。（Issue 原文）
- 广播不做可靠送达：不等 RabbitMQ 确认、不进事件登记表、没有死信、失败不重试。
- 停机时不等手上的推送和广播发完再关（用户 11-13 决定不加）。代价：事务已提交、推送还没发出去实例就停了，这次推送丢掉；别的实例上的连接最晚等连接满 30 分钟重连时更新，数据不受影响。见第 10 节。
- 不做「用户 → 实例」的路由表定向投递（第 14 节）。
- mini 继续只跑一台，`patra-infra/docker/docker-compose.apps.yaml` 不改；网关不改。
- 提醒邮件和其他 XXL-Job 任务不改（第 8、9 节）。

**反目标**（出现这些就算失败，哪怕测试是绿的）

- 单实例下推送有可感知的变化：多推一次、推得更晚，或者 RabbitMQ 不可用时本机推送跟着失败、变慢。
- 广播出问题（RabbitMQ 抖动、发不出去、收到坏消息）影响信箱写入事务、拖住信箱消费，或者把异常抛进用户请求。
- 同一实例对同一次变化推两次（自己的广播又推一遍）。
- 两台同时在消费 `notification.inbox`。

## 4. 选型：RabbitMQ fanout，不用 Redis 发布订阅

| | RabbitMQ fanout | Redis 发布订阅 |
|---|---|---|
| 依赖 | 通知服务已经连着 RabbitMQ（信箱、安全邮件） | 通知服务不连 Redis（compose 注释写明不加 `redis.env`），要新加依赖、密码、连接配置 |
| 实例断线期间的消息 | 临时队列随断线删除，丢掉 | 订阅者不在线就收不到，丢掉 |
| 能不能看见 | 管理界面能看到交换机、每个实例的队列和消费者 | 只有 `PUBSUB` 命令，可见性弱 |
| 延迟 | 毫秒级 | 毫秒级（略快，对铃铛没有意义） |

两者在「丢了不补」上一样，而这正是本场景接受的；差别在依赖和可见性。选 RabbitMQ。

## 5. 发送端

### 5.1 在哪发、先后顺序

`UnreadCountPushListener`（信箱事务提交后、`@Async` 在 Boot 的异步线程池上跑）现在只调 `registry.push(ids)`。改成：

1. 先 `registry.push(ids)`，本机推送与今天完全一样。
2. 再调广播端口。端口的实现只把发送任务交给专用线程池（5.2）就返回，不阻塞、不抛异常。

标已读这类在请求线程上触发的变化，不依赖 RabbitMQ 也照常推。

### 5.2 专用线程池：把 RabbitMQ 的慢隔离开（用户 11-13 拍板，按主流做法）

**为什么**：Boot 的 `applicationTaskExecutor` 是 8 个核心线程、无界队列，推送任务都跑在上面。如果广播直接在推送任务里同步发送，RabbitMQ 一旦网络不通（不是立刻拒绝），每次发送都要等满连接超时（事件工具库默认 5 秒）；资源告警时，发布连接被阻塞，发送会一直挂着。8 个线程很快被广播占满，后面任务里的本机推送只能排队，违反反目标第一条。

**做法**：舱壁隔离。一个依赖用自己的线程池，慢了只耗光自己那份。广播是尽力而为的，丢了能补（2.3），所以满了就丢。

- 线程池：`ThreadPoolTaskExecutor`，bean 名 `unreadBroadcastExecutor`。1 个线程，有界队列 500，线程名前缀 `unread-broadcast-`（数字是我的判断，写死，不做成配置项）。
- 满了：丢掉排得最久的一条，打 WARN。日志要防刷屏（例如限频，或者攒一段时间汇总打一条，实施者定）。
- 发送任务里的异常（连不上、超时、转换失败）全部接住、打 WARN，不往外抛。
- 停机时不等队列里的广播发完，直接丢掉（与第 3 节非目标一致）。
- 保住 Boot 的线程池：Boot 发现容器里已经有 `Executor` bean 时，就不再建 `applicationTaskExecutor`，推送的 `@Async` 会跟着换池。所以在 `application.yml` 里设 `spring.task.execution.mode: force`（Boot 4.1.2 的配置项，默认 `auto`），让 Boot 照建它自己的线程池。实施时确认 `@Async` 仍然落在 `applicationTaskExecutor` 上，并改掉 `RealtimeConfiguration` 里「服务里没有别的 `Executor` bean」那句注释。
- 用 bean 而不是在类里自己 new 一个：有 Micrometer 时，Boot 会自动给线程池类型的 bean 挂上监控指标（活跃线程数、排队数），能看出广播有没有在堆积。实施时确认通知服务确实带上了这些指标。

这样，RabbitMQ 卡死时最多耗光这一个线程和它的 500 个排队位；Boot 那 8 个线程不受影响，本机推送照常。

### 5.3 分层与命名（实施者可调整，守分包规则）

- 端口：`domain.realtime.port.<协作者>` 下的驱动端口，例如 `UnreadCountBroadcastPort#broadcast(Set<Long> userIds)`。
- 实现：`infra.realtime.<与端口包同名>` 下的 `UnreadCountBroadcastAdapter`，把发送任务交给 `unreadBroadcastExecutor`，任务里用 Boot 装配的普通 `RabbitTemplate` 发。线程池 bean 定义在哪一层由实施者定。不用 `ConfirmingRabbitMessagingTemplate`（它每次最多等 5 秒确认），不经 Modulith 事件登记表。
- 发布走单独的连接（我的判断）：通知服务加一个 `RabbitTemplateCustomizer`，打开 `usePublisherConnection`。原因：Boot 的 `RabbitTemplate` 默认和监听容器共用同一条连接；通知服务以前只消费不发布，这是它第一次在这条连接上发消息。RabbitMQ 在内存或磁盘告警时会阻塞发布过消息的连接，共用连接时信箱和安全邮件的消费会跟着停。分开以后，被阻塞的只是发布连接。这也是 RabbitMQ 官方「发布和消费用不同连接」的建议。定制器会和事件工具库的 mandatory 定制叠加，不冲突。
- 交换机：持久化的 fanout 交换机，名字 `notification.unread.broadcast`（我的判断）。持久化只是让交换机在 broker 重启后还在，和消息持不持久无关。
- 消息：JSON，两个字段：`origin`（发送实例 ID）、`userIds`（用户 ID 列表）。不带数字。

### 5.4 mandatory 与退回

事件工具库让所有 `RabbitTemplate` 发送都带 mandatory：没有队列可投时，broker 把消息退回。正常情况下 fanout 上至少绑着发送实例自己的队列，不会退回。停机或断线重连的瞬间，自己的队列可能已经删掉，这时广播被退回，忽略即可。实施时确认这种退回只打日志、不抛异常、不刷屏。

## 6. 接收端

### 6.1 队列与监听

- 每个实例声明一条 `AnonymousQueue`，绑到 `notification.unread.broadcast`。名字带前缀，便于在管理界面认出来，例如 `notification.unread.` 加随机串（`Base64UrlNamingStrategy`，我的判断）。
- 监听放 `adapter.realtime.mq`：`@RabbitListener` 监听这条队列，方法参数是具体的消息类型。事件工具库的 JSON 转换器遇到具体参数类型时按参数类型反序列化，不需要改 `patra.events.consumer.trusted-packages`。
- 收到后：`origin` 是本实例，丢弃；否则 `registry.push(userIds)`。`push` 本来就只处理本机有连接的用户，没有连接的用户不读库。
- 处理中的异常接住、打 WARN、不往外抛（我的判断）：免得事件工具库的监听重试（3 次，1 秒起翻倍）拖住这条队列；丢一次推送可以接受。
- 监听用自己的容器工厂，配置同 Boot 的默认工厂，只是不重试（实施时补充）：消息转换失败发生在监听方法之前，上一条的 try/catch 接不住；用默认工厂时一条坏广播会被重试约 7 秒，期间每个实例的广播消费都卡住、推送全部迟到。不重试时 Spring 把转换失败判为无法处理、直接拒绝，临时队列没有死信，就此丢掉。

### 6.2 实例 ID

- 每个 Spring 上下文启动时生成一个随机值（UUID 即可），发送和接收共用同一个 bean。
- 不能取主机名、进程号或静态字段：集成测试在同一个 JVM 里起两个上下文，用这些会让两个实例互相当成自己，广播全被丢掉。
- 放在哪个类、哪一层，实施者定。

### 6.3 消息类型放哪

发送在 infra、接收在 adapter，这两层互不依赖。实施者定：两边各定义一个 JSON 结构相同的 record，或者放在两边都能引用的位置。约束只有一条：这是通知服务内部的消息，不进 `patra-notification-api` 契约。

## 7. 信箱单消费线程：用 single active consumer 保住

### 7.1 问题

`InboxEventListener` 写着 `concurrency = "1"`，注释说明单消费线程是正确性前提：对象墓碑（对象删除后留下的标记，用来挡住之后迟到的事件）没有行可锁，靠顺序处理来互斥。两台各一个消费者，就是两条线程并行处理同一条队列，前提被打破。新旧容器重叠的那段时间也一样（信箱设计里提过，现在靠 CD 先停后起避开）。

### 7.2 改法

- `EventQueue` 加一个开关（例如 `.singleActiveConsumer()`），打开后主队列声明带 `x-single-active-consumer = true`。默认不开，别的队列声明不变；死信交换机和死信队列不受影响。
- 通知服务声明 `notification.inbox` 时打开它。`concurrency = "1"` 保留：每台一个消费线程，single active consumer 保证全局只有一台在收。
- 改 `InboxEventListener` 的注释：单实例内靠 `concurrency = "1"`，跨实例靠队列的 single active consumer。
- `patra-tool-events` 的 README 补上这个开关的用途，以及「已存在的队列要删掉重建」。

### 7.3 剩下的窗口

- 活跃实例崩溃：它没确认的消息退回队列，交给下一个消费者，没有重叠。
- 活跃实例优雅停机：Spring 先取消订阅，RabbitMQ 随即提升下一个消费者。Spring AMQP 默认还会把已经预取到本地的消息（事件工具库默认预取 10 条）处理完才停，这几条会和新活跃实例收到的消息并行。
- 处理：通知服务设 `spring.rabbitmq.listener.simple.force-stop: true`，停机时只处理完手上这一条，其余预取的退回队列。Spring AMQP 的 `setForceStop` 文档写明它适用于单活跃消费者。窗口缩到最多一条。

结论（实施时修订）：剩下「旧实例手上那一条和新实例的第一条并行」，接受。只在真跑多台、做滚动发布时出现；mini 只有一台、CD 先停后起，不会出现。

## 8. 提醒邮件「单机串行」：不用改

核对了 XXL-Job 3.2.0 调度中心源码（`ExecutorRouteFirst`、`JobRegistryHelper`）和提醒邮件代码。

1. **路由「第一个」**：调度中心每 30 秒整理一次在线执行器地址并排序，「第一个」取排序后的第一台。任一时刻，一次调度只派给一台。
2. **「只派一台」不等于「不会两台同时跑」**：
   - 阻塞处理「丢弃后续调度」只在执行器本机生效，管不到别的执行器。
   - 执行器上下线时，排序后的第一台会换人。实例 1 这一轮还没跑完，排序在它前面的新实例注册上来，下一分钟的调度就派给新实例，两台各跑一轮。
   - 执行器停了但还没过期（90 秒没心跳才算下线）时，派给它的调度失败，下一分钟再派。提醒邮件晚一两分钟，可以接受。
3. **两轮重叠时数据层挡得住**：
   - 到点处理（`FlushDueRemindersHandler`）：每人一个事务，先删掉（认领）排队行再建投递，只给认领到的建。注释写明这是为部署切换时两轮重叠设计的。
   - 每日汇总：部分唯一索引 `uk_reminder_delivery_digest` 加 `ON CONFLICT DO NOTHING`，一人一个汇总窗口只有一封。
   - 发送（`SendPendingDeliveriesHandler`）：`findDue` 是不加锁的普通查询，两轮可能取到同一条投递、都去发；投递 ID 就是 Resend 的幂等键（`Resend-Idempotency-Key`），24 小时内只送达一次。本机和 e2e 用的 Mailpit 不认幂等键，会收到两封，不影响线上。

结论：提醒邮件设计里「只有一个实例、不加分布式锁」在多实例下仍然成立。保障来自路由「第一个」加上数据层的认领、唯一索引和幂等键，而不是调度中心的串行。写进 notification README。

## 9. 顺带核对的其他单实例假设

| 项 | 多实例下 | 结论 |
|---|---|---|
| 在站信号 | `PresenceGatewayImpl.markSeen` 写数据库（按主键 upsert），离站邮件读库判断 | 不受影响 |
| 心跳（`@Scheduled`） | 每台给自己的连接发心跳、记在站 | 本来就该每台各跑 |
| 其他 XXL 任务（信箱保留期、注销清理、已处理事件清理） | 路由「第一个」；都是按条件删除，重叠时重复删一遍无害 | 不改 |
| 安全邮件监听 `SecurityMailListener` | 两台竞争消费，一条消息只给一台；重投靠发送记录和幂等键挡重复 | 不改 |
| 网关到通知服务 | 推送路由 `lb-push://patra-notification` 经负载均衡，重连可能落到另一台；本设计正是为此 | 不改 |
| 停机时 `closeAll` | 每台结束自己的连接，浏览器 3 秒后重连，网关转到别台 | 不改 |

## 10. 滚动发布期间

推送只是「变了」的信号、连上先推当前值（2.3），所以大多数情况自动补齐：

| 情况 | 结果 |
|---|---|
| A 连在正在停的实例上 | 停机时 `closeAll` 主动断开，浏览器 3 秒后重连到别台，连上先推当前值，中间的变化一次补齐 |
| 广播到达时 A 正在断开到重连之间 | 每台都没有 A 的连接，丢掉；重连时读库补齐。`open` 先登记连接、再读数：变化在读数之前提交，读数看得到；在登记之后提交，广播来时找得到连接，两种时序都不漏 |
| 重连打到还没下线干净的实例（网关的实例列表有缓存） | 拿到 503，门户立刻取一次未读数、改为轮询，60 秒后再试推送；数字对，实时性暂时退回 60 秒 |
| 触发推送的消息还在 `notification.inbox` 里 | 持久队列，留给活着的实例消费，照常推 |
| 处理到一半、事务没提交就停了 | 消息没确认，RabbitMQ 重投给别台，照常推 |
| 事务已提交、推送和广播还没发出就停了；或提交后、确认前崩溃，重投时被去重跳过 | **这次推送丢掉**。别的实例上 A 的连接等下一次变化，或连接满 30 分钟重连时更新。数据不受影响。用户决定不加「停机等推送发完」（第 3 节非目标） |

## 11. 测试

按 TDD 一个用例一个用例推进。

### 11.1 单元测试

- `EventQueue`：打开开关时主队列带 `x-single-active-consumer = true`；不开时声明与现在完全一样；死信队列不受影响。
- `UnreadCountPushListener`：先本机推、再调广播端口。
- 广播发送实现（线程池部分）：发送卡住时（mock 的 `RabbitTemplate` 阻塞在一个闩上），`broadcast` 照样立刻返回，连续调用也立刻返回；排队满了丢掉最旧的一条；发送抛异常时不往外抛。这就是「广播卡住时本机推送不变慢」的证据。
- 广播监听：`origin` 是本实例时不推；是别的实例时按 `userIds` 推；推送抛异常时不往外抛。
- 广播发送实现：发到 `notification.unread.broadcast`，消息带本实例 ID 和用户 ID（用 mock 的 `RabbitTemplate`，或放进集成测试，实施者定）。

### 11.2 集成测试

`patra-tool-events`：

- 一条打开开关的队列上挂两个监听容器：消息只进先订阅的那个；停掉它之后，后面的消息进另一个。

`patra-notification-boot`（真起两个实例）：

- 同一个 JVM 里起两个 Spring 上下文（实例 A 是测试类自己的上下文，实例 B 由测试另外启动），共用同一套 PostgreSQL、RabbitMQ 容器和 WireMock。B 用随机端口；测试配置已经关掉 XXL 执行器和 Nacos。
- 谁消费信箱要钉死：有了 single active consumer，先完成订阅的实例就是活跃消费者。用 A 先起、B 后起，确定 A 消费信箱。**不要**用 `spring.rabbitmq.listener.simple.auto-startup=false` 去关某个实例的信箱监听，它会把广播监听一起关掉。
- 用例：
  1. A 消费信箱消息，SSE 连在 B：B 上收到新的未读数（验收 1，经 MQ 触发的路径）。
  2. 同一用户在 A、B 上各有一条 SSE：两边都收到（验收 2）。
  3. 在 B 上调标已读接口，SSE 连在 A：A 上收到（请求线程触发的路径）。
  4. 两个实例都在时，信箱消息只被一个实例消费（验证通知服务确实打开了开关；具体断言方式实施者定，例如经 RabbitMQ 管理接口看活跃消费者，或记录处理消息的实例）。
- 原有 `UnreadCountStreamFlowIT` 不改、照常通过（验收 3）。
- 不连 RabbitMQ 的其他集成测试：标已读等触发的广播会发送失败、打 WARN；确认它们不因此失败或明显变慢。

## 12. 上线步骤（mini，仍是一台）

`notification.inbox` 已经存在、不带新参数，新版本启动时按新参数声明会被 RabbitMQ 拒绝（参数不一致）。而且队列被删时，还在跑的旧版本监听很可能会把它按旧参数重新声明出来。所以顺序必须是**先停、再删、再起**：

1. 合并前，在 mini 上停掉通知服务容器。
2. 在 RabbitMQ 管理界面确认 `notification.inbox` 里没有待处理消息，然后删掉这条队列。死信交换机、死信队列不动。
3. 合并 PR，CD 部署并启动新版本。新版本按新参数重建 `notification.inbox` 和它的全部绑定，同时建好 `notification.unread.broadcast` 和本实例的临时队列。
4. 检查：
   - `notification.inbox` 在管理界面上标着单活跃消费者，绑定和以前一样多；
   - `notification.unread.broadcast` 上绑着一条 `notification.unread.` 开头的队列；
   - 用测试账号回复另一个账号，对方门户的铃铛实时变化。

通知服务停着、队列还没重建的这段时间，interaction 发出的事件因为没有队列可投被退回，事件登记行留着，每分钟补投，新版本起来后送达，不丢。如果顺序弄错、新版本先起来了：停掉通知服务，删队列，再启动。

**CD 自动回滚时**（我的判断：写成人工步骤，不改 CD）：新版本不健康时，`patra-infra/cd/deploy.sh` 会自动回滚到上一个健康版本。旧版本按旧参数声明 `notification.inbox` 会被拒绝；事件工具库关掉了 RabbitMQ 健康检查，回滚后服务照样报健康，信箱却可能收不到消息。所以一旦发生回滚：停掉通知服务，删掉 `notification.inbox`，再启动旧版本，让它按旧参数重建。修好后重新部署时，再走一遍上面的 1～4 步。

**本地验收**（我的判断）：用两实例集成测试的结果和日志验收，不在本机连 mini 的 RabbitMQ 跑新代码。Nacos 的 dev 配置让本机通知服务连的是 mini 上的 RabbitMQ：切换前在本机跑新代码，声明会被拒；切换后在本机跑旧分支，也一样。

## 14. 考虑过、没选的做法

- **Redis 发布订阅**：见第 4 节。
- **全部绕 RabbitMQ、本机不直推**：见 2.2。
- **路由表定向投递**：在 Redis 里记「用户 → 实例」，靠 TTL 和心跳续期，消息只投给持有连接的实例。省掉无关实例的消息，但要维护路由表的一致性（实例崩溃后的残留、续期失败）。连接数大到广播成本可观时才划算，Patra 的规模用广播更简单。
- **独立长连接网关或托管服务**（AWS API Gateway WebSocket、Azure Web PubSub、Pusher、Ably）：连接和业务分开，适合超大规模；对单人项目是过度设计。
- **用 Resilience4j 的 `ThreadPoolBulkhead` 做隔离**：效果和 5.2 一样，但只为一处引一个框架不划算。主流项目里这类框架主要包在服务间的 HTTP / RPC 调用外面。
- **全局打开虚拟线程**（`spring.threads.virtual.enabled`）：阻塞的虚拟线程几乎不占资源，8 个线程的问题本身就没了。但这是全局开关，Tomcat 请求线程和所有异步任务都会受影响，不在本 Issue 范围内。
- **停机时等推送和广播发完**：把 Boot 异步线程池配成停机时等几秒，能关掉第 10 节最后一种情况的大部分。用户决定不加。
- **把信箱交接窗口压到零**：给信箱监听单独配一个预取 1 的容器工厂也只能做到「最多一条」，和 `force-stop` 一样；要真正为零得让新实例等旧实例确认完，RabbitMQ 的单活跃消费者不提供。不做。
- **给提醒邮件加分布式锁**：数据层已经挡住重复（第 8 节），锁没有增量收益。
- **换信箱的互斥方式**（例如给对象墓碑加可锁的行）：改动大；single active consumer 一个队列参数就解决。
