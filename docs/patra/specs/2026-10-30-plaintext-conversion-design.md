# 正文转纯文本：规则定稿与转换器搬家（PAP-128）

> **Issue**：PAP-128（v0.16 决策 J）
> **release spec**：`docs/patra/release-specs/v0.16-notification.md` 第 4 节 J
> **上一版设计**：`docs/patra/specs/2026-10-27-interaction-notification-design.md` 第 6.2 节（v0.14 的摘录做法，本文取代其中的转换规则）
> **状态**：定稿（2026-10-30 用户确认总原则、引用块与链接的写法）

## 1. 要解决什么

评论正文是 Markdown，@ 存成 `<@用户ID>`。站内提醒、逐条提醒邮件、每日汇总都要显示一段摘录，摘录得是**纯文本**：只有字，没有 `**`、`[]()` 这类标记。

v0.14 已经有一个转换器（`CommonmarkPlainTextAdapter`），但有三个问题：

1. **放错了地方**。它在 interaction 的 `notification` 子域里，PAP-143 要删掉这个子域。决策 J 定了「interaction 转好、事件里带全文纯文本，通知服务只截断」，转换器得搬到评论和投稿经验都能用的位置。
2. **和门户看到的对不上**。门户只认 Markdown 的一部分语法，转换器却按完整的 Markdown 解析：图片、代码块、分隔线在门户上显示的是原文，转换器给出的却是别的东西。
3. **只适合站内单行显示**。所有换行都压成了一个空格；邮件想分行显示时，已经找不回原来的段落。

本文定下：每种元素怎么转、转换器放哪、纯文本里 `<@ID>` 的约定、各渠道怎么截断。

## 2. 几个概念

- **Markdown 子集**：门户只放行 Markdown 的一部分语法（粗体、斜体、引用、列表、链接、行内代码），其余的（代码块、HTML、分隔线、图片……）关掉，关掉的写法按原文显示。这样评论区不会出现大标题、外链图片，也不会被 HTML 注入。代码在 `patra-portal/src/lib/markdown/subset.ts`。
- **语法树**：解析器先把 Markdown 读成一棵树：段落下面挂文字、粗体、链接，链接下面再挂链接文字。转纯文本就是走一遍这棵树，只收集文字。用正则硬剥标记会把转义、行内代码里的星号也剥掉，所以要走树。
- **源位置（source span）**：解析器可以给树上每个节点记下它在原文里从第几个字符开始、有多长。门户对图片这类关掉的写法要显示原文，转换器就靠源位置把那一段原文取回来。
- **扩展字素簇**：用户眼里的「一个字」。`é` 可能是两个码点，一个家庭 emoji 是七个码点拼成的，但都只算一个字。按它截断，才不会把 emoji 切成乱码。Java 里用 `BreakIterator.getCharacterInstance()` 数。
- **零宽连接符（U+2060 WORD JOINER）**：一个看不见、不占宽度、也不会在这里换行的字符。下文用它把「长得像提及的普通文字」断开（第 4 节）。

## 3. 转换规则

### 3.1 总原则

**纯文本 = 读者在门户上看到的那些字，去掉样式，结构只留换行。**

门户关掉的写法显示原文，纯文本也给原文；门户渲染成样式的，纯文本只留文字。这样提醒里看到的摘录，和点进去看到的评论是同一段话。

### 3.2 逐元素

| 元素 | 写法举例 | 门户显示 | 纯文本 |
|---|---|---|---|
| 提及（服务端写下的） | `<@42>` | `@用户名` 链接 | `<@42>` 原样保留，不换成名字（决策 J） |
| 长得像提及的普通文字 | `` `<@42>` ``、`\<@42>`、不在提及名单里的 `<@42>` | 原文 `<@42>` | `<⁠@42>`：`<` 与 `@` 之间插一个 U+2060，看起来一样，但不会被认成提及（第 4 节） |
| PMID / DOI / 网址 | `PMID: 27940189`、`doi:10.1038/x`、`https://…` | 原文，自动成链接 | 原文，一个字不改 |
| 链接 | `[这篇综述](https://…)` | 文字（链接） | 只留文字：`这篇综述` |
| 尖括号网址 | `<https://x.org>` | 原文（门户关掉了这个写法） | 原文 `<https://x.org>` |
| 引用式链接 | `[x]` 加一行 `[x]: https://…` | 原文（门户关掉了链接定义） | 两处都是原文 |
| 图片 | `![图](https://…/a.png)` | 原文（门户不加载图片） | 原文 `![图](https://…/a.png)` |
| 行内代码 | `` `a*b` `` | 代码样式的 `a*b` | `a*b` |
| 跨行的三反引号 | ```` ```\ncode\n``` ```` | 原文，按行显示 | 原文，按行保留 |
| 缩进四格的行 | `    x` | 普通段落（门户关掉了缩进代码块） | 普通文字 `x` |
| 引用块 | `> 文中说 OR=1.8` | 引用样式 | 外面加中文引号：`“文中说 OR=1.8”` |
| 无序列表 | `- 一\n- 二` | 圆点列表 | 每项一行，前缀 `• `：`• 一`、`• 二` |
| 有序列表 | `3. 甲\n4. 乙` | 编号列表（从 3 开始） | 每项一行，前缀「编号. 」：`3. 甲`、`4. 乙` |
| 列表里套列表 | `- a\n  - b` | 外层是列表，里层按原文显示 | 外层同上，里层原文 `- b` |
| 标题 | `# 结论`、`结论\n---` | 粗体段落 | 文字一行 |
| 粗体、斜体 | `**粗**`、`*斜*` | 样式 | 只留文字；配不成对的星号（`2 * 3`）原样 |
| HTML | `<b>x</b>`、`<div>` | 原文（门户不渲染 HTML） | 原文 |
| 分隔线 | `***`、`---` | 原文（门户关掉了分隔线） | 原文 |
| 转义 | `\*`、`&amp;` | `*`、`&` | `*`、`&` |
| 段落、列表项、引用之间 | 空行分段 | 分段 | 换行 `\n` |
| 段落里的换行 | 回车、行尾两空格、行尾 `\` | 换行（门户装了 remark-breaks） | 换行 `\n` |
| 空白 | 连续空格、制表符、全角空格、不换行空格 | — | 每行内合成一个空格；每行去掉首尾空白；去掉空行 |

**引用块（用户 2026-10-30 选定）**：文献讨论里引用的多是论文原句，删掉的话评论人后面说的话就没了上下文；原样保留又分不清哪句是引用。所以推荐**保留内容、外面加中文引号**。另两个选项：原样保留不加标记（v0.14 的做法）；删掉引用、只留评论人自己的话（Discourse 论坛摘要的做法，整条只有引用时才保留）。多层引用每层各加一对引号；空引用整个省略。代价（用户已知）：引用一长，站内 120 字、汇总 80 字的摘录可能整段都是引文，不另加规则。

**链接只留文字（用户 2026-10-30 选定）**：和门户看到的一样；邮件里有「查看并回复」按钮，点回站上就能看到链接。另一个选项「文字（网址）」会让网址占掉摘录的大部分字数。

**列表前缀**：圆点和编号在门户上是看得见的，留下前缀，压成一行时项与项之间也分得开（`• 一 • 二`）。

### 3.3 和 v0.14 的差别

| 元素 | v0.14 | 现在 |
|---|---|---|
| 图片 | 替代文字 | 原文 |
| 三反引号代码 | 去掉反引号，只留代码 | 跨行的给原文；单行的仍是行内代码，只留代码 |
| 缩进四格的行 | 代码块，里面名单内的 `<@ID>` 也当提及 | 普通段落（与门户一致），提及照常 |
| 分隔线 | 一个空格 | 原文 |
| 尖括号网址 | 去掉尖括号 | 原文 |
| 引用式链接 | 链接文字，定义行消失 | 原文 |
| 转义的 `\<@ID>` | 在名单里就当提及 | 一律是普通文字 |
| 换行、段落 | 压成一个空格 | 换行 `\n` |
| 引用块 | 只留文字 | 加中文引号 |
| 列表 | 只留文字 | 每项一行，带前缀 |

## 4. 纯文本里 `<@ID>` 的约定

**问题**：纯文本是一个普通字符串，消费方（通知服务、以后的搜索）只能靠找 `<@数字>` 认出提及。但正文里也可能有长得一样的普通文字：用户在行内代码里写了 `` `<@42>` ``，或者打了 `\<@42>`（客户端发来的标记会被服务端转义），或者投稿经验的正文（不解析 @，用户手打的 `<@42>` 原样存着）。如果这些也被当成提及，邮件里会出现「@某个真实用户的名字」：既显示错了，也等于让人用随便一个用户 ID 换出这个人的名字。

**可选做法**：

- **转义**：字面的 `<` 写成 `\<`、`\` 写成 `\\`（v0.14 存库的 `ExcerptText` 就是这么做的；Slack 把字面的 `<`、`>`、`&` 写成 HTML 实体）。消费方必须先反转义，忘了的话 `p<0.05` 会显示成 `p\<0.05`，而医学评论里 `p<0.05` 很常见。
- **随事件带提及名单**：消费方只把名单里的 ID 当提及。每个消费方都得保存、对照名单。
- **把字面的那几处断开**：在 `<` 与 `@` 之间插一个看不见的字符，字面文字就再也匹配不上提及的写法。Discord 的机器人防止误 @ 全体，就是在 `@` 后面插零宽空格。

**选择**：断开。

- 转换器认定提及的条件：门户也会把它当提及（不在行内代码里、没被转义），**并且** ID 在调用方给的提及名单里。评论传事件里的 `mentionedUserIds`；投稿经验传空名单，正文里的 `<@ID>` 一律是普通文字。
- 其余凡是正好写成 `<@数字>` 的文字（`数字` = `[1-9][0-9]{0,18}`，包括超出 long 范围的 19 位数），输出时在 `<` 与 `@` 之间插入 U+2060，写成 `<⁠@42>`。
- 消费方的约定：**输出里每个 `<@数字>` 都是真提及**，用正则 `<@([1-9][0-9]{0,18})>` 找出来、按 ID 现查名字即可，不用名单，也不用反转义。U+2060 看不见，原样显示即可。
- 拼字的情况也算：`<@*5*>`、`<@5` 后面接粗体 `>` 这类拆在几个节点里的写法，按拼好后的整段文字判断。

**代价**：纯文本里会混进一个看不见的字符（只在这种罕见写法里出现），复制出去时会带着它；按字素数时它单独算 1。

## 5. 截断规则（通知服务实现，PAP-143 / PAP-146）

转换器给的是全文，截多长由显示方按渠道决定。所有渠道共用一套截法：

1. **换名字**：每个 `<@ID>` 换成 `@名字`（主页对收件人可见时用用户名，否则用昵称，identity 不认识的写成 `@已注销用户`，同 v0.14 的 `ExcerptRules`）。
2. **单行渠道先压成一行**：`\n` 换成空格。要压的话必须在数字数之前做：`BreakIterator` 把 `\n` 也算一个字素。
3. **按字素数**：数的是换好名字后的文字。
4. **提及不切开**：`@名字` 整个放得下才放，放不下就停在它前面。不会出现 `@chen-` 这种半个名字。
5. **截了才加省略号**：截掉了东西时，去掉末尾空白，再加 `…`（U+2026）；省略号不计入长度。站内提醒的省略号由门户加（接口返回 `excerptTruncated`）。

**默认长度**（按 PAP-140 设计稿，用户 2026-10-30 确认）：

| 渠道 | 长度（字素） | 换行 | 理由 |
|---|---|---|---|
| 站内提醒摘录 | 120 | 压成一行 | 沿用 v0.14，门户列表两行截断 |
| 单条提醒邮件 | 300 | 保留 | 一封只有一条提醒，给够读懂一段回复的量 |
| 每日汇总、多条合一的邮件（列表每条） | 140 | 压成一行 | 一次列多条，每条看个大意，点进去看全文；一封最多列 10 条（归 PAP-146） |

**例子**（`<@5>` 的名字是 `chen-yu`，`@chen-yu` 占 8 个字素）：

- `同意 <@5> 的看法`，上限 12：`同意 `（3）+ `@chen-yu`（8）+ 空格（1）正好 12，`的` 放不下 → `同意 @chen-yu…`（去掉末尾空格再加省略号）。
- 同一句，上限 10：`同意 ` 之后 `@chen-yu` 整个放不下，停在它前面 → `同意…`，而不是 `同意 @chen-…`。
- `第一段\n第二段`：单行渠道 → `第一段 第二段`；邮件 → 保留两行。

**放进邮件 HTML 时要转义**：纯文本里可能有字面的 `<b>`、`<https://…>`，消费方把它当文本插进邮件，不能当 HTML。

## 6. 落点

### 6.1 放进底座子域 subject

interaction 的子域里，普通子域只公开 `port.read`、`model.read`、`event` 三个包；**底座**（`subject`）对同服务所有子域完全公开，约定只放被两个以上子域共用的东西。

- 评论（`discussion`）和投稿经验（`post`）的正文是同一种 Markdown 子集：门户用同一个 `MarkdownBody` 组件渲染两者。转换器只认这个格式，属于两个内容子域共用的东西，放底座。
- 放在 `discussion` 的话，`post` 以后要用（搜索、经验的摘录）就得再搬一次；放在 `notification` 就是现在的问题。
- 使用方：`notification` 现在就用（到 PAP-143 删除为止）；PAP-141 由 `discussion` 发集成事件时用；`post` 以后需要时直接用。

| 东西 | 位置 |
|---|---|
| 端口 `PlainTextPort` | `domain.subject.port.markdown` |
| 值对象 `PlainText` | `domain.subject.model.vo` |
| 实现 `CommonmarkPlainTextAdapter` | `infra.subject.markdown`（与端口包同名，分包规范的要求） |
| 解析器扩展 `AngleBracketInlineParser`、`MentionNode` | `infra.subject.markdown` |

删除：`domain.notification.port.excerpt.PlainTextPort`、`infra.notification.excerpt.CommonmarkPlainTextAdapter`。`InteractionArchitectureTest` 不用改：依赖底座不用声明。

### 6.2 接口

```java
// domain.subject.port.markdown
public interface PlainTextPort {
  PlainText toPlainText(String markdown, Set<Long> mentionedUserIds);
}

// domain.subject.model.vo
public record PlainText(String value) {
  public static final Pattern MENTION = Pattern.compile("<@([1-9][0-9]{0,18})>");
}
```

`PlainText` 把第 4 节的约定写在类注释里，`MENTION` 是消费方认提及用的正则。PAP-141 把 `value()` 原样放进集成事件。

### 6.3 实现要点（commonmark-java 0.30.1）

- **对齐门户的子集**：
  - `enabledBlockTypes(Heading, BlockQuote, ListBlock)`：关掉缩进代码块、围栏代码块、HTML 块、分隔线，这些写法落回普通段落或行内文字，和门户的 `DISABLED_CONSTRUCTS` 一致。
  - 自定义行内解析器 `AngleBracketInlineParser`，碰到 `<` 触发（自定义的排在内置的前面）：是 `<@数字>` 就产出 `MentionNode`；否则把这个 `<` 当普通文字吃掉。这样尖括号网址和行内 HTML 都解析不出来，等于关掉了这两种写法。转义和行内代码先于它处理，所以 `\<@42>` 和代码里的 `<@42>` 进不来。
  - 门户在解析后按原文显示的写法（图片、列表项里的子列表、跨行的三反引号），以及门户关掉了的链接定义、引用式链接，用源位置（`includeSourceSpans(BLOCKS_AND_INLINES)`）取回原文。每行一个源位置，引用块里的行不含开头的 `>`。
- **收集文字**：走一遍语法树，字面文字先攒着；碰到真提及时，先把攒着的文字断开长得像提及的部分（第 4 节）再写出，然后写 `<@ID>`。引用块、列表项先在一个子收集器里转好，再加引号或前缀。
- **整理空白**：按 `\n` 分行，每行把连续空白（Unicode 空白，含全角空格、不换行空格）合成一个空格、去掉首尾空白，删掉空行，再用 `\n` 拼回。
- 解析器线程安全，全局共用一个；自定义行内解析器每次解析由工厂新建。
- 正文最多 5,000 字素，一次转换是微秒到毫秒级。

### 6.4 notification 子域的过渡（到 PAP-143 为止）

提醒摘录照常可用，按新规则输出：

- `CommentNotificationListener` 改用底座的 `PlainTextPort`，再把 `PlainText` 转成存库的 `ExcerptText`。
- 新增 `ExcerptText.fromPlainText(PlainText)`：`<@ID>` 变成提及段，其余是字面段，`\n` 换成空格（站内是单行渠道）。存库写法、300 单位的存储上限不变。
- `ExcerptRules.render` 按第 5 节截断：提及不切开；截了时去掉末尾空白。仍是 120 字素，省略号仍由门户加。

## 8. 不做的事

- 集成事件的字段与发布（PAP-141）；通知服务里的截断、换名字、邮件版式（PAP-143、PAP-146）。本文只定规则和长度建议。
- 已存的提醒摘录不回头重算：PAP-143 会连同表一起删掉。
- 门户自己的 `markdownToPlain`（经验列表的两行摘录、页面描述）用途不同，不改。
- 投稿经验正文里手打的 `<@ID>` 在门户上会显示成「@已注销用户」：门户的问题，已报编排会话。

- 纯文本里用 U+2060 断开同形文字（第 4 节）。
- 列表前缀 `• ` 与「编号. 」；多层引用各加引号。
- 截断的五条规则（第 5 节）；默认长度按 PAP-140 设计稿，用户已确认。
- 门户关掉的写法一律给原文，包括引用式链接与链接定义（极少出现，但规则统一）。
