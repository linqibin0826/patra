# v0.16 Notification 上线 runbook

> 一次性操作手册：把 v0.16 的后端（新服务 notification、RabbitMQ，以及 interaction、identity、`patra-tool`、网关的改动）上到 mini。
> 设计依据：`docs/patra/specs/2026-10-30-notification-skeleton-design.md` 第 12 节（接入核对单）、第 14 节（XXL-Job）、第 15 节（本机启动与 mini 操作）、第 17 节（本手册结构）。
>
> - 在 MacBook 的仓库根目录执行；mini 上的命令经 `ssh mini` 执行。
> - 每步给出命令、预期结果和失败时的动作。**改动 mini 的步骤，先确认上一步的预期全部满足，并征得用户同意再执行。**
> - 不打印任何密钥：命令只输出状态码、计数和名字。
> - 实测结果写回 release spec 第 5 节（D3、D10 等）的「实际：」行。
>
> 本手册由 PAP-139 建立，写了环境约定与 notification 的接入。**其他 Issue 不另建 runbook**：合并前的步骤补进第 5 步，合并后的步骤补进第 7 步，各自一个小节，标明 Issue。


预期：`6600 空闲`、`6601 空闲`、`0`。端口被占：查清是谁再继续。库已存在（`1`）：跳过下一条命令。

```bash
ssh mini 'docker exec patra-postgres psql -U postgres -c "CREATE DATABASE patra_notification"'

```

预期：`CREATE DATABASE`，然后 `1`。

## 3. 本机冒烟需要时：推送 notification 的 Nacos 配置

只有在合并前要在本机起 notification 时才做（开发期可能做多次）。合并后 CD 的 `nacos-push` 每次都会全量同步，不用手动推。

`nacos-push.sh` 是全量同步：Nacos 里有、目录里没有的会被删掉。v0.16 有多个分支并行开发，别的分支可能已经推了自己的配置，从这个分支推会把它们删掉。先只对比：

```bash
NACOS_ADDR=http://100.103.73.27:8848 bash patra-infra/scripts/nacos-push.sh --check
```

预期：退出码 `2`，差异**只有**当前分支相对 main 改过的文件（PAP-139 时只有「新增 patra-notification.yaml」）。`--check` 只打印「新增 / 更新 / 删除 X」，看不出改动是谁的，按下面的规则判断，有一条不满足就**停下，不推**，把差异交给编排会话：

- 出现任何「删除 X」：停。那是别的分支推上去、本分支没有的文件，推了就删掉它。
- 「新增 X」或「更新 X」：X 必须是本分支改过的文件，即 `git diff --quiet origin/main -- patra-infra/nacos/dev/X` 的退出码非零（先 `git fetch origin main`）。X 在本分支与 main 一致却出现在差异里，说明别的分支推过它，推了就冲掉对方的改动：停。

差异里有别的服务的配置时要格外小心：推上去后 mini 上正在跑的 main 版本服务会立刻热刷新，新值它不认就刷新失败、一直用旧值（`patra-infra/CLAUDE.md`「Nacos 配置写错时镜像回滚没用」）。先确认 main 上的代码接受这些新值，拿不准就不推，等后端 PR 合进 main 由 CD 推。

确认后推送：

```bash
NACOS_ADDR=http://100.103.73.27:8848 bash patra-infra/scripts/nacos-push.sh
NACOS_ADDR=http://100.103.73.27:8848 bash patra-infra/scripts/nacos-push.sh --check; echo "exit=$?"
```

预期：第二条 `exit=0`。

**注意**：后端 PR 合进 main 之前，main 每次有后端路径的推送，CD 都会按 main 的目录全量同步，把 `patra-notification.yaml` 删掉。本机起 notification 报「没读到签到 patra.config-source.service」时，重做本步。

## 6. 后端 PR 合进 main、CD 结束后：核对 notification

改了 `build.gradle.kts`、`settings.gradle.kts`、`patra-infra/cd/*`，CD 会全量重建并重部署全部 6 个后端服务，这是预期的。部署顺序：registry、identity、gateway、catalog、interaction、notification。

```bash
SHA="$(git rev-parse origin/main)"   # 先 git fetch origin main，确保是这次合并的提交
until RUN_ID="$(gh run list --workflow cd.yml --commit "$SHA" -L 1 --json databaseId -q '.[0].databaseId')" && [ -n "$RUN_ID" ]; do sleep 10; done
gh run watch "$RUN_ID" --exit-status > /dev/null; echo "CD exit=$?"
gh run view "$RUN_ID" --log | grep -E '===== deploy|全部部署成功|自动回滚|✗'
```

按提交号取运行：合并后 CD 的运行要过几秒才创建，按分支取最新一次会拿到上一次运行、马上「成功」返回。

预期：`CD exit=0`；有 `===== deploy notification`，最后是 `✓ 全部部署成功`。

```bash
ssh mini 'bash -s' <<'EOF'
docker ps --filter name=patra-notification --format '{{.Names}}\t{{.Image}}\t{{.Status}}'
curl -s http://127.0.0.1:6600/actuator/health | jq -c '{status}'
curl -s -o /dev/null -w 'api-docs via gateway: %{http_code}\n' http://127.0.0.1:9528/patra-notification/v3/api-docs
curl -s -o /dev/null -w 'actuator via gateway: %{http_code}\n' http://127.0.0.1:9528/patra-notification/actuator/health
docker stats --no-stream --format '{{.Name}}\t{{.MemUsage}}' patra-notification
EOF
```

预期：

- 容器镜像 tag 是本次合并的提交 sha，状态 `healthy`。
- `{"status":"UP"}`。
- `api-docs via gateway: 200`；`actuator via gateway: 403`（网关拒绝名单，符合设计）。
- 内存一栏的上限是 `1GiB`，用量在上限内。

```bash
ssh mini 'cd ~/actions-runner/_work/patra/patra && bash patra-infra/scripts/nacos-verify.sh --expect-services'
```

预期：全部 PASS，第 10 项「public 下 6 个 patra 服务都有实例」PASS。

调度中心：执行器管理里 `patra-notification` 的 OnLine 机器地址是 `http://<容器 IP>:6601/`。

退路：

| 情况 | 会发生什么 | 怎么办 |
|---|---|---|
| notification 不健康 | 第一次部署没有 last-good，它停在 unhealthy，不影响其他服务 | `ssh mini 'docker logs patra-notification --tail 100'`：库不存在回第 2 步；Nacos 签到缺失查 CD 的 nacos-push；修好后重新推送 |
| 日志报 `Migration checksum mismatch` / `Validate failed` | 已经在 mini 的 `patra_notification` 上执行过的脚本被改了（开发期本机连 mini 的库时最容易发生），Flyway 校验不过 | dev 数据可丢：删库重建（`DROP DATABASE patra_notification` 再按第 2 步建），或对改动无害的情况跑 `flyway repair`。在 mini 上执行过的脚本不再改，有改动就新增脚本 |
| gateway 不健康 | `deploy.sh` 自动回滚到 last-good；回滚后的网关没有 notification 路由，`/patra-notification/**` 返回 404，其余照常 | 看网关日志，修好后重新推送 |
| 执行器不在线 | 服务照常，只是定时任务调不到 | 查第 4 步的执行器是否已建、AppName 是否是 `patra-notification`；看服务日志里 `XXL-Job 执行器初始化完成` 那行的 port |

### PAP-142：提醒偏好与一键退订

> 合并前不用动 mini：`preference` schema 与表由 notification 第一次启动时的 Flyway 建；身份断言公钥在 `patra-common.yaml`，identity 分组超时写在 jar 的 `application.yml`，不改 Nacos；identity 只多了内部接口 `POST /_internal/users/recipients`，随 identity 的 CD 部署。D5 的完整验收（Gmail 里的退订头、门户落地页）要等 PAP-146 发出真邮件、PAP-148 的页面上线。

**1. 表已建**

```bash
ssh mini 'docker exec patra-postgres psql -U postgres -d patra_notification -Atc "\dt preference.*"'
```

预期：一行 `preference|email_preference|table|…`。失败：看 notification 启动日志里 Flyway 那段。

**2. 偏好接口与一键退订**（在 MacBook 上执行，用测试账号 E，凭据在 `~/.patra/secrets/e2e-e.env`；不打印令牌）

```bash
set -a; source ~/.patra/secrets/e2e-e.env; set +a
GW=http://100.103.73.27:9528
code() { curl --noproxy '*' -s -o /dev/null -w '%{http_code}' "$@"; }
BODY="$(jq -nc --arg e "$PATRA_E2E_VERIFIED_E_EMAIL" --arg p "$PATRA_E2E_VERIFIED_E_PASSWORD" '{email:$e,password:$p,clientType:"web"}')"
T="$(curl --noproxy '*' -s -X POST "$GW/patra-identity/auth/login" -H 'Content-Type: application/json' -d "$BODY" | jq -r .sessionToken)"
P="$GW/patra-notification/me/notification-preferences"
echo "未登录读：$(code "$P")"
echo "读：$(curl --noproxy '*' -s -H "Authorization: Bearer ${T}" "$P")"
echo "改 @ 我的为汇总：$(curl --noproxy '*' -s -X PUT -H "Authorization: Bearer ${T}" -H 'Content-Type: application/json' -d '{"mode":"DIGEST"}' "$P/MENTION")"
```

预期：`未登录读：401`；`读：{"reply":"INSTANT","mention":"INSTANT"}`（E 以前没改过）；`改 @ 我的为汇总：{"reply":"INSTANT","mention":"DIGEST"}`。

接着取 E 的令牌，验落地页读接口与一键退订（令牌只在变量里，不打印）：

```bash
UID_E="$(curl --noproxy '*' -s -H "Authorization: Bearer ${T}" "$GW/patra-identity/auth/me" | jq -r .userId)"
TOKEN="$(ssh mini "docker exec patra-postgres psql -U postgres -d patra_notification -Atc \"SELECT unsubscribe_token FROM preference.email_preference WHERE user_id = ${UID_E}\"")"
U="$GW/patra-notification/unsubscribe"
echo "落地页读：$(curl --noproxy '*' -s "$U?token=${TOKEN}&category=DIGEST" | jq -c '{maskedEmail,alreadyUnsubscribed,othersEnabled}')"
echo "读后档位：$(curl --noproxy '*' -s -H "Authorization: Bearer ${T}" "$P")"
echo "一键退订：$(code -X POST -d 'List-Unsubscribe=One-Click' "$U/one-click?token=${TOKEN}&category=DIGEST")"
echo "再来一次：$(code -X POST -d 'List-Unsubscribe=One-Click' "$U/one-click?token=${TOKEN}&category=DIGEST")"
echo "退订后档位：$(curl --noproxy '*' -s -H "Authorization: Bearer ${T}" "$P")"
echo "令牌错一位：$(curl --noproxy '*' -s "$U?token=A${TOKEN:1}&category=DIGEST" | jq -c '{code,traits}')"
```

预期：落地页读带脱敏邮箱、`alreadyUnsubscribed:false`、`othersEnabled:true`；读后档位不变（`mention` 仍 `DIGEST`）；两次一键退订都 `200`；退订后 `{"reply":"INSTANT","mention":"OFF"}`；令牌错一位得 `NOTIFICATION-0404` 且 `traits` 含 `UNSUBSCRIBE_LINK_INVALID`（令牌首字符本来就是 `A` 时换成 `B`）。

**3. 收尾**：把 E 的「@ 我的」改回 `INSTANT`（`PUT …/MENTION`、`{"mode":"INSTANT"}`），确认 `读` 又是两类 `INSTANT`。

**4. 登记注销清理任务**（PAP-142 建的底座流程；PAP-143 以后给 inbox 接上同一个任务，不另建）

控制台：任务管理 → 执行器选 `patra-notification` → 新增：
- 任务描述 `注销清理（偏好与退订令牌；以后含提醒）`，负责人 `linqibin`
- 调度类型 CRON，`0 30 6 * * ?`（每天 06:30，错开 interaction 的 06:00）
- 运行模式 BEAN，JobHandler `deletedUserCleanupJob`，无任务参数
- 路由策略「第一个」，阻塞处理「单机串行」，任务超时 600 秒，失败重试 0 次

保存后启动，再「执行一次」。预期：调度日志成功，消息形如 `已核对 N 人：清理 M 人，删除 K 行`；notification 日志有 `注销清理完成: scannedUsers=…`。失败（标红、消息 `失败 1 批`）：identity 当时不可用，看 identity 是否健康，次日会自动重跑。
