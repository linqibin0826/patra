# v0.18 Analytics 上线 runbook

> 一次性操作手册：把 v0.18 的后端上到 mini。
> 设计依据：`docs/patra/specs/2026-11-01-analytics-infra-design.md`（PAP-165，第 4 节设计、第 7 节部署方式）。
>
> - 在 MacBook 的仓库根目录执行；mini 上的命令经 `ssh mini` 执行。
> - 每步给出命令、预期结果和失败时的动作。**改动 mini 的步骤，先确认上一步的预期全部满足，并征得用户同意再执行。**
> - 不打印任何密钥：命令只输出状态码、计数和名字。
> - 实测结果写回 release spec 第 5 节的「实际：」行。
>
> 本手册由 PAP-165 建立，写了环境约定与 pipeline 栈（ClickHouse、Kafka）和 Grafana 数据源。**其他 Issue 不另建 runbook**：在第 8 节后各加一个小节，标明 Issue。

| 项 | 值 |

**本机演练的对照值**（MacBook，OrbStack，2026-11-01，同一份 compose）：

| 项 | 值 |
|---|---|

## 1. 部署前：记录资源基线

```bash
ssh mini 'docker stats --no-stream --format "{{.Name}}\t{{.MemUsage}}" | sort; df -h / | tail -1; orbctl config show | grep -i memory'
```

预期：磁盘剩余 ≥ 30 GB（看门狗红线 20 GB；Kafka 最多约 4.4 GiB，ClickHouse 剩余低于 22 GB 时拒绝写入）。把输出贴进 release spec 的「实际：」行，标「上线前」。

剩余不足 30 GB：停下，先清理（旧镜像、构建缓存）。OrbStack 内存：pipeline 栈按上限要 3 GB、Grafana 多 128 MB；release spec 决策 C 算过按上限只剩约 0.6 GB，先按第 6 步实测再定要不要调 OrbStack。

## 2. 部署前：端口空闲

```bash
ssh mini 'for p in 8123 9000 9092; do lsof -nP -iTCP:$p -sTCP:LISTEN >/dev/null && echo "$p 被占" || echo "$p 空闲"; done; echo "PATRA_INFRA_HOST=${PATRA_INFRA_HOST:-未设置}"'
```

预期：三个都空闲；`PATRA_INFRA_HOST=未设置`（或 `linqibins-mac-mini`）。被占：查清是谁再继续。

`PATRA_INFRA_HOST` 决定 Kafka 对外通告的地址（compose 里是 `${PATRA_INFRA_HOST:-linqibins-mac-mini}`）。mini 的非交互 ssh 环境里它若是 IP 或 `127.0.0.1`，MacBook 和 apps 容器拿到的就是这个地址，连接会在引导之后失败；先查清它从哪来（`~/.zshenv` 等）再部署。

## 3. 部署前：密钥

`clickhouse.env`（两台机器同一份）在 MacBook 生成后复制到 mini；`clickhouse-grafana.env` 只在 mini 生成。全程只写文件。

```bash
umask 077 && printf 'CLICKHOUSE_PATRA_PASSWORD=%s\n' "$(openssl rand -hex 32)" > ~/.patra/secrets/clickhouse.env
scp -p ~/.patra/secrets/clickhouse.env linqibin@linqibins-mac-mini:.patra/secrets/
ssh mini 'umask 077 && printf "CLICKHOUSE_GRAFANA_PASSWORD=%s\n" "$(openssl rand -hex 32)" > ~/.patra/secrets/clickhouse-grafana.env'
ssh mini 'ls -l ~/.patra/secrets/clickhouse*.env | awk "{print \$1, \$NF}"; grep -c "=." ~/.patra/secrets/clickhouse.env ~/.patra/secrets/clickhouse-grafana.env'
```

预期：两个文件都是 `-rw-------`，每个文件 `1`（有一行非空值）。

## 4. 部署

```bash
ssh mini 'cd ~/Projects/patra && git pull --ff-only && bash patra-infra/scripts/init-volumes.sh >/dev/null && bash patra-infra/scripts/compose-all.sh up pipeline observability'
```

预期：`==> up patra-pipeline`、`==> up patra-observability` 都无报错。Grafana 首次启动要下载插件，约 1 分钟后才健康。

失败时：

- `env file ... not found`：第 3 步的文件没放到 mini。
- Grafana 一直不健康、日志里插件下载失败（mini 的容器连不上 grafana.com）：按第 7 节「离线装插件」处理。

## 5. 验收（PAP-165 的验收标准）

```bash
ssh mini 'bash -s' <<'EOF'
cd ~/Projects/patra
docker ps --filter name=patra-clickhouse --filter name=patra-kafka --filter name=patra-grafana --format '{{.Names}}\t{{.Status}}'
docker inspect -f '{{.State.ExitCode}}' patra-kafka-init
docker logs --tail 1 patra-kafka-init
# ClickHouse：两个账号（密码从文件读进变量，不打印）
. ~/.patra/secrets/clickhouse.env; . ~/.patra/secrets/clickhouse-grafana.env
curl -s -u "patra:$CLICKHOUSE_PATRA_PASSWORD" --data-binary 'SELECT 1' http://127.0.0.1:8123/
curl -s -u "grafana:$CLICKHOUSE_GRAFANA_PASSWORD" --data-binary 'CREATE TABLE patra_analytics.x (a UInt8) ENGINE=Memory' http://127.0.0.1:8123/ | grep -o 'Code: [0-9]*'
# Kafka：对外通告的地址，以及两个 topic 的配置
docker exec patra-kafka grep '^advertised.listeners' /opt/kafka/config/server.properties
docker exec -e KAFKA_HEAP_OPTS=-Xmx128m patra-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server patra-kafka:29092 --describe --topics-with-overrides | grep -E '^Topic: events'
# Grafana 对 ClickHouse 执行查询（管理员密码从容器环境里取，不写进命令）
GF_PW="$(docker exec patra-grafana printenv GF_SECURITY_ADMIN_PASSWORD)"
curl -s -u "admin:$GF_PW" http://127.0.0.1:3000/api/datasources/uid/clickhouse/health
EOF
```

预期：

1. 三个容器 `Up ... (healthy)`；`patra-kafka-init` 退出码 `0`，最后一行 `topic 初始化完成`。
2. `patra` 返回 `1`；`grafana` 建表返回 `Code: 497`（权限不足）。
3. 通告地址为 `advertised.listeners=INTERNAL://patra-kafka:29092,EXTERNAL://linqibins-mac-mini:9092`；`events.raw` 行 `PartitionCount: 3` 且 `retention.ms=172800000,retention.bytes=1073741824,segment.bytes=268435456,segment.ms=21600000`；`events.dlq` 行 `PartitionCount: 1`、`retention.bytes=536870912,segment.bytes=134217728`。
4. Grafana 健康检查 `"status":"OK"`。

再从 MacBook 验一次 Kafka 的外部地址（通告的是 `linqibins-mac-mini:9092`）：

```bash
nc -zv linqibins-mac-mini 9092
nc -zv linqibins-mac-mini 8123
```

**压满测试**（AC：压满 `events.raw` 时按上限清理）：用不限速的写入压一次最坏情况。会占用约 8.5 GB 磁盘约 1 分钟，先确认第 1 步剩余 ≥ 30 GB。

```bash
ssh mini 'bash -s' <<'EOF'
D=~/.patra/docker/kafka/data
( for i in $(seq 40); do echo "$(date +%T) $(du -sk $D/events.raw-* | awk '{s+=$1} END {printf "%.2f GiB", s/1048576}')"; sleep 5; done ) &
docker run --rm --network patra-net -e KAFKA_HEAP_OPTS=-Xmx256m apache/kafka:4.3.2 \
  /opt/kafka/bin/kafka-producer-perf-test.sh --topic events.raw --num-records 7000000 --record-size 1024 \
  --throughput -1 --producer-props bootstrap.servers=patra-kafka:29092 acks=1 linger.ms=20 batch.size=262144 | tail -1
wait
df -h / | tail -1
EOF
```

预期：写完后约 35 秒内回落，最后稳定在 3.75 GiB 以下；`df` 剩余不低于 20 GB。超出上限的那段 = 写入速率 × 约 35 秒（清理检查 30 秒 + 删除延迟 5 秒）。

压满测试写进去的是假数据，PAP-168 的消费者上线前要清掉（topic 删掉重建）：

```bash
ssh mini 'for t in events.raw events.dlq; do docker exec -e KAFKA_HEAP_OPTS=-Xmx128m patra-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server patra-kafka:29092 --delete --topic $t; done; cd ~/Projects/patra && bash patra-infra/scripts/compose-all.sh up pipeline'
```

## 6. 部署后：记录资源

同第 1 步的命令。预期：`patra-clickhouse` ≤ 2 GiB、`patra-kafka` ≤ 1 GiB、`patra-grafana` ≤ 384 MiB。贴进 release spec 的「实际：」行，标「上线后」，并对照第 0 节的本机值。

OrbStack 用量逼近上限（`orbctl` 显示的内存接近 12 GB，或其他容器被 OOM）：先 `compose-all.sh down pipeline` 腾出内存，再和用户定是收紧上限还是调高 OrbStack（release spec 决策 C）。

## 7. 回滚与常见处理

**整栈撤下**（数据保留，重新 up 即恢复）：

```bash
ssh mini 'cd ~/Projects/patra && bash patra-infra/scripts/compose-all.sh down pipeline'
```

**连数据一起清掉**（ClickHouse 的库、Kafka 的 topic 都会重建为空；⚠️ 不可恢复）：

```bash
ssh mini 'cd ~/Projects/patra && bash patra-infra/scripts/compose-all.sh down pipeline && rm -rf ~/.patra/docker/clickhouse/data ~/.patra/docker/kafka/data && bash patra-infra/scripts/init-volumes.sh >/dev/null'
```

**Grafana 撤掉 ClickHouse**：`git revert` 本 Issue 对 `docker-compose.observability.yaml` 与 `datasources.yaml` 的两处改动，mini 上 pull 后 `compose-all.sh up observability`。插件文件留在 `~/.patra/docker/grafana/data/plugins/` 不影响运行。

**离线装插件**（mini 的容器下载不到时）：在 MacBook 下载、复制过去解压，Grafana 启动时发现已装好的同版本就不再下载。

```bash
curl -fL -o /tmp/ch-plugin.zip 'https://grafana.com/api/plugins/grafana-clickhouse-datasource/versions/4.22.1/download?os=linux&arch=arm64'
scp /tmp/ch-plugin.zip linqibin@linqibins-mac-mini:/tmp/
ssh mini 'cd ~/.patra/docker/grafana/data/plugins && unzip -oq /tmp/ch-plugin.zip && docker restart patra-grafana'
```

**改密码**：改对应的密钥文件（两台机器的 `clickhouse.env` 要一致），再重建容器。ClickHouse 每次启动从环境变量读密码，不用进容器改。

```bash
ssh mini 'cd ~/Projects/patra/patra-infra/docker && docker compose -f docker-compose.pipeline.yaml up -d --force-recreate clickhouse'
# 改的是 clickhouse-grafana.env 时再加：
ssh mini 'cd ~/Projects/patra/patra-infra/docker && docker compose -f docker-compose.observability.yaml up -d --force-recreate grafana'
```

**Kafka 起不来，日志里有 `Invalid cluster.id`**：compose 里的 `CLUSTER_ID` 被改过。改回原值；确实要换集群 ID 只能连数据一起清掉。

**ClickHouse 写入报 `NOT_ENOUGH_SPACE`**：mini 剩余磁盘低于 22 GB，是兜底生效了。先清理磁盘；事件在 Kafka 里最多留 2 天，消费者会接着写。
