# v0.13 Library 上线 runbook

> 一次性操作手册：把 v0.13 的后端（新服务 interaction，以及 identity、catalog 的改动）上到 mini。
> 设计依据：`docs/patra/specs/2026-10-24-interaction-skeleton-design.md` 第 10 节（接入核对单）、第 11 节（XXL-Job）、第 12 节（本机启动与 mini 操作）、第 14 节（本手册结构）。
>
> - 在 MacBook 的仓库根目录执行；mini 上的命令经 `ssh mini` 执行。
> - 每步给出命令、预期结果和失败时的动作。**改动 mini 的步骤，先确认上一步的预期全部满足，并征得用户同意再执行。**
> - 不打印任何密钥：命令只输出状态码、计数和名字。
> - 实测结果写回 release spec 第 5 节（D3、D12）的「实际：」行。
>
> 本手册由 PAP-111 建立，覆盖 interaction 的接入；其他 Issue（如 catalog 的回填重导）把自己的上线步骤补在第 6 步之后。

## 0. 环境与约定

| 项 | 值 |
|---|---|
| mini SSH | `ssh mini` |
| core 栈的检出 | mini `~/Projects/patra`（sparse checkout，只有 `patra-infra`） |
| apps 栈的检出 | mini `~/actions-runner/_work/patra/patra`，由 CD 部署 |
| last-good | mini `~/.patra/cd/last-good-<服务>` |
| 网关 | mini 上 `http://127.0.0.1:9528` |
| XXL-Job 调度中心 | `http://linqibins-mac-mini:7070/xxl-job-admin`，账号见 `patra-infra/docker/README.md`；登录接口是 `POST /auth/doLogin`；MacBook 上 curl 要加 `--noproxy '*'` |
| Nacos 推送 | `patra-infra/scripts/nacos-push.sh`，账号从 `~/.patra/secrets/nacos-push.env` 读 |

前提：后端 PR 的分支已通过门禁（`./gradlew check`、两个 CD 脚本测试）。

## 1. 合并前：记录资源基线（D12）

```bash
ssh mini 'docker stats --no-stream --format "{{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}" | sort; df -h / | tail -1'
```

预期：磁盘剩余 ≥ 20 GB（runner 看门狗的阈值）。把输出贴进 release spec D12 的「实际：」行，标「上线前」。

剩余不足 20 GB：停下，先清理（旧镜像、构建缓存），不要上线。

## 2. 合并前：建 `patra_interaction` 库

必须在服务第一次启动之前：Flyway 要求库已经存在。

```bash
ssh mini 'bash -s' <<'EOF'
lsof -nP -iTCP:6500 -sTCP:LISTEN || echo "6500 空闲"
lsof -nP -iTCP:6501 -sTCP:LISTEN || echo "6501 空闲"
docker exec patra-postgres psql -U postgres -tAc "SELECT count(*) FROM pg_database WHERE datname = 'patra_interaction'"
EOF
```

预期：`6500 空闲`、`6501 空闲`、`0`。端口被占：查清是谁再继续。库已存在（`1`）：跳过下一条命令。

```bash
ssh mini 'docker exec patra-postgres psql -U postgres -c "CREATE DATABASE patra_interaction"'
ssh mini 'docker exec patra-postgres psql -U postgres -tAc "SELECT count(*) FROM pg_database WHERE datname = '"'"'patra_interaction'"'"'"'
```

预期：`CREATE DATABASE`，然后 `1`。

## 3. 本机冒烟需要时：推送 interaction 的 Nacos 配置

只有在合并前要在本机起 interaction 时才做（开发期可能做多次）。合并后 CD 的 `nacos-push` 每次都会全量同步，不用手动推。

`nacos-push.sh` 是全量同步：Nacos 里有、目录里没有的会被删掉。先只对比：

```bash
NACOS_ADDR=http://100.103.73.27:8848 bash patra-infra/scripts/nacos-push.sh --check
```

预期：退出码 `2`，差异只有「新增 patra-interaction.yaml」，以及版本分支上已有、main 上还没有的配置改动。出现说不清来源的差异：停下，先弄清是谁推的。

差异里有别的服务的配置时要格外小心：推上去后 mini 上正在跑的 main 版本服务会立刻热刷新，新值它不认就刷新失败、一直用旧值（`patra-infra/CLAUDE.md`「Nacos 配置写错时镜像回滚没用」）。先确认 main 上的代码接受这些新值，拿不准就不推，等后端 PR 合进 main 由 CD 推。

确认后推送：

```bash
NACOS_ADDR=http://100.103.73.27:8848 bash patra-infra/scripts/nacos-push.sh
NACOS_ADDR=http://100.103.73.27:8848 bash patra-infra/scripts/nacos-push.sh --check; echo "exit=$?"
```

预期：第二条 `exit=0`。

**注意**：后端 PR 合进 main 之前，main 每次有后端路径的推送，CD 都会按 main 的目录全量同步，把 `patra-interaction.yaml` 删掉。本机起 interaction 报「没读到签到 patra.config-source.service」时，重做本步。

## 4. 合并前：调度中心建执行器 `patra-interaction`

执行器在服务启动时上报地址，先建好执行器，第一次部署后马上能看到它在线。

控制台：执行器管理 → 新增：AppName `patra-interaction`，名称 `互动服务`，注册方式「自动注册」。

或者用接口（密码从环境变量读，不写进命令）：

```bash
BASE=http://linqibins-mac-mini:7070/xxl-job-admin; CK="$(mktemp)"
curl -s --noproxy '*' -c "$CK" "$BASE/auth/doLogin" --data-urlencode userName=admin --data-urlencode "password=${XXL_ADMIN_PASSWORD:?先 export XXL_ADMIN_PASSWORD}" | jq -c '{code}'
curl -s --noproxy '*' -b "$CK" "$BASE/jobgroup/pageList" -d 'appname=patra-interaction&title=&start=0&length=10' | jq -c '[.data[]?.appname]'
curl -s --noproxy '*' -b "$CK" "$BASE/jobgroup/insert" --data-urlencode appname=patra-interaction --data-urlencode title=互动服务 -d addressType=0 | jq -c '{code, msg}'
rm -f "$CK"
```

预期：登录 `{"code":200}`；查询结果为 `[]`（已存在就跳过 insert）；insert `{"code":200, ...}`。

## 5. 后端 PR 合进 main、CD 结束后：核对部署

改了 `patra-tool-test`、`build.gradle.kts`、`patra-infra/cd/*`，CD 会重建并重部署全部 7 个后端服务（foundation 扇出），这是预期的。部署顺序：object-storage、registry、identity、gateway、catalog、interaction、ingest。

```bash
SHA="$(git rev-parse origin/main)"   # 先 git fetch origin main，确保是这次合并的提交
until RUN_ID="$(gh run list --workflow cd.yml --commit "$SHA" -L 1 --json databaseId -q '.[0].databaseId')" && [ -n "$RUN_ID" ]; do sleep 10; done
gh run watch "$RUN_ID" --exit-status > /dev/null; echo "CD exit=$?"
gh run view "$RUN_ID" --log | grep -E '===== deploy|全部部署成功|自动回滚|✗'
```

按提交号取运行：合并后 CD 的运行要过几秒才创建，按分支取最新一次会拿到上一次运行、马上「成功」返回。

预期：`CD exit=0`；有 `===== deploy interaction`，最后是 `✓ 全部部署成功`。

```bash
ssh mini 'bash -s' <<'EOF'
docker ps --filter name=patra-interaction --format '{{.Names}}\t{{.Image}}\t{{.Status}}'
curl -s http://127.0.0.1:6500/actuator/health | jq -c '{status}'
curl -s -o /dev/null -w 'api-docs via gateway: %{http_code}\n' http://127.0.0.1:9528/patra-interaction/v3/api-docs
curl -s -o /dev/null -w 'actuator via gateway: %{http_code}\n' http://127.0.0.1:9528/patra-interaction/actuator/health
docker exec patra-postgres psql -U postgres -d patra_interaction -tAc "SELECT string_agg(schema_name, ',' ORDER BY schema_name) FROM information_schema.schemata WHERE schema_name IN ('subject','collection')"
EOF
```

预期：

- 容器镜像 tag 是本次合并的提交 sha，状态 `healthy`。
- `{"status":"UP"}`。
- `api-docs via gateway: 200`；`actuator via gateway: 403`（网关拒绝名单，符合设计）。
- `collection,subject`。

```bash
ssh mini 'cd ~/actions-runner/_work/patra/patra && bash patra-infra/scripts/nacos-verify.sh --expect-services'
```

预期：全部 PASS，第 10 项「public 下 7 个 patra 服务都有实例」PASS。

调度中心：执行器管理里 `patra-interaction` 的 OnLine 机器地址是 `http://<容器 IP>:6501/`。

最后再记一次资源（D12）：

```bash
ssh mini 'docker stats --no-stream --format "{{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}" | sort; df -h / | tail -1'
```

预期：剩余 ≥ 20 GB。与第 1 步一起写进 D12 的「实际：」行，标「上线后」。

退路：

| 情况 | 会发生什么 | 怎么办 |
|---|---|---|
| interaction 不健康 | 第一次部署没有 last-good，它停在 unhealthy，不影响其他服务 | `ssh mini 'docker logs patra-interaction --tail 100'`：库不存在回第 2 步；Nacos 签到缺失查 CD 的 nacos-push；修好后重新推送 |
| 日志报 `Migration checksum mismatch` / `Validate failed` | 已经在 mini 的 `patra_interaction` 上执行过的脚本被改了（开发期本机连 mini 的库时最容易发生），Flyway 校验不过，服务起不来 | dev 数据可丢：确认没有要留的数据后删库重建（`DROP DATABASE patra_interaction` 再按第 2 步建），或对改动无害的情况跑 `flyway repair`。以后在 mini 上执行过的脚本不再改，有改动就新增脚本 |
| gateway 不健康 | `deploy.sh` 自动回滚到 last-good；回滚后的网关没有 interaction 路由，`/patra-interaction/**` 返回 404，其余照常 | 看网关日志，修好后重新推送 |
| 执行器不在线 | 服务照常，只是定时任务调不到 | 查第 4 步的执行器是否已建、AppName 是否是 `patra-interaction`；看服务日志里 `XXL-Job 执行器初始化完成` 那行的 port |

## 6. 第 5 步之后：建两个每日任务（PAP-112 / PAP-113 的代码已在后端 PR 里）

在调度中心「任务管理」选执行器 `patra-interaction` 新增，两项共同设置：路由策略「第一个」，阻塞处理「单机串行」，超时与失败重试按 PAP-112 / PAP-113 的工程 spec。

| 任务 | JobHandler | Cron | 负责人 |
|---|---|---|---|
| 对象对账 | `subjectReconciliationJob` | `0 30 6 * * ?` | 对象登记表（PAP-112）；任务超时 600 秒，失败重试 0 次（有批次失败时调度中心标红，次日自动重跑） |
| 注销清理 | `deletedUserCleanupJob` | `0 0 6 * * ?` | 收藏与收藏夹（PAP-113）；任务超时 600 秒，失败重试 0 次（identity 不可用跳过的批次让调度中心标红，次日自动重跑） |

建好后各手动执行一次。预期：调度日志「调度结果」「执行结果」都成功；`ssh mini 'docker logs patra-interaction --since 5m'` 里有处理条数，没有 ERROR。

对象对账的执行结果形如 `已核对 N 个：换 ID a、失效 b、复活 c`；服务日志有一行 `对象对账完成: type=PUBLICATION, scanned=…, failedBatches=0`。`failedBatches` 大于 0 时执行结果是 `已核对 N 个，失败 M 批`，先查 catalog 是否健康。这一次手动执行的输出写进 release spec D7 的「实际：」。

**catalog 任何换库重建或重跑导入之后（含 PAP-110 的回填），立即手动执行一次 `subjectReconciliationJob`。** 否则到次日 06:30 之前，登记表里还是旧的 catalog ID：文献库按旧 ID 取不到卡片、显示「已失效」，「我的状态」显示没收藏。实现的 Issue 若改了 handler 名或 Cron，以那个 Issue 的工程 spec 为准，同时改这张表。

注销清理的执行结果形如 `已核对 N 人：清理 a 人，条目 b、收藏夹 c`；服务日志有一行 `注销清理完成: scannedUsers=…, deletedUsers=…, failedBatches=0`。`failedBatches` 大于 0 时执行结果是 `已核对 N 人，失败 M 批`，先查 identity 是否健康。日志里的 `identity 不认识这个用户，不删` 是 WARN：identity 省略的 ID 不当成已注销，不删数据，出现时去 identity 核对这个用户 ID。

### 6.1 注销清理的实测（D8）

1. 用测试账号在门户收藏两篇、建一个收藏夹；记下它的用户 ID（`ssh mini` 进 PG 查 `patra_interaction` 的 `collection.library_item`）。
2. 在门户发起注销，等冷静期执行（或按 identity 的 runbook 手动触发注销执行任务），确认 identity 里该用户是 `DELETED`。
3. 手动执行一次 `deletedUserCleanupJob`；执行结果里「清理」至少 1 人。
4. 再查 `collection.library_item`、`collection.collection`、`collection.collection_item` 里该用户 ID 都是 0 行；结果写进 release spec D8 的「实际：」。
