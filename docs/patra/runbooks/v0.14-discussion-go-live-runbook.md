# v0.14 Discussion 上线 runbook

> 一次性操作手册：把 v0.14 的后端（catalog、identity、interaction 的改动）上到 mini。
> 设计依据：release spec `docs/patra/release-specs/v0.14-discussion.md` 第 5 节 D3、D8、D11；各 Issue 的工程 spec：
> [catalog 期刊身份（PAP-117）](../specs/2026-10-27-catalog-venue-identity-design.md) 第 11 节、
> [identity 提及支撑（PAP-118）](../specs/2026-10-27-identity-mention-support-design.md) 第 7 节、
> [interaction 底座扩展（PAP-120）](../specs/2026-10-27-interaction-foundation-extension-design.md) 第 14 节。
>
> - 在 MacBook 的仓库根目录执行；mini 上的命令经 `ssh mini` 执行。
> - 每步给出命令、预期结果和失败时的动作。**改动 mini 的步骤，先确认上一步的预期全部满足，并征得用户同意再执行。**
> - 不打印任何密钥：命令只输出状态码、计数和名字。
> - 实测结果写回 release spec 第 5 节对应 D 项的「实际：」行。
>
> 本手册由 PAP-120 建立。PAP-121 ~ PAP-123（讨论、投稿经验、提醒）的步骤先留好章节，由各 Issue 完成时补上。PAP-119（PubMed 审稿周期）已于 2026-10-27 撤出本版，本手册不含它的步骤。

## 2. 合并前：catalog `nlm_id` 只读核对（PAP-117）

后端 PR 合入 main 后，CD 部署 catalog，Flyway 在启动时执行 `V12__add_venue_nlm_unique.sql`，加两条唯一约束（`uk_venue_nlm_id`、`uk_venue_identifier_nlm`）。库里一旦有重复，迁移失败、catalog 起不来。所以**合并之前**在 mini 上跑一次只读核对（2026-10-27 的结果全部为 0）：

```bash
ssh mini 'export PATH="/opt/homebrew/bin:/usr/local/bin:$PATH";
  docker exec -i -e PGOPTIONS="-c default_transaction_read_only=on" patra-postgres \
  psql -U postgres -d patra_catalog -v ON_ERROR_STOP=1' <<'SQL'
BEGIN READ ONLY;
-- Q1 主 NLM 重复（含软删行），期望 0 行
SELECT nlm_id, array_agg(id ORDER BY id) FROM cat_venue
WHERE nlm_id IS NOT NULL GROUP BY nlm_id HAVING count(*) > 1;
-- Q2 同一个 NLM 挂在多个期刊上，期望 0 行
SELECT identifier_value, array_agg(venue_id ORDER BY venue_id) FROM cat_venue_identifier
WHERE identifier_type = 'NLM' GROUP BY identifier_value HAVING count(DISTINCT venue_id) > 1;
-- Q3 主 NLM 不在该期刊的标识符里，期望 0
SELECT count(*) FROM cat_venue v WHERE v.nlm_id IS NOT NULL AND NOT EXISTS (
  SELECT 1 FROM cat_venue_identifier i WHERE i.venue_id = v.id
    AND i.identifier_type = 'NLM' AND i.identifier_value = v.nlm_id);
-- Q4 有 NLM 标识符但主 NLM 为空，期望 0
SELECT count(*) FROM cat_venue v WHERE v.nlm_id IS NULL AND EXISTS (
  SELECT 1 FROM cat_venue_identifier i WHERE i.venue_id = v.id AND i.identifier_type = 'NLM');
ROLLBACK;
SQL
```

预期：Q1、Q2 各 0 行；Q3、Q4 都是 `0`。

**从核对到合并之间，不要手动触发 `venuePubmedImportJob`（XXL-Job 任务 11）**：旧代码按 ISSN-L 优先匹配，可能把一个 NLM 挂到第二个期刊上。

任何一项不为 0：先不合并，把结果交给用户。处理办法见 PAP-117 spec 第 11.2 节，每一步都是写操作，逐条经用户同意后执行；处理完重跑本步，全为 0 后再合并。

## 4. 后端 PR 合进 main、CD 结束后：核对部署

改了 `patra-tool-test`，CD 会重建并重部署全部后端服务（foundation 扇出），这是预期的。

```bash
SHA="$(git rev-parse origin/main)"   # 先 git fetch origin main，确保是这次合并的提交
until RUN_ID="$(gh run list --workflow cd.yml --commit "$SHA" -L 1 --json databaseId -q '.[0].databaseId')" && [ -n "$RUN_ID" ]; do sleep 10; done
gh run watch "$RUN_ID" --exit-status > /dev/null; echo "CD exit=$?"
gh run view "$RUN_ID" --log | grep -E '===== deploy|全部部署成功|自动回滚|✗'
```

预期：`CD exit=0`；有 `===== deploy catalog`、`identity`、`interaction`，最后是 `✓ 全部部署成功`。

# 2. 经网关访问内部接口是 403

  -H 'Content-Type: application/json' -d '{"nlmIds":["0404401"]}'
# 期望：403

# 3. 在 mini 本机直连 catalog：主 NLM 与副 NLM 都解析到同一个期刊

  -H 'Content-Type: application/json' -d '{\"nlmIds\":[\"0404401\",\"100970884\"]}'"
# 期望：两行 exists=true、id 相同、nlmId 都是 "0404401"

# 4. 门户批量卡片经网关可访问，带 nlmId（id 用第 3 步返回的）

### 4.3 interaction（PAP-120）

两条新迁移在 `subject` schema：登记表扩到期刊与本地对象（加所有者两列与约束）、发表计数表。只加列、加约束、加表，mini 上现有的行都是文献、所有者为空，新约束全部满足。

```bash
ssh mini 'export PATH="/opt/homebrew/bin:/usr/local/bin:$PATH";
  docker exec patra-postgres psql -U postgres -d patra_interaction -At -c "
    SELECT string_agg(version, '"'"','"'"' ORDER BY installed_rank) FROM public.flyway_schema_history
     WHERE success AND version >= '"'"'20261027000000'"'"';
    SELECT string_agg(conname, '"'"','"'"' ORDER BY conname) FROM pg_constraint
     WHERE conrelid = '"'"'subject.registry'"'"'::regclass AND conname LIKE '"'"'ck_registry_%'"'"';
    SELECT to_regclass('"'"'subject.publish_quota'"'"');
    SELECT count(*) FROM subject.registry WHERE owner_user_id IS NOT NULL;"'
```

预期：

- 第一行含 `20261027120000,20261027120100`（PAP-121 ~ 123 合入后还会有它们的版本）。
- 约束有 `ck_registry_journal_key`、`ck_registry_owner_local`、`ck_registry_owner_pair`、`ck_registry_post_key`、`ck_registry_publication_key`、`ck_registry_source_present`、`ck_registry_state`、`ck_registry_target_type`。
- `subject.publish_quota`。
- `0`（还没有任何投稿经验）。

interaction 日志报 `Migration checksum mismatch` / `Validate failed`：已在 mini 上执行过的脚本被改了，处理办法同 v0.13 runbook 第 5 步的退路表。

## 5. 第 4 步之后：手动执行两个每日任务各一次

两个任务的 handler 名、Cron 都没变，调度中心不用改配置，只需各手动执行一次确认新代码正常。

| 任务 | JobHandler | 本版的变化 |
|---|---|---|
| 对象对账 | `subjectReconciliationJob` | 只对外部对象；多了期刊（按 NLM ID 回查，锚不随主副 NLM 互换而变） |
| 注销清理 | `deletedUserCleanupJob` | 改为底座的公共流程：合并各子域有数据的用户，一批回查一次 identity，删除已注销用户在各子域登记的个人数据（现在是收藏与发表计数，PAP-123 起加提醒）；讨论与投稿经验保留 |

预期：

- 对象对账：调度日志「执行结果」形如 `已核对 N 个：换 ID a、失效 b、复活 c`；`ssh mini 'docker logs patra-interaction --since 5m'` 里有 `对象对账完成: type=PUBLICATION, …, failedBatches=0` 和 `对象对账完成: type=JOURNAL, …, failedBatches=0` 两行（上线当天还没有期刊登记，`scanned=0`）。
- 注销清理：「执行结果」形如 `已核对 N 人：清理 a 人，删除 b 行`；日志有 `注销清理完成: scannedUsers=…, deletedUsers=…, deletedRows=…, bySubdomain={…}, failedBatches=0`。有失败批次时执行结果是 `已核对 N 人，失败 M 批`，先查 identity 是否健康。

## 7. 回滚

| 情况 | 会发生什么 | 怎么办 |
|---|---|---|
| catalog 的 V12 在部署时失败 | PG 的 DDL 在事务里，Flyway 整体回滚，历史表里没有失败记录，catalog 起不来 | 按 PAP-117 spec 第 11.2 节处理重复后重启 catalog；要先恢复服务就回滚到上一个镜像（库结构没变） |
| V12 上线后 catalog 回滚到旧镜像 | 两条约束留在库里，旧代码的读接口照常工作 | **回滚期间不要触发 `venuePubmedImportJob`（任务 11）**：旧导入在新约束下可能整批回滚，或改掉合并期刊的主 NLM；回到新镜像后再用。不用撤销 V12 |
| identity 回滚到旧镜像 | V2 只加了两个索引，旧代码照常工作 | 不用撤销 |
| interaction 回滚到旧镜像 | 两条迁移只加列、加约束、加表；旧代码写入时不写新列（为空），文献行满足全部约束。旧代码只按 `target_type = 1` 查登记表、只拿收藏表里引用的 ID、只对账文献，读不到期刊与投稿经验的行；读到快照里多出的 `abbreviation` 键也不报错（Jackson 默认忽略未知字段） | 不用撤销，可以直接回滚 |

## 8. 通用规则（沿用 v0.13，本版起也保护期刊）

**catalog 任何换库重建或重跑导入之后，立即手动执行一次 `subjectReconciliationJob`。** 否则到次日 06:30 之前，登记表里还是旧的 catalog ID：文献库与投稿经验按旧 ID 取不到卡片，「我的状态」显示没收藏。

对期刊还多一层：mini 上有 15 个期刊是改名前后两条 NLM 记录合并成的。整库重导后主副 NLM 可能互换，如果对账之前有人在这样的期刊下首次写经验，会多出一条登记行，原来那行挂着的经验会一直显示「已失效」（PAP-120 spec 第 5.4 节）。重导后立即对账，就把这个窗口压到几分钟。
