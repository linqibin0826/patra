## 1. 版本目标 / 价值

医生和科研人员不在站上时，也能通过邮件知道有人回复或 @ 了自己，点邮件直接回到那条讨论。每类提醒都能单独选：不发邮件、逐条发，还是每天汇总成一封；在邮件里就能一键退订。自己的评论和投稿经验被点「有帮助」时，会收到按天合并的一条提醒。

现在的提醒只在站内：一位医生在文献页提了问题就离开，别人回复后，他要等哪天回到站上看到铃铛才知道，人少的社区讨论多半就断在这一步。v0.15 的「有帮助」也一样，作者被点了完全不知道。这一版把「把人拉回站上」的链路建起来，同时清掉挂在通知中心名下的基建旧账：通用事件模块（Outbox）、安全邮件可靠投递（PAP-104）、通知抽成独立服务（PAP-105）、正文转纯文本（PAP-128），并加上实时推送。

**规划时的现状**（2026-10-30 核对，main `b554d9961`）：

- **站内提醒**：在 interaction 的 `notification` 子域，只有 3 类（回复了你的评论、评论了你的经验、@ 了你），分「回复我的」「@ 我的」两个标签。提醒与评论在同一事务里同步写入（`CommentNotificationListener`），收件人规则在 `NotificationRules`。摘录由 `CommonmarkPlainTextAdapter` 把 Markdown 转成纯文本、截 120 字，@ 存成 `<@用户ID>`。未读数每 60 秒轮询一次，没有任何偏好设置。
- **有帮助**：v0.15 的 `reaction` 子域，点与取消都不发事件，没有提醒。
- **邮件**：全部由 identity 发，13 类安全邮件（验证、找回密码、改邮箱、注销等）。发送用进程内队列：最多发一次，失败不重试，重启时队列里的邮件会丢。经 SMTP 发出：线上是 Resend，本机与 e2e 是 Mailpit。
- **事件基建**：只有 ingest 有手写的 Outbox，`patra-tool` 里没有通用事件模块。RocketMQ 实际零使用；ingest 与 RocketMQ 由单独的 `refactor/remove-ingest` 删除（第 3 节 J）。
- **网关**：Spring Cloud Gateway Server MVC 5.0.3，读超时 60 秒（空闲超时）；长连接只在建立时校验一次会话。
- **门户**：10/28 起 `patra.linqibin.dev` 经 Cloudflare Tunnel 对公网开放，给少数人体验；tailnet 直连走 HTTP/1.1。带令牌访问网关只能经 `lib/gateway.ts`，其中 `gatewayStream` 不带令牌。

**验证场景**：

1. A 在文献页发了根评论后离开，B 回复了他。A 一直没看站内提醒，过一段时间，A 的邮箱收到一封邮件，里面有 B 回复的摘录和「查看并回复」按钮，点开直接落到那一楼。
2. 如果 A 先在站内看到了这条提醒，就不会再收到同一条的邮件。
3. A 在设置里把「@ 我的」改成每日汇总。当天 C、D 各 @ 了他一次，第二天他只收到一封汇总邮件。
4. C、D 先后给 A 的投稿经验点了「有帮助」，A 的站内提醒里多一条：「D 等 2 人觉得你的投稿经验有帮助」。
5. A 点邮件底部的「退订这类邮件」，不用登录就生效，设置页里对应的开关也同步关掉。

### 2.1 产品定义

| 项 | 规则 | 依据 |
|---|---|---|
| 提醒分类 | 三个标签：回复我的、@ 我的、有帮助（新增） | B 站分「回复我的 / @我的 / 收到的赞」 |
| 有帮助怎么合并 | 按「被点的那条内容 × 北京时间一天」合成一条，名字写最近一位点的人：C、D 先后点，显示「D 等 2 人觉得你的投稿经验有帮助」。当天再有人点，名字换成这个人、人数加一、重新变未读，时间与排序用最新一次（10/30 用户确认：让条目重新亮起来的是新点的人）；有人取消，不撤回已发的提醒 | 业界无共识：Discourse 按点赞人合并，按内容合并只见于第三方对 B 站的描述 |
| 有帮助进不进红点 | 不进。铃铛只数回复和 @，「有帮助」标签自己显示未读数 | 业界无共识：Discourse 计入但排得靠后 |
| 有帮助发不发邮件 | 不发，偏好里也不提供邮件选项 | Discourse、Mastodon 默认都不为点赞发邮件 |
| 邮件选项 | 「回复我的」「@ 我的」各自三选一：关 / 离站时逐条 / 每日汇总 | GitHub、GitLab、Mastodon 都是「类型 × 渠道」 |
| 默认值 | 两类都是「离站时逐条」 | Discourse 默认只在不在站上时发 |
| 什么算「离站」 | 提醒生成后等 10 分钟。到点时已读，或者这 10 分钟里在站上（开着推送连接或拉过未读数，决策 H），就不发；到点的同一类多条合成一封（回复一封、@ 一封，不混发，退订才说得清关的是哪一类） | Discourse 等 10 分钟，Mastodon 等 2 分钟；多条合成一封学 Jira、Slack |
| 每日汇总 | 每天北京时间 8:00，列出过去 24 小时里仍未读的回复和 @（设为每日汇总的类型合在一封里），没有就不发 | Stack Exchange 用滚动窗口；用户都在国内，固定钟点更好预期 |
| 一键退订 | 每封提醒邮件带 RFC 8058 一键退订。逐条邮件只关这一类；每日汇总邮件关掉所有设为每日汇总的类型。邮箱客户端的一键退订（POST）直接生效；邮件底部的链接先打开确认页，点「退订」才生效，防止企业邮箱网关预抓链接把人被动退订。落地页上还能点「关闭全部提醒邮件」。站内提醒照常。不用登录，链接长期有效 | RFC 8058；GitLab 的 POST 直接退订、GET 先出确认页 |
| 安全邮件 | 13 类安全邮件不进偏好、不能退订、不带退订头 | Discourse、GitLab、Novu 都把这类排除在偏好之外 |
| 邮箱未验证 | 不发提醒邮件；通知设置页顶部提示「验证邮箱前不会收到提醒邮件」 | 决策 F：发送时向 identity 查是否已验证 |
| 推送什么 | 只推三个未读数。铃铛立刻更新；正开着提醒页时刷新列表；不推正文 | Mastodon 推完整提醒；只推数字少暴露内容 |
| 后台与断线 | 标签页切到后台就断开连接，切回来时重连并取一次；连不上退回 60 秒轮询。登出时前端立即断开；被封禁的账号最晚 30 分钟内断开（连接到期重建、重新校验） | Mastodon、GitLab 都保留轮询兜底；HTTP/1.1 下 6 个标签页就占满连接 |

## 3. 范围边界（不做的事）

> 下面这些都和通知中心高度相关、很容易被顺手加进来，列在这里是明确「本版不做」。

| # | 不做的事 | 理由 |
|---|---------|------|
| A | **站内与邮件以外的渠道**：浏览器系统通知（Web Push）、微信、短信、App 推送 | 本版只把邮件这条把人拉回来的路做通 |
| B | **WebSocket 双向通道**：推送提醒内容、在线状态、「正在输入」 | 只需要服务器告诉浏览器「未读数变了」，单向的 SSE 就够；提醒内容仍由页面自己拉 |
| C | **通知服务多实例推送** | SSE 连接挂在某一台上，事件被另一台处理就推不到；多实例要再加一层广播（RabbitMQ fanout 或 Redis 发布订阅）。现在一台够用 |
| D | **系统公告与站务群发**（管理员一次发给所有人） | 和「有人回复了你」是两种需求 |
| E | **和「关注」有关的提醒**：有人关注了你、你关注的人发了新内容 | 关注功能还不存在 |
| F | **更细的设置**：按某条讨论静音或单独订阅、免打扰时段、自选汇总时间 | 本版设置只到「类型 × 三档」，汇总固定北京时间 8:00 |
| G | **退信与投诉回调**（Resend webhook） | 公网只开放了门户，接回调要再开一个对外入口并验证签名；发信量很小。代价是坏地址会继续收到发信，发件信誉可能慢慢变差 |
| H | **打开与点击追踪**：追踪像素、改写链接统计点击 | 不收集这类行为数据 |
| I | **注册时的「同意接收提醒邮件」勾选** | 回复和 @ 的提醒邮件默认开启，每封邮件都带一键退订兜底；隐私政策里关于邮件的条款归合规包 |
| J | **删除 ingest、下线 RocketMQ** | 由单独的 `refactor/remove-ingest` PR 完成，本版只接入 RabbitMQ |
| K | **把别的同步调用改成事件** | 事件只覆盖提醒和安全邮件用到的几种（评论、投稿经验、有帮助、identity 安全邮件），catalog 等其他服务不动 |
| L | **迁移旧提醒** | interaction 里现有的提醒随 `notification` 子域一起删掉，切换后信箱从空开始；代价是 10/28 公网开放以来几位测试者已有的提醒会消失 |

## 4. 关键决策

> 每条按「问题 → 可选做法 → 业界 → 选择 → 代价」写。进本节的门槛：影响 2 个以上 Issue、同时影响前后端、或事后很难改回来。依据见文末「调研依据」。

### A. 提醒归通知服务，interaction 只发「发生了什么」

- **影响 Issue**：PAP-141 / PAP-143 / PAP-144
- **问题**：现在评论和提醒在同一个事务里写入（`CommentNotificationListener`），要么一起成功，要么一起回滚，这叫**强一致**。提醒搬到另一个服务后，两个库放不进同一个事务，只能做到**最终一致**：评论先提交，提醒稍后才出现。另外要定下来，由谁决定通知谁。
- **可选做法**：
  - **事实型事件**：interaction 只说「C 回复了 B 的评论，正文里 @ 了 D」，由通知服务自己算出该提醒谁。
  - **指令型调用**：interaction 自己算好收件人，直接说「给 B 发一条回复提醒」。
- **业界**：Novu、Knock 这类通知平台用指令型，因为平台不懂业务；产品内部拆服务时多用事实型，规则跟着通知服务走。
- **选择**：事实型。
  - `NotificationRules` 现有的规则搬进通知服务：先列被回复的人，再列经验作者（只对根评论），最后列 @ 到的人；同一个人只按第一次出现的类型提醒；去掉作者本人。
  - 事件里带齐计算收件人要用的事实：作者、被回复评论的作者、@ 到的用户 ID、是否匿名，通知服务不回头调 interaction 查数据。这叫**事件携带状态转移**（Martin Fowler 的说法）。
- **代价**：
  - 评论发出后，提醒要过一会儿才出现：平时是毫秒级；RabbitMQ 或通知服务挂了，就要等它恢复。
  - 「评论成功、提醒失败」不再一起回滚，要靠决策 C 的补投和决策 E 的重试最终送达。
  - 新增一种提醒时，interaction 可能要在事件里多带字段。

### B. 事件分两层：领域事件留在服务内，集成事件放进 -api 模块

- **影响 Issue**：PAP-137 / PAP-141 / PAP-104 / PAP-105
- **问题**：领域层不能依赖框架，也不该被别的服务直接引用；但事件要跨服务传递，消费方得知道消息里的 JSON 长什么样。
- **两个概念**：
  - **领域事件**：服务内部记录的事实，比如 `CommentPublishedEvent`，字段怎么方便聚合就怎么定。
  - **集成事件**：对外公布的契约，字段要稳定，只放别的服务需要的内容。
- **可选做法**：把领域事件直接序列化发出去；另外定义集成事件，发送前转换一次；用 Avro、Protobuf 加 schema 仓库。
- **业界**：DDD 社区普遍主张把两者分开（Vaughn Vernon《实现领域驱动设计》）；schema 仓库多见于用 Kafka 的大团队。
- **选择**：
  - 集成事件写成 record，放在发布方的 `patra-{service}-api` 模块，和现有 HTTP Interface 契约同一处，消费方依赖这个模块。
  - 领域事件到集成事件的转换写在 boot 层的 `EventExternalizationConfiguration`，同时在这里定好哪些事件外送、发到哪个交换机、带什么路由键。
  - 领域层不贴 `@Externalized`。
- **代价**：每种外送事件要写两个类，外加一段映射；改集成事件的字段时，要留意队列里还没消费的旧消息。

### C. 可靠发出：用 Modulith 事件发布登记当 Outbox，外送到 RabbitMQ 并等它确认

- **影响 Issue**：PAP-137 / PAP-141 / PAP-104
- **问题：双写**。写数据库和发消息是两个系统，做不到一起成功或一起失败。先提交再发，进程在两步中间崩掉，消息就丢了；先发再提交，事务回滚了，消息却已发出，说的是一条不存在的评论。
- **可选做法**：
  - **提交后直接发**：简单，但会丢消息。
  - **Outbox（发件箱）**：把待发的消息和业务数据写进同一个库、同一个事务，提交后由后台发出；发送失败时消息还留在表里，可以重发。
  - **事务消息**：RocketMQ 特有，本版已经不用 RocketMQ。
- **业界**：Outbox 是解决双写的标准做法（microservices.io 的 Transactional Outbox、Debezium）。Spring 官方的实现是 Spring Modulith 的**事件发布登记**：一张 `event_publication` 表，事务内发布的事件自动写进去。
- **选择**：
  - interaction 和 identity 引入 Spring Modulith 2.1.x（与 Boot 4.1 配套；Boot 已由 PAP-152 升到 4.1.2）的 JDBC 登记表和 `spring-modulith-events-amqp`。事务提交后立即外送；XXL-Job 定时把还没完成的再投一遍，卡住的登记行用 Modulith 自带的 `markStalePublicationsFailed` 解开。
  - **Patra 自己补一步：等 RabbitMQ 确认收到。** Modulith 默认的外送模式（2.0 与 2.1 一样）在发送调用返回时就把事件标为完成，不管 broker 有没有真正收下。RabbitMQ 的 **publisher confirm** 是它收下并写盘后给发送方的回执；我们在发送时同步等这个回执，等不到就抛异常，让登记行保持未完成，留给补投。2.1 新增的 outbox 外送模式虽然会等确认，但要引入 Namastack 或 JobRunr 这类第三方库，而且只认 nack、不管超时和「没有队列可投」，所以不用。
  - 登记表只放需要外送的事件：用 2.1 的 `spring.modulith.events.registry-trigger-annotation` 指向 `ApplicationModuleListener`，只有外送器进登记表，服务里普通的 `@TransactionalEventListener` 照 Spring 原来的行为走、不登记、不补投。这个配置项 2.0.8 没有，这是 10/30 决定先升级 Boot 的原因（PAP-152）。
  - 通知服务只消费、不发布，不需要登记表；它自己的提交后推送（决策 I）不受影响。
  - 「没有队列可投」也算发送失败，事件留在登记表等补投，所以通知服务晚于 interaction 部署也不丢事件；代价是只能外送有消费者的事件，否则会被无限重试。
  - 表由 Flyway 建，关掉框架的自动建表。
  - `transaction.md` §3 里手写中继的写法（租约、`PUBLISHING`）随 ingest 删除过时，由 PAP-137 改写成登记表的用法。
- **代价**：
  - 这是**至少一次投递**：补投时可能把已经送达的事件再发一遍，必须配合决策 D 的去重。
  - 每个发布事件的服务多一张表；每次发送多等一次回执，大约几毫秒。

### D. 消费端：按事件 ID 去重，用墓碑和版本号处理乱序

- **影响 Issue**：PAP-143 / PAP-105 / PAP-144 / PAP-146
- **两个概念**：
  - **幂等**：同一条消息处理多次，结果和只处理一次一样。
  - **乱序**：后发生的事件先被处理。比如「评论发布」第一次处理失败进了重试，几秒后「评论删除」反而先处理完。
- **业界**：RabbitMQ 文档明确说消费者会收到重复投递，要自己处理；microservices.io 把这叫 Idempotent Consumer。ingest 的 Outbox 靠分区键保证顺序，但 RabbitMQ 一旦重投就不保证顺序，所以顺序只能在消费端兜底。
- **选择**：
  - 通知服务建一张「已处理事件」表，事件 ID 唯一，和业务数据在同一个事务里写入；同一个事件第二次到达时插入冲突，直接跳过。
  - 删除先于发布到达：先记一条**墓碑**（标记「这条已删除」的记录），后到的发布看到墓碑就丢弃。
  - 编辑：按版本号或更新时间只保留最新的一次，晚到的旧编辑不覆盖新的。
- **代价**：每种事件都要考虑「先到」和「晚到」两种情况，并写进对应 Issue 的测试。
- **和决策 G 的关系**：去重表只防「同一个事件被处理两次」。邮件已经发出、处理记录提交前进程挂了，重试会再发一遍，这一层由 Resend 幂等键挡住，所以两层都要。

### E. RabbitMQ 的结构

- **影响 Issue**：PAP-137 / PAP-138 / PAP-141 / PAP-104 / PAP-105
- **概念**（用寄信打比方）：
  - **交换机**（exchange）：分拣台，发布方只把消息交给它。
  - **队列**（queue）：信箱，消费方从这里取消息。
  - **路由键**（routing key）和**绑定**（binding）：信封上的标签和分拣规则。消息带着 `comment.published` 这样的标签，交换机按绑定规则投进匹配的队列。
  - **ack**：消费方处理完才回「收到」，RabbitMQ 这时才删掉这条；没回 ack 就断开，消息会重新投递。
  - **prefetch**：一个消费者手里最多同时攥几条消息，防止囤积。
  - **死信**：重试几次仍失败的消息，被转进另一个专门的队列留存，不再堵住正常消息。
- **业界**：RabbitMQ 官方教程和 Spring AMQP 的常见做法是每个发布方一个 topic 交换机、每个消费方一个自己的队列；失败先在本地退避重试，最后进死信。
- **选择**：
  - `interaction.events`、`identity.events` 两个 topic 交换机，路由键就是事件类型。
  - 通知服务按用途建队列（站内提醒、邮件），各自只绑定需要的路由键。
  - 手动 ack；失败后按指数退避（每次间隔翻倍）在本地重试几次，仍失败进该队列的死信队列；prefetch 设小。
- **代价**：死信队列里的消息不会自己回来，要人去查看或重放；本版不为它加告警。

### F. 收件信息分两路：安全邮件随事件带地址，提醒邮件在发送时现查

- **影响 Issue**：PAP-104 / PAP-105 / PAP-146
- **问题**：发邮件要知道收件地址，但 interaction 不知道用户的邮箱，`UserSummaryResp` 里也没有。安全邮件还有特殊情况：换邮箱时，确认信发到新地址，变更通知发到旧地址，这只有 identity 在当时知道。
- **可选做法**：事件里直接带地址；发送时按 user_id 调 identity 查；通知服务存一份用户信息副本（Novu 叫 subscriber）。
- **业界**：Kratos 由认证服务自己带上地址投递；Novu 存副本，代价是要订阅用户变更来保持同步。
- **选择**：
  - identity 的安全邮件事件带上收件地址和链接，通知服务照着发。
  - 提醒邮件在发送的那一刻，按 user_id 调 identity 新增的内部接口，查地址、是否已验证、账号状态，以及邮件里要显示的用户名（包括 `<@ID>` 对应的名字）。
  - 通知服务不存邮箱副本，与「用户名只存在 identity，用的时候现查」一致。
- **代价**：
  - identity 挂了，提醒邮件跟着推迟，等重试补上。
  - 安全邮件里的一次性令牌链接会经过 identity 的 `event_publication` 表和 RabbitMQ 消息。对策：登记表设成发送完成即删除（DELETE 模式）；RabbitMQ 只在 tailnet 内开放；通知服务的发送记录不存邮件正文。

### G. 用 SMTP 发信，带 Resend 幂等键

- **影响 Issue**：PAP-105 / PAP-146 / PAP-148
- **可选做法**：Resend 的 HTTP API，或者 SMTP。两种都支持幂等键；HTTP 会同步返回邮件 ID，方便和退信回调对账。
- **选择**：SMTP。
  - 本机开发和 e2e 继续用 Mailpit 收信，线上走 Resend 的 SMTP。
  - 每封邮件带 `Resend-Idempotency-Key`，值为这次投递的 ID，24 小时内同一个键不会重复送达。
  - 提醒邮件带 RFC 8058 的两个一键退订头（`List-Unsubscribe`、`List-Unsubscribe-Post`），安全邮件不带。
- **代价**：拿不到 Resend 的邮件 ID；以后要接退信回调（第 3 节 G）时得改走 HTTP。

### H. 「在不在站上」由通知服务自己判断

- **影响 Issue**：PAP-146 / PAP-145 / PAP-149
- **问题**：「离站逐条」要知道用户在这 10 分钟里有没有在站上。
- **业界**：Discourse 由服务端记录用户最后活跃时间（`last_seen_at`）；Mastodon 看有没有推送连接，有就算在线。
- **选择**：两种信号本来就都打到通知服务上：推送连接在线，或者推送断开期间、10 分钟窗口内用 60 秒轮询拉过未读数，就算在站。不跨服务去查。
- **代价**：门户标签页切到后台就会关掉推送连接（2.1 的规则），在后台超过 10 分钟算离站，会收到邮件。这是有意为之：这段时间用户确实没在看。

### I. 实时推送：SSE 放在通知服务里，事务提交后再推

- **影响 Issue**：PAP-145 / PAP-147 / PAP-149，另外改网关
- **选择**：
  - 通知服务提供 SSE 接口，在内存里维护「用户 → 连接」表。
  - 提醒写入的事务**提交后**才推送，否则浏览器收到通知去拉数据时可能读到还没提交的内容。
  - 只推三个未读数；连接一建立就先推一次当前值，所以不需要 `Last-Event-ID` 断点续传。
  - WebSocket 与多实例见第 3 节 B、C。
- **开工前要先解决的四件事**：
  1. **显式设置异步超时**：不设会用 Tomcat 默认的 30 秒，连接每 30 秒被掐断一次。
  2. **每 25 秒发一次心跳**（一行注释）：短于网关 60 秒和 Cloudflare 125 秒的空闲超时，否则中间的代理会把连接当成死连接断掉。
  3. **每条连接最长活 30 分钟**：网关只在建立连接时校验一次会话，不设上限的话登出和封禁都断不掉已建好的连接。到点后服务端主动结束，浏览器自动重连，网关重新查一次会话。
  4. **网关给推送单独配连接池**：默认每个下游服务只有 max(CPU, 8) × 2 条连接、排队最多等 45 秒，长连接一多会把普通请求挤掉。
- **两条网络路径**：
  - **tailnet 直连**：HTTP/1.1，浏览器对同一站点最多开 6 条连接，开 6 个标签页就占满，所以标签页隐藏时要关连接。
  - **公网经 Cloudflare Tunnel**：HTTP/2。Tunnel 默认缓冲响应，但对 `text/event-stream` 不缓冲。门户 10/28 起已对公网开放，这条路径要和 tailnet 一起测。
- **门户**：`gatewayStream` 目前不带登录令牌，要扩展；Route Handler 做流式转发有导出接口的先例。
- **业界**：Mastodon 用独立的推送进程；Discourse 用长轮询，后台标签页降到 60 秒；Lemmy 删掉 WebSocket 改回轮询。共同点是都保留轮询兜底。
- **代价**：每次部署通知服务，所有推送连接都会断开，浏览器自动重连并重拉一次。

### J. 正文转纯文本：谁定义格式，谁负责转

- **影响 Issue**：PAP-128 / PAP-141 / PAP-143 / PAP-146
- **问题**：提醒列表和邮件都要显示正文摘录。正文是 Markdown，@ 存成 `<@用户ID>`。现在的转换器 `CommonmarkPlainTextAdapter` 在 interaction 的 `notification` 子域里，PAP-143 会删掉这个子域，转换器必须搬家。
- **可选做法**：
  - interaction 转好，事件里带全文纯文本，通知服务只负责截断。
  - 事件里带 Markdown 原文，由通知服务自己解析。
- **选择**：interaction 来转。
  - 正文格式是 interaction 定的，懂这个格式的代码只留在一处；通知服务不用引入 Markdown 解析库，以后搜索这类消费方也能直接用。
  - 转换时保留 `<@ID>`，不替换成名字；名字由负责显示的一方（站内列表或邮件）按 ID 现查。
  - 截多长由通知服务按渠道决定。
- **分工**：本节只定「在哪一层转」；各元素怎么转和截断规则归 PAP-128。
- **代价**：每次发布事件都要转一遍正文；规则改了只影响之后发出的事件，已存的摘录不回头重算。

## 调研依据

2026-10-30 并行做了 5 路代码核对与调研，又加派 1 路实时推送调研，报告在当天会话里，这里只记结论和用到的来源。

**代码核对**

1. **interaction 与 identity 现状**：提醒子域的同事务写入与收件人规则、摘录转换、未读数轮询；identity 的 13 个邮件模板与进程内发送队列。结论见第 1 节「规划时的现状」。
2. **ingest、Outbox 与 RocketMQ**：ingest 从未在 mini 上跑过（XXL 无执行器、10 张表 0 行、broker 无 INGEST topic），全仓无下游；catalog 引了 RocketMQ 依赖但零代码。据此另开 `refactor/remove-ingest` 单独删除（第 3 节 J）。
3. **门户落点**：设置页导航、提醒查询与轮询、提醒 schema、流式 Route Handler 先例、`gatewayStream` 不带令牌。

**调研**

1. **产品规则**：Discourse 只在离站时发、等 10 分钟、发前复查已读与最后活跃，点赞不发邮件；Mastodon 有流式连接即视为在线、等 2 分钟；GitHub、GitLab、Mastodon 都是「类型 × 渠道」的偏好；安全邮件排除在偏好之外；RFC 8058 一键退订的要求。来源：[Discourse user_email.rb](https://github.com/discourse/discourse/blob/main/app/jobs/regular/user_email.rb)、[Discourse notification_emailer.rb](https://github.com/discourse/discourse/blob/main/app/services/notification_emailer.rb)、[Discourse 点赞合并](https://github.com/discourse/discourse/blob/main/app/services/notifications/consolidation_planner.rb)、[Mastodon notify_service.rb](https://github.com/mastodon/mastodon/blob/main/app/services/notify_service.rb)、[GitHub 通知设置](https://docs.github.com/en/account-and-profile/managing-subscriptions-and-notifications-on-github/setting-up-notifications/configuring-notifications)、[GitLab 通知](https://docs.gitlab.com/ee/user/profile/notifications.html)、[RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html)、[RFC 2369](https://www.rfc-editor.org/rfc/rfc2369.html)、[Gmail 发件人要求](https://support.google.com/a/answer/81126)、[Jira 通知合并](https://support.atlassian.com/jira/kb/batching-notifications-in-jira-cloud/)。
2. **事件基建与可靠投递**：Spring Modulith 事件发布登记的原理、完成模式与补投 API，外送支持 Kafka / AMQP / JMS、不支持 RocketMQ；2.0 外送不等 broker 确认；认证系统发信普遍是「持久化队列 + 后台重试」；Resend 的幂等键与退订头；通知服务取用户数据的三种做法。来源：[Spring Modulith 事件](https://docs.spring.io/spring-modulith/reference/events.html)、[Modulith 附录](https://docs.spring.io/spring-modulith/reference/appendix.html)、[Modulith #395](https://github.com/spring-projects/spring-modulith/issues/395)、[Ory Kratos courier](https://www.ory.com/docs/kratos/self-hosted/mail-courier-selfhosted)、[Resend 幂等键](https://resend.com/docs/dashboard/emails/idempotency-keys)、[Resend 退订头](https://resend.com/docs/dashboard/emails/add-unsubscribe-to-transactional-emails)、[Novu 偏好](https://docs.novu.co/platform/concepts/preferences)、[Fowler：事件驱动的几种含义](https://martinfowler.com/articles/201701-event-driven.html)。
3. **实时推送**：网关 Server MVC 对 `text/event-stream` 逐块 flush、读超时是空闲超时、长连接只校验一次会话；Tomcat 异步默认 30 秒；Cloudflare 空闲超时 125 秒、Tunnel 不缓冲事件流；HTTP/1.1 每站 6 条连接；开源社区的推送做法都保留轮询兜底。来源：[WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)、[MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)、[Spring MVC 异步](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html)、[Cloudflare 连接限制](https://developers.cloudflare.com/fundamentals/reference/connection-limits/)、[Cloudflare Tunnel 常见错误](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/troubleshoot-tunnels/common-errors/)、[Mastodon streaming](https://docs.joinmastodon.org/methods/streaming/)、[Discourse MessageBus](https://github.com/discourse/message_bus)、[Lemmy 0.18](https://join-lemmy.org/news/2023-06-23_-_Lemmy_Release_v0.18.0)。

**规划中的两次转向**

- **消息队列换成 RabbitMQ**（10/30 用户拍板）：RocketMQ 没有选型记录（随最早的 ingest 进来），实际零使用，mini 上 3 个容器空占约 1.58 GB；`rocketmq-spring` 未声明支持 Boot 4、只认 Jackson 2，Spring Modulith 也不支持，要自写桥接。RabbitMQ 有 Boot 自带的 `spring-boot-starter-amqp`、官方的 `spring-modulith-events-amqp` 和 Testcontainers 模块。
- **站内提醒搬出 interaction**（10/30 用户确认）：提醒与通知将来的玩法多，偏好、邮件、汇总、推送都要读同一份信箱，信箱留在 interaction 就做不成独立服务。代价见决策 A。
