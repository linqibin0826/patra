## 1. 版本目标 / 价值

后端共享代码按「技术能力 / 业务」两类归位：所有技术能力集中在 `patra-tool/` 的 12 个能力模块里，模块名就是能力名，业务代码各回各家；去掉 `linqibin` 命名，包根统一为 `dev.patra`。新写一段共享代码时，问两个问题就能定位置：它是不是一种技术能力？有几个服务在用？引入一个模块只带来它那一种能力；依赖规则、自动配置写法、默认配置归属由 `./gradlew check` 守住，不靠人记。

这版的受益人是写代码的开发者本人，没有面向门户用户的变化。

**验证场景**：

1. 新建一个只依赖 `patra-tool-jpa` 的模块，类路径上不会出现 web、batch、security 的任何类。
2. 在 `patra-tool-web` 里加一条对 `patra-api` 的依赖、或给工具模块加一个 `@Component`，`./gradlew check` 失败并指出规则。
3. 服务的 `application.yml` 只剩和默认值不同的键：删掉 6 个服务里的 `logging` / `management` 段后，启动日志路径、actuator 端点、指标标签与删前一致。
4. 全仓 `grep -r linqibin` 只命中 git 远端地址和历史文档。

## 3. 范围边界（不做的事）

| # | 不做的事 | 理由 |

| A | **不补新的通用能力**（幂等、限流、操作日志、缓存、脱敏这类脚手架常见能力） | 这版只整理结构；需要哪项时按放置规则单独加 |

## 4. 关键决策

> **现状事实**（2026-10-13 ~ 10-15 盘点，以下决策的依据）：
>
> - 共享区 22 个模块、约 4 万行，其中 1.65 万行只有 ingest 在用（provenance、expr、expr-kernel、provenance-api、commons-core 的 `Priority` / `ChannelKey` / `JsonNormalizer` 等）。`patra-starters` 与 `patra-common` 里技术能力和业务代码混放，「算通用还是算专属」没有答案。
> - 8 条 `api` 依赖声明了但源码从未引用；starter-redisson 零使用方，batch 对它的死依赖迫使两个集成测试专门排除 Redisson；14 个公开类型零引用。
> - `checkBoundary` 没挂进 `check`（文件头说是 Gradle 9.5 bug，但同一套 build-logic 里 `hexagonal-domain` 就是这么挂的）；domain 纯净性是黑名单。
> - 自动配置包名有 5 种写法，配置前缀有 3 种，17 个配置类只有 1 个是 record，14 个 starter 只有 5 个有契约测试。
> - 6 个服务 `scanBasePackages = "dev.linqibin"`，工具模块里 9 个 bean 靠这条扫描进容器，其中 6 个与自动配置双重注册。
> - 日志路径、management 段 6 个服务各写一遍；三份 `*-error-config.yaml` 只差一个前缀，还带着熔断段和死键。
> - starter-core 把 `logback-spring.xml` 放在 jar 根，Boot 无条件采用。
> - SpringBlade 的 blade-tool 按「技术 / 业务」分得清楚，但 `blade-core-boot` 写死依赖 6 个 starter 和 MySQL / Druid / MyBatis；Spring Boot 自己用构建期检查守依赖规则。

### A. 按「技术能力 / 业务」分，不按「通用 / Patra 专属」分

- **影响 Issue**：PAP-79、PAP-81、PAP-82
- **决策**：技术能力全部进 `patra-tool/`，模块名就是能力名；业务代码按归属放：某服务对外契约放该服务，多服务共用业务词汇放 `patra-common`，只有一个服务用的留在该服务。说不出属于哪种能力的零散工具类不进 `patra-tool`，按业务代码同样的归属规则放。
- **否决**：保留「通用 / 专属」两层只补规则——「算通用还是算专属」这个问题本身没有答案，commons-core 就是这么变成杂物间的。拆成独立仓库——没有仓库外使用方，换不来好处。

### B. 去掉 `linqibin` 命名，四层一起换，包根 `dev.patra`

- **影响 Issue**：全部
- **决策**：目录与模块名（`patra-tool/patra-tool-<能力>`）、约定插件 id（`linqibin.*` → `patra.*`）与 Gradle group（`dev.patra`）、配置前缀、Java 包根（`dev.linqibin` → `dev.patra`，1983 个 Java 文件加 76 个非 Java 引用）一次换完，作为第一个提交单独落地。不需要真域名，项目不发布到 Maven Central。
- **否决**：只改前三层保留包根——每个 import 还是旧名字，等于只改表面。

### C. 依赖规则由构建守，`./gradlew check` 是唯一门禁

- **影响 Issue**：PAP-80，并约束 PAP-79、PAP-81、PAP-82
- **决策**：
  - R1 `patra-tool/*` 不依赖 `patra-api/*`，由 `patra.tool-module` 插件自动应用，挂 `check`。
  - R2 工具间 `api` / `implementation` / `runtimeOnly` 只允许 → `patra-tool-core`（测试 → `patra-tool-test`）；其余协作只能 `compileOnly` + `@ConditionalOnClass`；显式白名单仅 security → web，写在 build-logic。
  - R3 domain 编译类路径白名单：JDK、`patra-tool-core`、`patra-common`、Lombok、Jackson annotations、Jackson 3 core / databind、Hutool core、MapStruct。
  - R4 自动配置类检查：`@AutoConfiguration` ⇔ imports 双向一致；类在 `dev.patra.tool.<能力>.autoconfigure` 包且 `public final`；有同名契约测试；禁裸数字 `@Order`；工具模块主代码禁 `@Component` / `@Service` / `@Repository`，`@Configuration` 只在 `autoconfigure` 包；`autoconfigure` 外禁 `JsonMapper.builder()` / `new ObjectMapper`。
  - R5 dependency-analysis-gradle-plugin `buildHealth` 挂 `check`；plan 里放探针任务先看噪音，压不下则退回自写「声明的 project 依赖必须被 import」检查。（实际：探针 unused 575 / undeclared 2207，空聚合 starter 必被判 unused，退回自写 `checkDeclaredDependencies`，见工程 spec 4.6 / 6.4。）
  - 改依赖后重跑 `dumpModuleGraph` 并提交 `module-graph.json`。
- **否决**：规则写在文档里——`checkBoundary` 写了半年没挂进 `check`，8 条死依赖没人发现。

### D. 默认配置随模块走：`EnvironmentPostProcessor` 以最低优先级并入

- **影响 Issue**：PAP-81、PAP-82，以及以后每个新 starter
- **决策**：自己的键靠 record 的 `@DefaultValue`；别人的键（`logging.*`、`management.*`、`spring.jackson.*`）由唯一归属模块的 `EnvironmentPostProcessor` 用 `DefaultPropertiesPropertySource.addOrMerge` 并入，与 v0.9 的 `NacosDefaultsPostProcessor` 同一写法，服务 yml、Nacos、环境变量都能覆盖；每个键只能有一个模块出默认值，归属写在该模块 README（observability：`logging.file.path`、`logging.level.dev.patra=DEBUG`、`management.*`；launch：Nacos 连接与服务发现）。logback 不再放 jar 根，改为 observability 包路径下的文件加 `logging.config` 默认属性，服务配一个键即可覆盖。
- **否决**：`@PropertySource`（加入太晚，管不到 `logging.*`，RuoYi、continew 的做法）；EPP 里 `System.setProperty`（服务覆盖不了，pig 的做法）；jar 里的 `application.yml`；`spring.config.import`。

### E. 配置键按能力命名 `patra.<能力>.*`，不带模块名

- **影响 Issue**：PAP-81、PAP-82，`patra-infra/nacos/dev/`
- **决策**：17 个前缀收成 12 个（`linqibin.starter.<x>`、`patra.starter.<x>`、`patra.security` 全部改成 `patra.<能力>`）；以后能力在模块间搬家不改键。旧键直接替换，`patra-infra/nacos/dev/` 里的 `patra-common.yaml`（object-storage 段）、`patra-catalog.yaml`（batch、rest-client 段）同一 PR 改，先推 Nacos 再部署。
- **否决**：沿用 `linqibin.starter.<模块>`——前缀里带的是 artifact 名，拆 starter-core 就得改键。

### F. JSON 只从容器拿（已先行落地，PR #234）

- **影响 Issue**：PAP-80 的 R4 把它变成规则
- **决策**：容器只有 Boot 装配的 `JsonMapper`，不带 Long→String；注入类型写 `JsonMapper` 不写 `ObjectMapper`（`XmlMapper extends ObjectMapper`，ingest 里会撞）；Long→String 只在 MVC 响应转换器（portal 的 `userId` 用 `z.string()` 校验，这条不能收窄）；JPA 映射器用 `JsonColumnCodec`；不在容器里的类由创建者把 `JsonMapper` 当构造参数传入；刻意例外只有输出进哈希的 `JsonNormalizer`、`ExprJsonCodec`，各自内置固定 mapper。
- **否决**：静态 Holder——拿到哪个实例取决于初始化顺序，已经造成 `JobOperatorHelper` Long 参数变字符串、`WindowSpec.IdRange` 读回抛异常两个潜伏 bug。

### G. 组件扫描只扫服务自己的包，工具模块的 bean 一律由自动配置注册

- **影响 Issue**：PAP-81、PAP-82
- **决策**：6 个启动类改回裸 `@SpringBootApplication`（catalog 的 `exclude = DataRedisRepositoriesAutoConfiguration` 随 redisson 删除后已无必要，一并删），只扫 `dev.patra.<service>`；工具模块里 9 个靠扫描的 bean（3 个命令拦截器、`GlobalRestExceptionHandler`、`SecurityExceptionRethrowAdvice`、`JpaErrorMappingContributor`、`JpaAuditingConfig`、`HibernatePropertiesCustomizer`、`CoreErrorAutoConfiguration` 多余的 `@Configuration`）改由自动配置注册，规则进 R4。
- **否决**：继续 `scanBasePackages = "dev.linqibin"`——同一个 bean 在服务里靠扫描、在切片测试里靠自动配置，来源不同、顺序不同，其中 6 个本来就是双重注册。

### H. 一个版本、一个后端 PR、一份 spec、一份 plan

- **影响 Issue**：全部
- **决策**：4 个 Issue 共用 `feat/v0.10-tool-reorg-api`，从合入 PR #234 之后的 main 切出；工程 spec 与 plan 各一份覆盖整版，plan 按 Issue 分 4 段；文件数超 100，CodeRabbit 跳过，Codex + Claude Action + CI 兜底。
- **否决**：按 Issue 开 PR——中间状态（改了一半的模块名）没法单独合进 main。

> **已排除出本字段**（留给工程 spec 与 plan）：12 个模块各自的类清单与搬迁去向、R4 检查的实现方式（Gradle 任务扫源码还是 ArchUnit）、`PatraOrders` 的具体常量、契约测试的用例模板、Nacos 文件逐键改法。
