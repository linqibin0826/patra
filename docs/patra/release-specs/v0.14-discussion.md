## 1. 版本目标 / 价值

医生和科研人员能在文献页讨论一篇文献，在期刊页查看和写下同行的投稿经验（审稿周期、结果、过程）；讨论和经验都可以追问、回复、@ 同行，被回复或被 @ 时在站内收到提醒。

这是社区互动的第二个版本，建在 v0.13 的互动服务和对象登记表上。点赞与计数、通知中心、关注动态、行为数据、审核等合规能力都不在本版（见第 3 节）。期刊页另外展示从 PubMed 记录算出的客观审稿周期：投稿经验起步时一定很少，这组数据开箱就有。

**规划时的现状**（2026-10-27 核对）：

- interaction 只有 `subject`（对象底座）和 `collection`（收藏）两个子域。`SubjectType` 只有文献，能力只有收藏。子域之间只能依赖对方的读端口与读模型；底座另外公开网关、值对象和枚举，且不依赖任何其他子域。服务内没有进程内事件，也没有 Outbox。注销清理写在 collection 内部，没有扩展点；用户名片（`UserCard` 等）在 collection 的私有包里。
- catalog 的期刊只有一个创建来源（NLM LSIOU，`venuePubmedImportJob`），换库重导会换内部 ID。`nlm_id` 没有全局唯一约束，也没有索引；导入按 ISSN-L → NLM → ISSN 匹配，重复在实践中少见，但没有约束兜底。没有期刊的内部解析接口和批量卡片接口。
- catalog 没有任何审稿周期数据：PubMed History 里的 received、accepted 日期在解析时被丢掉（只取 pmc-release）。原始 XML 已存在 `cat_publication_source`，有离线重解析任务 `pubmedReparseJob`。
- identity 只能按完整用户名查公开主页，没有按前缀搜用户，也没有按用户名批量查 ID。旧用户名保留 90 天，期间可解析到原用户。账号有 `ACTIVE`、`BANNED`、`PENDING_DELETION`、`DELETED` 四种状态；主页可见性规则只有 `ProfileAccess` 一份。邮件走 SMTP + Thymeleaf，13 份模板全是事务或安全类，没有互动类通知。
- 网关对 `/*/_internal/**` 一律返回 403；传给下游的身份断言只有用户 ID、会话 ID、账号类型、客户端类型。
- 门户的文献页、期刊页都是 RSC，期刊页还没有任何互动区块。窄屏顶栏只有搜索和菜单按钮。没有 @ 联想组件、没有 Markdown 渲染依赖、没有任何轮询先例。用户主页的标签写死为「关于 · 收藏夹」。

**验证场景**：

1. A 在一篇文献页发起讨论，质疑它的样本量；C 回复。
2. A 在某刊期刊页写一条投稿经验：3 月投稿，首轮 6 周，大修后录用。期刊页的汇总随之更新。
3. B 在 A 的经验下追问，并 @A。
4. A 在导航栏的提醒入口看到第 1、3 步的两条提醒，点进去回复。

### 2.1 讨论与投稿经验的定义

本节是产品定义，按最终形态定好。来源见文末「调研依据」。

#### 2.1.1 文献讨论

| 项 | 规则 |
|---|---|
| 可讨论的对象 | 本版只有文献。投稿经验下的回复用同一套规则（2.1.2） |
| 结构 | 数据按树存（父评论 + 根评论）。界面只显示两层：根评论下，整楼回复按时间平铺；回复的不是根评论时标「回复 @X」；「查看对话」展开整条回复链 |
| 排序 | 根评论默认按时间正序，可切到「最新」；楼内按时间正序。本版没有按热度排序 |
| 正文 | Markdown 子集：粗体、斜体、引用、列表、行内代码、链接。不支持图片、标题、HTML。PMID、DOI 自动变成链接。≤ 5,000 字（按字素计，同时限制字节数） |
| @ 提及 | 只在评论里生效，一条最多 @ 10 人。联想按用户名或昵称的前缀匹配，只列出主页对你可见的正常账号，本讨论的参与者优先（匿名作者不在其中）；完整输入用户名时，任何正常账号都能 @ 到；90 天保留期内的旧用户名能 @ 到原用户；解析不到的保持纯文本 |
| 编辑 | 作者可编辑，显示「已编辑」，修改历史公开；发布后 5 分钟内的修改不记版本 |
| 删除 | 作者可删除自己的评论。有回复的留下「该评论已删除」占位，楼中楼保留；没有回复的整条去掉 |
| 「作者」标记 | 对象有所有者时（投稿经验），所有者的评论旁显示「作者」；文献没有所有者 |
| 资格 | 登录、邮箱已验证、账号状态正常；冷静期中的账号不能发表 |
| 频率 | 两条评论至少间隔 10 秒，每人每天最多 100 条 |
| 永久链接 | 每条评论有永久链接，打开对象页的「单楼视图」：只显示该根评论和整楼回复，高亮目标 |
| 谁能看 | 匿名访客可读 |
| 空状态 | 认真设计，引导第一条评论。PubMed Commons 四年只有约 0.02% 的文献有评论 |
| 公开计数 | 不显示讨论数、回复数（第 3 节 A） |
| 审核 | 本版没有审核：门户只在 tailnet 内可访问（第 3 节 D） |

#### 2.1.2 投稿经验

| 项 | 规则 |
|---|---|
| 是什么 | 作者向某刊投稿的一次经历，供后来者选刊参考。在期刊页查看和填写 |
| 数据结构 | 按「帖子」结构存：帖子基表（类型、挂在哪个对象下、作者、是否匿名、正文、修订历史、状态）加经验扩展表（结构化字段）。本版只有「投稿经验」一种帖子类型，界面上不出现「帖子」。以后加求助帖只新增类型，不改表（决策 B） |
| 粒度 | 一篇稿件一条经验。同一人对同一刊可以写多条，但投稿日期不能相同 |
| 必填 | 投稿日期、首轮决定日期、首轮结果（直接拒稿 / 审后拒稿 / 大修 / 小修 / 录用）、最终结果（录用 / 拒稿 / 撤稿 / 进行中）、文章类型（取值在工程 spec 定） |
| 选填 | 最终决定日期、审稿轮数、审稿质量评分与编辑沟通评分（1–5 分）、是否付 APC、是否转投过、正文（Markdown 子集，≤ 2,000 字，不解析 @） |
| 校验 | 日期不晚于今天；首轮决定日期不早于投稿日期；最终决定日期不早于首轮决定日期；最终结果为「进行中」时不填最终决定日期。首轮结果与最终结果的一致性规则在工程 spec 定 |
| 时长 | 只收日期，时长由系统算出 |
| 期刊页汇总 | 条数；首轮用时（不含直接拒稿）的中位数与 P25–P75；直接拒稿用时的中位数；结果分布；录用率 = 录用 ÷（录用 + 拒稿），撤稿与进行中不计入。默认统计近 3 年（按投稿日期），可切到全部；不到 5 条只显示条数。读取时计算，写完立刻更新 |
| 匿名 | 发布时可选匿名，之后不能改。匿名时：显示「匿名作者」，不链接主页；接口不向他人返回作者 ID；作者在这条经验下的回复也显示「匿名作者」；由此产生的提醒里，触发人显示「匿名作者」；不出现在 @ 联想的参与者里；不出现在作者主页的「投稿经验」标签里（本人看自己的主页时可见，并标注匿名） |
| 回复 | 经验下可以追问、回复，规则同 2.1.1；作者的回复带「作者」标记 |
| 编辑与删除 | 作者可编辑（修改历史公开，规则同评论）和删除。删除后从期刊页列表与汇总中去掉，经验页显示「该经验已删除」，下面的回复不再展示 |
| 页面 | 期刊页放汇总和经验列表（不显示回复数）；每条经验有独立页面 `/posts/{id}`，经验正文与回复都在这里 |
| 用户主页 | 新增「投稿经验」标签，列出本人的非匿名经验 |
| 资格与频率 | 登录、邮箱已验证、账号状态正常；每人每天最多 10 条 |

#### 2.1.3 PubMed 审稿周期

| 项 | 规则 |
|---|---|
| 数据来源 | PubMed 记录 History 里的收稿（received）与录用（accepted）日期，由 catalog 解析和存储。现有文献用离线重解析回填（原始 XML 已在库），不重新下载 |
| 口径 | 只统计最终录用并收录进 PubMed 的论文，计算收稿到录用的天数；看不到拒稿 |
| 统计 | catalog 按期刊批量预先计算：中位数、P25–P75、样本量；按录用日期统计近 3 年。样本少于 5 篇时只显示样本量 |
| 展示 | 期刊页与「同行经验」汇总并排，分别标注来源，注明「只统计录用论文」；两组不合成一个数 |
| 覆盖 | 不是每篇文献都有这两个日期，回填后记录覆盖率（D7） |

#### 2.1.4 提醒

| 项 | 规则 |
|---|---|
| 类型 | 「回复我的」：有人回复我的评论、有人评论我的经验；「@ 我的」：有人在评论里 @ 我 |
| 规则 | 不提醒自己；同一条评论里既回复又 @ 同一个人，只发一条，归「回复我的」；编辑后只对新增的 @ 发提醒；匿名作者触发的提醒，触发人显示「匿名作者」 |
| 入口 | 导航栏的提醒图标带未读数，桌面和窄屏都要有（窄屏顶栏目前只有搜索和菜单按钮，具体位置由设计稿定）。提醒列表页分「回复我的」「@ 我的」两栏 |
| 刷新 | 未读数每 60 秒取一次，没变化时服务端返回 304；切回页面时立即取一次 |
| 已读 | 点开单条即已读，可一键全部已读 |
| 跳转 | 走评论永久链接，打开单楼视图并高亮目标 |
| 保留期 | 5 个月，由每日任务清理 |
| 渠道 | 只有站内。不发邮件、没有实时推送、不能按类型关闭（第 3 节 C） |
| 不是什么 | 不是用户之间的私信，也不是通知中心 |

#### 2.1.5 账号状态与数据

| 项 | 规则 |
|---|---|
| 注销 | 注销执行后，评论与经验保留，作者显示「已注销用户」；@ 他的地方显示占位，不暴露用户名；他的提醒与收藏由每日清理任务删除 |
| 冷静期 | 不能发表评论和经验；已发表的内容照常显示 |
| 封禁 | 内容保留（下架属于合规包）；封禁期间不能发表（identity 已删除其会话）；昵称照常显示、头像隐藏（identity 规则） |
| 用户相关字段 | 任何表只存用户 ID，不存用户名、昵称、头像；正文里的 @ 存 `<@用户ID>`（仓库规则「用户名只存 identity」） |

## 3. 范围边界（不做的事）

> 下面这些都和讨论、投稿经验高度相关，列在这里是明确「本版不做」。

| # | 不做的事 | 理由 |
|---|---------|------|
| A | **点赞、「有帮助」、公开计数与热度排序**：讨论数、回复数、讨论串的最后回复时间 | 点赞的价值靠显示数字和按「最有帮助」排序，需要异步计数管线加每晚对账，应一次服务所有计数（收藏数、讨论数、经验数、点赞数）；讨论刚上线、内容少时，按时间排序就够用 |
| B | **浏览量与行为数据**：埋点、ClickHouse | 浏览属于行为数据，量大，不进 PG；事件格式要和关注动态的推荐一起定；mini 加 ClickHouse 要单独评估资源 |
| C | **通知中心**：互动邮件提醒、渠道与偏好设置、按类型关闭提醒、实时推送（SSE / WebSocket）、公共事件模块（Outbox），以及 PAP-104、PAP-105 | 本版只有一个来源（interaction）、一个渠道（站内），建中心会成为只有一个消费方的公共模块。通知中心单独做一版；提醒表按以后的信箱设计，到时整体迁入。PAP-104、PAP-105 已于 2026-10-27 加评论说明 |
| D | **审核、举报、申诉、拉黑、楼主管理评论区、实名、网关限流与熔断** | 属于公开上线前的合规包：《互联网跟帖评论服务管理规定》要求发表类互动后台实名，并有举报、申诉渠道。**硬门槛：合规包完成前，讨论和投稿经验只在 tailnet 内开放，不对公网开放**（D10）。以后的贴吧式发帖属于论坛类功能，个人主体备案的网站不能开，还要先解决备案主体问题 |
| E | **贴吧式帖子的其余部分**：吧和版块、帖子标题、求助帖类型、楼层号、置顶和精品、只看楼主、帖子列表页 | 本版只把帖子的数据结构定成最终形态，投稿经验是第一种类型（决策 B）；其余部分等做帖子时按真实需求设计 |
| F | **文献之外的对象开讨论**（期刊页自由讨论、作者、机构、MeSH），以及文献讨论里的「论文作者」认证标记 | 期刊页本版只放投稿经验和经验下的回复。论文作者认证要核实作者身份，catalog 里约 75% 的作者没有 ORCID |
| G | **正文里的图片、附件、公式、表情；PMID、DOI 显示成文献卡片** | 正文只支持 Markdown 子集（决策 C）。图片要接对象存储和内容审核，帖子才真正需要；PMID、DOI 本版只自动变成链接 |
| H | **用户主页「讨论」标签和「我的评论」列表** | 主页本版只加「投稿经验」标签，经验是要长期维护的内容；评论靠提醒和原文页就能找到 |
| I | **讨论与经验的全文检索；期刊检索页按审稿周期筛选或排序** | 两组审稿周期数据只在期刊详情页展示。放进检索要扩展期刊检索的索引和筛选项，而经验数据起步很稀，拿来排序意义不大 |
| J | **经验填 DOI 后与库内文献核对、标「已核实」** | 需要按 DOI 反查 catalog，是一条新链路；上线初期人少，靠经验条数和修改历史就够 |

## 4. 关键决策

> 依据：2026-10-27 的 4 路代码核对与 2 路产品调研（见文末）。Issue 编号见 2.2。

### A. 新增三个子域：讨论、投稿经验（按帖子结构存）、提醒；评论与提醒用进程内事件联动

- **影响 Issue**：PAP-120 / PAP-121 / PAP-122 / PAP-123
- **决策**：interaction 新增 `discussion`（讨论）、`post`（投稿经验，按帖子结构存）、`notification`（提醒）三个子域，每个子域一个 schema，共用服务的一份 Flyway 历史（沿用 v0.13 决策 B）。代码里子域叫 `post`、`notification`，spec 与界面只说「投稿经验」「提醒」。评论写入时，讨论子域在同一个事务里发布进程内领域事件（如「评论已发表」「评论已编辑」），提醒子域订阅后按自己的规则算出收件人并写入。依赖方向：提醒 → 讨论（只依赖事件契约）→ 底座；投稿经验 → 底座；没有环。子域 ArchUnit 规则的公开包清单增加「事件契约」一项。存储：提醒表按收件人 `user_id` 哈希分 16 区、用原生 SQL（与收藏条目相同，服务「我的未读」）；评论、投稿经验、修改历史表不分区（按对象读，量很小）。
- **为什么**：提醒规则（回复了谁、谁是楼主、@ 了谁、去重、不提醒自己）留在提醒子域里；以后迁到通知中心时，只需把进程内订阅换成 Outbox 中继，发布方不改；在同一事务里写入，不会丢提醒。
- **否决**：讨论子域直接调提醒的写接口（讨论要懂提醒规则，以后每种互动都要依赖提醒）；评论提交后再异步写提醒（服务崩溃时会丢）；本版建 Outbox（只有一个消费方，第 3 节 C）。

### B. 对象底座：期刊按 NLM ID 锚定，投稿经验登记成带所有者的本地对象

- **影响 Issue**：PAP-117 / PAP-120 / PAP-121 / PAP-122 / PAP-123
- **决策**：
  - **期刊**（`JOURNAL`）：对外 key 是 catalog 的期刊内部 ID（门户 URL 已在用，按数字解析 key 的逻辑不变）；`natural_key` 是 `nlm:{NLM Unique ID}`，按字符串存（NLM ID 有前导零）。catalog 先在 mini 上核对没有重复，再给 `nlm_id` 加全局唯一约束，并提供内部批量解析接口；解析与每日对账的做法和文献相同。
  - **投稿经验**：按帖子结构存，对象类型叫 `POST`，是本地对象，`natural_key` 是 `post:{ID}`。创建经验时由投稿经验子域经底座网关登记，删除经验时由它更新状态；不经外部解析，也不进每日对账；启动时「每种类型恰好一个外部来源」的校验对本地类型豁免。以后的帖子类型（如求助帖）共用这一种对象类型。
  - **所有者**：登记表新增所有者用户 ID 和「所有者是否匿名」（外部对象都为空；登记时写入，之后不变，与 E 的「匿名不能改」一致）。讨论区和提醒只靠登记表就能给所有者标「作者」、发「回复我的」提醒、把匿名所有者显示为「匿名作者」并排除出 @ 联想，不需要依赖投稿经验子域。
  - **能力矩阵**：文献可以收藏、讨论；期刊可以挂投稿经验；投稿经验可以讨论。
- **为什么**：底座不能依赖其他子域，本地对象只能由所属子域主动登记；期刊和文献一样，catalog 换库重导会换内部 ID，必须锚定外部标识；匿名标记放在登记表里，决策 A 的依赖方向不用多出「讨论 → 投稿经验」这条边；以后加求助帖只新增帖子类型，不动底座和表结构。
- **否决**：经验单独登记成 `EXPERIENCE` 对象（被帖子结构取代）；门户 URL 改用 NLM ID（和文献的写法不一致）；讨论区经读端口向投稿经验子域查匿名标记（多一条子域依赖，以后每种本地对象都要加一条）；讨论区同时支持挂在对象下和挂在经验下两种方式。

### C. 正文与 @：存 Markdown 原文和用户 ID 标记，用户名由服务端解析

- **影响 Issue**：PAP-118 / PAP-121 / PAP-122 / PAP-124 / PAP-125
- **决策**：
  - 正文存 Markdown 原文，不存 HTML。门户按场景用白名单渲染（本版评论与经验正文都不放图片、标题、HTML）；后端只校验字数和 @ 人数，不渲染。以后帖子要放图片，只放开该场景的白名单，不迁数据。
  - @ 只在评论里生效，经验正文不解析 @。
  - 客户端只发 `@用户名`；interaction 写入时调 identity 内部接口批量解析（含 90 天保留期内的旧用户名），存成 `<@用户ID>`；解析不到或不是正常账号的保持纯文本；超过 10 人拒绝。编辑时由服务端把标记换回当前用户名。
  - 联想接口由 interaction 对外提供（要求登录）：先列本讨论参与者（不含匿名作者），再并上 identity 内部前缀联想（用户名或昵称）的结果；主页可见性由 identity 按访客执行。
- **为什么**：网关对 `/_internal/**` 一律 403，门户调不到 identity 的内部接口；v0.13 已否决公开的查人接口；「参与者优先」只有 interaction 知道；用户名只存 identity，存 ID 标记改名后不失效。
- **否决**：存 HTML（白名单一改就要迁数据，还有 XSS 风险）；存 `@用户名`（违反「用户名只存 identity」，改名后 @ 失效）；门户经网关直接调 identity 的公开联想接口（可被枚举，也不知道谁是讨论参与者）；纯文本加自动链接（引用、列表是学术讨论最常用的格式）。

### D. 提醒：两类、按通知中心的信箱设计、轮询取未读数

- **影响 Issue**：PAP-121 / PAP-123 / PAP-126
- **决策**：两类提醒：「回复我的」（回复我的评论、评论我的经验）与「@ 我的」。表结构按以后通知中心的信箱设计：收件人、类型、触发人、对象、评论、创建时间、已读时间。未读数接口支持条件请求：门户每 60 秒取一次，没变化时服务端返回 304，切回页面时立即取一次；门户自己的 Route Handler 要把条件请求头原样转发。每条提醒一行，不做「A 等 3 人」聚合。保留 5 个月，由每日任务清理。点开提醒走评论永久链接（决策 F）。
- **为什么**：通知中心单独做一版（第 3 节 C），到时整体迁入；单机小规模下，轮询加 304 最省事，门户也只多一处轮询。
- **否决**：SSE / WebSocket（单机要维护长连接，不划算）；聚合提醒（主要用于点赞，本版没有点赞）；本版建通知中心（只有一个来源、一个渠道）。

### E. 发表资格、频率限制、匿名

- **影响 Issue**：PAP-120 / PAP-121 / PAP-122 / PAP-123 / PAP-125 / PAP-126
- **决策**：
  - **资格**：发评论、写经验要求邮箱已验证、账号状态为 `ACTIVE`。每次写入经 identity 内部接口回查，和解析 @ 合起来最多两次调用；网关身份断言不加字段（沿用 v0.13 决策 F）。
  - **频率**：在 PG 里按作者计数：评论至少间隔 10 秒、每天最多 100 条；经验每天最多 10 条。这段逻辑放在底座的「发表守卫」里，讨论和投稿经验共用。
  - **匿名**：发布时选择，之后不能改。匿名由服务端遮蔽：接口不向他人返回作者 ID；作者在自己匿名经验下的评论、这些评论引起的提醒里的触发人，都显示「匿名作者」；匿名作者不进 @ 联想的参与者列表；匿名经验不出现在作者主页的公开「投稿经验」标签里。
- **为什么**：给断言加字段要改约 51 个文件（v0.13 决策 F）；按作者计数在 PG 里精确、重启不丢，现有量下不需要新组件；只在门户隐藏作者时，接口数据里已经泄露；允许事后切换匿名，前后对照就能反推出身份。
- **否决**：断言加邮箱验证状态；用 Redis 做频率限制（interaction 目前不用 Redis，为此新增依赖不划算）；只在前端隐藏匿名作者；允许发布后切换匿名。

### F. 读路径与链接

- **影响 Issue**：PAP-116 / PAP-121 / PAP-122 / PAP-124 / PAP-125 / PAP-126
- **决策**：
  - 讨论区、经验区的首屏由服务端取：匿名访客可读；已登录时带会话，拿到「这条是我发的」标记和作者主页是否可见。每个区块单独 Suspense、超时降级为「暂不可用」，文献页、期刊页主体照常显示（沿用 v0.13 决策 H）。经验区是期刊页的第一个互动区块。
  - 评论作者和被 @ 的人，由 interaction 一次批量向 identity 取齐，嵌进响应（沿用 v0.13 决策 E）。
  - 每条经验有独立页面 `/posts/{id}`，经验正文与回复都在这里；期刊页只放汇总和经验列表。
  - 评论的永久链接打开对象页的「单楼视图」：只显示该根评论和整楼回复，高亮目标；提醒与分享都用它，不做「翻到第 N 页再定位」。
- **为什么**：匿名经验的「这条是我发的」只能由服务端按会话判断；互动服务出问题不能拖垮文献页、期刊页；前面的评论被删后页码会错位，单楼视图不受影响。
- **否决**：全部放到客户端取（匿名经验要另开一个「我的」接口）；按页码定位评论；经验详情做成期刊页里的展开层（没有独立地址，提醒无处落地）。

### G. 两组审稿周期数据分开计算、分开标注

- **影响 Issue**：PAP-119 / PAP-122 / PAP-125
- **决策**：期刊页并排展示两组数据并标清来源。「同行经验」由 interaction 在读取时计算（口径见 2.1.2）；「PubMed 记录：收稿到录用」由 catalog 解析 History 的收稿、录用日期后按期刊批量预算（口径见 2.1.3），现有文献走离线重解析回填（原始 XML 已在 `cat_publication_source`），不重新下载。
- **为什么**：两组口径不同：PubMed 只统计最终录用的论文，看不到拒稿；经验包含拒稿，但样本少。合成一个数会误导人。经验写完期刊页要立刻更新，且每刊样本很少，读时计算即可；PubMed 每刊动辄上千篇，适合批量预算。
- **否决**：把两组合成一个综合周期；经验汇总每天预算一次；运行时调 NCBI 取日期（每秒 3 次限制，且原始 XML 已在库）。

### H. 注销：内容保留并匿名化，个人数据删除

- **影响 Issue**：PAP-120 / PAP-121 / PAP-122 / PAP-123
- **决策**：用户注销后，他的评论和经验保留，作者显示「已注销用户」（identity 已返回占位，interaction 不改写内容）；他的收藏和提醒被删除。注销清理从 collection 的内部实现改为底座的公共流程，各子域登记自己的清理动作（收藏、提醒删除；讨论、投稿经验不动）。
- **为什么**：删掉评论会打断别人的楼中楼；经验是公共参考信息，删除会让期刊汇总失真；identity 删除邮箱、昵称等个人信息后，剩下的用户 ID 已对应不到具体的人。
- **否决**：内容一并删除；在 interaction 里改写作者（违反「其他服务只存用户 ID」）；每个子域各写一个清理任务（重复枚举用户、重复回查 identity）。

## 调研依据

2026-10-27 并行做了 4 路代码核对和 2 路产品调研，报告在当天会话里，这里只记结论和用到的来源。

**代码核对（4 路）**

1. **catalog 期刊身份**：标识类型有 12 种，最适合做锚的是 NLM ID（与文献的 PMID 同属 PubMed 体系）；`nlm_id` 没有全局唯一约束和索引，按 NLM 查询遇到重复时结果不确定；期刊只有 `venuePubmedImportJob` 一个创建来源；PubMed History 的收稿、录用日期在解析时被丢掉。结论见第 1 节「规划时的现状」。
2. **interaction 底座**：`SubjectType`、`SubjectCapability`、`NaturalKeyScheme` 只覆盖文献；`SubjectSources` 在启动时要求每种类型恰好一个来源；子域边界规则在 `patra-tool-test` 的 `SubdomainArchitectureRules`；用户名片在 collection 私有包；注销清理没有扩展点；服务内没有进程内事件和 Outbox。
3. **identity 的 @ 支撑**：没有按前缀联想、也没有按用户名批量查 ID 的接口；旧用户名保留 90 天；主页可见性规则只在 `ProfileAccess`；网关对 `/_internal/**` 一律 403。
4. **门户落点**：讨论区放在文献页主栏最后，独立于全文区块；经验区放在期刊页「影响力速览」之后；窄屏顶栏要新增提醒图标；@ 联想需要定位到光标的新组件（现有组合框做不到）；没有 Markdown 依赖、没有轮询先例；用户切换时要清提醒相关缓存。

**产品调研（2 路）**

1. **讨论区与提醒**：两层展示和按时间正序最适合讨论量少的学术场景；修改历史公开；Markdown 子集加预览；@ 存 ID 标记、单条上限 10 人；提醒每条一行，未读数轮询加 304。来源：[单层嵌套的讨论](https://jefftkaufman.substack.com/p/single-level-nesting)、[Tildes 压平深层嵌套](https://tildes.net/~tildes.official/cjg/experimenting_with_a_way_of_avoiding_deeply_nested_comment_threads)、[PubMed Commons 关停公告](https://ncbiinsights.ncbi.nlm.nih.gov/2018/02/01/pubmed-commons-to-be-discontinued/)、[ResearchGate 删除文献评论](https://help.researchgate.net/getting-started/commenting-on-research-items)、[bioRxiv 改用 Hypothesis](https://web.hypothes.is/blog/strengthening-scientific-dialogue-biorxiv-launches-article-level-commenting-with-hypothesis/)、[GitHub 评论修改历史](https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment)、[Discourse 站点默认设置](https://raw.githubusercontent.com/discourse/discourse/main/config/site_settings.yml)、[Discourse 匿名化账号](https://meta.discourse.org/t/anonymizing-a-user-account/314902)、[PubPeer FAQ](https://pubpeer.com/static/faq)、[Hypothesis 的 Markdown](https://web.hypothes.is/help/formatting-annotations-with-markdown/)、[Slack 消息格式](https://docs.slack.dev/messaging/formatting-message-text)、[Hypothesis 的 @ 提及](https://web.hypothes.is/help/mentions-for-the-hypothesis-web-app/)、[GitHub 通知](https://docs.github.com/en/subscriptions-and-notifications/concepts/about-notifications)、[GitHub 通知 API 的轮询](https://docs.github.com/en/rest/activity/notifications)。
2. **投稿经验**：一篇稿件一条经验；只收日期、时长由系统算；首轮与最终结果分开记；汇总用中位数加四分位，样本少时只显示条数；前台昵称、后台实名，可以匿名展示。社区产品普遍用平均值、把「结果未知」算进录用率分母，这两点不学。来源：[SciRev 期刊页](https://scirev.org/journal/neuroscience/)、[SciRev 数据论文](https://pmc.ncbi.nlm.nih.gov/articles/PMC5629227/)、[LetPub 投稿经验](https://www.letpub.com.cn/index.php?journalid=8695&page=journalapp&view=detail)、[小木虫投稿经验](http://muchong.com/bbs/journal.php?view=detail&jid=748)、[Elsevier Journal Finder](https://elsevier.support/publishing/answer/how-can-i-find-the-right-journal-for-my-paper-in-journal-finder)、[期刊审稿时长公示示例](https://www.explorationpub.com/Journals/ei/Journal_Metrics)、[互联网跟帖评论服务管理规定](https://www.cac.gov.cn/2022-11/16/c_1670253725725039.htm)。
