## 1. 版本目标 / 价值

读者可以用 Google、GitHub 或 ORCID 账号登录 Patra，首次登录验证邮箱后就建好账号；已有账号的用户可以在设置页绑定和解绑这些第三方账号。

**验证场景：**

- **新用户**：小陈点「用 GitHub 登录」，填用户名和邮箱，输入邮件里的验证码，账号建好。退出后再点 GitHub，回到同一个账号。
- **老用户**：老王已有邮箱密码账号，在设置页绑定 ORCID，下次直接用 ORCID 登录，进的还是原来的账号。

**学习目标**（不是对读者的承诺）：练习用主流框架接入 OAuth2 和 OIDC，把授权码流程、预劫持防护和再认证讲清楚。

### 2.1 产品规则

| 项 | 规则 |
|---|---|
| 平台 | Google、GitHub、ORCID |
| 登录入口 | 登录页、注册页显示三家入口，按服务端配置显示：线上公网和本机显示，tailnet 不显示（决策 G） |
| 老用户登录 | 按 `(provider, subject)` 找到账号，发现有的不透明会话；封禁、注销中的处理与密码登录一致 |
| 首次登录 | 填用户名和邮箱，能预填就预填（GitHub 的 `login`，对方给的邮箱），输入邮件验证码后才建账号 |
| 邮箱撞车 | 填写已注册邮箱时不建账号、不合并，提示先用原方式登录，再到设置页绑定 |
| 绑定 | 设置页「登录方式」卡片；要求再认证，邮箱须已验证；每家只能绑一个；已绑给别人的账号被拒绝 |
| 解绑 | 要求再认证；没有密码且只剩这一种登录方式时拒绝 |
| 安全邮件 | 绑定、解绑各发一封 |
| 再认证 | 只认密码；第三方登录不算；没有密码的用户先经找回密码流程设置密码 |
| 第三方资料 | 头像、昵称不导入；用户名只作预填建议 |
| 账号标识 | 设置页显示用：Google 显示邮箱，GitHub 显示 `login`，ORCID 显示 iD |
| 权限范围 | Google `openid email`；GitHub `read:user`；ORCID `openid` |
| 注销 | 到期执行时删除外部身份，同一个第三方账号可以重新注册 |

## 3. 范围边界（不做的事）

| | 不做的事 | 为什么 |
|---|---|---|
| A | **其他平台**：微信、机构登录等 | 这版只做三家 |
| B | **在公开主页显示 ORCID iD，或认领作者** | 这次 ORCID 只当登录方式 |
| C | **Patra 当授权服务器**，开放给别的应用接入；多站单点登录 | 这次 Patra 只当客户端 |
| D | **使用第三方资料**：头像、昵称不导入，用户名只作预填建议 | 用不上，也符合最小必要 |
| E | **保存第三方令牌**，替用户调对方接口，比如同步 ORCID 作品 | 只做登录，确认身份后就丢弃 |
| F | **一家绑多个账号** | 由 `(user_id, provider)` 限制为每家一个 |
| G | **其他再认证方式**：跳回第三方、邮件验证码再认证 | 再认证只认密码；首次注册的邮箱验证码不在此列 |
| H | **人机验证和两步验证** | 验证码发送按 IP 和邮箱限次数；ALTCHA 留给决定对外开放的那一版 |

## 4. 关键决策

> 每条按「问题 → 选择 → 为什么 → 代价」写。进本节的门槛：影响 2 个以上 Issue、同时影响前后端、或事后很难改回来。

### A. 用 Spring Security 官方的 `oauth2Login`

- **影响 Issue**：PAP-180 / PAP-182 / PAP-184
- **问题**：协议流程自己编排，还是用框架。
- **选择**：用 `spring-boot-starter-security-oauth2-client` 的 `oauth2Login`，靠官方扩展点接入：`AuthorizationRequestRepository`、`OAuth2AuthorizedClientRepository`、成功和失败处理器。
- **为什么**：这是企业常规做法；state、nonce、PKCE、换令牌、验签都由框架完成，并按 `openid` scope 自动区分 OIDC 与纯 OAuth2。
- **代价**：要处理三个默认行为：① [`patraSecurityFilterChain`](../../../patra-tool/patra-tool-security/src/main/java/dev/patra/tool/security/autoconfigure/SecurityServletAutoConfiguration.java) 在已有过滤器链时不生效，要改 starter 让两条链共存；② `{baseUrl}` 会解析成内网地址，`redirect-uri` 要按环境写完整地址；③ 框架默认留存 access token，要换成什么都不存的实现。

### B. 门户收回调，identity 换令牌

- **影响 Issue**：PAP-180 / PAP-184 / PAP-186
- **问题**：浏览器只和门户打交道，而 client secret 只应放在后端。
- **选择**：门户转发授权和回调请求；identity 跑 `oauth2Login` 并返回结果；Cookie 只由门户写。授权请求存 Redis，identity 保持无状态。门户把 `state` 写进短期 Cookie（`SameSite=Lax`），回调时先核对。
- **为什么**：Redis 里的记录证明「这个 state 是我们发的」，Cookie 证明「是这个浏览器发起的」，两者都对上才能防登录 CSRF 和绑定 CSRF。
- **代价**：门户多两个转发路由，要手动处理跳转（`redirect: manual`）。

### C. 外部身份单独一张表

- **影响 Issue**：PAP-182 / PAP-183 / PAP-184
- **问题**：账号重建设计第 12.1 节预留的表里有 `raw_profile`、`email_at_provider`，还要不要。
- **选择**：`idn_user_external_identity` 只存 `user_id`、`provider`（`GOOGLE` / `GITHUB` / `ORCID`）、`subject`、`account_label`、`linked_at`、`last_login_at` 和审计列；唯一约束 `(provider, subject)`、`(user_id, provider)`。`subject` 存规范形式，ORCID 只存裸 iD。不存令牌和资料快照。
- **为什么**：用不上的数据不收。登录过程中的短命数据（授权请求、待补填记录）放 Redis，丢了重走一遍即可。
- **代价**：要查对方资料时只能重新授权。

### D. 永不按邮箱合并；验证邮箱后才建账号

- **影响 Issue**：PAP-183 / PAP-186
- **问题**：`idn_user.email` 不能为空，第三方又不一定给邮箱，用户要自己填。如果先建账号后验证，老王可以用自己的 GitHub 加小陈的邮箱建号；小陈走找回密码进入账号后，老王的 GitHub 还绑在上面。
- **选择**：账号在邮箱验证通过时才创建，之前只有 Redis 里的待补填记录。用验证码，必须填回发起的页面，不用邮件链接。
- **为什么**：验证码填回发起页，老王拿不到；链接却可能被诱导点开。这样第三方注册的用户邮箱都已验证，也不存在「填错邮箱卡死」。
- **代价**：多一种邮件和一套限次逻辑；现有 `idn_email_token` 外键指向用户表，用不上，验证码放 Redis。这里替代了 v0.12 决策 B 之下「先建账号后验证」的默认流程。

### E. 再认证只认密码

- **影响 Issue**：PAP-184 / PAP-187
- **问题**：只用第三方登录的用户没有密码，v0.12 写过「跳回提供方再认证」。但 Google、GitHub 文档都没有强制重新输密码的办法，第三方登录状态还在时可能一闪而过。
- **选择**：第三方登录不写 `auth_at`，`auth_at` 改为可空，守卫把空值当作已超时。没有密码的用户做敏感操作时，引导其经现有找回密码流程设置密码，重设处理器没有凭据行时已经会新建。`/auth/me` 增加 `hasPassword`，供门户选择弹框。
- **为什么**：保护强度不因绑定第三方而下降；不引入第二种再认证机制。
- **代价**：设置密码后所有设备下线，要重新登录一次。替代 v0.12 关键决策里的「跳回提供方再认证」。

### F. 代码放现有的 `account` 子域

- **影响 Issue**：PAP-180 / PAP-182 / PAP-183 / PAP-184
- **问题**：是否新建子域。
- **选择**：放 `account`，用例族 `usecase.oauth`。domain 与 app 只看到值对象 `ProviderAccount`，不沾 Spring 的类型。
- **为什么**：首次登录要创建 `User`，规范不允许跨子域写对方仓储；单独成子域反而绕。
- **代价**：`account` 继续变大。

### G. 第三方登录入口只在公网域名显示

- **影响 Issue**：PAP-181 / PAP-185 / PAP-186
- **问题**：回调地址要提前注册且必须 HTTPS（Google 只对 localhost 例外，ORCID 正式环境只接受 HTTPS）；tailnet 的 `http://...:4000` 不满足，Cookie 也绑定各自的域名。
- **选择**：入口按服务端配置显示：线上公网和本机显示，tailnet 不显示；本机覆盖用 `PATRA_OAUTH_HOST`。本版不动 `PATRA_SESSION_COOKIE_SECURE`。
- **代价**：经 tailnet 访问门户时只能用邮箱密码登录。

### H. 环境分开，测试不连真实平台

- **影响 Issue**：PAP-181 / PAP-180 / PAP-182 / PAP-183 / PAP-184 / PAP-186
- **问题**：本机、线上回调地址不同；启动和 CI 不应依赖外部服务。
- **选择**：本机和线上各一套应用（GitHub OAuth App 只能填一个回调地址），ORCID 本机用沙箱、线上用正式接口。三家都写明确的端点地址，不用 `issuer-uri`，否则 Spring Boot 启动时要联网读发现文档。自动化测试用 WireMock 模拟平台，真实三家在 mini 上手工验收。
- **代价**：要维护多份应用与配置；模拟平台不能替代真实验收。

### 外部约束

- **ORCID 公共 API 只允许非商业使用**，不能用在创收的产品上。Patra 目前是学习项目，符合条件；以后要收费，须换会员 API。
- **ORCID 的 PKCE**：发现文档没有声明，由 PAP-181 用沙箱实测，结果决定 `requireProofKey` 的开关。Google、GitHub 打开。

## 5. Done 判定

「mini 实测」指 CD 部署 main 最新提交后，在 `patra.linqibin.dev` 上用真实账号操作。

### 流程（mini 实测）

- [ ] **D1 三家首次登录**：Google、GitHub、ORCID 各走一遍。补填用户名和邮箱，输入验证码后账号建好；退出再登录，回到同一个账号。
- [ ] **D2 邮箱撞车**：首次登录填写已注册的邮箱时，提示先用原方式登录再绑定，不建账号，原账号也没有变化。
- [ ] **D3 绑定与解绑**：有密码的用户在设置页绑定三家，之后能用它们登录；解绑后不能再用它们登录；每次绑定、解绑都收到安全邮件。
- [ ] **D4 绑定被拒**：已绑到其他账号的第三方账号绑定时被拒绝；只剩一种登录方式、又没有密码时，解绑被拒绝。
- [ ] **D5 再认证**：只用第三方登录的用户做注销这类操作时，界面提示先设置密码；设好后输入密码能完成操作。第三方登录本身不开放再认证窗口。
- [ ] **D6 注销后重新注册**：注销到期后，外部身份行被删除，同一个第三方账号可以重新注册。

### 自动化测试（`./gradlew check`、identity 和 notification 的集成测试、门户测试全部通过）

- [ ] **D7 协议攻击被拒绝**：用模拟平台覆盖以下场景，都不会建账号或发会话：`state` 不一致或记录已被用过；缺少 Cookie；`id_token` 的签名、nonce 或受众不对。
- [ ] **D8 账号攻击被拒绝**：预劫持路径有测试守住：验证码没通过就不建账号；用别人的回调绑定时，因发起人和会话对不上而被拒绝。
- [ ] **D9 门户流程**：Playwright 用模拟平台跑通首次登录、老用户登录和绑定，桌面和手机布局都检查过。

### 安全与文档

- [ ] **D10 令牌和密钥不留痕**：第三方令牌不进数据库、Redis 和日志；client secret 只在 `~/.patra/secrets/`，gitleaks 通过。
- [ ] **D11 文档同步**：identity README 和隐私政策写清第三方登录收集什么；工程设计记下被替代的 v0.12 决策；ORCID 公共 API 的非商业限制写在本文件。
