# v0.20 Human Verification：人机验证

> **目标**：同一个网络或同一个账号短时间内连续登录失败时，再次提交必须先通过人机验证，撞库和爆破的成本都会明显提高；注册和找回密码每次都要先过验证，正常输对密码的用户感觉不到它。Turnstile 和 TRUSTTURN 改配置就能切换，业务代码不用动。
> **Linear Project**：[v0.20 Human Verification](https://linear.app/papertrace/project/v020-human-verification-2f6e620c5e6d)（P-PAP-17）
> **Issue 池**：PAP-190、PAP-192 ~ PAP-195（BE 3 + FE 2）
> **创建日期**：2026-11-05
> **状态**：进行中
> **上一版**：[v0.19-social-login](v0.19-social-login.md)（第三方登录，尚未收尾，两版互不阻塞）

## 1. 版本目标 / 价值

现有的登录限制只按邮箱计数：一个邮箱 15 分钟内失败 5 次就锁定 15 分钟。它防得住对单个账号爆破，防不住撞库（每个邮箱只试一两次，到不了门槛）；攻击者也能连错 5 次，把别人的账号锁住。门户 2026-10-28 起已经通过 `https://patra.linqibin.dev` 对外，注册和找回密码还没有人机验证，被刷会影响 `linqibin.dev` 的发信信誉。

**验证场景**：

- 同一个 IP 换多个邮箱连续失败，到门槛后，不带令牌的请求不再校验密码。
- 同一个邮箱换多个 IP 连续失败，也一样。
- 换一个 IP 和邮箱的正常用户仍能直接登录。

## 3. 范围边界（不做的事）

| 不做 | 原因 |
|---|---|
| **网关流量限流**（PAP-189） | 这版只管要不要验证、验证能否通过，不限制请求速率 |
| **ALTCHA 或其他加载失败兜底** | 攻击者可以声称组件加载失败，专走较弱的路径，反而拉低防护 |
| **按 IP 封禁** | 到门槛只要求验证，不封禁，同一网络下的正常用户不受连累 |
| **改动账号锁定规则** | 5 次失败锁 15 分钟保持不变。人机验证会提高恶意锁号的成本，但这版不根除这个问题 |
| **给其他接口加验证** | 第三方登录相关接口、`/reset`、`/reauth` 都不加，它们有平台凭证、邮件令牌或登录态把关 |
| **验证国内能否加载 Turnstile** | 加载不了时可以通过配置切到 TRUSTTURN |
| **检查密码是否在泄露名单里、两步验证** | 和这版目标相关，但都是另一层防护 |

## 4. 关键决策

### A. 校验放在 identity

验证只在 identity 里判断，不放在网关或门户。只有 identity 知道失败次数，也只有服务端校验才防得住绕过前端直接调接口。

### B. 当前厂商只配置在 identity

门户从 identity 的公开接口读取厂商和 `sitekey`，不再另配一份。切换厂商只改 Nacos，门户不用重新部署。CSP 同时放行两家。切到 TRUSTTURN 时打警告；如果它的密钥没配，切换要明确报错。

原定默认通道是 Turnstile。11/06 实测通过后，用户决定线上长期用 TRUSTTURN，`provider` 已改成 `trustturn`；代码里没配时的默认值仍是 Turnstile。TRUSTTURN 的运营方、价格和隐私政策都没有公开说明，所以保留这些隔离要求：只用 iframe 加 `sandbox`，不加载它域名下的脚本，校验时不传用户数据，它返回的结果不作为登录的唯一防线。使用期间，访客的 IP 和浏览器信息会发给它，它也可以对任何请求都返回成功。

### C. 验证不了一律拒绝

第三方校验失败、超时或组件加载失败，都不放行，也不用第三家兜底。超时重试时必须带 `idempotency_key`，否则同一个令牌第二次校验会被判为重复。

**代价**：Turnstile 或校验接口故障期间，新用户注册和找回密码暂时不可用；被触发验证的登录也走不通。正常用户登录不受影响。

### D. 两个触发条件，满足任一个就要验证

- **同一 IP**：15 分钟内失败 5 次。登录成功不清零，否则攻击者用自己的账号登录一次就能清掉计数。IPv6 按 /64 计数。
- **同一邮箱**：15 分钟内失败 3 次，复用现有失败计数。必须小于锁定门槛 5，配置反了就启动失败。不存在的邮箱同样会计失败，所以看不出邮箱是否存在。
- **已锁定的账号**：直接提示锁定，不要求验证，也不调第三方。

校验放在事务外，并且在 `loginThrottle.begin` 之前，所以校验失败的请求不占失败限制名额，也不做密码哈希。

### E. 门户先提交，被要求后才显示组件

- **登录**：平时不显示组件。后端返回“需要验证”后才显示，用户通过后重新提交。正常用户不会加载第三方组件，也省去一次预检请求。
- **注册和找回密码**：组件一直显示。

令牌只能用一次，提交失败后门户要重置组件拿新令牌。

### F. 真实 IP 从 `CF-Connecting-IP` 取

外网访问经 OrbStack 端口转发进入，门户看到的来源都是 `192.168.97.1`，不解决的话所有外网用户都算同一个 IP。门户取到真实 IP 后继续走现有的转发链路，网关和 identity 不用改。

**代价**：能直连 4000 端口的 tailnet 或局域网设备可以伪造这个头，这些都是用户自己的设备，风险可接受。这个头能否经隧道完整到达门户，要在 mini 上实测确认。

### G. 测试和真实服务分开

自动化测试用 WireMock 模拟两家，CI 不连真实服务。本机用 Turnstile 官方测试密钥，真实密钥只绑定 `patra.linqibin.dev`，在 mini 上手工验收。

**代价**：从 tailnet 用 IP 访问门户时，真实密钥的组件校验不过，注册、找回密码和被触发验证的登录都要走公网域名。

### H. PAP-190 先落地

人机验证接在重构后的登录用例上，后端 PR 的第一步是提交 PAP-190，避免两边改同一个方法。

### I. 后端和门户的 PR 一起合并

只上后端的话，门户不会传令牌，注册和找回密码全部被拒绝；门户也还没取真实 IP，所有外网用户共用一个 IP 计数，任何人累计失败 5 次后，所有外网用户都登录不了。这版不留关闭开关，所以两个 PR 都准备好后一起合并，前端开发期间连本机后端。

**代价**：不走“后端先合 main”的惯例；两个 PR 部署之间有几分钟不一致，现在只有少数体验用户，可以接受。

## 5. Done 判定

### 线上实测（`patra.linqibin.dev`，真实密钥）

- [ ] **Turnstile 走通**：注册和找回密码都要先通过组件，通过后业务正常完成。
- [ ] **撞库**：同一个 IP 换多个邮箱连续失败，到门槛后再提交必须先过验证。
- [ ] **爆破**：同一个邮箱连续失败 3 次后再提交要先过验证，第 5 次失败后锁定。
- [ ] **正常用户**：换一个网络和账号输对密码，全程不出现组件。
- [ ] **切换通道**：只改 Nacos 配置就切到 TRUSTTURN，三个页面都走通后再切回 Turnstile，门户不用重新部署。
- [ ] **真实 IP**：外网访问时，登录设备列表显示的是真实 IP，不再是 `192.168.97.1`。

### 自动化测试

- [ ] **适配器单测**：两家都覆盖通过、失败、令牌重复、`hostname` 或 `action` 不符、超时。TRUSTTURN 的签名、时间戳和 nonce 也有测试。
- [ ] **防绕过**：集成测试证明，绕过前端、不带令牌直接调三个接口都会被拒绝。
- [ ] **校验顺序**：集成测试证明，校验失败的请求不占失败限制名额，也不做密码哈希。
- [ ] **服务不可用**：第三方不可用时一律拒绝，错误码和账号锁定不同。
- [ ] **门户**：表单测试覆盖需要验证、验证失败后重置令牌、组件加载失败这几种情况，并验证提示文案和账号锁定不同。
- [ ] **全量通过**：`./gradlew check integrationTest` 和门户测试全部通过。

### 安全与文档

- [ ] **TRUSTTURN 隔离**：逐条确认只用 iframe、`sandbox` 生效、CSP 的 `script-src` 不放行它、校验时不传用户数据。
- [ ] **实测记录**：用开发者工具记录 TRUSTTURN 实际发出的请求和采集的内容。
- [ ] **密钥安全**：仓库里没有 `secret` 和 `app_secret`，只放在 `~/.patra/secrets/`。
- [ ] **文档**：identity README 和基础设施文档写明两家的配置、切换方法和真实 IP 的来源，并删掉“没有人机验证”和“外网来源都是 `192.168.97.1`”这两条已知限制。
