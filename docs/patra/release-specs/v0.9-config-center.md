## 1. 版本目标 / 价值

**改一项配置只需要改一个地方，所有服务一致生效**：非敏感配置在 git 里改一个文件后推送，密钥在 Nacos 控制台改一次。本机 IDE 和 mini 容器两种运行方式读到的是同一份配置。白名单内的配置不用重启就能生效；不合法的新值会让刷新报错、健康检查转为 DOWN，靠 Nacos 文件的评审把关。

本版是配置管理的地基：建起配置中心、动态刷新机制和加固后的 Nacos。以后新增的可调参数都在这套机制上接入。

**验证场景**：

1. 在 `patra-infra/nacos/dev/` 里改 ingest 的 outbox 批大小并推送，正在运行的 ingest 不重启就用上新值。
2. 把批大小改成不合法的值再推送，ingest 的刷新报错、`/actuator/health` 转为 DOWN，日志里有原因。
3. 在 Nacos 控制台改 Redis 密码后，两台机器上的服务各自重启即生效，不再需要 scp 密钥文件。
4. 同一个服务分别在 IDE 和 mini 容器里启动，除了 PAP-72 选定的本地变量，读到的配置完全相同。

## 4. 关键决策

> **现状事实**（2026-10-10 核对，以下决策的依据）：
>
> - 只引入了 nacos-discovery。6 个服务各有 `application.yml`、`application-dev.yml`、`application-container.yml`，Nacos 配置段原样复制了 6 遍。
> - 容器的配置由 compose 的 env 文件三层叠加注入（`.env.common` → `.env.<服务>` → `~/.patra/secrets/*.env`）；IDE 靠 `PATRA_INFRA_HOST` 加 `~/.patra/secrets`。
> - 容器用容器名加容器内端口访问基础设施（`postgres:5432`、`redis:6379` 等），IDE 用 mini 的 tailscale 地址加宿主机映射端口（15432、16379 等）。例外是 RocketMQ broker：`BROKER_IP1` 是 tailscale 的 MagicDNS 短名，但容器里解析不了它，容器里的 ingest 实际上连不上 broker（2026-10-13 PAP-72 实测）。
> - `patra-infra/docker/.env` 里的 Nacos token 签名密钥和 identity 随公开仓库提交；应用用默认账号连 Nacos。
> - Nacos 服务端是 3.0.2。SCA 2025.1.0.0 依赖 nacos-client 3.1.1，没有声明服务端兼容范围，只支持 `spring.config.import`。Nacos 3.1 线停在 3.1.2（2026-03-26），当前稳定版是 3.2.4（2026-08-27）。
> - 28 个 `@ConfigurationProperties` 类中 5 个是 record；Spring Cloud 官方文档写明构造器绑定（含 record）无法刷新，原地重新绑定期间并发读者可能看到中间状态。
> - `patra-infra/docker/.env.dev` 没有被任何 compose 命令加载，实际不生效。

### A. namespace 只区分环境；两种运行方式的差异放在 Nacos 之外

- **影响 Issue**：PAP-72、PAP-74、PAP-76、PAP-77
- **决策**：本版只有 dev 一个环境，只有一个 `dev` namespace，每个服务在 Nacos 里只存一份配置。密钥不进 Nacos（决策 E）。PAP-71 建的 `dev-secrets` 已在 PAP-74 撤销：SCA 让一个应用只连一个 namespace，要从两个 namespace 导入就得自己实现配置加载。IDE 和容器是同一个 dev 环境的两种运行方式，差异收敛为放在 Nacos 之外的本地变量，做法由 PAP-72 实测选定。`dev`、`container` 两个 profile 去掉。
- **否决**：按运行方式建两个 namespace——每份配置存两份，差别只是地址。密钥单独放一个 namespace（PAP-71 原做法）——SCA 不支持一个应用从两个 namespace 导入。

### B. git 是非敏感配置的唯一来源；CD 自动推送，控制台只读

- **影响 Issue**：PAP-75、PAP-76、PAP-77
- **决策**：yaml 放在 `patra-infra/nacos/dev/`，幂等脚本经 Nacos v3 admin API 推送。合入 main 后由 CD 自动推送，本机可手动运行同一脚本。控制台只在应急时用；回滚靠 git revert 后重新推送。
- **改 Nacos 配置后重部署**（2026-10-14 补充）：`patra-<服务名>.yaml` 改动重部署该服务，`patra-common.yaml` 改动重部署全部 6 个，启动时读取的配置才能生效。
- **已知代价**（2026-10-14 补充）：推送先于部署，值不合法（如失败上限写成 0）时正在运行的服务刷新失败、健康检查转为 DOWN，部署脚本回滚到上一个镜像也没用——旧镜像读的是同一份配置。恢复靠 git revert 该配置后重新推送，CD 推送正确配置并重部署。注意只手动推送、不重部署时恢复不了：推回与出错前完全相同的内容，Nacos 客户端认为监听器已有这一版（失败的那版从没被处理成功），不会再通知，服务仍用着坏值；要么重启服务，要么推一版内容不同的配置（如多一行注释）触发刷新（2026-10-14 收尾实测）。不做推送前的完整校验和部署失败后的 Nacos 自动恢复：单人开发，revert 几分钟即可恢复。
- **否决**：以控制台为准——没有评审和 diff，仓库和线上会对不上。SQL 直接写 Nacos 内部表——依赖 Nacos 的表结构。Spring Cloud Config——要多维护一个服务，而 Nacos 已在运行。

### C. 配置分三层，Nacos 覆盖 jar 里的默认值

- **影响 Issue**：PAP-74、PAP-76、PAP-77、PAP-78
- **决策**：
  - jar 里的 `application.yml`：代码默认值和引导配置。
  - `patra-common.yaml`：跨服务共享的配置。
  - `{服务名}.yaml`：单个服务的环境差异和可调参数。

  导入设置 `preference=remote`，让 Nacos 的值覆盖 jar 里的默认值；SCA 默认本地优先，jar 里的默认值会盖掉 Nacos。进程级覆盖（启动参数、系统属性、环境变量）高于 Nacos，Nacos 高于 jar，PAP-74 集成测试已实测。
- **否决**：本地优先，并要求同一个键不在两处出现——只能靠人记，迟早出错。

### D. 动态刷新用 Spring Cloud 自带的重新绑定：需要刷新的配置写成可变类（2026-10-14 改定，取代原定的 `RefreshableProperties<T>`）

- **影响 Issue**：PAP-73（取消）、PAP-78，以及以后所有可调参数
- **决策**：
  - 需要在线刷新的配置写成带默认值的可变 `@ConfigurationProperties` 类，配置变更时由 Spring Cloud 的 `ConfigurationPropertiesRebinder` 原地重新绑定；使用方每次用时再读，不缓存到字段或构造器里。默认值写在类的字段上，jar 的 `application.yml` 里不写这些键：要调就在 Nacos 文件里加键（「jar 与 Nacos 不重复写同一个键」由 `JarConfigOverlapCheckerTest` 检查）。
  - 不需要刷新的配置（数据源、端口、密钥等）继续用 record。Spring Cloud 刷新时会跳过 record，所以原地重新绑定不用关闭。
  - 可刷新的配置类加 `@Validated`，不合法的值让刷新报错、`/actuator/health` 转为 DOWN；新值在校验前已经写入对象，不会保留旧值，靠 Nacos 文件进 git、改动走评审把关。
  - 日志级别直接在 Nacos 里写 `logging.level.*`，由 Spring Cloud 自带机制刷新。调回时先把级别写回原值（如 `INFO`）推送一次，再删键：Spring Cloud 只应用环境里现有的级别，直接删键不会恢复，要等重启（2026-10-14 mini 实测）。
- **为什么改**：调研 Spring Cloud、SCA、Apollo、Micronaut、Archaius 后，业界普遍用可变类自动重新绑定或 `@RefreshScope`，没有广泛采用的「不可变快照 + 原子替换 + 校验失败保留旧值」方案。原定组件要补的三个缺口都成立（record 刷新不了、重新绑定时可能读到重置后的默认值、非法值拦不住），但对单人项目、几个互相独立的参数，代价都可以接受，不值得在共享库里新建一个 starter。
- **已知代价**：重新绑定先把字段重置成默认值再绑定，期间并发读者可能读到默认值；一个配置类刷新失败会中断其后配置类的重新绑定（`ConfigurationPropertiesRebinder` 不吞异常）。
- **否决**：自研 `RefreshableProperties<T>`（原决策）——见上；`@RefreshScope`——引入代理，新值不合法时 Bean 重建失败、异常抛给业务调用方。

### E. 密钥不进 Nacos：配置里用 `${变量}` 引用，值留在本地（PAP-74 改定，取代 PAP-71 的密钥 namespace）

- **影响 Issue**：PAP-71、PAP-74、PAP-75、PAP-76、PAP-77
- **决策**：Nacos 配置分两类写法。
  - 公开的 dev 默认值（PG、MinIO、xxl-job 的账号密码，已在仓库公开）：直接写，或写成 `${变量:默认值}`。
  - 真正的密钥（Redis 密码、网关签身份断言的私钥、外部数据源 API key）：只写 `${变量}`，不给默认值。值留在两台机器的 `~/.patra/secrets/`：本机由 starter 读取，容器经 compose 的 env_file 注入。

  Nacos 自身的加固（PAP-71）照旧：token 签名密钥和 identity 不在仓库、默认管理员密码已改、应用账号只读、推送账号只能写 `dev`。
- **为什么改**：
  - PAP-71 把密钥放在单独的 namespace `dev-secrets`，但 SCA 让一个应用只连一个 namespace，同时读 `dev` 和 `dev-secrets` 就得自己实现配置加载。
  - git 推送是整份文件覆盖。「git 推送」「密钥写在普通配置文件里」「仓库公开」三者不能同时成立。
  - 所以密钥留在本地，配置文件里只放引用。v0.8 决策 G 的理由仍然成立：Redis 密码一公开，任何能连上的人都能写入假会话。
- **已知代价**：
  - 改一个真正的密钥，仍要在两台机器的 `~/.patra/secrets/` 各改一次。只涉及 Redis 密码、网关私钥、几个外部 API key。
  - 本机进程能读到 `~/.patra/secrets/` 下的所有密钥。
- **否决**：
  - 密钥放单独的 namespace（PAP-71 原做法）——要自己实现跨 namespace 的配置加载。
  - SOPS 加密后进 git——要多保管一把私钥，密文永久留在公开仓库历史里。

### F. 连接由 starter 注入，导入由启动器加（PAP-74 改定）

- **影响 Issue**：PAP-74、PAP-76、PAP-77
- **决策**：
  - 连接和服务发现设置由 starter 的 `EnvironmentPostProcessor` 注入，并入 default properties（优先级最低），地址和账号从环境变量读取。
  - 服务名和导入由启动器 `PatraApplication.run("服务名", X.class, args)` 放进 default properties。两条导入都不标 `optional:`，拿不到配置时由签到检查让启动失败。
  - 测试不经过启动器，不连 Nacos 配置中心。
- **与 SpringBlade 的区别**：SpringBlade 的启动器写 System properties，环境变量覆盖不了；这里写 default properties，环境变量、配置文件、Nacos 都能覆盖。
- **否决**：
  - 导入写在各服务的 `application.yml`——初始导入里的服务名占位符解析不了，测试也关不掉这条导入。
  - 构建时注入账号（pig、JeecgBoot）——换环境要重新打包。

### G. Nacos 服务端升到 3.2.4；客户端只用 `spring.config.import`（2026-10-10 改定）

- **影响 Issue**：PAP-71、PAP-74
- **决策**：服务端升到当前稳定版 3.2.4。客户端沿用 SCA 2025.1.0.0 带的 nacos-client 3.1.1；Nacos 官方承诺 3.x 服务端兼容 2.x、3.x 客户端，兼容性在 PAP-71 上 mini 实测确认。不引入 bootstrap 依赖，它会导致动态刷新失效。
- **为什么不是原定的 3.1.x**：3.1 线已停止维护。3.1.2 按 id 批量删除、导出配置时不检查 namespace，只对 `public` 有写权限的账号也能删掉 `dev` 里的配置（包括 `patra-secrets.yaml`），3.2.3 才修复；3.2.4 还修了授权元数据解析的问题。
- **已知代价**：3.2 删除了 v1/v2 HTTP API，脚本只能用 v3；这个服务端与客户端的版本组合 SCA 没有专门测过。
- **否决**：继续用 3.0.2；停在 3.1.2 并靠收窄权限绕开漏洞——拿不到之后的安全修复。
