## 1. 版本目标 / 价值

**改一项配置只需要改一个地方，所有服务一致生效**：非敏感配置在 git 里改一个文件后推送，密钥在 Nacos 控制台改一次。本机 IDE 和 mini 容器两种运行方式读到的是同一份配置。白名单内的配置不用重启就能生效，不合法的新值会被拒绝、继续沿用旧值。

本版是配置管理的地基：建起配置中心、动态刷新机制和加固后的 Nacos。以后新增的可调参数都在这套机制上接入。

**验证场景**：

1. 在 `patra-infra/nacos/dev/` 里改 ingest 的 outbox 批大小并推送，正在运行的 ingest 不重启就用上新值。
2. 把批大小改成不合法的值再推送，ingest 继续用旧值，并在日志里报告拒绝原因。
3. 在 Nacos 控制台改 Redis 密码后，两台机器上的服务各自重启即生效，不再需要 scp 密钥文件。
4. 同一个服务分别在 IDE 和 mini 容器里启动，除了 PAP-72 选定的本地变量，读到的配置完全相同。

## 3. 范围边界（不做的事）

| # | 不做的事 | 理由 |
|---|---------|------|
| A | **prod 环境与多环境隔离**：只建 `dev` 一个 namespace | 现在只有一个 dev 环境；上云做 prod 时再加 namespace |
| B | **密钥加密或专门的密钥管理**（KMS、Vault、Nacos 加密插件、SOPS） | 本版靠加固 Nacos 和 tailnet 隔离保护密钥；加密插件只起混淆作用；prod 时重新评估 |
| C | **把所有可调参数都改成可动态刷新** | 首批只接 3 项证明机制；其余按需逐项接入，每接一项都要同时改读取它的代码 |
| D | **配置变更的评审、灰度、审批流程**（含 Nacos beta 灰度发布） | 单人开发，git 提交加 CD 推送即变更记录；回滚靠 git revert 后重新推送 |
| E | **基础设施自身的配置进 Nacos**（PG、Redis、RocketMQ、xxl-job、Nacos 容器本身的 compose 配置） | 它们在 Nacos 之前就要就绪；Nacos 自己的凭据只能放在外面 |
| F | **Nacos 集群与高可用** | 继续单机部署，客户端靠本地快照兜底 |
| G | **服务发现的 namespace 隔离** | 保持现状，本机实例和 mini 容器仍能互相发现 |
| H | **前端 portal 的配置进 Nacos** | portal 是 Next.js，配置走它自己的环境变量体系 |
| I | **Nacos 数据备份** | dev 数据可丢弃；生产环境才需要 |

## 4. 关键决策

> **现状事实**（2026-10-10 核对，以下决策的依据）：
>
> - 只引入了 nacos-discovery。6 个服务各有 `application.yml`、`application-dev.yml`、`application-container.yml`，Nacos 配置段原样复制了 6 遍。
> - 容器的配置由 compose 的 env 文件三层叠加注入（`.env.common` → `.env.<服务>` → `~/.patra/secrets/*.env`）；IDE 靠 `PATRA_INFRA_HOST` 加 `~/.patra/secrets`。
> - 容器用容器名加容器内端口访问基础设施（`postgres:5432`、`redis:6379` 等），IDE 用 mini 的 tailscale 地址加宿主机映射端口（15432、16379 等）。例外是 RocketMQ broker：`BROKER_IP1` 是 tailscale 的 MagicDNS 短名，两种运行方式都经它连接。
> - `patra-infra/docker/.env` 里的 Nacos token 签名密钥和 identity 随公开仓库提交；应用用默认账号连 Nacos。
> - Nacos 服务端是 3.0.2。SCA 2025.1.0.0 依赖 nacos-client 3.1.1，没有声明服务端兼容范围，只支持 `spring.config.import`。Nacos 3.1 线停在 3.1.2（2026-03-26），当前稳定版是 3.2.4（2026-08-27）。
> - 28 个 `@ConfigurationProperties` 类中 5 个是 record；Spring Cloud 官方文档写明构造器绑定（含 record）无法刷新，原地重新绑定期间并发读者可能看到中间状态。
> - `patra-infra/docker/.env.dev` 没有被任何 compose 命令加载，实际不生效。

### A. namespace 只代表环境；两种运行方式的差异放在 Nacos 之外

- **影响 Issue**：PAP-72、PAP-74、PAP-76、PAP-77
- **决策**：本版只有 `dev` 一个 namespace，每个服务在 Nacos 里只存一份配置。IDE 和容器是同一个 dev 环境的两种运行方式，差异收敛为放在 Nacos 之外的本地变量，做法由 PAP-72 实测选定。`dev`、`container` 两个 profile 去掉。
- **否决**：按运行方式建两个 namespace——每份配置存两份，差别只是地址。

### B. git 是非敏感配置的唯一来源；CD 自动推送，控制台只读

- **影响 Issue**：PAP-75、PAP-76、PAP-77
- **决策**：yaml 放在 `patra-infra/nacos/dev/`，幂等脚本经 Nacos v3 admin API 推送。合入 main 后由 CD 自动推送，本机可手动运行同一脚本。控制台只在应急时用；回滚靠 git revert 后重新推送。
- **否决**：以控制台为准——没有评审和 diff，仓库和线上会对不上。SQL 直接写 Nacos 内部表——依赖 Nacos 的表结构。Spring Cloud Config——要多维护一个服务，而 Nacos 已在运行。

### C. 配置分三层，Nacos 覆盖 jar 里的默认值

- **影响 Issue**：PAP-74、PAP-76、PAP-77、PAP-78
- **决策**：
  - jar 里的 `application.yml`：代码默认值和引导配置。
  - `patra-common.yaml`：跨服务共享的配置。
  - `{服务名}.yaml`：单个服务的环境差异和可调参数。
  - `patra-secrets.yaml`：密钥（决策 E）。

  导入设置 `preference=remote`，让 Nacos 的值覆盖 jar 里的默认值；SCA 默认本地优先，jar 里的默认值会盖掉 Nacos。环境变量、启动参数等进程级覆盖的优先级在 PAP-74 实测确定。
- **否决**：本地优先，并要求同一个键不在两处出现——只能靠人记，迟早出错。

### D. 动态刷新统一用 `RefreshableProperties<T>`

- **影响 Issue**：PAP-73、PAP-78，以及以后所有可调参数
- **决策**：可调配置用 record 加 `RefreshableProperties` 持有：配置变更时重新绑定、校验，通过后原子替换；校验失败保留旧值并记录原因；使用方每次经 `get()` 读取，或在变更回调里重建自己的对象。静态配置（数据源、端口、密钥）继续用 record，不刷新。Spring Cloud 自带的原地重新绑定是否关闭由 PAP-73 决定。
- **否决**：改成普通类、靠框架原地重新绑定——有中间状态，失去不可变性。`@RefreshScope`——引入代理，作用域语义不直观，新值不合法时 Bean 重建失败而不是保留旧值。

### E. 密钥放在 Nacos 的独立 dataId，不进 git（取代 v0.8 决策 G）

- **影响 Issue**：PAP-71、PAP-74、PAP-76、PAP-77
- **决策**：密钥只写在 `patra-secrets.yaml`，只经控制台或 API 管理，是「git 是唯一来源」的唯一例外。前提是先加固 Nacos：已公开的 token 签名密钥和 identity 移出仓库并重新生成；改掉默认管理员密码；应用账号对配置只读，推送账号只能写非敏感配置；密钥放在单独的分组，只有管理员能改。唯一留在 Nacos 之外的是 Nacos 自己的连接凭据。
- **为什么取代决策 G**：每改一个密钥都要手动 scp 到两台机器。放进 Nacos 后只改一处；加固之后 Nacos 的保护程度不低于本机文件。
- **已知代价**：
  - 密钥以明文存在 Nacos，安全性依赖 Nacos 鉴权和 tailnet 隔离。
  - Nacos 的存储放在现有业务 PG 的 `patra_nacos` 库里（PAP-71），而 PG 超级用户密码是公开的 dev 默认值，本版不换：在 tailnet 内可以绕过 Nacos 鉴权直接读到密钥。
  - 不做备份：Nacos 数据丢失即密钥丢失，要重新生成后写回。
- **否决**：维持 `~/.patra/secrets`——仍要手动分发。SOPS 加密后进 git——多保管一把私钥，密文永久留在公开仓库历史里。

### F. Nacos 的引导配置由 starter 统一注入

- **影响 Issue**：PAP-74、PAP-76、PAP-77
- **决策**：一个 `EnvironmentPostProcessor` 统一注入 Nacos 连接信息和导入列表，地址和账号从环境变量读取。容器里的导入不标 `optional:`，并挂载本地快照目录。
- **否决**：硬编码在代码里并写进 System properties（SpringBlade）——环境变量覆盖不了。构建时注入账号（pig、JeecgBoot）——换环境要重新打包。

### G. Nacos 服务端升到 3.2.4；客户端只用 `spring.config.import`（2026-10-10 改定）

- **影响 Issue**：PAP-71、PAP-74
- **决策**：服务端升到当前稳定版 3.2.4。客户端沿用 SCA 2025.1.0.0 带的 nacos-client 3.1.1；Nacos 官方承诺 3.x 服务端兼容 2.x、3.x 客户端，兼容性在 PAP-71 上 mini 实测确认。不引入 bootstrap 依赖，它会导致动态刷新失效。
- **为什么不是原定的 3.1.x**：3.1 线已停止维护。3.1.2 按 id 批量删除、导出配置时不检查 namespace，只对 `public` 有写权限的账号也能删掉 `dev` 里的配置（包括 `patra-secrets.yaml`），3.2.3 才修复；3.2.4 还修了授权元数据解析的问题。
- **已知代价**：3.2 删除了 v1/v2 HTTP API，脚本只能用 v3；这个服务端与客户端的版本组合 SCA 没有专门测过。
- **否决**：继续用 3.0.2；停在 3.1.2 并靠收窄权限绕开漏洞——拿不到之后的安全修复。

> **已排除出本字段**（留给各 Issue 的工程设计）：`RefreshableProperties` 的 API、各 dataId 内部的键结构、推送脚本的语言、PAP-72 选 B 还是 C、Nacos 账号的命名。
