## 1. 版本目标 / 价值

医生和科研人员能给有价值的评论（根评论和楼内回复）和投稿经验点「有帮助」，讨论区和期刊页的经验列表都能按「最有帮助」排序；文献、讨论串和投稿经验上显示公开计数（有帮助数、回复数和最后回复时间、收藏人数、讨论数），用户主页显示「获赞」数。

这是社区互动的第三个版本，建在 v0.13 的对象底座、收藏和 v0.14 的讨论、投稿经验上。热度（首页热议、按热度排序）在规划时考虑过，本版不做（第 3 节 A）。

**规划时的现状**（2026-10-29 核对，main `7e68ce5cb`）：

- interaction 有 `subject`（底座）、`collection`、`discussion`、`post`、`notification` 五个子域，全部用 `JdbcClient` 写原生 SQL。除收藏夹自己的 `item_count`（与条目同事务加减）外，没有任何计数列：评论、帖子、文献库条目上都没有有帮助数、回复数、最后回复时间。
- 文献库条目 `library_item` 与收藏夹条目都按 `user_id` 哈希分 16 区，没有以 `subject_id` 开头的索引，「一篇文献被多少人收藏」现在要扫全部分区。
- 讨论列表按 `created_at` 正序或倒序、用游标分页；期刊页经验列表固定按投稿日期倒序，没有排序参数。
- 进程内事件只有讨论的「已发表 / 已编辑 / 已删除」和投稿经验的「已删除」，订阅方只有提醒，都是同事务的同步监听。
- 底座能力只有收藏、讨论、投稿经验三种；发表守卫 `publish_quota` 只有评论、帖子两个种类。
- interaction 不依赖 Redis 与 RocketMQ；Outbox 只有 ingest 有，`patra-tool` 里没有通用事件模块。
- catalog 文献检索在 PG 里排序，只有「最近更新」「年份」两种；catalog 里没有任何互动数据。
- 门户：讨论、经验、提醒的 schema 都没有计数字段，v0.13、v0.14 的设计简报明文排除了计数；检索结果卡片故意不显示被引数（数据全 0）；首页「此刻热议」是写死的关键词云；主页头部给「关注 · 粉丝 · 获赞」预留了一行；提醒每条都必须挂一条评论。

**验证场景**：

1. A 在期刊页写一条投稿经验，B、C 都点「有帮助」。期刊页这条显示「2 人觉得有帮助」，切到「最有帮助」后排第一。
2. A 在文献页发根评论，C 回复；B 给 C 的回复点「有帮助」，回复旁显示 1；B 再给 A 的根评论点「有帮助」，切到「最有帮助」后这一楼排第一。根评论下显示楼内回复数和最后回复时间。
3. 检索结果里这篇文献的卡片显示「N 人收藏 · N 条讨论」。
4. A 的主页显示「获赞 3」。

### 2.1 产品定义

#### 2.1.1 有帮助

| 项 | 规则 |
|---|---|
| 能点的对象 | 所有评论（根评论和楼内回复）与投稿经验。文献、收藏夹不能点 |
| 谁能点 | 登录、邮箱已验证、账号状态正常（与发表相同）；冷静期不能点；未登录点击时引导登录 |
| 自己的内容 | 不能点，包括匿名经验的作者给自己的经验点。自己的内容照常显示数字，只是没有可点的按钮（Discourse 的做法）。「有帮助」表达对别人有用，并进排序和获赞；问答类平台（Stack Overflow、Discourse）都禁止给自己投，社交类平台的「赞」才允许（2026-10-29 用户确认） |
| 取消 | 可以取消，数字同步减 |
| 频率 | 每人每天最多 300 次；取消不退次数 |
| 显示 | 大于 0 才显示数字，0 只显示「有帮助」；不公开谁点了；自己点过的高亮 |
| 已删除 | 「该评论已删除」占位不显示数字、不能点。评论被整条删掉、经验被删除时，它收到的有帮助一并删除 |
| 注销 | 有帮助的数据不做任何清理：注销用户点过的有帮助继续计入数字，他收到的有帮助与获赞统计也保留。不公开点赞人，保留不会暴露身份；注销用户的主页打不开，获赞不会显示。以后做点赞人列表时，与评论作者一样显示「已注销用户」 |
| 匿名经验 | 别人照常能点、数字照常显示；不计入作者的「获赞」，作者在自己匿名经验下以「匿名作者」身份发的评论收到的有帮助也不计入，避免由获赞涨落反推身份 |
| 提醒 | 不发（第 3 节 B） |

#### 2.1.2 排序

| 位置 | 规则 |
|---|---|
| 讨论区 | 根评论在「正序 / 最新」之外加「最有帮助」：按根评论自己的有帮助数降序，相同时新的在前。默认仍为正序。楼内回复始终按时间正序，楼内回复的有帮助数不计入楼主 |
| 期刊页经验列表 | 新增排序切换：「最新投稿」（现有的投稿日期倒序，默认）与「最有帮助」 |
| 排序状态 | 写在 URL 的 `?sort=` 里，刷新与分享保持 |

#### 2.1.3 公开计数

| 计数 | 口径 | 显示位置 |
|---|---|---|
| 有帮助数 | 当前有效的有帮助条数 | 每条评论；每条经验（期刊页列表、经验页、主页经验列表） |
| 楼内回复数 | 这一楼未删除的回复数 | 根评论下，取代不带数字的「展开更多回复」 |
| 最后回复时间 | 这一楼最新一条未删除回复的发表时间 | 根评论下 |
| 讨论数 | 文献下未删除的评论总数（含楼内回复） | 文献页讨论区标题；文献卡片 |
| 收藏人数 | 把文献收进文献库的人数，一人放进多个收藏夹只算一次 | 文献页；文献卡片 |
| 经验回复数 | 经验下未删除的评论总数 | 期刊页与主页的经验行 |
| 获赞 | 本人未删除、非匿名的评论与经验收到的有帮助总数 | 主页头部预留行，关注、粉丝两格仍空 |

- 文献卡片指四处：检索结果、我的文献库、公开收藏夹、首页文献流。
- 所有计数写完立刻更新（决策 A）；为 0 时一律不显示数字。

## 3. 范围边界（不做的事）

> 下面这些都和有帮助、计数高度相关，列在这里是明确「本版不做」。

| # | 不做的事 | 理由 |
|---|---------|------|
| A | **热度**：首页热议、文献流「热议」标签、检索按热度排序 | 用户只有个位数、没有浏览量，信号太稀，热议榜会长期只有寥寥几篇；热度公式等浏览量有了再一起定。检索按热度排序还要把互动数据跨库同步到 catalog |
| B | **有帮助的提醒**：「X 觉得你的评论有帮助」、「A 等 3 人」聚合 | 业界普遍不进红点、按天合并成汇总；合并与按类型关闭属于通知中心。现在的提醒每条都必须挂一条评论，经验被点时无处可挂 |
| C | **踩 /「没帮助」、表情回应、多种回应类型** | 小社区公开踩容易起对立，Discourse、GitHub 都没有踩；学术场景只用「有帮助」一种语义 |
| D | **点赞人列表**（谁觉得有帮助） | 本版只公开数字；匿名经验的点赞人更不能暴露 |
| E | **浏览量与行为数据**：埋点、ClickHouse | 与关注动态一起做，事件格式到时一次定死 |
| F | **给文献、收藏夹点有帮助；收藏夹的被关注数、热门收藏夹** | 文献靠收藏表达认可，避免变成给论文打分；收藏夹的公开计数随关注一起做 |
| G | **主页的关注、粉丝两格** | 属于关注动态，本版只填「获赞」 |
| H | **声望、信任等级、新号权重、按信任调额度** | 本版只有每天 300 次的上限；按信任分级属于合规包的防刷部分 |
| I | **讨论串参与人数；贴吧式帖子列表页（按最后回复排序）** | 本版只做楼内回复数与最后回复时间；帖子列表页等做帖子时设计 |
| J | **公共事件模块（Outbox）、PAP-104、PAP-105、ingest 去留** | 计数和明细都在 interaction 一个库里，同事务即可保证一致（决策 A），用不上消息管线；三者仍归通知中心 |
| K | **审核、举报、实名、网关限流与熔断** | 按《互联网跟帖评论服务管理规定》，点赞同属需要后台实名的互动。**硬门槛不变：合规包完成前，门户只在 tailnet 内开放**（D9） |

## 4. 关键决策

> 依据：2026-10-29 的 2 路代码核对与 2 路调研（见文末）。Issue 编号见 2.2。

### A. 计数与明细同事务写入，不建异步计数管线

- **影响 Issue**：PAP-131 / PAP-132 / PAP-133
- **决策**：有帮助、回复、文献库条目的明细行真的插入或删除时（影响行数为 1），在同一事务里对统计行原子地 `+1` / `-1`。有帮助一人对一个目标只有一条，由唯一约束保证，重复点用 `ON CONFLICT DO NOTHING` 挡掉。「最后回复时间」在删回复时先锁住该楼统计行，再取剩余回复的最新时间。不做每晚对账；提供手动触发的「按明细重算」任务修数据。现有数据由迁移一次回填。
- **为什么**：计数与明细在同一个库，同事务天然一致；Discourse、GitLab、Lobsters、Mastodon 都在写明细的事务里更新计数，只有 Reddit 这种规模才走队列。v0.13 实测的「同事务 +1 吞吐降到 1/13 ~ 1/32」是人为制造热点行高并发测出的，现有规模下同一目标几乎不会被同时写。用 `c = c + 1` 而不是「按明细重数再覆盖」：在 PG 默认的读已提交隔离下，两个事务同时写同一目标时，重数的子查询用的是语句开始时的快照，可能少算一次；`+1` 在等到行锁后基于最新版本计算，不会丢。真出现热点行时，主流补法是在 Redis 里先攒增量再定时写回（GitLab `CounterAttribute`），表结构不变。
- **否决**：异步计数管线加每晚对账（v0.13、v0.14 的原假设：要 Outbox，计数有延迟）；读时 `COUNT`（「最有帮助」排序和文献卡片要反复数）；每次写入按明细重数再覆盖（并发下可能少算）。

### B. 新建 `reaction` 子域管有帮助；各项统计归各自子域

- **影响 Issue**：PAP-131 / PAP-132 / PAP-133
- **决策**：
  - `reaction` 子域负责有帮助明细（目标是「评论或帖子 + ID」）、每个目标的有帮助数、每个用户的获赞、资格检查与不能给自己点。它经讨论、投稿经验的读端口取目标的作者、状态、是否匿名；订阅两者的删除事件，删掉被删目标的有帮助并扣回获赞。频率限制复用底座发表守卫，新增一个种类（每天 300 次、无间隔）。
  - 讨论子域维护楼内回复数、最后回复时间，以及每个对象下的评论总数。文献的讨论数和经验的回复数是同一张表（投稿经验在底座里就是一种对象）。
  - 收藏子域维护每篇文献的收藏人数。
  - 讨论、经验列表要显示有帮助数、按它排序时，由读适配器用 SQL 关联 `reaction` 的统计表。
  - 依赖方向：reaction → 讨论、投稿经验（只依赖读端口与事件契约），没有环。
- **为什么**：评论和经验的有帮助规则相同，放在一处不写两遍，以后加别的回应也只改这个子域；把有帮助数写进评论表，讨论子域就要订阅 reaction 的事件，而 reaction 又要读讨论，会成环（ArchUnit 禁止）；仓库规则允许读适配器用 SQL 读本服务库的任何表。
- **否决**：有帮助分别做在讨论、投稿经验两个子域（两张表两套规则）；有帮助数写进评论表、帖子表（成环，或讨论子域要懂有帮助的规则）。

### C. 读路径：列表直接带计数，文献卡片按屏批量取

- **影响 Issue**：PAP-132 / PAP-133 / PAP-134 / PAP-135
- **决策**：
  - 评论、楼、经验的响应直接带有帮助数、回复数、最后回复时间；有会话时带「我点过没有」，与 v0.14 的「这条是我发的」一样由服务端判断。
  - 文献卡片的收藏人数与讨论数由一个批量接口按一屏一批地取，挂在底座的读端，读适配器读收藏、讨论两张统计表，这是本版唯一一处跨子域读。门户与收藏状态同一时机取；取不到时卡片只是不显示数字，文献照常显示（沿用 v0.13 的降级原则）。
  - 主页获赞由 interaction 提供，门户单独取一次，不改 identity。
- **为什么**：检索结果、首页文献流由 catalog 渲染，catalog 里没有互动数据；由门户服务端拼装，比把计数同步进 catalog 简单，也不跨库。
- **否决**：计数同步到 catalog（要跨服务推送，等于又建 Outbox）；门户分别调收藏、讨论两个统计接口（一屏多一次往返，降级处理两处）。

### D. 前端：有帮助乐观更新，计数不轮询

- **影响 Issue**：PAP-134 / PAP-135
- **决策**：点有帮助时数字立刻加减，失败回滚并提示（参照收藏按钮）；成功后把相关讨论、经验缓存标为过期。别人点的、回复带来的计数变化在重新取数据时更新（翻页、切排序、刷新、切回页面），不轮询。「最有帮助」翻页期间数字可能变化，前端按 ID 去重。
- **为什么**：有帮助是高频轻操作，等服务端返回会显得卡；计数晚几秒对得上不影响使用。
- **否决**：不做乐观更新（每次点击等一个来回）；给计数加轮询（门户已有一处 60 秒未读数轮询，再加不划算）。
