## 1. 版本目标 / 价值

用户在 Patra 有一个可以被别人看见的身份：唯一的用户名、昵称、头像、简介、专业背景和一个公开主页。用户也能自己管好这个账号：验证邮箱、改密码、改邮箱、忘记密码时自助找回、查看并踢掉其他登录设备、注销账号。之后的收藏、关注、讨论、第三方登录都挂在这个身份上，不再改账号模型。

Patra 的用户是医学科研人员和临床医生，两种身份一视同仁：资料同时装得下「医院、科室、职称」和「机构、研究方向」，一个人两边都填也行，除用户名外都不强制。

**规划时的现状**（2026-10-20 核对）：

- identity 只有三张表：`idn_user`（邮箱、状态 ACTIVE / BANNED）、密码凭据、登录记录。用户除邮箱外没有任何资料。
- 门户登录态只有邮箱首字母的圆形标识和一个「退出登录」菜单项，没有任何设置页。
- 系统没有发邮件的能力，所以没有邮箱验证、找回密码、改邮箱。
- 网关会剥掉入站的转发头，门户也不转发浏览器的 IP 和 User-Agent，登录记录里没有真实 IP。
- catalog 已导入 ROR 全量机构数据（`cat_organization`，含中文名与别名）和 MeSH 全量数据，但没有对门户和其他服务开放的建议 / 校验接口。
- v0.8 边界里留下的债：邮箱验证、找回密码、改密码、改邮箱、注销（边界 B）、个人资料（边界 G）。账号设计已预留「每种凭据一张表」，第三方登录是以后新增一张外部身份表，不动用户表。

**验证场景**：

1. 注册时填邮箱、用户名、密码，注册后直接是登录态，收到验证邮件并点通。进用户中心设昵称、头像、简介、医院与科室、关注领域；用匿名窗口打开 `/u/<用户名>` 能看到主页，看不到邮箱。
2. 改密码后，另一台设备上的登录被踢掉并收到「密码已修改」邮件；点「忘记密码」收到邮件，按链接重设后用新密码登录。
3. 改邮箱：新邮箱确认后立即生效，旧邮箱收到通知；点旧邮箱里的「不是我」能撤回并锁住账号。
4. 登录设备页看到两台设备的浏览器、系统、IP 属地和最后活跃时间，踢掉另一台后它的下一次请求是 401。
5. 申请注销后全部设备下线、主页消失；冷静期内登录看到「取消注销」确认页；到期后邮箱可以重新注册一个与旧账号无关的账号。

### 2.1 用户中心的定义

本节是产品定义，按最终形态一次定好。各条规则的来源见文末「调研依据」；六个拍板点（公开运营假设、注册即登录、用户名可改、密码长度、冷静期、MeSH）已于 2026-10-20 定下。

#### 2.1.1 账号与用户名

| 项 | 规则 |
|---|---|
| 登录标识 | 只有邮箱。用户名不用于登录：它是公开的，若能用它登录，任何看到主页的人都能连输 5 次密码把对方锁 15 分钟 |
| 登录态响应 | 登录、注册的成功响应是 `{ sessionToken, user }`，`user` 与 `/auth/me` 同构 |
| 用户名（username） | 注册必填、全站唯一、公开主页地址 `/u/<用户名>`。3 ~ 30 个字符，只允许小写字母、数字、`_`、`-`；首尾必须是字母或数字，不允许连续的 `_` 或 `-`，不允许纯数字；输入不分大小写，统一存小写；不收中文（中文留给昵称，避免 URL 百分号编码和形近字冒充） |
| 保留字 | 路由段（`settings`、`login`、`papers`、`journals`、`api`、`u`…）、角色词（`admin`、`staff`、`official`、`system`、`support`）、站名与数据源名（`patra`、`pubmed`、`ncbi`、`crossref`、`epmc`、`nlm`）。匹配时做同形归一（`0→o`、`1→i`、`3→e`、`5→s`），清单在代码里维护 |
| 改用户名 | 可改，两次修改间隔 ≥ 30 天。旧用户名保留 90 天：期间只有原主能改回，`/u/旧名` 跳到新名（identity 接口回 301 且不缓存，门户做临时跳转，因为 90 天内可能改回）；90 天后释放。@ 提及一律存用户 ID 而不是文本，改名不影响历史内容 |
| 昵称（display name） | 注册时默认等于用户名，之后可改（库里不存默认值，空表示跟随用户名，改名后没设过昵称的人昵称跟着变）。2 ~ 30 个字素（汉字计 1）且 ≤ 120 字节；允许任何文字、数字、空格、`·` 和 emoji；存 NFC，去首尾空白、折叠连续空白；拒绝控制字符、零宽字符、双向控制符、换行；拒绝网址、邮箱、手机号、微信号形态；拒绝保留字和官方 / 职业身份词（「官方」「医生」「主任」「教授」「专家」等，清单在代码里维护）。允许重复，所有展示昵称的地方并排显示 `@用户名`。不限修改频率，修改记入审计（本版只记 INFO 日志；账号审计记录以后单独开版本做成一张通用的账号事件表，2026-10-22 定） |
| 状态 | `ACTIVE` / `BANNED` / `PENDING_DELETION` / `DELETED`，见 2.1.9 |
| 邮箱 | 唯一；只在 `DELETED` 时为空。带 `email_verified_at`，见 2.1.6 |

#### 2.1.2 资料

资料是账号旁边的一个独立聚合，与 `idn_user` 一对一（决策 A）。

| 字段 | 规则 | 结构化 |
|---|---|---|
| 头像 | 见 2.1.3 | 对象键 |
| 简介 | 纯文本 ≤ 200 字素、最多 3 行；拒绝的字符同昵称 | — |
| 链接 | ≤ 5 条，每条标题 ≤ 30 字、URL ≤ 300 字符，只收 `http` / `https`；页面上渲染为 `rel="nofollow noopener noreferrer ugc"`；邮箱未验证时不展示 | — |
| 身份大类 | 枚举：医师 `PHYSICIAN` / 护士 `NURSE` / 药师 `PHARMACIST` / 医技 `TECHNICIAN` / 科研人员 `RESEARCHER` / 学生 `STUDENT` / 行业从业者 `INDUSTRY` / 其他 `OTHER`；可空 | 枚举 |
| 职称 / 职位 | 自由文本 ≤ 50；国内职称在卫生、高校、科研几个系列之间不统一，不做枚举 | — |
| 机构 | 从 catalog 的 ROR 数据里选（中文名、别名都能搜），存 ROR ID + 名称快照；搜不到的允许自由文本（无 ROR ID）。手填名称 ≤ 200；ROR 名称快照以 catalog 为准，不受这个上限约束（PAP-95） | ROR ID |
| 科室 / 院系 | 自由文本 ≤ 100；ROR 不收录院系 | — |
| 关注领域 | MeSH 主题词，≤ 10 个，从 catalog 的 MeSH 数据里选；存 MeSH UI + 英文名快照，按用户排序。只能显示英文：中文版 CMeSH 的版权归中国医学科学院医学信息研究所 | MeSH UI |

不收、也不预留的字段：性别、生日、住址、婚姻、政治面貌、民族、健康状况（PIPL 最小必要，文献平台没有业务必要）；手输的 ORCID / Scopus ID（标识符只能由 OAuth 认证后写入，见边界 C）；教育与履历条目、资助、同行评审、学会任职（Patra 没有断言来源，自填无法验证，见边界 F）。

身份大类、职称、机构、科室这四个字段是「自述」，公开主页上按原样展示，不带任何「已认证」外观；认证标识只在以后做了职业认证之后才出现（边界 B）。

#### 2.1.3 头像

- 收 JPEG / PNG / WebP，原图 ≤ 5 MB，短边 ≥ 128 px；不收 GIF 和动图。
- 浏览器先裁成正方形（设计简报定交互），服务端重新编码为 WebP、剥掉 EXIF 等元数据，生成 512 和 128 两档。
- 存 MinIO，对象键带内容哈希（`avatar/{userId}/{哈希}-512.webp`），换头像就换键，所以响应可以按不可变长期缓存。
- 读取经门户同源接口转发：浏览器 → 门户 Route Handler → 网关 → identity 从 MinIO 流式读出，不开公开桶、不用预签名链接（沿用 v0.11 决策 F）。
- 默认头像：昵称里第一个非标点字素（跳过开头的标点和空白，如「·小林」取「小」；汉字取首字，拉丁字母取大写首字母；昵称里没有可取的字时取用户名首字母）+ 按用户 ID 哈希从 12 色板取色，改昵称不变色。色号由服务端算好，作为 `avatarPalette`（0–11）放进 `/auth/me` 与 `GET /users/{username}`：公开主页响应不含用户 ID，门户自己算不出来（2026-10-22 定，PAP-92）。与现在导航栏的首字母标识一脉相承。不接 Gravatar（要把邮箱哈希发给第三方）。
- 删除头像回到默认。

#### 2.1.4 公开主页 `/u/<用户名>`

- **头部**：头像、昵称、`@用户名`、简介、加入时间（到月）、链接（邮箱已验证才展示）。
- **专业背景**：身份大类、职称、机构、科室；整块受「专业背景可见性」开关控制（2.1.5）。
- **关注领域**：MeSH 标签；点标签进文献检索。
- **本版没有的**：关注 / 粉丝 / 获赞计数、动态、讨论、公开收藏夹。这些由以后的 interaction 服务提供，主页布局在设计简报里给它们留位置。
- **访客看不到的**：邮箱、登录设备、任何设置。
- **主页对别人不存在（404）的情况**：主页可见性不是「公开」（匿名访客）或是「仅自己」（登录用户）；邮箱未验证；账号在冷静期或已注销；账号被封禁。本人看自己的主页不受这些 404 约束（只要还能登录），响应里 `audience` 为 `SELF`。
- `/auth/me` 加上用户名、昵称、头像地址、默认头像色号（`avatarPalette`）、邮箱是否已验证、账号状态、注销到期时间（`deletionDueAt`）、下次可改名时间（`nextUsernameChangeAt`），导航栏显示头像，昵称在头像菜单的头部（顶栏放不下 30 字的昵称，PAP-92 定）。

#### 2.1.5 隐私设置

| 开关 | 取值 | 默认 |
|---|---|---|
| 主页可见性 | 公开 / 仅登录用户 / 仅自己 | 公开 |
| 专业背景可见性 | 公开 / 仅自己 | 公开 |
| 允许搜索引擎收录主页 | 开 / 关（`noindex`） | 关 |

邮箱永不展示，没有开关。关注 / 粉丝名单、收藏夹的可见性归 interaction，到时在它那里加。

#### 2.1.6 邮箱验证

- 注册即登录（决策 C）。注册后发验证邮件；未验证期间顶部常驻提示。
- **未验证不能做的事**：主页对别人不可见；链接不展示；不能绑定第三方登录（以后）；不能发言、评论、点赞、关注（以后）。可以浏览、检索、改资料、改邮箱、重发邮件、以后的私人收藏。
- 验证链接 24 小时有效、一次性；重发使旧链接作废。重发冷却 60 秒，每账号每小时 ≤ 5 次、每天 ≤ 10 次；每 IP 每小时 ≤ 30 次。
- 注册发出的首封计入重发的冷却与配额：注册后 60 秒内点重发是 429。
- 验证时保留当前会话、撤销该用户其余会话（登录记录标 `REVOKED`）；匿名设备点链接验证则撤销全部会话。
- 邮件链接不由 GET 消费：令牌放在 URL 片段里，落地页点按钮后 POST 消费，避免邮件安全网关预取把一次性令牌用掉。
- 未验证的账号不自动清理：它是有私人数据的真实账号。别人占了你的邮箱先注册，你用「忘记密码」就能拿回来（见 2.1.7）。

#### 2.1.7 账号安全

| 操作 | 规则 |
|---|---|
| 再认证（sudo 模式） | 改邮箱、踢设备、注销、以后的绑定 / 解绑第三方登录，都要求 10 分钟内输过一次密码。会话里记 `auth_at`（登录、注册、再认证、改密码都写；本功能上线前建立的会话视作从未再认证）；`POST /auth/reauth` 校验密码（共用登录失败限制，密码错是 401 + `PASSWORD_MISMATCH`，门户不当登出）后换新令牌保留会话 ID 并刷新 `auth_at`，旧令牌立即失效（上次密码验证距今不足 10 秒时不换，响应 `sessionToken` 为 `null`、门户保持现有 Cookie：两个标签页并发再认证时先换出的令牌保持有效）；identity 按断言里的会话 ID 读 `auth_at`，超时回 403 `REAUTH_REQUIRED`，门户弹密码框后重试；网关不用改（PAP-98 定） |
| 改密码 | 每次都要输当前密码（再认证窗口内也要；共用登录失败限制）；新密码不能与当前密码相同，不存历史密码；本机换新令牌保留登录，其他会话全部撤销；两次并发改密码只有先到的生效（锁下再比一次当前密码的哈希）；按用户批量作废令牌（含待用的重设令牌与待确认的改邮箱）；发「密码已修改」邮件 |
| 密码规则 | 保持 8 ~ 64 个码点 + 常见密码名单 + 登录失败限制，不改。NIST SP 800-63B-4（2025-07 定稿）要求单因子密码至少 15 位，这是一处有意偏离（决策 K） |
| 找回密码 | 申请一律回 202 并异步发信，未注册的邮箱不发（防枚举）；令牌 1 小时有效；提交新密码后撤销全部会话、作废全部令牌、取消待生效的改邮箱，不自动登录，清零该邮箱的登录失败计数，发「密码已重设」邮件；发给未验证的邮箱也可以，重设成功同时视为邮箱已验证（证明了对邮箱的控制）；申请和提交都不计入登录失败；被封禁的账号不发信（PAP-98 定） |
| 改邮箱 | 再认证 → 向新邮箱发确认链接（1 小时）→ 点通后立即生效 → 旧邮箱收到通知，内含 7 天有效的「不是我」链接。点「不是我」：邮箱改回旧地址、撤销全部会话、作废密码（删凭据）并向旧邮箱发重设链接；注销冷静期内也能撤，撤销不碰注销状态。同一时间只能有一个待确认的改邮箱（就是一条未过期的确认令牌，`GET /me/email/change` 可查），可取消；新邮箱已被别人使用回 409（和注册一致：注册接口本来就会告诉你邮箱是否已注册，PAP-98 定）；确认时地址被抢注回 409；撤销时旧地址被抢注回 409，当前邮箱已经是旧地址则照常撤销 |
| 一次性令牌 | 邮箱验证、找回密码、改邮箱确认、改邮箱撤销四种令牌共用一张表：32 字节 CSPRNG、base64url（原文 43 个字符），库里只存 SHA-256（十六进制）；带用途、用户、发往的邮箱、过期时间、消费时间、撤销时间；同一用户同一用途只留一个有效令牌，签发前在同一事务里作废旧的；消费是一条带条件的 `UPDATE … RETURNING`；改密码、重设、改邮箱生效、注销、封禁时按用户批量作废（改邮箱撤销令牌例外：可并存、不被批量作废，旧邮箱的撤销链接在 7 天内始终有效）；过期 30 天后删行，由 XXL-Job 任务 `emailTokenCleanupJob` 每天清理 |
| 限流 | 找回密码：同邮箱 60 秒冷却、每天 ≤ 5 次，同 IP 每小时 ≤ 20 次，提交令牌每 IP 每分钟 ≤ 10 次。改邮箱：每账号每天 ≤ 3 次 |

#### 2.1.8 登录设备

- **列表**只列活跃会话：设备名（浏览器主版本 · 系统族，登录时用 Yauaa 解析 User-Agent）、端、IP 与属地（登录时用 ip2region 离线库解析到国家 / 省 / 市，IP 不出服务器）、登录时间、最后活跃（精度 60 秒）；「本机」置顶。
- **踢设备**：先过再认证；可踢单个或「其他全部」；本机只能「退出登录」。登录记录的结束原因记 `REVOKED`。
- **新设备邮件**：设备标识在该账号 180 天内没出现过才发；注册后第一次登录不发；同一设备 24 小时内最多 1 封。门户给浏览器种一个长期的随机设备标识 Cookie，登录时带上。
- **链路前提**：门户是唯一受信代理，把客户端 IP 和 User-Agent 转发给网关，网关只信任配置里的代理地址，再转给 identity（决策 I）。
- **留存**：登录记录在结束或过期满 190 天后清理（《网络安全法》日志留存 ≥ 6 个月）。
- 设备列表只给本人看，按账号安全目的处理；公开主页展示 IP 属地是社区版的事（边界 A）。

#### 2.1.9 注销账号

- **发起**：再认证 + 输入自己的用户名确认；不要求邮件确认（丢了邮箱的人也要能注销）。
- **冷静期 15 天**：状态转 `PENDING_DELETION`，撤销全部会话、作废令牌、主页对外消失。期内登录成功即进入「取消注销」确认页，点了才恢复，不静默恢复。发起、到期前 3 天、完成各发一封邮件。
- **到期执行**（定时任务，每小时跑一次；到期后到真正执行前仍可取消）：状态转 `DELETED`。删除密码凭据、关注领域、头像文件、令牌、以后的外部身份，资料行置空不删；邮箱置空（同一邮箱可以立即注册新账号，与旧账号无关联）；`idn_user` 行保留 ID 和状态供外键；用户名永久占用、不释放。以后社区里的内容保留，作者显示「已注销用户」。
- **被封禁的账号**不能自助注销（登录就是 403），只能由后台操作（以后）。
- 登录记录按 2.1.8 的留存规则清理，不随注销立即删。

#### 2.1.10 安全通知邮件

- **要发**：新设备登录；密码已修改；密码已重设；改邮箱（新邮箱确认、旧邮箱通知 + 撤销链接、生效后新旧各一封）；注销已提交（写明到期日和怎么取消）、即将删除提醒（到期前 3 天）、已取消、已完成；以后的绑定 / 解绑第三方登录。
- **不发**：登录失败、触发锁定、常用设备登录、会话过期、主动登出、自己踢设备。
- **内容**：时间、设备、IP 与属地，「不是我」该怎么办；不放登录链接，从不索要密码；链接域名取配置，不取请求的 Host 头。
- **发信**：Spring Mail 走 SMTP，Thymeleaf 模板出文本 + HTML 两部分；开发环境接本地邮件收集器容器，mini 接真实服务商，凭据在 `~/.patra/secrets/`（决策 D）。
- **片段**：各安全通知邮件共用 `SecurityNotice` 片段（时间、设备、IP 与属地、「不是我」该怎么办）；PAP-99 之前设备与属地显示「未知」。「建议到安全设置……」一句由各模板按场景自己写（PAP-98 定：改回邮箱后密码已作废的人登不进去）。
- **清单**（PAP-98 之后共八封）：验证邮箱、重设密码链接、密码已修改、密码已重设、确认新邮箱、旧邮箱通知（含撤销链接）、新邮箱已绑定、已改回并重设。

## 4. 关键决策

> 草案。依据：2026-10-20 的五路调研（见文末）与仓库现状核对。

### A. 资料留在 identity，作为账号旁边的独立聚合

- **影响 Issue**：PAP-93 / PAP-95 / PAP-97 / PAP-100
- **决策**：资料（`idn_user_profile`）与账号（`idn_user`）一对一，同一个服务，不另起资料服务。身份系统的共识边界是「标识、验证状态、谁都要用的显示身份」，业务数据各归各家：地址与发票归以后的 commerce，收藏可见性归 interaction，通知偏好归通知。
- **为什么**：资料和账号同生同灭（注销一起匿名化）；用户名、状态在账号表，昵称、头像在资料表，一次查询就能给出用户摘要；单人维护少一个服务；资料改得勤，不该和封禁共用一把乐观锁，所以是独立聚合而不是账号表加列。
- **否决**：另起 `patra-profile` 服务——为十来个字段多一套部署，跨服务拼用户摘要。

### B. 邮箱是唯一登录标识；永不按邮箱自动合并账号

- **影响 Issue**：PAP-93 / PAP-98，以及以后的第三方登录
- **决策**：用户名只作公开标识，不能用它登录。以后做 OAuth 时，外部身份按 `(provider, subject)` 定位；邮箱撞上已有账号时先用原方式登录再关联；提供方的「邮箱已验证」只作参考，邮箱一律由 Patra 自己验证；OAuth 首次登录要补填用户名和邮箱。
- **为什么**：预劫持攻击的根因就是按邮箱自动合并（Better Auth 2026-05 的漏洞、USENIX Security 2022 的论文）。本版 `email_verified_at` 就用上，外部身份表的结构在工程 spec 里预留。

### C. 注册即登录，未验证邮箱的账号受限

- **影响 Issue**：PAP-93 / PAP-95 / PAP-96 / PAP-101
- **决策**（2026-10-20 定）：保持 v0.8「注册即登录」，未验证账号的能力边界见 2.1.6。找回密码可以发给未验证的邮箱，重设成功即视为已验证。
- **否决**：先验证后激活（注册只回「邮件已发送」，验证后再登录）——更干净地堵住预劫持，但用户注册后要多登录一次；Patra 注册的第一动机是收藏文献，不该在门口拦人。预劫持的两条路径已由决策 B 和「验证 / 重设时撤销此前全部会话」堵住。

### D. 邮件：Spring Mail + SMTP，模板用 Thymeleaf，端口化

- **影响 Issue**：PAP-96 / PAP-98 / PAP-99 / PAP-100
- **决策**：identity 定义邮件发送端口，infra 用 Spring Boot 的 Mail starter 走 SMTP，服务商在部署时定（mini 实测出站后在 PAP-96 里定）；模板用 Thymeleaf 同时出纯文本和 HTML；开发环境 compose 里加一个本地邮件收集器容器；SMTP 凭据放 `~/.patra/secrets/`，仓库只留 `.example`。
- **落地**（PAP-96，2026-10-21）：mini 实测各家 SMTP 465 / 587 均通，服务商定为 Resend（`smtp.resend.com`，凭据在 `~/.patra/secrets/mail.env`）；开发收集器是 core 栈的 Mailpit（SMTP 1025、UI 8025）；集成测试用 GreenMail。代码里没有 Resend 专属的东西，换服务商只改 `mail.env`。
- **否决**：服务商 HTTP API 的 SDK——绑定一家；自建通知服务——现在只有 identity 一个发信方。

### E. 敏感操作用会话里的再认证时间戳

- **影响 Issue**：PAP-98 / PAP-99 / PAP-100 / PAP-102
- **决策**：会话 HASH 加 `auth_at`，`/auth/reauth` 校验密码后换令牌并刷新；窗口 10 分钟；identity 按断言里的会话 ID 判断，超时回 403 `REAUTH_REQUIRED`。改密码不走窗口，每次都输当前密码。
- **为什么**：这是 GitHub sudo 模式的做法，网关不用改；没有密码的 OAuth 账号以后跳回提供方再认证，同样写 `auth_at`。

### F. 机构用 ROR、关注领域用 MeSH，都从 catalog 取

- **影响 Issue**：PAP-95 / PAP-94 / PAP-101
- **决策**：资料里存 ROR ID 和 MeSH UI 这两个权威自然键加名称快照，不存 catalog 的内部 ID（重导时会变）。门户的搜索选择调 catalog 的建议接口；identity 保存时经 catalog 内部接口校验 ID 并取名称，不信前端传来的名称。机构允许无 ROR 的自由文本兜底：ROR 收录了 7,823 家中国机构（医疗类 1,079 家），但中文名覆盖不全。
- **否决**：调 ROR 公网 API——官方计划限流且暂停发 client ID；自由标签做关注领域——不能用于推荐，catalog 的 MeSH 数据现成。

### G. 头像存对象键，服务端处理，经门户同源转发

- **影响 Issue**：PAP-97 / PAP-101
- **决策**：见 2.1.3。不存完整 URL（基地址来自配置），不开公开桶，不接 Gravatar。
- **为什么**：和 v0.11 的 PDF / 图片转发一条路；对象键带哈希才能按不可变缓存。

### H. 四态状态机，注销冷静期 15 天，匿名化保留行

- **影响 Issue**：PAP-93 / PAP-100，以及以后所有引用 `user_id` 的服务
- **决策**（冷静期天数 2026-10-20 定）：`ACTIVE ⇄ BANNED`（后台）；`ACTIVE → PENDING_DELETION → DELETED`（本人申请，冷静期 15 天，到期由任务执行）；`BANNED → DELETED` 只能后台。`PENDING_DELETION` 必须是独立状态，因为它改变登录行为。`DELETED` 时 `idn_user` 行保留，用户名永不释放，邮箱立即释放。`user_id` 永不复用。会话不带状态，状态只在登录、注册响应和 `/auth/me` 里。
- **为什么**：微信 15 天、X 30 天都是「期间登录即撤销」；《认定方法》要求人工处理注销不超过 15 个工作日。用户名永不释放最省（不需要释放表），也没有冒名风险，Mastodon、Reddit 都这样。订单以后要留 3 年（电商法 §31），所以行只能匿名化不能物理删。

### I. 客户端 IP 与 User-Agent 的受信转发链路

- **影响 Issue**：PAP-99 / PAP-101，以及以后所有要记真实 IP 的地方
- **决策**：门户是唯一受信代理，调网关时带上客户端 IP 和 User-Agent；网关只信任配置里的代理地址发来的转发头（其他来源一律剥掉，保持现状），再转给下游；identity 在登录时写入。
- **为什么**：登录记录、设备列表、新设备邮件、以后的 IP 属地展示都要真实 IP；现在网关剥掉一切转发头是对的，只是要给门户开一个口子。服务之间的机器身份仍是 v0.8 边界 F 的事。

### J. identity 库推倒重建，Flyway V1 重写为最终形态

- **影响 Issue**：PAP-93 ~ PAP-100
- **决策**：把 V1、V2 合并重写成一份最终形态的 V1，不写 `ALTER` 迁移；mini 和本机的 `patra_identity` 库直接重建。
- **为什么**：绿地项目禁止数据迁移；现有用户都是开发数据，可以丢弃。

### K. 密码规则保持 8 ~ 64 位，记录与 NIST 的偏离

- **影响 Issue**：PAP-98（工程 spec 记录偏离）
- **决策**（2026-10-20 定）：密码规则不改。NIST SP 800-63B-4 要求单因子密码至少 15 位，Patra 有意不采：注册的门口不拦人；常见密码名单、Argon2id、登录失败限制、敏感操作再认证已经兜住；OWASP ASVS 5.0 L1 的 8 位要求满足。偏离与理由按 ASVS 7.1.1 的要求写进工程 spec（`docs/patra/specs/2026-10-22-identity-account-security-design.md` 第 14 节）。

### L. 用户名可改：30 天冷却，旧名保留 90 天并跳转

- **影响 Issue**：PAP-93 / PAP-101 / PAP-102
- **决策**（2026-10-20 定）：规则见 2.1.1。@ 提及存用户 ID，所以改名不影响历史内容；旧名保留并跳转是为了分享出去的主页链接不失效、不被抢注。
- **否决**：注册后锁定——零改名复杂度，但选错了就一辈子；GitHub 式零冷却立即释放——旧链接失效或被抢注。

> **不进本字段**（留给各 Issue 的工程设计）：表的完整字段与索引、Redis 会话 HASH 的新字段、令牌表的约束写法、保留字清单、敏感词清单、邮件模板文案、Yauaa 与 ip2region 的版本与数据更新方式、定时任务的调度方式。

## 调研依据

2026-10-20 五路并行调研，报告在当天会话里，这里只记结论用到的来源：

1. **国际学术平台的资料**（ORCID、ResearchGate、Google Scholar、Semantic Scholar 等）：资料页都很薄，分量在验证和文献关联；只有机构被普遍结构化（ROR）；邮箱从不公开。来源：[ORCID 记录结构](https://info.orcid.org/documentation/integration-guide/orcid-record/)、[ORCID 机构标识符](https://info.orcid.org/documentation/integration-guide/working-with-organization-identifiers)、[ResearchGate 验证](https://help.researchgate.net/profile/verification-on-researchgate)、[ROR 数据结构](https://ror.readme.io/docs/ror-data-structure)。
2. **中国医学社区与法规**（丁香园、好大夫、知乎等；账号信息管理规定、跟帖评论规定、网络安全法 2025 修正、PIPL）：发言由手机号实名决定，职业认证只决定标识；自称职业身份的账号信息平台要核验；注销要匿名化且日志留存 ≥ 6 个月。来源：[互联网用户账号信息管理规定](https://www.cac.gov.cn/2022-06/26/c_1657868775042841.htm)、[互联网跟帖评论服务管理规定](https://www.cac.gov.cn/2022-11/16/c_1670253725725039.htm)、[个人信息保护法](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)、[关于规范“自媒体”医疗科普行为的通知](https://www.cac.gov.cn/2025-08/01/c_1755764425442686.htm)。
3. **通用社区产品的规则**（GitHub、Discourse、Mastodon、Bluesky 源码级；X、Reddit、微博、知乎）：用户名一律 ASCII、昵称放开；头像服务端生成多档；注销冷静期 15 ~ 30 天、内容匿名化保留。来源：[Discourse username_validator](https://github.com/discourse/discourse/blob/main/app/models/username_validator.rb)、[Discourse user_anonymizer](https://github.com/discourse/discourse/blob/main/app/services/user_anonymizer.rb)、[Mastodon account 模型](https://github.com/mastodon/mastodon/blob/main/app/models/account.rb)、[Bluesky handle 规范](https://atproto.com/specs/handle)、[GitHub 改用户名](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-user-account-settings/changing-your-github-username)。
4. **账号安全标准**（OWASP ASVS 5.0、OWASP 速查表、NIST SP 800-63B-4、预劫持论文）：令牌、找回密码、改密码踢会话、再认证、注销留存的每条参数。来源：[ASVS 5.0](https://github.com/OWASP/ASVS/tree/v5.0.0/5.0/en)、[NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)、[Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)、[Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[Pre-hijacked accounts](https://arxiv.org/abs/2205.10174)、[GitHub sudo 模式](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/sudo-mode)。
5. **身份建模与架构**（Kratos、Keycloak、Auth0、Supabase 的身份 / 资料边界；账号关联；ROR / MeSH；用户摘要；电商的顾客与账号）：资料留在 identity、永不按邮箱合并、自然键快照、顾客不等于账号。来源：[Kratos 最佳实践](https://www.ory.com/docs/kratos/manage-identities/best-practices)、[Supabase 身份关联](https://supabase.com/docs/guides/auth/auth-identity-linking)、[Auth0 账号关联](https://auth0.com/docs/manage-users/user-accounts/user-account-linking)、[ORCID 登录集成](https://info.orcid.org/documentation/integration-guide/sign-in-using-orcid-credentials/)、[Medusa 身份与顾客](https://docs.medusajs.com/resources/commerce-modules/auth/auth-identity-and-actor-types)。
