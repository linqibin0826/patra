## 1. 版本目标 / 价值

读者在 Patra 上能看到每篇文献有多少人看过、多少人读了全文；首页和检索结果里有「近期热读」，文献页下方有「看过这篇的人还看了」。登录用户能翻看自己的阅读历史，也能一键关闭记录、清空历史。

浏览量从 v0.13 起就被一版版推迟（「量大，不进 PG」），v0.15 的热度也因为「没有浏览量，信号太稀」没做。这一版把行为数据的整条链路建起来：埋点方案、采集、消息队列、列式存储、数据分层，再到用户看得到的计数、热读和推荐，以及一块只给作者看的运营分析面板。

这一版也是作者学习行为数据的第一版，目的是为以后在公司里做这类系统做准备，所以每一环都按业界通行做法来，不只求最小可用。真实访客几乎为零，规模靠自己写的流量模拟器造出来：按真实的访问规律灌进亿级事件，让小批量写入、消费滞后、去重、磁盘容量这些问题真实出现。

**规划时的现状**（2026-11-01 核对，main `1229adf73`）：

- **埋点**：门户里没有任何埋点、`sendBeacon` 或曝光观察器；仓库里没有 ClickHouse、Kafka 的任何代码或配置。
- **文献出现的地方**：首页文献流用 `PaperCard`；检索结果、公开收藏夹、我的文献库共用 `PaperListItem`（服务端组件，在我的文献库里进客户端树）。期刊页没有文献列表，只链到 `/papers?venue=`。文献详情页是服务端组件，全文嵌在详情页里（`FullTextSection`），没有单独的阅读路由；PDF 下载、引用、导出都走门户的 Route Handler。
- **门户到后端**：所有请求经 `lib/gateway.ts`；网关校验会话后为每个请求现签身份断言（`sub` 为用户 ID）。门户调 catalog 的 `/portal/**` 不带会话。
- **访客标识**：设备 cookie `__Host-patra_device`（400 天、httpOnly）只在登录或注册时写入，从没登录过的访客没有任何标识。identity 的登录记录里存了设备 ID 与用户 ID 的对应关系，并用 Yauaa 解析 UA、ip2region 查地区。
- **真实 IP**：公网访客的 IP 全部记成 `192.168.97.1`（mini 上 713 条登录记录无一例外）：cloudflared 在宿主机上经 OrbStack 转发，门户删掉入站的转发头，全仓没有代码读 `CF-Connecting-IP`。本版不修（第 3 节 L）。
- **现有计数**：收藏人数、讨论数在 interaction 里同事务 ±1，门户经 `POST /subjects/stats` 批量取；首页文献流有 `recent`、`cited` 两个标签（`GET /patra-catalog/portal/publications`）。
- **设置页**：资料、账号、安全、隐私、通知五个分区；隐私页有三个即时保存的开关（数据在 identity）。
- **隐私政策、服务条款**：都不存在，页脚没有链接。
- **mini 资源**：物理内存 16 GB，OrbStack 上限 12 GB、已用约 7.3 GB；磁盘剩余 41 GB（runner 看门狗红线 20 GB）。各服务的内存上限：catalog 2g、identity 1536m、其余后端服务 1g、RabbitMQ 768m。
- **测试基座**：`patra-tool-test` 支持 PostgreSQL、Redis、MinIO、RabbitMQ 四种容器，Testcontainers 1.21.4。

**验证场景**：

1. B 打开一篇文献、读了全文，1 分钟内文献页的浏览数和全文数各加一。同一个人反复刷新只算一次，爬虫不算。
2. 首页「热读」按最近 7 天的阅读排序，跟「最新」列表明显不一样；检索结果里，在热读榜上的文献带「近期热读」标记。
3. 文献页的「看过这篇的人还看了」列出的是和这篇常被一起读的文献，不是随机推荐。
4. C 在设置里关闭「阅读记录」之后再打开文献，阅读历史里不出现这条；清空历史后，阅读历史页为空。这两步都不影响浏览量。
5. **挑战部分**：流量模拟器按真实的访问规律（少数热门文献占大部分访问、白天多夜里少）往管线里灌亿级事件。灌的同时，门户的计数和热读照常更新，mini 的磁盘和内存守在定好的上限里。

### 2.1 产品定义

| 项 | 规则 | 依据 |
|---|---|---|
| 浏览量 | 显示「N 人看过」，**按人长期去重**，不是请求次数：同一个人（登录用户按账号，访客按设备）看同一篇多少次都只算 1（11/01 PAP-164 时改定；原写「一次会话里只算一次」） | 面板另按 COUNTER 5.1 的 Unique Item Investigations（按会话）统计 |
| 全文阅读 | 全文区在屏幕上可见、累计停留 ≥ 10 秒（标签页在前台），或下载了 PDF，算一次；同样按独立读者计 | COUNTER 的 Unique Item Requests；Medium 的 read 要读满 30 秒 |
| 会话 | 30 分钟没有活动就开始新会话 | 业界通用切法 |
| 爬虫 | 按 COUNTER-Robots 的 UA 列表，加「同一标识请求频率异常」两条规则标记，不进任何对外数字，面板里能看到 | COUNTER 5.1 要求排除机器人 |
| 近期热读 | 首页文献流在「最新 / 高被引」之外加第三个标签「热读」；检索结果里，在热读榜前 100 名的文献带「近期热读」标记。不按热度排序 | v0.15 把检索按热度排序推迟，本版仍不做（第 3 节 D） |
| 热读算法 | 取近 14 天，每人每天对每篇只算一次；读全文的权重是只看摘要的 3 倍；按 3 天半衰期衰减（每过 3 天分量减半）。近 7 天独立读者 ≥ 3 才上榜；上榜的不够时用「最新收录」补位，并明确标出，不冒充热读。每小时重算一次 | HN、Reddit 的时间衰减骨架；学术站没有公开公式 |
| 看过这篇的人还看了 | 把同一个人同一天读过的文献看成一组，统计两篇被多少人一起读过，用余弦相似度压低热门文献天然占优的影响。至少 3 个不同的人一起读过才算数；每组最多取 20 篇；每天算一次，每篇留前 20 名。不足 6 条时依次用同 MeSH 主要主题词、同期刊的文献补位，补位部分标题改为「同主题文献」 | Amazon item-to-item 共现；只以当前文献为键，不读个人画像 |
| 阅读历史 | 只记录登录用户的文献详情浏览与全文阅读。**默认开启**，隐私政策里写明。关闭后不再记录，已有的保留；支持单条删除、一键清空；12 个月后自动清理；注销账号时清空 | YouTube 暂停记录只停后续、提供自动删除 |
| 两层数据 | 个人阅读历史和匿名统计是两套数据。关闭记录、清空历史只影响前者，浏览量照常累计 | 业界通行拆法 |
| 访客标识 | 设备 cookie 改成所有访客第一次访问就下发，不再等到登录；访客登录后，靠登录记录里的设备与账号对应关系把之前的记录认回账号 | 神策、PostHog 的匿名 ID + 登录关联 |
| IP | 分析事件不存 IP，只存省级地区；爬虫判断用完 IP 就丢 | Matomo、Plausible 的 IP 处理；个保法最小必要 |
| 保留期 | 事件明细 90 天；汇总数据长期；Kafka 2 天；个人阅读历史 12 个月 | 决策 J |
| 合成流量 | 模拟器造的事件带合成标记，门户对外的计数、热读、推荐默认排除；开发环境可用配置打开 | 合成数据不进正式指标（决策 I） |
| 隐私政策 | 新增隐私政策页，页脚可达：采集了什么、用来做什么、两层数据的区别、怎么关闭和删除、保留多久、只用第一方 cookie、不用第三方统计 | 站点已对公网开放，采集行为数据要告知 |
| 屏幕 | 桌面端设计与验收；手机上保证正文能读、页面不横向溢出 | 沿用 v0.17 |

**首批事件**（命名用 Object Action，PAP-164 定稿）：

| 来源 | 事件 |
|---|---|
| 门户服务端 | `Article Viewed`（文献详情）、`Search Performed`、`PDF Downloaded`、`Export Completed`、`Article Collected` |
| 浏览器 | `Page Viewed`、`Article Impressed`（卡片曝光：≥ 50% 可见且连续 ≥ 1 秒）、`Article Clicked`、`Fulltext Read`（全文区停留）、`Citation Copied`（复制只发生在浏览器里，PAP-164 改定） |

## 3. 范围边界（不做的事）

| # | 不做的事 | 理由 |
|---|---------|------|
| A | **帖子**：求助帖、分享帖、版块、帖子列表 | 用户定了先做行为数据。帖子要和举报、审核、注册防护一起规划；v0.14 第 3 节 D 定过「合规包完成前讨论与投稿经验不对公网开放」，与门户 10/28 起公网开放的现状冲突，到时一起讨论 |
| B | **关注动态**：关注作者、期刊、主题，动态流 | 关注本身是一整块，和行为数据合在一起 Issue 数会翻倍 |
| C | **个性化推荐（猜你喜欢）**：根据个人阅读历史推荐 | 本版推荐只以当前文献为键，不读个人画像。按《算法推荐管理规定》第 17 条，做个性化推荐要同时提供关闭开关 |
| D | **按热度排序检索**，热度进检索排序 | 只在检索结果上加标记 |
| E | **流处理引擎（Flink）与「恰好一次」投递（Kafka Connect）** | 本版的计算用 ClickHouse 物化视图与定时任务就能完成；「恰好一次」只在工程 spec 里讲清原理，不部署 |
| F | **集群与高可用**：ClickHouse 副本、Kafka 多节点、数据备份 | mini 是单机；事件明细丢了可以用模拟器再生成 |
| G | **第三方统计**：百度统计、Google Analytics、PostHog 云服务 | 全部自建，数据不出站，也正好学全套 |
| H | **创作者数据**：投稿经验、讨论被浏览了多少次 | 浏览量只显示在文献上；事件字典会记下这些页面，只是不展示 |
| I | **用户分群、画像标签、A/B 实验平台** | 行为数据的下一层应用，本版只做到指标与面板 |
| J | **前端性能监控**：页面加载速度、Web Vitals、前端报错上报 | 属于可观测性，不属于行为数据 |

| L | **注册防护、合规包与真实 IP 修复**：人机验证、按 IP 限次数、举报审核、实名、`CF-Connecting-IP` 打通 | 现在没有外部用户。代价：真实访问的地区与按 IP 识别爬虫都不准（所有访客都是同一个内网地址），identity 按 IP 的限次数实际是全站共用；合成流量自带地区分布，相关逻辑仍能测到 |

## 4. 关键决策

> 每条按「问题 → 可选做法 → 选择 → 代价」写。进本节的门槛：影响 2 个以上 Issue、同时影响前后端、或事后很难改回来。依据见文末「调研依据」。

### A. 事件同时带账号 ID 与设备 ID

- **影响 Issue**：PAP-164 / PAP-167 / PAP-168 / PAP-172 / PAP-173
- **问题**：「7 日留存」是第一天来的人里第 7 天还有多少人回来，要能认出跨天的同一个人。
- **可选做法**：
  - **持久标识**：每条事件带设备 ID，登录用户再带用户 ID（神策、PostHog）。
  - **每天换一个匿名 ID**：用「每日轮换的盐 + IP + UA」哈希（Plausible），只能认出当天的同一个人。
- **选择**：持久标识。`device_id` 来自所有访客都有的设备 cookie，`user_id` 来自网关的身份断言，只存 ID、不存用户名（项目规则）。
- **代价**：用户注销时要用 ClickHouse 的删除语句清掉他的事件（PAP-168）；隐私政策要写明这一点。

### B. 个人阅读历史存 PostgreSQL，不从 ClickHouse 查

- **影响 Issue**：PAP-168 / PAP-169 / PAP-174
- **问题**：阅读历史要按人翻页、单条删除、清空，这类按行修改与点查是 PG 擅长、ClickHouse 不擅长的。
- **选择**：`patra-analytics` 有自己的 PG 库，个人历史一张表。采集端点收到事件后，登录且开着记录的用户同步写一行历史（同一篇只保留最近一次的时间）。
- **代价**：同一次浏览在 ClickHouse 与 PG 各存一份；两边删除各自负责。好处是「清空历史不影响浏览量」自然成立。
- **否决**：直接查 ClickHouse 明细当历史。

### C. 新建 `patra-analytics` 服务

- **影响 Issue**：PAP-167 / PAP-168 / PAP-170 / PAP-169 / PAP-171
- **问题**：采集端点、入库消费者、数据产品接口放在哪。
- **选择**：一个新服务，层模块内按子域分包：`collect`（采集）、`ingest`（入库）、`insight`（计数、热读、推荐）、`history`（阅读历史），子域边界由 ArchUnit 守。内存上限 768 MB。
- **为什么**：行为数据是独立的业务领域，业界的采集服务也通常单独部署。内存预算：ClickHouse 2 GB + Kafka 1 GB + 本服务 0.75 GB，按上限算 OrbStack 只剩约 0.6 GB 余量（门户、PG、Redis、Nacos 没设上限）；PAP-165 部署后先实测，余量不够时再定是收紧上限还是调高 OrbStack。
- **否决**：把采集端点放进网关或 interaction，会把不相干的职责混进去。

### D. 用 Kafka（单节点 KRaft 模式），不复用 RabbitMQ

- **影响 Issue**：PAP-165 / PAP-167 / PAP-168 / PAP-171
- **问题**：行为事件进库前要有一个缓冲。ClickHouse 停机或变慢时，采集端点照常收、事件不丢。
- **区别**：RabbitMQ 是「邮局」，消息被取走就没了，适合业务通知（v0.16 用它）。Kafka 是「只追加的日志本」，消息按保留期一直留着，多个消费者各读各的，也能倒回去重读，所以行为数据与日志管线几乎都用它。
- **选择**：Kafka 单节点、KRaft 模式（不需要 ZooKeeper），堆 512 MB、容器上限 1 GB。两个 topic：`events.raw`（原始事件）、`events.dlq`（校验没通过的事件，留着排查，不丢）。保留 2 天，同时设 5 GB 磁盘上限，防止压测把 mini 磁盘写满。
- **代价**：多一个中间件要运维；RabbitMQ Streams 也能做追加日志，但 ClickHouse 没有对应的接入，生态也弱。

### E. 入库：自写批量消费者，至少一次投递 + 去重

- **影响 Issue**：PAP-168 / PAP-171
- **问题**：「至少一次」是保证消息不丢但可能重复，要靠去重兜底。另外 ClickHouse 怕小批量写入：每写一次就在磁盘上多一个数据片段，片段太多会报 `TOO_MANY_PARTS`。
- **可选做法**：ClickHouse 的 Kafka 表引擎 + 物化视图；Kafka Connect 的 ClickHouse Sink（可开「恰好一次」）；自写消费者批量写。
- **选择**：自写 Java 消费者，攒满 5 万条或满 1 秒写一批。每批用「topic + 分区 + 偏移量范围」当 `insert_deduplication_token`，并设 `non_replicated_deduplication_window`，重试同一批时 ClickHouse 自动丢弃。事件自带的 `event_id` 作业务层最后一道去重（汇总按 `event_id` 去重计数）。
- **代价**：消费者代码要自己写、自己测。要注意一个坑：物化视图在写入时就汇总，重复事件会在去重之前被算进汇总，所以重复必须在批次层面拦住，不能指望事后合并去重。
- **否决**：Kafka 表引擎（偏移量与错误不好观测）；Kafka Connect（要多部署一套 Connect，mini 扛不住）。

### F. 所有埋点从门户发出，后端服务不埋

- **影响 Issue**：PAP-164 / PAP-167 / PAP-173
- **问题**：服务端事件由谁发；浏览器事件怎么到采集端点。
- **选择**：
  - 服务端事件（文献详情浏览、检索、PDF 下载、导出、复制引用、收藏）由门户服务端在处理请求时发，不等结果、不影响页面。
  - 浏览器事件发到门户自己域名下的一个路径（不用 `/analytics`、`/ingest` 这类会被广告拦截器认出的路径），由门户补上设备、会话与登录身份，再经网关转给采集服务。
- **为什么**：门户服务端同时知道会话、设备和请求内容，而门户调 catalog 本来就不带会话；第一方路径不会被拦截器挡掉。
- **否决**：在 catalog、interaction 里各埋一遍（两处来源，还要合并去重）。

### G. 数据分层：明细层 → 汇总层 → 应用层

- **影响 Issue**：PAP-168 / PAP-170 / PAP-172
- **选择**：
  - **明细层**（相当于业界的 ODS + DWD）：一张事件明细表，按天分区，90 天 TTL（到期整个分区丢弃）。
  - **汇总层**（DWS）：物化视图在写入时汇总成「每篇文献每天的独立读者数」「每天的活跃用户」等，长期保留。
  - **应用层**（ADS）：计数接口直接查汇总表，外面套 Redis 60 秒缓存，浏览量 1 分钟内更新；热读与共现由定时任务算好写进 PG 快照表，页面只读快照。
- **为什么**：计数要新鲜，排名不需要；ClickHouse 擅长大批量汇总，不适合扛大量在线请求，排名结果放 PG 分担。
- **代价**：同一个口径（独立读者）在物化视图与定时任务里各实现一次，测试要覆盖两边一致。

### H. 事件格式只有一份定义：JSON Schema

- **影响 Issue**：PAP-164 / PAP-167 / PAP-171 / PAP-173
- **选择**：事件字典写成 JSON Schema 放在 `patra-analytics` 的 api 模块里，带版本号。采集端点按它校验；模拟器按它造事件；门户的 TypeScript 类型由它生成，CI 检查两边一致。
- **为什么**：Snowplow（Iglu）、Segment（Protocols）都用这种做法防「埋点越埋越乱」。

### I. 合成数据用一个字段标记，全程和真实数据一起走

- **影响 Issue**：PAP-168 / PAP-170 / PAP-171 / PAP-172
- **选择**：事件带 `is_synthetic`。门户对外的计数、热读、推荐默认排除合成数据，开发环境可用配置打开（`patra.analytics.include-synthetic`），用来看热读和推荐被填满的样子；运营面板可切换。
- **模拟器**：Java 写，放在 `patra-analytics` 下作为一个模块，与服务共用事件定义。灌历史模式直接写 ClickHouse；实时压测模式经 HTTP 打采集端点，用虚拟线程模拟大量并发用户。
- **否决**：k6 / Locust 写压测脚本，要用另一种语言把用户行为模型再写一遍。

### J. 隐私与保留期

- **影响 Issue**：PAP-167 / PAP-168 / PAP-169 / PAP-174
- **选择**：
  - 分析事件不存 IP，只存省级地区；地区查询复用 identity 在用的 ip2region 离线库。
  - 保留期：事件明细 90 天，汇总数据长期，Kafka 2 天，个人阅读历史 12 个月。
  - 隐私政策写清：采集了什么、用来做什么、两层数据的区别、怎么关闭和删除、保留多久。
- **依据**：个保法第 28 条没有把浏览记录列为敏感信息，但医生的文献阅读轨迹可能暴露其科研方向与健康关注，按接近敏感保守处理（规划时的解读，不是法律意见）。
