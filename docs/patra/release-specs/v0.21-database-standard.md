## 1. 版本目标 / 价值

项目里现在有两套库表做法。registry、catalog、identity 三个老服务的表都在 `public`，带 `sys_` / `cat_` / `idn_` 前缀，每张表有雪花 `id`，用 JPA 实体加基类写入。从 v0.13 起的 interaction、notification、analytics 三个新服务按子域分了 11 个 schema，表名没有前缀，有 25 张表没有自己的 `id`，全部用原生 SQL 写入，审计列只有零散的时间。仓库里没有成文的库表规范，约定只存在于 catalog 的先例里，所以新服务另起了一套。

这一版把六个服务的库表按同一份规范重建。任何一张表，看名字就知道属于哪个服务；每张表都有雪花 `id` 和两个由数据库填的审计时间，主表再带操作人、IP、备注；全项目没有外键，没有第二个 schema。规范写成规则文件，并由集成测试检查迁移后的真实表结构来守：新建一张不合规范的表，`./gradlew check integrationTest` 会失败并指出是哪条规则。

这一版的受益人是写代码的开发者本人。门户用户看不到变化。

**验证场景**：

1. 在任一服务加一张不带服务前缀、没有 `id` 或没登记的表，结构检查测试失败并指出规则。
2. 在迁移脚本里写 `CREATE SCHEMA` 或建一条外键，检查失败。
3. 用 IDEA 打开 mini 上的六个库，业务表全部在 `public` 下，按前缀排在一起。
4. 直接在库里给一条用户记录的 `record_remarks` 写上备注，再从门户改一次这个用户的昵称，备注还在。（现状：identity 每次保存都会把这一列清空。）
5. 在重建后的 mini 上，门户的核心流程照常跑通：注册登录、收藏文献、发评论、发投稿经验、收到提醒、看阅读历史。

## 3. 范围边界（不做的事）

1. **不填 `ip_address`。** 列建好、类型改成 `INET`、映射好，但这一版没有代码去填它。要填得把请求 IP 从控制器一路传到仓储，是一个独立的功能。
2. **不删任何表的 `deleted_at` 列。** 生产代码里只有文献会被软删，但期刊和字典有代码在读这一列，没查清谁在写之前不动。
3. **新三个服务不去掉 JPA 依赖。** 「代码里不得出现实体」由 ArchUnit 守。它们靠这个依赖带进来雪花 ID、Flyway、数据库驱动、唯一冲突转 409 的映射；拆出独立的 JDBC 工具模块是另一件事。
4. **不删 catalog 那 5 张没有代码读写的表**（`cat_publication_reference`、`_external_reference`、`_related_item`、`_supplemental_object`、`_history`）。它们照规范重写后留着。
5. **不改接口，不改门户。** 接口返回的字段名保持原样。比如评论仍然返回 `createdAt`，值改从新的 `published_at` 列取。
6. **不做数据迁移。** 六个库直接清空重建。catalog 靠重跑导入任务恢复，其余四个库的测试数据重新造。
7. **不动 ClickHouse。** 它没有 schema 和外键这些概念，另立规范。
8. **不换持久化技术。** 不引入 MyBatis 或 Spring Data JDBC，新服务不改成 JPA，catalog 的大表不改联合主键也不分区。
9. **不修顺带发现、但和库表规范无关的问题。** catalog 的乐观锁没生效（8 个 Mapper 忽略了版本号）；提醒投递、阅读记录设置、对象登记表的对账写回三处并发保护不完整。已记为 Backlog Issue PAP-208、PAP-209。

「identity 把备注清空」和「catalog 子表每行先查再插」不在第 9 条里，这两个随基类调整（PAP-201）在这一版修掉。

## 4. 关键决策

### A. 库表规范以 2026-11-13 的定稿为准

- **影响 Issue**：全部
- **决策**：规范全文写在规则文件里（PAP-199 交付），这里只列要点。

| 项 | 规则 |
|---|---|
| 表名 | 业务表全部在 `public`，表名 `{服务前缀}_{聚合}[_{子表}]`，前缀 `sys` `cat` `idn` `itr` `ntf` `anl`；禁止 `CREATE SCHEMA` |
| 主键 | 每张业务表都有 `BIGINT` 雪花 `id` 当主键，应用层预分配；自然键另建唯一索引（不用唯一约束，见决策 E 第 3 条的验证）；分区表主键写成 `(分区键, id)` |
| 必备列 | 每张表 `id`、`created_at`、`updated_at`；主表再加 `created_by`、`updated_by`、`ip_address`、`record_remarks` |
| 时间列 | `created_at` / `updated_at` 只做审计，由数据库填，应用不写；业务规则要用的时间单独起名，由应用用可注入的时钟写 |
| 外键 | 全项目不建，引用关系由应用保证 |
| 软删除 | 只用显式的 `deleted_at` 列，查询自己写「未删除」条件；禁用 `@SoftDelete` |
| 命名 | 约束和索引显式命名：`uk_` `ck_` `idx_` 加完整表名加用途短语；任何名字不超过 63 字节 |
| 列类型 | 枚举存大写字符串加检查约束；JSON 用 `JSONB`；IP 用 `INET`；时间用 `TIMESTAMPTZ` |
| 注释 | 每张表、每个业务列写中文 `COMMENT` |

- **否决**：按子域分 schema（v0.13 决策 B，本版推翻）；子表和关系行用联合主键；按服务建外键；应用写时间加数据库兜底；`@SoftDelete`。
- **为什么**：主键、外键回到了老三个服务原来的做法，一句话能说清，结构检查一条能守住。时间列改由数据库填，是因为新服务用原生 SQL，没有框架替它自动填，只有数据库填才能让两类服务都不靠人记。

### B. 写侧技术按服务声明

- **影响 Issue**：PAP-200、PAP-201、PAP-202 ～ PAP-206
- **决策**：registry、catalog、identity 用 JPA，不经实体的写入只能是 Dao 上带 `@Modifying(flushAutomatically = true, clearAutomatically = true)` 的 `@Query`，写侧不得用 `JdbcClient`。interaction、notification、analytics 用原生 SQL，代码里不得出现 JPA 实体，主表的写入语句显式写操作人。读适配器两类服务都不限。
- **否决**：统一走 JPA；统一不用 ORM；换 MyBatis。
- **为什么**：新服务的主要写法是幂等写入和单条条件更新，JPA 表达不了；两种技术混在一个事务里才会读到旧数据，纯原生 SQL 的服务没有这类问题。

### C. 靠检查真实表结构来守，不引入第三方检查工具

- **影响 Issue**：PAP-200、PAP-202 ～ PAP-206
- **决策**：集成测试里迁移跑完后，遍历真实的表结构做断言，配每个服务一份表登记文件。这是 GitLab 的做法。
- **否决**：Squawk、SQLFluff、pgrubic、Atlas。能表达「必须带前缀、必须有某些列」的只有后两个，一个是 GPL 许可的小众工具，一个要付费。
- **为什么**：扫描脚本文本看不到最终的表结构，后续的 `ALTER`、`DROP` 会让结果失真。

### D. 结构检查先行

- **影响 Issue**：PAP-200、PAP-202 ～ PAP-206
- **决策**：PAP-200 先落地。每个服务的重建以「它的结构检查从失败变成通过」为完成标志。
- **为什么**：这就是这一版的先写测试。规范先变成一个会失败的检查，再把服务改到通过。

### E. 五条推断验证不过就停下

- **影响 Issue**：PAP-199、PAP-201、PAP-202 ～ PAP-206
- **决策**：下面五条是读文档和源码得出的，没跑过。PAP-199 各用一个测试验证，有一条不成立，对应的规则回来改，不带着往下做。
  1. 触发器按「行内容真的变了才刷新 `updated_at`」来写。
  2. JPA 实体对审计时间做只读映射时，不会让 Hibernate 关掉批量插入。
  3. 普通表以后可以把现成的唯一索引提升为主键，低成本改回联合主键。
  4. 去掉 `@SoftDelete` 之后，现有的两条批量删除语句会变成真删除。
  5. Spring Data 把预先分配了主键的实体当成「已存在」去合并，实现 `Persistable` 后改为直接插入。
- **为什么**：第 3 条是定主键时的依据之一，它不成立要重新确认主键的决定。

### F. 原地重写迁移脚本，不写增量迁移

- **影响 Issue**：PAP-202 ～ PAP-207
- **决策**：六个服务的迁移脚本按规范重写，版本号统一成 14 位时间戳。规则文件里写明：出现第一个不能丢数据的环境后，已执行的脚本禁止再改。
- **否决**：在现有脚本后面追加改名和加列的增量脚本。
- **为什么**：现在没有要保的数据，增量迁移只会留下一串历史包袱。

### G. 合并和重建在同一个时间窗做

- **影响 Issue**：PAP-207
- **决策**：顺序是：mini 上停服务、删库重建、合并 PR、等自动部署、重跑导入任务。期间 `patra.linqibin.dev` 不可用，时长主要取决于 catalog 的导入任务。
- **为什么**：合并后 mini 会自动部署新版本，旧库和新脚本对不上，服务起不来。

### H. 一份设计文档加一份计划覆盖整版

- **影响 Issue**：PAP-199 ～ PAP-206
- **决策**：工程设计文档和计划各一份，计划按 Issue 分段，在同一个会话里按计划逐段做，不派子代理写实现。
- **为什么**：v0.10 工具层重组是这么做的；各服务的重建是同一套规则的重复应用，逐 Issue 做设计会重复。

### 和别的工作的关系

PAP-196（事件登记表发送成功后保留记录）已于 2026-11-13 经 PR #419 合入，这一版基于它。事件登记表是框架表，规范里豁免，重写脚本时保留它的现状。

新服务哪 8 张表算主表、种子数据的 `id` 在脚本里怎么写死，这类只影响单个 Issue 的细节放进工程设计文档。
