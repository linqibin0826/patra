## 1. 版本目标 / 价值

访客能在 Patra 门户**用邮箱注册账号并登录**。登录状态在各页面间保持；登出或账号被封禁后立即失效。匿名浏览论文和期刊保持不变。

本版是用户系统的地基：把账号、会话、鉴权三件事建起来，让以后所有「需要知道你是谁」的功能有处可依。本版不交付任何依赖登录的业务功能。

**验证场景**：在门户注册一个账号，注册后直接是登录态，导航栏显示用户菜单。刷新页面、打开论文详情，仍是登录态。点登出，导航栏回到「登录」。重新登录后，调用封禁接口封禁这个账号，它的下一次请求即被拒绝。

## 4. 关键决策

> **现状事实**（2026-10-04 核对，以下决策的依据）：
>
> - 全仓库没有任何认证代码，网关只有路由配置。
> - 网关用的是 Spring Cloud Gateway 的 WebFlux 版，其余服务都是 servlet。
> - 所有服务端口都映射到宿主机（6000 / 6100 / 6200 / 6300），局域网和 tailnet 上可以绕过网关直连。
> - Redis 没有密码（`protected-mode no`，宿主端口 16379）。
> - 网关按前缀整段转发，外部请求可以经网关到达 `/_internal/**`。
> - 服务之间通过 Nacos 发现后直连（`lb://`），不经过网关。
> - `BaseJpaEntity` 预留了 `created_by` / `updated_by`（Long），`AuditorAware` 是空实现。

### A. 自建 `patra-identity`，不用现成身份产品，也不用 Spring Authorization Server

- **影响 Issue**：PAP-62 ~ PAP-66
- **决策**：新建六边形微服务 `patra-identity`，独立库 `patra_identity`，负责账号、凭据、会话。用户 ID 沿用雪花 Long，与现有审计列一致。
- **否决**：Keycloak 一类的身份产品——登录页不在 portal，还要多运维一个组件。Spring Authorization Server——不支持密码直接换令牌，登录页必须由它渲染。前端认证库——身份的归属会落到前端工程。

### B. 会话用「不透明令牌 + Redis 会话」

- **影响 Issue**：PAP-62 / PAP-64 / PAP-65 / PAP-67
- **决策**（2026-10-05 改定，取代原来的「短期 JWT + 可轮换刷新令牌 + 撤销名单」）：
  - 会话令牌：不透明随机串，不带任何信息。各端统一用 `Authorization` 头携带。
  - 会话：登录时写入 Redis，登出、封禁、踢下线时删除；Redis 里只存令牌的哈希。每次请求续期；30 天不活跃过期。
  - 会话里带账号类型、客户端类型、设备标识（可空）、创建时间、最后活跃时间、绝对过期时间。有效期按「账号类型 × 客户端类型」配置，本版只有前台用户 × Web 一行。
  - 登录记录：每次登录在 identity 的 PostgreSQL 里记一条（谁、哪个端、何时登录、何时以何种原因结束），只用于审计和查看登录设备，不在请求路径上。
- **为什么改**：以后还有 admin 后台、移动端、小程序。会话方案下每个端只带一个令牌，收到 401 就重新登录；JWT 方案下每个端都要实现「刷新一次再重放」，移动端和小程序在进程被杀或切后台时还会被误判成重放而登出。admin 要的空闲超时和踢人下线，在会话方案下就是过期时间和删记录。下游拿到的是网关查完会话后签的内部令牌（决策 C），各端不受影响。
- **补充**（2026-10-09，PAP-64 设计）：会话令牌带账号类型前缀（前台用户是 `patra_user_`），是对「不带任何信息」的一处有意偏离：键里带账号类型是 PAP-63 定下的约束，网关拿到令牌要知道查哪个键空间；前缀只说明令牌属于哪类账号，不含用户信息，顺带让泄露的令牌能被认出、被密钥扫描工具抓到。identity 和网关共用的存储契约放在独立模块 `patra-identity-session` 里，只有这两个消费者。理由见 PAP-64 工程设计第 5、6.1 节。
- **否决**：短期 JWT + 可轮换刷新令牌 + 撤销名单——网关同样每个请求查一次 Redis，却多出签名密钥、公钥端点、轮换、重放检测、并发宽限窗口和门户里的续期。纯无状态 JWT——封号不能即时生效。

### C. gateway 统一鉴权并签发身份断言；下游验签

- **影响 Issue**：PAP-62 / PAP-63 / PAP-64 / PAP-65 / PAP-70
- **决策**（2026-10-08 改定，取代原来的「明文身份头 + 共享内部令牌」；改版由 PAP-70 落地）：
  - 网关负责：查会话、续期、路由级规则（哪些接口要登录）。通过后用自己的私钥签一个 60 秒的内部 JWT（身份断言），放进 `Authorization: Bearer` 转给下游；先剥掉外部请求自带的 `Authorization` 头。匿名请求不带断言。
  - 下游负责：用网关的公钥验签，从断言得到当前用户；数据级权限自己判断。下游不连会话存储。没带断言按匿名；断言无效返回 401。
  - 断言的受众是整个 Patra（`aud: patra`）：服务替用户同步调用另一个服务时，内部客户端把断言原样转发，对方用同一套规则验签。领域事件、定时任务、消息消费里不转发断言，发起人的用户 ID 作为数据传递，消费方以系统身份执行。
  - 每个请求现签、不缓存，所以登出和封禁的撤销即时生效。
  - 带了无效或过期的会话令牌按匿名处理，是否放行由路由规则决定；查会话时 Redis 不可用返回 503。
  - 本版从断言取身份的只有 identity（边界 E）。
- **为什么改**：共享内部令牌要分发到每个识别用户的服务，任一服务泄露即可冒充任何用户，下游也分不出身份头是真是假。签名断言下私钥只在网关，用户身份只能从网关产生；下游只持有公钥，泄露也无妨。OWASP 的身份传递指南同样不推荐只信代理写的明文头。这正是 phantom token 模式：客户端拿不透明令牌，内部用签名 JWT，网关负责翻译。
- **已知代价**：私钥泄露等于能冒充任何用户，所以私钥只在网关、由 secret 注入（决策 G）。服务之间调用时调用方自己的身份仍不验证，是边界 F 的事。
- **否决**：明文身份头 + 共享内部令牌——见上。下游各自查 Redis——每个服务都要 Redis 凭据，并和 identity 的会话存储格式耦合。每个服务用自己的私钥重签断言——对方能同时验证用户和调用方，但任何一个服务都能签出任何用户，信任模型变成「信每个服务」，还要每个服务一对密钥、一份信任清单；留给边界 F。

### D. 账号分两类，分开建模；会话带账号类型；本版只实现前台用户

- **影响 Issue**：PAP-62 / PAP-63 / PAP-64 / PAP-65
- **决策**：

  | | 前台用户（`USER`） | 后台账号（`STAFF`） |
  |---|---|---|
  | 怎么产生 | 自己注册 | 由管理员创建 |
  | 登录入口 | 门户登录页 | 后台登录页 |
  | 角色 | 没有 | 有，比如管理员、运营 |

  会话里带账号类型，前台用户的会话进不了后台接口。本版只实现前台用户；后台账号是以后新增的表和接口，不改前台用户这一套。封禁 / 解封是后台接口，放在 `/admin/` 下；本版没有后台账号，网关拒绝外部访问它，只能在内网直连调用。
- **补充**（2026-10-06，PAP-63 设计）：重新调研了 50 多个系统后维持分开建模。类型名不用 `PORTAL`（门户只是一个 Web 前端，App、小程序用的是同一批前台账号），也不用 `ADMIN`（管理员只是后台的一种角色）。调研结论和命名见 PAP-63 工程设计第 4 节。
- **否决**：一张账号表加角色——前台注册路径上的缺陷可能波及后台账号，两类账号的生命周期和安全要求也不同。

### E. 浏览器只持有 HttpOnly Cookie；不引入 Auth.js

- **影响 Issue**：PAP-64 / PAP-67 / PAP-68
- **决策**：
  - 会话令牌放在一个 Cookie 里，只存在于浏览器和门户服务端之间；门户服务端调网关时换成 `Authorization` 头。`HttpOnly` 和 `SameSite` 始终开启；`Secure` 默认开启，只在显式配置的非 HTTPS 环境（本机、tailnet）关闭。
  - 门户不做续期：会话的有效期由网关在每次请求时延长，门户只负责定期刷新 Cookie 自身的过期时间。
  - 注册、登录、登出走 Server Action。
  - 匿名内容的请求不带令牌；用户态数据单独请求，不缓存。
- **否决**：令牌放 localStorage——页面被注入脚本就能偷走。Auth.js——已进入只修安全问题的维护状态。

### F. 安全 starter 作为新增的独立模块

- **影响 Issue**：PAP-62 / PAP-63 / PAP-64 / PAP-65
- **决策**：当前用户的获取做成新增的独立 starter 模块，放在 `patra-starters`。domain 层通过端口拿当前用户，不依赖任何 Web 或安全框架。审计列自动填当前用户 ID，做法是改 starter-jpa 的默认审计人，让它通过一个小接口取当前操作人。
- **说明**（2026-10-05）：linqibin-commons 已与 super-nb 分离，只为 Patra 服务。原来「不挂进被下游消费的 5 个模块、不改 starter-jpa 的审计人契约」的约束不再存在；模块仍然独立，是因为身份约定属于 Patra 的业务，不属于通用库。
- **否决**：把它塞进 starter-web——没有登录功能的服务也会被带上。

### G. 密钥与凭据不进仓库

- **影响 Issue**：PAP-64 / PAP-65 / PAP-66 / PAP-70
- **决策**：Redis 密码、网关签身份断言的私钥放在仓库外的 `~/.patra/secrets/`，容器由 compose 按绝对路径加载，本机进程由 dev profile 导入同一批文件；仓库里只保留 `.example` 模板。对应的公钥不是机密，随各下游的配置给出。会话的真相在 Redis 里，所以 Redis 加密码是本版的硬前提。
- **说明**（2026-10-10）：原定的 `.env.*.secret` 放在 compose 目录里，而 CD 每次运行前的 `git clean` 会删掉 runner 工作区里被忽略的文件，这套机制在 CD 下从来没生效过，所以改放仓库外。见 `docs/patra/specs/2026-10-10-identity-deploy-design.md` 第 5 节。
- **否决**：沿用随仓库提交的 dev 凭据——仓库是公开的；Redis 没有密码时，任何能连上它的人都能写入一条假会话。

### H. 网关切到 Spring Cloud Gateway 的 WebMVC 版，全仓库只留 servlet 一套

- **影响 Issue**：PAP-62 / PAP-65 / PAP-69
- **决策**（2026-10-05 追加）：网关从 WebFlux 版换成 WebMVC 版，作为独立的 Issue 排在网关鉴权之前，先换技术栈并回归，再加鉴权。安全 starter 因此只做 servlet 一套；网关直接用 starter-web 的统一错误格式；查会话是普通的同步 Redis 调用。
- **已知代价**：WebMVC 版成熟度不如 WebFlux 版（上游维护者自己的说法），存量项目里 WebFlux 仍占多数；WebMVC 版不代理 WebSocket。Patra 目前没有 WebSocket 需求，服务端推送可以用 SSE。
- **否决**：保持 WebFlux 网关——安全 starter、错误输出、测试都要写两套，查会话要用响应式 Redis 客户端。

### I. 认证框架用 Spring Security；会话存储自己写

- **影响 Issue**：PAP-62 / PAP-63 / PAP-64 / PAP-65
- **决策**（2026-10-05 追加）：网关和需要识别用户的服务都接 Spring Security，用它的过滤器链、线程上下文、密码哈希和测试支持；以后 admin 后台的角色与方法级权限也用它。会话存储（决策 B）自己写在 Redis 里。Spring Security 只经安全 starter 进入 classpath，本版只有 identity 和 gateway 引入。
- **为什么现在就引入**：admin 后台确定要做。按最终形态设计的话，线程上下文、测试支持、401 / 403 的输出迟早要换成它的那一套，现在手写一版等于写两遍。
- **否决**：全部手写——做 admin 时要返工。Sa-Token——令牌明文存储，下游只读请求头的用法它不支持，维护高度依赖一位作者，近一年有过反序列化导致的远程代码执行漏洞。Spring Security + Spring Session——它把整个登录上下文对象序列化进 Redis，identity 写、网关读要共用一份序列化契约；不提供绝对过期；按用户查会话要依赖 Redis 的键空间通知；没有找到把它用在「多端请求头令牌 + 网关」上的公开案例。

> **已排除出本字段**（留给各 Issue 的工程设计）：密码哈希算法、登录失败限制的阈值、会话令牌的长度与哈希方式、Redis 里的键设计、续期的写入频率、传递身份的请求头名称、网关路由规则的写法。
