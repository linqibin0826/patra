## 1. 版本目标 / 价值

访客能在 Patra 门户**用邮箱注册账号并登录**。登录状态在各页面间保持；登出或账号被封禁后立即失效。匿名浏览论文和期刊保持不变。

本版是用户系统的地基：把账号、会话、鉴权三件事建起来，让以后所有「需要知道你是谁」的功能有处可依。本版不交付任何依赖登录的业务功能。

**验证场景**：在门户注册一个账号，注册后直接是登录态，导航栏显示用户菜单。刷新页面、打开论文详情，仍是登录态。点登出，导航栏回到「登录」。重新登录后，调用封禁接口封禁这个账号，它的下一次请求即被拒绝。

## 4. 关键决策

> **现状事实**（2026-10-04 核对，以下决策的依据）：
>
> - 全仓库没有任何认证代码，网关只有路由配置。
> - 所有服务端口都映射到宿主机（6000 / 6100 / 6200 / 6300），局域网和 tailnet 上可以绕过网关直连。
> - Redis 没有密码（`protected-mode no`，宿主端口 16379）。
> - 网关按前缀整段转发，外部请求可以经网关到达 `/_internal/**`。
> - 服务之间通过 Nacos 发现后直连（`lb://`），不经过网关。
> - `BaseJpaEntity` 预留了 `created_by` / `updated_by`（Long），`AuditorAware` 是空实现。

### A. 自建 `patra-identity`，不用现成身份产品，也不用 Spring Authorization Server

- **影响 Issue**：PAP-62 ~ PAP-66
- **决策**：新建六边形微服务 `patra-identity`，独立库 `patra_identity`，负责账号、凭据、会话。令牌用 Spring Security 的 `NimbusJwtEncoder` 自己签发。用户 ID 沿用雪花 Long，与现有审计列一致。
- **否决**：Keycloak 一类的身份产品——登录页不在 portal，还要多运维一个组件。Spring Authorization Server——不支持密码直接换令牌，登录页必须由它渲染。前端认证库——身份的归属会落到前端工程。

### B. 会话用「短期 JWT + 可轮换刷新令牌 + 会话记录 + 撤销名单」

- **影响 Issue**：PAP-62 / PAP-64 / PAP-65 / PAP-67
- **决策**：
  - 访问令牌：JWT，RS256 签名，有效期 15 分钟。
  - 刷新令牌：随机串，每用一次换一个新的；旧的被重复使用就撤销整个会话（并发续期留宽限窗口）；30 天不活跃过期。
  - 会话记录：一次登录一条，存 identity 的 PostgreSQL，只存刷新令牌的哈希。
  - 撤销名单：被撤销会话的 ID，存 Redis，保留 15 分钟。登出和封禁即时生效。
- **否决**：若依式 JWT + Redis——所有服务共用密钥、下游信明文头。纯无状态 JWT——封号不能即时生效。外部用不透明令牌、内部换 JWT——每次请求都要向 identity 换令牌。

### C. gateway 统一鉴权；JWT 原样转给下游；下游自己解析 JWT 得到当前用户

- **影响 Issue**：PAP-62 / PAP-63 / PAP-64 / PAP-65
- **决策**：
  - 网关负责：验签、查撤销名单、路由级规则（哪些接口要登录）。
  - 下游负责：用公钥解析 JWT（解析即验签），取出用户 ID 和账号类型；数据级权限自己判断。下游不查撤销名单。
  - 私钥只在 identity；网关和下游通过 identity 的公钥端点取公钥并缓存。
  - 服务之间替某个用户发起的调用，原样转发 `Authorization` 头。
  - 本版实际解析令牌的是 gateway 和 identity（边界 E）。
- **否决**：网关注入明文用户头——下游拿到的身份没有签名保护，而服务端口可以绕过网关直连。只解码不验签——等于接受任何人伪造的令牌。

### D. 账号分两类，分开建模；令牌带账号类型；本版只实现门户用户

- **影响 Issue**：PAP-62 / PAP-63 / PAP-64 / PAP-65
- **决策**：

  | | 门户用户 | 后台账号 |
  |---|---|---|
  | 怎么产生 | 自己注册 | 由管理员创建 |
  | 登录入口 | 门户登录页 | 后台登录页 |
  | 角色 | 没有 | 有，比如管理员 |

  令牌里带账号类型，门户的令牌进不了后台接口。本版只实现门户用户；后台账号是以后新增的表和接口，不改门户用户这一套。封禁 / 解封是内部接口，不经网关。
- **否决**：一张账号表加角色——门户注册路径上的缺陷可能波及后台账号，两类账号的生命周期和安全要求也不同。

### E. 浏览器只持有 HttpOnly Cookie；续期在 portal 的 proxy 里完成；不引入 Auth.js

- **影响 Issue**：PAP-64 / PAP-67 / PAP-68
- **决策**：
  - 访问令牌和刷新令牌各放一个 Cookie。`HttpOnly` 和 `SameSite` 始终开启；`Secure` 默认开启，只在显式配置的非 HTTPS 环境（本机、tailnet）关闭。
  - 访问令牌快到期时，在 proxy 里用刷新令牌换新（proxy 是 Next.js 16 里 middleware 的新名字）。
  - 注册、登录、登出走 Server Action。
  - 匿名内容的请求不带令牌；用户态数据单独请求，不缓存。
- **否决**：令牌放 localStorage——页面被注入脚本就能偷走。Auth.js——已进入只修安全问题的维护状态，也不适合对接外部签发的 JWT。

### F. 安全 starter 作为新增的独立模块

- **影响 Issue**：PAP-62 / PAP-63 / PAP-64 / PAP-65
- **决策**：令牌解析与当前用户做成新增的独立 starter 模块，不挂进已被下游 super-nb 消费的 5 个模块，不改 starter-jpa 现有的审计人契约。domain 层通过端口拿当前用户，不依赖 Spring Security。
- **否决**：把令牌解析塞进 starter-web——会改变下游的行为。

### G. 密钥与凭据不进仓库

- **影响 Issue**：PAP-64 / PAP-65 / PAP-66
- **决策**：签名私钥、Redis 密码通过 `.env.*.secret` 注入，仓库里只保留 `.example` 模板。
- **否决**：沿用随仓库提交的 dev 凭据——仓库是公开的，签名私钥泄露等于任何人都能伪造登录。

> **已排除出本字段**（留给各 Issue 的工程设计）：密码哈希算法、登录失败限制的阈值、令牌里的字段清单、网关路由规则的写法、宽限窗口的时长、公钥的缓存与轮换细节。

  - 同一个刷新令牌被重复使用，整个会话失效
