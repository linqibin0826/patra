## 一条提交信息是写给三类人看的

提交信息不是随手写的备注。它至少有三类读者：

- **以后翻历史的你**：半年后想知道某行代码为什么这样改，先看的就是它。
- **评审的人**：PR 合并时（Patra 用 squash，一个 PR 压成一条提交），这条信息就是 main 历史上的一行。
- **机器**：检查工具、变更记录生成器，都要靠固定格式来解析。

格式统一，三类读者都省力。Patra 采用业界常见的 Conventional Commits：

```text
类型(范围): 标题
```

类型是一个小写英文词，范围可选，写这次改动属于哪个模块，标题用中文写“做了什么”。

## 类型和规则

仓库根目录的 `commitlint.config.cjs` 把规则定死了：

<CodeRef at="commitlint.config.cjs@5d70c422611867be5ba1dcc441dc62e1f997ffdb" />

| 类型 | 用在 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `refactor` | 重构，行为不变 |
| `test` | 加或改测试 |
| `perf` | 性能优化 |
| `style` | 只调格式，不改逻辑 |
| `ci` | 改流水线 |
| `build` | 改构建、依赖 |
| `chore` | 其他杂务 |

几条硬规则：

- 类型必须小写，且在上面的名单里。
- 标题不能为空，不能以英文句号结尾。
- 整个标题行不超过 100 个字符。
- 范围如果写，必须小写。

还有两条来自标准预设，容易踩：**标题不能以大写字母开头**（所以别把类名或 Issue 编号放在标题最前面，用中文动词起头）；**正文每行不超过 100 个字符**，注意它按字符数而不是字节数算，用 awk 按字节数去量会误报。

在 Patra 里，这份配置分四块：

<CodeRef at=".pre-commit-config.yaml@3cf6fa5757b3be54c3b030e4cace871f53e2599c" lines="7-51" />

| 钩子 | 拦什么 | 为什么 |
|---|---|---|
| 通用检查 | 合并冲突残留、坏掉的 YAML / JSON、2 MB 以上的大文件、私钥、行尾空格 | 低级错误别进历史 |
| gitleaks | 看起来像密钥的字符串 | 仓库是公开的，密钥一进历史就永久可读 |
| spotless | Java 与 gradle 脚本的格式，自动改好 | 格式争论交给机器 |
| commitlint | 提交信息格式 | 就是上面这些规则 |

<Callout kind="warn">

gitleaks 认的是“长得像密钥”，不是“确实是密钥”。测试里写一个名字含 TOKEN、长度 43 位的随机字面量，也会被当成密钥拒绝提交。Patra 的 identity 测试里改用 `"F".repeat(43)` 这种明显不随机的写法就过了。

</Callout>

## 钩子只在你电脑上，所以不是唯一一道

钩子装在每个人自己的电脑上，`git commit --no-verify` 就能跳过。所以它不是安全的最后防线，只是**最快的第一道**：几秒钟就能拦下低级错误，不用等云端几分钟的检查再报错。真正兜底的在后面：PR 上的云端检查，以及评审工具里的密钥扫描。
