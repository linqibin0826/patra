## 普通 HTTP 只能「你问我答」

回顾一下：HTTP 是客户端发请求、服务器回响应。服务器没有办法在没被问的时候，自己开口告诉浏览器什么。

但很多页面需要「有新东西就立刻知道」：铃铛的未读数、聊天消息、构建进度。有三种办法。

Patra 的未读数推送选了 SSE：通知只需要服务器告诉页面，页面不需要在这条连接上说话。

## SSE 长什么样

SSE 就是一次 GET 请求，响应的 `Content-Type` 是 `text/event-stream`，而且**响应不结束**。服务器之后想说话，就往里写一段文本。格式极其简单：

```text
HTTP/1.1 200
Content-Type: text/event-stream
Cache-Control: no-cache, no-transform

retry: 3000
event: unread-count
data: {"total":2,"replies":1,"mentions":1,"helpful":0}

:ping

event: unread-count
data: {"total":3,"replies":2,"mentions":1,"helpful":0}

```

规则：

- 每条事件由若干行 `字段: 值` 组成，**以一个空行结束**。
- `event:` 是事件名，`data:` 是数据（这里是 JSON）。
- `retry:` 告诉浏览器断线后隔多少毫秒重连。
- 以冒号开头的行是**注释**，浏览器收到什么也不做，不触发任何事件。

<CodeRef at="patra-api/patra-notification/patra-notification-adapter/src/main/java/dev/patra/notification/adapter/realtime/rest/UnreadCountStreamController.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="15-47" />

值得注意的细节：

- `produces = text/event-stream`，返回 `SseEmitter`，Spring 负责保持连接。
- 响应头 `Cache-Control: no-cache, no-transform`。`no-transform` 禁止中间层改写内容：压缩中间件会攒满一块再发，事件就卡住了。
- 连接寿命就是 `SseEmitter` 的超时，到点正常结束；结束、出错、超时都要从连接表里注销，不然会泄漏。

## 网关一侧，和前端的退路

推送连接一借就是 30 分钟，如果和普通请求抢同一个连接池，会把普通请求挤死。所以网关给推送路由单独一个池子，上限 500；满了**立刻**回 503，不排队。

<CodeRef at="patra-portal/src/lib/notifications/stream.ts@4a13287485468f2c489027f1aac0bb6174643e8d" lines="69-72" />

- 已登录且页面可见时才连；页面隐藏、登出就断开（浏览器对同一站点的 HTTP/1.1 连接数有上限，通常 6 条）。
- 拿到非 200（比如 503），EventSource 不会再重连，页面也看不到状态码。这时前端立刻查一次未读数，60 秒后再试推送，其间回到轮询。
- 推送是锦上添花，轮询是兜底。推送不可用，页面功能不能坏。
