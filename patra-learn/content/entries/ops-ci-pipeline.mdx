## 四个词，一张图

GitHub Actions 是 GitHub 提供的自动化平台。它有四个核心概念，先分清它们：

- **事件（event）**：触发的原因，比如“有人开了 PR”。
- **workflow（工作流）**：一份写在 `.github/workflows/` 下的 yml 文件，是整套剧本。
- **job（任务）**：剧本里的一个任务，里面有一串**步骤（step）**。没有特别说明时，各个 job 同时开工。
- **runner（执行机器）**：真正执行 job 的那台机器。

## 触发器：什么时候开工

Patra 的 ci.yml 订阅了四种事件：

<CodeRef at=".github/workflows/ci.yml@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="6-18" />

| 事件 | 含义 |
|---|---|
| `pull_request`（目标是 main） | 有人开了或更新了指向 main 的 PR，**这是日常最主要的一种** |
| `push` 到 main | 代码合并进了 main 之后再验证一次 |
| `schedule` | 每天定点跑一次全量检查兜底，写的是 UTC 18:00，换成北京时间是次日凌晨 2 点 |
| `workflow_dispatch` | 在 GitHub 页面上手动点按钮触发 |

## 一个 job 长什么样

detect-changes 是最简单的一个 job，通过它能认出一个 job 的所有部件：

<CodeRef at=".github/workflows/ci.yml@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="28-45" />

- `runs-on`：这个 job 去哪种机器上跑。
- `timeout-minutes`：超过这个时间就强行终止，防止卡死一直占着机器。
- `steps`：按顺序执行。`uses:` 是引用别人写好的现成步骤（action），`run:` 是直接执行 shell 命令。
- `outputs`：job 把结果传给后面依赖它的 job。

第一步 checkout 是把仓库代码拉到这台机器上，因为云端机器一开始是空的。

<Callout kind="insight">

看 `uses:` 的写法：版本号后面跟着的是一长串 40 位字符，并在末尾用注释标出版本。这是把第三方 action 钉在**确切的提交**上，而不是一个可以被移动的标签。后面讲流水线安全时会解释为什么。

</Callout>

## 排队、取消与并行

两个小设置，值得认识：

- `needs`：声明一个 job 要等另一些 job 完成才开工。没有 `needs` 的 job 之间同时开工。
- `concurrency`：同一组里同一时间只留一个。Patra 的写法是：同一个 PR 又推送新提交时，**取消**还在跑的旧检查，反正它检查的是过时的代码；但推送到 main 的那次不取消。

## 云端机器是一次性的

`ubuntu-latest` 是 GitHub 租给你的云端机器。每次 job 开工，它都是一台全新的干净机器，用完就销毁。这既是优点（不会被上次的残留干扰），也意味着：

- 缓存要主动配置，否则每次都从零开始下载依赖。
- 它在云端，摸不到你家里的服务器。需要在自己机器上执行的任务，要用自己的 runner。这是下面几篇之一的主题。
