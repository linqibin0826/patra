<Callout kind="lead">

Jackson 是 Java 里最常用的 JSON 库。对象写成 JSON 叫**序列化**，JSON 读回对象叫**反序列化**。Spring MVC 收发 JSON 时，背后干活的就是它。

</Callout>

## 两个方向

上一篇的 Controller 里，两个方向都出现过：

- **进来**：登录接口的 `@RequestBody LoginRequest request`。请求体是一段 JSON 文本，Jackson 按 `LoginRequest` 这个 record 的字段名，把同名的键读进去，造出一个 Java 对象。这是反序列化。
- **出去**：方法返回 `SessionsRevokedResponse`，Jackson 把它的字段一个个写成 JSON 的键值。这是序列化。

规则大体是直觉的：

| Java 里 | 写成 JSON |
|---|---|
| record 或带 getter 的对象 | 对象 `{ … }`，字段名就是键名 |
| `List`、数组 | 数组 `[ … ]` |
| `String` | 字符串 |
| `int`、`long`、`boolean` | 数字、布尔 |
| 枚举，如 `DeviceClass.DESKTOP` | 字符串 `DESKTOP` |
| `null` | `null` |

Patra 的容器里只有一个由 Spring Boot 装配的 `JsonMapper`（Jackson 的入口对象），谁要用 JSON 就注入它，不自己 new（v0.10 决策 F）。这样 Boot 的默认设置在全项目只有一份。

## 问题出在大整数

Patra 的主键是「雪花 ID」：一种按时间加机器号拼出来的 64 位整数，Java 里用 `Long` 装，正好。可浏览器里的 JavaScript 只有一种数字类型，能精确表示的整数最大是 2 的 53 次方减 1，也就是 `9007199254740991`，16 位。雪花 ID 远超这个范围。

## Patra 的做法：只在 HTTP 响应里把 Long 写成字符串

<CodeRef at="patra-tool/patra-tool-web/src/main/java/dev/patra/tool/web/json/LongToStringHttpMessageConvertersCustomizer.java@b6e01875bb5692356021c8a19562f557f319fc54" lines="12-33" />

```java
/// 让 MVC 响应里的包装类型 `Long` 以字符串输出。
///
/// 雪花 ID 超过 JavaScript 的安全整数范围（2^53），浏览器端必须拿到字符串。这是 HTTP 响应的
/// 策略，所以只挂在 MVC 的 JSON 转换器上：转换器用的是从容器 `JsonMapper` 派生出来的实例，
/// 保留 Boot 的全部默认配置与 ProblemDetail 定制，只多一个 `Long` 序列化器。容器里的
/// `JsonMapper` 本身不受影响，持久化、消息、服务间请求体里的 `Long` 仍是数字。
///
/// 原始类型 `long` 不受影响。
public final class LongToStringHttpMessageConvertersCustomizer
    implements ServerHttpMessageConvertersCustomizer, Ordered {

  private final JacksonJsonHttpMessageConverter jsonConverter;

  /// 从容器的 `JsonMapper` 派生出带 Long → String 序列化器的响应转换器。
  ///
  /// @param jsonMapper 容器里的 `JsonMapper`
  public LongToStringHttpMessageConvertersCustomizer(JsonMapper jsonMapper) {
    SimpleModule module = new SimpleModule("LongToString");
    module.addSerializer(Long.class, ToStringSerializer.instance);
    this.jsonConverter =
        new JacksonJsonHttpMessageConverter(jsonMapper.rebuild().addModule(module).build());
  }
```

它做了三件事：

1. 从容器里的 `JsonMapper` **复制**一份（`rebuild()`），在复制品上加一条规则：遇到 `Long` 就用 `ToStringSerializer`，写成字符串。
2. 用这个复制品做一个 JSON 转换器，替换 Spring MVC 写响应时用的那个。
3. 容器里原来的 `JsonMapper` 一点没动。

为什么不干脆在容器的 `JsonMapper` 上加这条规则？因为 `JsonMapper` 不只用来写 HTTP 响应。下面三种做法并排比：

为什么不「数字也收」？数字到这一步已经被 `JSON.parse` 改错了，收下来就是在用一个错的 ID。前后端两头都守住，问题在第一次联调时就会暴露。
