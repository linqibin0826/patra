## 三条写入语句

读数据用 `SELECT`，写数据有三条，对应「增、改、删」：

| 语句 | 做什么 | 例子（示意） |
|---|---|---|
| `INSERT` | 新增一行 | `INSERT INTO cat_venue (id, venue_type, title, provenance_code) VALUES (101, 'JOURNAL', '示例医学杂志', 'PUBMED')` |
| `UPDATE` | 修改已有的行 | `UPDATE cat_venue SET title = '新标题' WHERE id = 101` |
| `DELETE` | 删除行 | `DELETE FROM cat_venue WHERE id = 101` |

写入时数据库会替你把关：所有 `NOT NULL` 的列必须有值，类型要对，唯一约束不能撞。哪一条不满足，整条语句失败，**一行也不会写进去**。

每条语句执行完，数据库会告诉你**影响了几行**。这个数字很有用：`INSERT` 影响 1 行说明真的插入了，`UPDATE` 影响 0 行说明 `WHERE` 没找到人。后面会看到 Patra 怎么靠它做决定。

## UPDATE 和 DELETE：WHERE 是唯一的筛子

`UPDATE` 和 `DELETE` 的作用范围完全由 `WHERE` 决定。动手拖一拖，看影响多大：

怎么降低这类风险：

1. 先把 `WHERE` 原样放进 `SELECT` 里跑一遍，看看会命中哪几行、几行，再改成 `UPDATE`。
2. 重要的修改放进事务里做，不对就回滚（下面「事务」那一篇讲）。
3. 业务上要「删除」时，很多表用软删除：加一列 `deleted_at`，删除就是给它填上时间，查询时用 `deleted_at IS NULL` 过滤。Patra 的 catalog 里不少表（期刊、文献、作者）这样做，误删时还能找回。

## 插入时已经有了：upsert

导入数据时常遇到这件事：这一行可能已经在表里了。比如导入期刊实例，同一期刊同一年同一卷同一期，只能有一行。直接 `INSERT` 会撞上唯一约束，语句失败。

PostgreSQL 让你在 `INSERT` 后面写 `ON CONFLICT`，告诉它撞上了怎么办：

- `ON CONFLICT (...) DO NOTHING`：已经有了就算了，不插入也不报错；
- `ON CONFLICT (...) DO UPDATE SET ...`：已经有了就改成新值。这就是常说的 **upsert**（update + insert）。

括号里写的是"撞的是哪个唯一约束"。

这三种在 Patra 里都有。看 catalog 导入期刊实例时的「找或建」：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/java/dev/patra/catalog/infra/publication/persistence/VenueInstanceRepositoryAdapter.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="112-123" />

```java
  public boolean insertJournalInstanceIfAbsent(VenueInstanceAggregate instance) {
    long id = SnowflakeIdGenerator.getId();
    int inserted =
        entityManager
            .createNativeQuery(
                """
                INSERT INTO cat_venue_instance
                    (id, venue_id, volume, issue, publication_year, publication_month, publication_day)
                VALUES (:id, :venueId, :volume, :issue, :year, :month, :day)
                ON CONFLICT (venue_id, volume, issue, edition, conference_name, publication_year)
                DO NOTHING
                """)
```

它先试着插，撞上唯一键就当没发生，然后再把那一行查出来用。方法的返回值是"是否真的插入了新行"。代码注释里还写了一个重要理由：**冲突时不抛异常，所在事务继续可用**。如果改成"先 `INSERT`，抓住异常再查"，PostgreSQL 的事务在报错后就作废了，后面什么都做不了。

"覆盖"的写法在另一个文件 `PublicationSyncRepositoryAdapter` 里：按 PMID 写来源行，`ON CONFLICT (pmid) DO UPDATE SET ...`，已有的整行覆盖成最新解析结果。

<Callout kind="insight" label="影响行数不只是个统计">

Patra 的"有帮助"功能要保证每人对每个目标只能点一次，计数还要对得上。做法是：先用 `INSERT ... ON CONFLICT DO NOTHING` 插明细，**只有影响行数是 1**（真的插进去了）才给计数加 1。重复点击影响 0 行，计数就不动。这个判断为什么必须和插入放在同一个事务里，在「事务」那一篇讲。

</Callout>
