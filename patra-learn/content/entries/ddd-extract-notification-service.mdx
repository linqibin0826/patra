## 背景：提醒越长越大

v0.16 通知中心那一版开工前（2026-10-30）核对的现状：

- 站内提醒是 interaction 服务里的一个子域，只有三类：回复了你的评论、评论了你的投稿经验、@ 了你。
- 提醒和评论在**同一个事务**里写入：发评论时，监听器同步算出收件人、写提醒，要么一起成功，要么一起回滚。这叫**强一致**。
- 铃铛上的未读数每 60 秒轮询一次，没有任何偏好设置。

这一版要加的是：提醒邮件、每类提醒的「不发 / 逐条 / 每日汇总」三档偏好、邮件里的一键退订、实时推送未读数。这些新概念（偏好、退订令牌、在不在站上、汇总窗口）只属于「通知」这块业务，和评论本身无关。再塞在 interaction 里，评论模块就要知道「这个人要不要收邮件」。

作者的判断是：提醒和通知是一块以后还会长大的业务，单独成一个限界上下文，新建 `patra-notification` 服务，接管信箱、偏好、邮件、汇总和推送。

## 第一个问题：怎么告诉通知服务「有人回复了」

Patra 选了发事件。事件怎么做到「不丢」（发件箱、发布确认、补投、去重）是消息路线的内容，这里只关心边界：interaction 不再知道通知服务的存在，只宣布事实。

## 第二个问题：谁来决定通知谁

事件里写什么，有两种做法：

<DecisionOptions
  options={[
    { name: "事实型事件", summary: "interaction 只说「C 回复了 B 的评论，正文里 @ 了 D」，由通知服务自己算出该提醒谁。", pros: "收件人规则跟着提醒走；以后别的功能也想知道有新评论，订阅同一个事件就行，interaction 不用改。", cons: "事件里要带齐算收件人用的事实；新增一种提醒时，事件可能要多带字段。", chosen: true },
    { name: "指令型调用", summary: "interaction 自己算好收件人，直接说「给 B 发一条回复提醒」。", pros: "通知服务很薄，只负责投递。", cons: "通知的规则留在了评论模块里，等于没拆。Novu、Knock 这类通知平台用这种，因为平台本来就不懂业务。" }
  ]}
/>

产品内部拆服务时多用事实型。Patra 把 interaction 原来的收件人规则原样搬进了通知服务：先列被回复的人，再列经验作者（只对经验下的根评论），最后列 @ 到的人；同一个人只按第一次出现的类型提醒；最后去掉作者本人。

```java
public static List<Recipient> forPublished(CommentFacts facts) {
  Map<Long, NotificationType> recipients = new LinkedHashMap<>();
  if (facts.parentAuthorId() != null) {
    recipients.putIfAbsent(facts.parentAuthorId(), NotificationType.COMMENT_REPLY);
  }
  if (facts.rootOnPost()) {
    recipients.putIfAbsent(facts.subjectOwnerId(), NotificationType.POST_COMMENT);
  }
  for (Long mentioned : facts.mentionedUserIds()) {
    recipients.putIfAbsent(mentioned, NotificationType.MENTION);
  }
  recipients.remove(facts.authorId());
  // ……
}
```

事件里带齐了算收件人要的事实：作者、被回复评论的作者、@ 到的用户 ID、是否匿名。通知服务不回头调 interaction 查数据。这种让事件携带对方需要的状态的做法，Martin Fowler 称为「事件携带状态转移」。

## 通知服务里面怎么分

新服务一开始就按子域分好：底座 `kernel`（提醒类别、取用户名的端口、在站信号等被几个子域共用的东西），加上 `inbox` 信箱、`preference` 偏好与退订、`mail` 邮件、`realtime` 实时推送。子域之间只有三条允许的依赖，写在架构测试里，违反就让构建失败：

## 代价

<Callout kind="cost">

- **提醒晚一点出现**：平时是毫秒级；RabbitMQ 或通知服务挂了，就要等它恢复。
- **不再一起回滚**：「评论成功、提醒失败」时，靠事件的补投和消费端的重试最终送达，两边都要处理重复和乱序。
- **事件契约要维护**：新增一种提醒时，interaction 可能要在事件里多带字段。
- **旧提醒没有迁移**：interaction 里原有的提醒随旧子域一起删掉，切换后信箱从空开始。门户对外开放后几位测试者已有的提醒因此消失了。

</Callout>
