<Callout kind="lead">

新版本出问题是常态，退回去只是流程里的一个分支。Patra 的回滚分两种：

- **自动回滚**：验货没过，部署脚本自己翻出「上一个好版本」换回去
- **手动回滚**：上线后才发现问题，手动触发流水线，填服务名和旧版本号

</Callout>

## 自动回滚：靠一本小账

每个服务验货通过后，部署脚本立刻把当前版本号写进一个文件，位置在部署机的 `~/.patra/cd/last-good-<服务名>`。文件里只有一行：一个提交的 SHA，意思是「这个服务上一次确认好用的版本」。

注意两个细节：

1. **每个服务一份账**。catalog 的和 identity 的各记各的，回滚时互不牵连。
2. **通过一个记一个**，不等整批结束。一批里最后一个服务翻车了，前面成功的几个也已经记好了新版本。

最容易想错的是「已恢复，整单仍失败」。回滚成功后，脚本会打印「已回滚并恢复健康」，然后整体 `exit 1`。于是流水线是红的，GitHub 的通知（App 推送加邮件）会找上你。反过来也成立：手机没响，就是这次上线成功了。

没有 last-good 的典型场景是服务第一次上线就失败：账本里还没有它，脚本不硬来，直接标记需要人工介入。

## 手动回滚：填两个空

自动验货抓不住的是另一类问题：上线一切健康，第二天才发现新版逻辑有 bug。这时用流水线留的手动按钮 `workflow_dispatch`：

<CodeRef at=".github/workflows/cd.yml@b6e01875bb5692356021c8a19562f557f319fc54" lines="39-48" />

```bash
gh workflow run cd.yml -f service=catalog -f image_tag=<旧提交的 SHA>
```

填了 `image_tag` 之后，流水线里所有构建、打镜像、归档推送的步骤都会跳过（它们的条件是 `IMAGE_TAG_INPUT == ''`），直接拿这个版本去跑 `deploy.sh`。整个过程不用重新编译，两分钟上下。

旧 SHA 去哪找？这靠合并方式埋的伏笔：合并进 main 时用 squash，main 的历史一行一件事，每个提交都是一个可以部署的版本号。翻 `git log` 按提交号精确点名就行。

门户和学习站各有自己的流水线，手动触发时只填 `image_tag`，因为每条流水线只管一个服务。

旧版本的镜像通常还在部署机本地：部署脚本先看本地有没有，缺了才去镜像仓库拉。这就是镜像仓库虽然不再是部署的必经之路，仍然要保留一份备份的原因。

## 回滚管不到的两件事

回滚换的是镜像，别的东西不会跟着退。

<Callout kind="warn">

**配置写错时，回滚镜像没用。** Patra 的 CD 先把配置推到 Nacos，再部署。如果配置值不合法，服务启动失败或刷新失败，回滚到旧镜像后，旧镜像读的还是同一份坏配置。要恢复得改配置本身：`git revert` 那次配置修改，让 CD 重新推送。

</Callout>

<Callout kind="warn">

**回滚用的是当前检出的 compose 文件和环境文件。** 如果新版本删掉了旧镜像还需要的环境变量，回滚旧镜像就会因为缺变量起不来。例如某个版本删了一个 Redis 地址的环境变量，之前的版本要回滚前，得先把这一行补回密钥文件。

</Callout>
