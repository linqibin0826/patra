## Hook 是以 use 开头的函数

`useState` 是一个 Hook。React 提供的这类函数都以 `use` 开头，让组件函数能「记住东西」或「在渲染之外做事」。用的时候有两条规矩：只能在组件函数（或另一个 Hook）的最外层调用，不能放进 `if` 或循环里；每次渲染调用的顺序必须一样。React 靠调用顺序认出「这是第几个状态」。

你也可以把几个 Hook 组合成自己的 Hook，名字照样以 `use` 开头。下面会看到门户里的 `useDebounced`。

## 渲染之外的事叫副作用

组件函数的本分是算出界面。开定时器、给 window 加监听、发请求，这些会碰到组件外面世界的事叫**副作用**。诊断题已经说明了：把它们直接写在函数体里，每渲染一次就做一次。

`useEffect` 是放副作用的地方。传给它的函数不在渲染时跑，而是等 React 把这一轮的结果画到屏幕上之后才跑。第二个参数是依赖数组，决定它什么时候再跑：

| 写法 | 什么时候跑 |
|---|---|
| 不写依赖数组 | 每次渲染后都跑 |
| `[]` | 只在组件第一次出现在页面上之后跑一次 |
| `[value, delay]` | 第一次之后，`value` 或 `delay` 变了才再跑 |

## 再跑之前，先收拾上一次

传给 `useEffect` 的函数可以返回另一个函数，叫**清理函数**。依赖变了要再跑时，React 先调用上一次返回的清理函数，再跑新的；组件从页面上移除时，也会调用最后一次的清理函数。

门户讨论区的「@ 联想」要等用户停下 200 毫秒再查人，不然每打一个字就请求一次网关。这个「等停手」的逻辑就是一个自定义 Hook：

<CodeRef at="patra-portal/src/components/discussion/MentionSuggest.tsx@d0ca49caf72d9d9aacd7459c1054cf9131b3759e" lines="34-41" />

```tsx
function useDebounced<T>(value: T, delay: number): T {
  const [settled, setSettled] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setSettled(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);
  return settled;
}
```

`value` 每变一次，effect 就开一个 200 毫秒的定时器；清理函数负责把没到点的定时器取消。点下一步看用户快速打出 `@wan` 时发生了什么：

## 监听也一样：加了就要去掉

⌘K 唤起快速检索，靠的是导航栏 `TopNav` 在 window 上加的键盘监听：

<CodeRef at="patra-portal/src/components/portal/TopNav.tsx@d0ca49caf72d9d9aacd7459c1054cf9131b3759e" lines="73-83" />

```tsx
  useEffect(() => {
    const onKeyDown = (e: KeyboardEvent) => {
      if ((e.metaKey || e.ctrlKey) && e.key.toLowerCase() === "k") {
        e.preventDefault();
        setSearchLoaded(true);
        setSearchOpen((open) => !open);
      }
    };
    window.addEventListener("keydown", onKeyDown);
    return () => window.removeEventListener("keydown", onKeyDown);
  }, []);
```

依赖是 `[]`，所以导航栏出现在页面上时只加一次。清理函数在导航栏被移除时把监听去掉；少了这一行，导航栏每出现一次就多挂一个监听，旧的还在，按一次 ⌘K 会被处理好几遍。

<Callout kind="warn">

门户的 `next.config.ts` 开着 `reactStrictMode`。开发模式下，React 会故意把每个组件「挂上、卸下、再挂上」一次，effect 因此跑两遍、中间清理一遍。漏写清理的 effect 在这时就会露馅（比如监听翻倍）。这只在开发模式发生，生产构建不会。

</Callout>

## useId：给元素一个稳定的 id

「@ 联想」的候选列表要用 `aria-controls` 告诉读屏软件「输入框控制的是哪个列表」，这需要一个 id。`useId` 给每个组件实例一个唯一、而且每次渲染都不变的 id：

<CodeRef at="patra-portal/src/components/discussion/MentionSuggest.tsx@d0ca49caf72d9d9aacd7459c1054cf9131b3759e" lines="66" />

```tsx
  const listId = useId();
```

为什么不随手写一个随机数？随机数每次渲染都不同，而且服务器上算出来的和浏览器里算出来的也不同。后一点在讲水合时还会碰到。
