## 背景：两类数字，对「新」的要求不一样

v0.18 给门户三类数据：每篇文献的「N 人看过」「N 人读过全文」，首页的「热读」，文献页的「看过这篇的人还看了」。它们都来自 ClickHouse 里的行为数据，但性质差得很远：

| | 计数 | 热读、看过还看了 |
|---|---|---|
| 要多新 | B 读完 1 分钟内 +1 | 每小时 / 每天变一次就够 |
| 算一次的代价 | 一屏 14 篇、最多 100 篇按主键取，毫秒级 | 扫近 14 天的全部阅读、排序、两两配对，秒级 |
| 谁扛在线请求 | ClickHouse 按主键查 + Redis 挡住重复请求 | PostgreSQL 快照表，按主键读几十行 |

还有一条硬约束：**ClickHouse 擅长「一次扫几千万行算一个结果」，不擅长「每秒几百个小查询」**。它的每个查询都要起一套并行执行，内存和线程的开销是按查询算的，小查询一多就吃不消。

所以这一版的应用层分成了两条路（release spec 决策 G）。

## 选择

<Callout kind="lead" label="选了什么">

计数现查 ClickHouse 的汇总表，前面挡一层 Redis，同一篇 60 秒内只查一次；排名由定时任务算好，整表替换进 PostgreSQL 快照，页面请求根本不碰 ClickHouse。

</Callout>

决定性的理由是**新鲜度和代价的组合**：计数便宜但要新，缓存 60 秒刚好是「1 分钟内更新」的上限；排名贵但不必新，干脆一小时算一次。

## 计数：先查 Redis，没有再查 ClickHouse

这种「读时先看缓存，没有再查数据源、查完写回缓存」的做法叫 **cache-aside**，是业界最常见的缓存用法。Patra 的计数是一次处理一批文献：

写回那一段：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/java/dev/patra/analytics/infra/insight/stats/CachingReaderStatsDecorator.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="100-121" />

```java
  private void writeBack(List<Long> misses, Map<Long, ReaderStats> loaded) {
    try {
      redis.executePipelined(
          (RedisCallback<Object>)
              connection -> {
                for (Long id : misses) {
                  ReaderStats s = loaded.getOrDefault(id, ReaderStats.none(id));
                  connection
                      .stringCommands()
                      .setEx(
                          key(id).getBytes(StandardCharsets.UTF_8),
                          TTL.toSeconds(),
                          (s.viewers() + ":" + s.fulltextReaders())
                              .getBytes(StandardCharsets.UTF_8));
                }
                return null;
              });
    } catch (DataAccessException e) {
      log.warn("写计数缓存失败：{}", e.getMessage());
      meters.counter(METER, "result", "error").increment();
    }
  }
```

`getOrDefault(id, ReaderStats.none(id))` 就是「没查到的也写 `0:0`」。另外几个细节：

- **60 秒就是「1 分钟内更新」的来源**：最坏情况是刚缓存完 B 就读了，要等这 60 秒过去。本人刚看过不会立刻 +1，门户的设计已经按这一点来。
- **键里带口径**：`analytics:insight:stats:real:{文献ID}`，`real` 表示排除合成事件；开发时打开「包含合成事件」后换成 `all`，切换开关不会读到另一种口径的旧缓存。
- **两种故障，两种处理**：Redis 出错时整次绕过缓存直接查 ClickHouse，只记一个 `error` 指标——缓存不能让 Redis 故障拖垮计数；ClickHouse 不可用时计数接口返回 503，门户少显示「看过」那几项。

计数接口还顺带返回「在不在热读榜」，那是从 PostgreSQL 的热读快照按 ID 查的，不缓存。

## 排名：算好，整张换掉

热读每小时第 5 分钟、看过还看了每天 04:30，由 XXL-Job 定时任务算好写进 PostgreSQL 的快照表。页面读的就是这张表：这正是读写分开里的读模型，只不过它的「写」是一个定时任务整批产出的。

每次算完都要把整张快照换成新的。换法有三种：

<DecisionOptions
  options={[

    { name: "版本切换", summary: "新快照写成新版本，切一个指针指向它，再删旧版本。", pros: "可以随时退回上一版。", cons: "退回上一版这一版用不上；每次读还要多关联一次指针表。" }

/>

DELETE 方案能让读者不受影响，靠的是 PostgreSQL 的多版本并发控制（MVCC）：一行被删除后，在删除它的事务提交之前，其他事务看到的仍是这一行的旧版本。所以写快照的那几秒里，首页读到的是完整的旧快照，不会读到「删了一半」的样子。

热读快照的写入：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/java/dev/patra/analytics/infra/insight/persistence/HotReadingSnapshotRepositoryAdapter.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="13-34" />

```java
/// `HotReadingSnapshotRepository` 的原生 SQL 实现：`DELETE` 全表 + `unnest` 批量插入，要求调用方的事务。
///
/// 不用 `TRUNCATE`：它要拿排他锁，提交前读这张表的页面请求都会被卡住；`DELETE` 下读者一直看到旧快照。
@Component
@RequiredArgsConstructor
public class HotReadingSnapshotRepositoryAdapter implements HotReadingSnapshotRepository {

  private final JdbcClient jdbc;

  /// 整表替换并记下计算时间。
  ///
  /// @param entries 新快照的全部行
  /// @param computedAt 计算时间
  @Override
  @Transactional(propagation = Propagation.MANDATORY)
  public void replace(List<HotReadingEntry> entries, Instant computedAt) {
    jdbc.sql("DELETE FROM insight.hot_reading").update();
    for (int from = 0; from < entries.size(); from += SnapshotRuns.CHUNK) {
      insert(entries.subList(from, Math.min(from + SnapshotRuns.CHUNK, entries.size())));
    }
    SnapshotRuns.record(jdbc, SnapshotRuns.HOT_READING, computedAt, entries.size());
  }
```

`Propagation.MANDATORY` 要求调用方已经开好事务，没有事务就直接报错，防止有人绕开事务单独调它。插入每 5,000 行一条 `INSERT ... SELECT FROM unnest(...)`，几百万行也只有几百条语句。

## 任务失败时，旧快照原样保留

整表替换还有一个好处：失败很好处理。任务的步骤是「ClickHouse 算候选 → 向 catalog 核对 → 拼出快照 → 写快照」，远程调用全在事务外面，事务里只有写快照这一步：

```java

      List<HotReadingCandidate> candidates =
          signals.hotCandidates(today, HotReadingRule.CANDIDATE_LIMIT);
      Set<Long> eligible =
          catalog.eligibleAmong(candidates.stream().map(HotReadingCandidate::articleId).toList());
      List<HotReadingCandidate> ranked =
          candidates.stream().filter(c -> eligible.contains(c.articleId())).toList();
      List<Long> latest =
          ranked.size() < HotReadingRule.PAGE_SIZE
              ? catalog.latestIds(HotReadingRule.LATEST_FETCH)
              : List.of();
      List<HotReadingEntry> board = HotReadingRule.board(ranked, latest);
      transactions.executeWithoutResult(status -> snapshots.replace(board, clock.instant()));
```

ClickHouse 或 catalog 失败，异常在走到最后一行之前就抛出去了，快照一行没动；写快照时 PostgreSQL 出错，事务回滚，同样是旧快照。调度中心把这次标红，下一个小时（共现是第二天）再算。整表替换天然幂等，重复跑也没关系。

首页因此不依赖 ClickHouse 和 catalog：它们出问题时，「热读」照常有内容，只是停在上一次成功的样子。快照表旁边的 `insight.snapshot_run` 记着每种快照最近一次成功的时间，接口把它作为 `computedAt` 返回。

## 代价

<Callout kind="cost">

- **同一个口径实现了两遍**：「看过的人」在物化视图（计数用）和定时任务（热读用）里各写了一次，所以要有测试守住两边一致：同一批事件，热读的近 7 天人数要等于计数接口的看过人数。
- **数字不是实时的**：计数最多旧 60 秒，热读最多晚一小时，看过还看了最多晚一天。
- **死行**：每次 DELETE 都留下一整张表的死行，靠 autovacuum 回收；真实数据下只有几行，合成数据灌满时共现快照约百万行。
- **什么时候该重新考虑**：排名要求做到分钟级更新，或者计数的访问量大到 60 秒缓存也挡不住时，要换成增量计算或者把计数也预算出来。

</Callout>
