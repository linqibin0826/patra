## 坑

网关上用了 Spring Security 的 `HttpSecurity`，它默认带 `HeaderWriterFilter`。响应里缺这些头时，它会补上：`Cache-Control: no-cache, no-store, max-age=0, must-revalidate`、`Pragma`、`Expires`、`X-Content-Type-Options`、`X-Frame-Options`、`X-XSS-Protection`。

网关转发下游的响应时，这个过滤器照样在链上。下游没写 `Cache-Control`，转出去就变成了 `no-store`。

## 为什么

这个默认值本身是为普通 Web 应用设计的：页面里可能有个人数据，默认不缓存最安全。它只看「响应里有没有这个头」，不知道这个响应是网关自己生成的，还是从下游转来的。

v0.8 账号那一版给网关接 Spring Security 时就发现了这一点：网关有一份「代理透传的响应保持下游原样」的约定，补头直接违反了它。

到 v0.14 讨论那一版，这件事有了具体的后果。提醒的未读数接口用条件请求省流量：200 与 304 都显式带 `ETag` 和 `Cache-Control: no-cache, private`，浏览器下次带 `If-None-Match` 来问，没变就回 304。经网关的流程测试专门断言 304 响应里**没有** `no-store`，防的就是网关替它补上。

## 怎么避开

网关有两条过滤器链。转发请求的那一条关掉默认的响应头写出器；只输出网关自己 403 的拒绝名单那一条保留默认值。

<Callout kind="warn">

关掉以后，网关不会再替任何响应加安全头。哪些头该加（比如门户页面的 `X-Frame-Options`），要由真正生成响应的那一方自己加。关掉之后要用集成测试钉住「透传的响应头和下游一致」，否则以后升级框架、改安全配置时又悄悄加回来。

</Callout>
