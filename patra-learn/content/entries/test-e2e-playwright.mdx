## 配置：谁启动、跑几遍、出错留什么

整份配置只有二十几行，却把端到端测试的几个关键决定都写明了：

<CodeRef at="patra-portal/playwright.config.ts@2907a521b2c7934a98252faf45c0b5503b49e47c" lines="1-28" />

挑几项读：

- `testDir: "tests/e2e"`：端到端测试和组件测试分开放，Vitest 配置里 `exclude` 掉的就是这个目录。
- `webServer`：测试前自动用 `pnpm dev` 启动门户。本地如果已经在跑，就直接复用（`reuseExistingServer`），CI 里则总是新启。
- `retries`：CI 里失败后最多重试 2 次，本地不重试；`workers` 在 CI 里是 1，不并行。
- `trace: "on-first-retry"`：第一次重试时录下完整的操作轨迹（截图、网络、每一步），失败后可以回放，是排查端到端失败的主要工具。
- `forbidOnly`：CI 里不许留着 `test.only`，免得有人提交了只跑一个用例的版本。

## 像用户一样找元素

Playwright 找元素的方式，和上一层测试讲过的 Testing Library 是同一个思路：按用户看到的东西去找，不按 CSS 类名。

<CodeRef at="patra-portal/tests/e2e/auth.spec.ts@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="97-118" />

```ts
await nav.getByRole("link", { name: "登录" }).click();
await page.getByLabel("邮箱").fill(account.email);
await page.getByRole("button", { name: "注册" }).click();
await expect(page).toHaveURL(SOURCE, ROUND_TRIP);
```

`getByRole`（按角色和名字）、`getByLabel`（按表单标签）、`getByText`（按文字）是三个主力。页面改了样式、换了标签，只要用户眼里这个按钮还叫「登录」，脚本就不用改。

## 不要 sleep：自动等待

这类问题的特征是：逻辑上每一步都对，只有真实的排版和时序才让它露馅。测试里为了稳定复现，特意让点击「按住 100 毫秒」，用手机视口模拟轻触，还用禁用脚本模拟「页面还没接管表单就提交」的情形。这三种都是组件测试没法表达的。

<Callout kind="insight">

一条经验：能在组件测试里说清楚的，不要放到端到端里。端到端测试专门留给「必须有真实浏览器和真实环境才测得出来」的东西。

</Callout>

## 测试数据：每次造一个新账号

注册、登录的流程要用账号。测试支持文件里的做法是：每跑一次，**现场生成**一个新的：

<CodeRef at="patra-portal/tests/e2e/support/account.ts@598dc3eeb2f5209dcc858393eff510a2a3c8a332" lines="9-24" />

邮箱和用户名后缀是随机的，密码在运行时临时生成，都不写进仓库、不打印出来；邮箱用的是邮件服务商提供的专门测试地址，发过去只记为已送达，不会真的投递。这样每次跑都不需要预先准备账号，也不会撞上上一次留下的数据。

## 什么时候跑

端到端在 CI 里的位置：

<CodeRef at=".github/workflows/ci.yml@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="214-218" />

从那几行能读出：门户有改动的 PR 上它会跑，但**失败不拦合并**（`continue-on-error`）；而每晚的定时全量运行里，失败是**阻塞**的。这是对速度和稳定性的折中：不让偶发的浏览器抖动卡住每一个 PR，同时每天有一次严格的检查兜底。

<Callout kind="warn">

测试页面前要等页面「接管」：服务端先把 HTML 发过来，React 随后才给元素挂上事件。接管之前点击，点到的是浏览器自带的默认行为，用例没修好也会通过。门户的支持文件里有专门的等待函数处理这一点，后面的实战文章会细讲。

</Callout>
