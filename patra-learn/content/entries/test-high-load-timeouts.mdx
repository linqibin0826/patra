## 坑

机器负载很高时（别的进程、好几个同时跑的构建把 CPU 占满），用默认 worker 数跑 Vitest 全量，用例会随机超时。这时放宽超时不但没用，还会让整轮测试一直挂着不结束。要做的是把 worker 数限到 2。

<Callout kind="insight" label="怎么认出它">

- 报错是 `[vitest-pool]: Failed to start forks worker … Timeout waiting for worker to respond` 和 `Test timed out in 5000ms`。
- 每次失败的用例都不一样。
- `uptime` 看到的 1 分钟负载远高于 CPU 核数。

</Callout>

## 两次实际遇到

- **第一次**（v0.8 账号登录那一版，2026-10-10）：门户全量测试连续两次失败。第一次 5 个组件测试超时，95 个文件只跑完 79 个；第二次跑了 593 秒（平时 9 秒），失败的又是另外 2 个。当时机器 12 核，1 分钟负载在 50 到 90 之间，起因是后台进程占满了 CPU，和改动无关。负载约 1.5 分钟后降到 12 以下，这时再跑，95 个文件、810 个用例全绿。
- **第二次**（v0.16 通知中心那一版，2026-10-31）：好几个会话同时在跑 Gradle 构建，负载到了 140 到 380。用默认 worker 数、再加上 `--testTimeout=30000` 放宽超时去跑全量，跑了近 7 个小时不结束：Vitest 一直在起新 worker，把整机负载拖到 300 到 400，最后被手动停掉。

## 怎么避开

全量测试一律限住 worker 数：

```bash
pnpm exec vitest run --maxWorkers=2
```

v0.16 那次换成这条命令后，同样的负载下用默认 5 秒超时，约 4 分钟全绿（355 个文件、3457 个用例）。

- 不要靠加 `--testTimeout` 硬跑全量。
- 运行在 node 环境、不渲染组件的测试受影响小，可以先跑。
- 单个文件的第一个用例偶发超过 5 秒、重跑能过的，算负载，在汇报里写明，不改代码。
