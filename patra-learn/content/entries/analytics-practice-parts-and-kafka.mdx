## 开始之前：两套工具，各自怎么保证只读

**ClickHouse** 的连法和练习一一样，SQL 存成 `query.sql`，用 curl 发给 HTTP 接口：

```bash
curl -u "patra:$CLICKHOUSE_PATRA_PASSWORD" \
  'http://<mini 的地址>:8123/?database=patra_analytics&readonly=1' \
  --data-binary @query.sql
```

`patra` 账号对 `patra_analytics` 有全部权限，另外被授权读 `system.parts`；地址里的 `readonly=1` 把这次请求锁成只读，写操作一律被拒绝。本篇查的 `system.parts`、`system.columns` 只读元数据，不扫数据，0.1 秒就回来。

**Kafka** 的命令行工具在 Kafka 容器里，通过 ssh 到 mini 上执行：

```bash
ssh <mini> docker exec -e KAFKA_HEAP_OPTS=-Xmx128m patra-kafka \
  /opt/kafka/bin/kafka-topics.sh --bootstrap-server patra-kafka:29092 --describe --topic events.raw
```

两个参数要解释：

- **`--bootstrap-server patra-kafka:29092`**：broker 有两个对客户端的监听器，容器内部用按容器名访问的 `INTERNAL` 那个（讲 Kafka 日志那篇的「两个地址」一节），健康检查也是这么连的。
- **`-e KAFKA_HEAP_OPTS=-Xmx128m`**：每个命令行工具都会另起一个 JVM。Kafka 容器的环境变量里把堆设成了 512 MB（给 broker 用的），整个容器的内存上限是 1 GB；不覆盖的话，工具也按 512 MB 起，和 broker 抢同一个容器的内存。compose 文件里健康检查的注释写的就是这件事，它把堆压到 64 MB，建 topic 的边车用 128 MB。这里照边车的值。

本篇用到的 Kafka 命令为什么都不改东西：

| 命令 | 做什么 | 为什么不改东西 |
|---|---|---|
| `kafka-topics.sh --describe` | 看 topic 的分区与配置 | 只读元数据；改配置是 `--alter`，本篇不用 |
| `kafka-get-offsets.sh` | 看每个分区的末端偏移量 | 只读元数据 |
| `kafka-consumer-groups.sh --describe` | 看消费组读到哪 | 只读；会改东西的是 `--reset-offsets` 和 `--delete`，本篇不用 |
| `kafka-console-consumer.sh --partition --offset` | 按位置取几条消息 | 不带 `--group`，不以任何已有消费组的身份读、不提交位点；消息本身也不会因为被读过而删除 |

<Callout kind="warn">

数据是流量模拟器造的（`is_synthetic = 1`），不是真实用户；下面两条 Kafka 消息也来自一次模拟器运行。结果是 2026-11-02 北京时间 18:50 左右查的。

</Callout>

## 第 1 题：每张表有几个片段、压缩比多少

**要查什么**：`patra_analytics` 里每张表当前的活跃片段数、分区数、行数、压缩前后的大小和压缩比。

**为什么值得查**：MergeTree 那篇讲过，片段太多会拖垮写入，分区决定过期数据怎么扔。这张表是日常巡检最先看的东西。

  questions={[

    }

/>

**提示**：`system.parts` 每个片段一行；只看 `active` 的（合并后被替换掉的旧片段 `active = 0`）；`data_compressed_bytes`、`data_uncompressed_bytes` 是压缩前后的字节数，`formatReadableSize()` 把它们变成 GiB、MiB。

**参考答案**：

```sql
SELECT table,
       count()                                   AS active_parts,
       uniqExact(partition)                      AS partitions,
       sum(rows)                                 AS rows,
       formatReadableSize(sum(data_compressed_bytes))   AS compressed,
       formatReadableSize(sum(data_uncompressed_bytes)) AS uncompressed,
       round(sum(data_uncompressed_bytes) / sum(data_compressed_bytes), 2) AS ratio
FROM system.parts
WHERE database = 'patra_analytics' AND active AND table != 'schema_migrations'
GROUP BY table ORDER BY sum(data_compressed_bytes) DESC
FORMAT PrettyCompactMonoBlock
```

**实际结果**（0.1 秒，整理成表）：

| table | active_parts | partitions | rows | compressed | uncompressed | ratio |
|---|---|---|---|---|---|---|
| `events` | 346 | 89 | 104,207,095 | 12.66 GiB | 29.32 GiB | 2.32 |
| `article_session_reads` | 12 | 1 | 31,325,736 | 1.63 GiB | 2.35 GiB | 1.44 |
| `daily_person_activity` | 6 | 1 | 3,546,916 | 131.69 MiB | 231.29 MiB | 1.76 |
| `session_quality` | 7 | 1 | 4,290,881 | 72.85 MiB | 78.18 MiB | 1.07 |

**怎么读**：

- **片段数是稳态，不是零**。`events` 89 个分区、346 个片段。合并会挑大小相近的片段归并，写入停下后片段数稳定在一个小数目，不会一路合到每个分区只剩一个。强行合并要用 `OPTIMIZE ... FINAL`，那是写操作，会重写整个分区，本篇不用，`readonly=1` 也不允许。
- **只有 `events` 分了区**。三张汇总表的建表语句里没有 `PARTITION BY`，整张表就是一个分区（MergeTree 那篇末尾提过）。`events` 按天分区，所以分区数就是天数：2026-08-06 到 11-02，89 天。
- **`rows` 数的是磁盘上的行**。它是活跃片段里的物理行数，还没被合并掉的重复行也在里面，所以不能拿它当事件条数；数条数照样要 `uniqExact(event_id)`。
- **压缩比差很多**。`events` 2.32，`session_quality` 只有 1.07：后者几乎只有一列 `session_id`（UUID）加三个小字段，而随机 ID 几乎压不动，下一题会看到。
- **没有 `dlq_events`**。死信表一行都没有（合成事件全部合格），没有行就没有片段，`system.parts` 里自然不出现。

## 第 2 题：events 表里，哪一列最占地方

**要查什么**：`events` 表按列看压缩后的大小，取最大的 6 列，连同各自的压缩比。

**为什么值得查**：列存按列存放、按列压缩（列式存储那篇）。想省盘，先知道钱花在了哪一列上。

**提示**：`system.columns` 每列一行，也有 `data_compressed_bytes` 和 `data_uncompressed_bytes`。

**参考答案**：

```sql
SELECT name, type,
       formatReadableSize(data_compressed_bytes)   AS compressed,
       round(data_uncompressed_bytes / data_compressed_bytes, 1) AS ratio
FROM system.columns
WHERE database = 'patra_analytics' AND table = 'events'
ORDER BY data_compressed_bytes DESC LIMIT 6
FORMAT PrettyCompactMonoBlock
```

**实际结果**（整理成表）：

| name | type | compressed | ratio |
|---|---|---|---|
| `device_id` | String | 2.12 GiB | 1.8 |
| `person_id` | String | 1.84 GiB | 2.0 |
| `properties` | String | 1.83 GiB | 3.4 |
| `event_id` | UUID | 1.16 GiB | 1.0 |
| `session_id` | UUID | 804.87 MiB | 1.5 |
| `derived_at` | DateTime64 | 399.45 MiB | 1.5 |

**怎么读**：

- **随机 ID 几乎压不动**。`event_id` 压缩比 1.0，存多少占多少。压缩靠的是重复和规律，随机串两样都没有。
- **`person_id` 是第二份 `device_id`**。它不是采集来的字段，是写入时算出来存下的计算列：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V1__events.sql@8140a9d9482324670b63f00ab3c62690102196c5" lines="27-29" />

```sql
    properties      String,
    article_id      UInt64 MATERIALIZED toUInt64OrZero(JSONExtractString(properties, 'article_id')),
    person_id       String MATERIALIZED if(user_id != 0, concat('u:', toString(user_id)), concat('d:', device_id))
```

没登录的读者，`person_id` 就是 `d:` 加设备 ID，几乎把 `device_id` 又存了一遍，多花 1.84 GiB。换来的是：它能进排序键，按人去重的查询直接用，不用每次现算（设备 ID、会话与「一个人」那篇讲过 `u:` / `d:` 的规则）。这是一笔明确的空间换时间。

- **它比 `device_id` 压得好一点**（2.0 对 1.8），大致是因为 `person_id` 在排序键里，排好序后相邻行更常是同一个人。`session_id` 的 1.5 也类似：同一个会话的几条事件常常挨在一起。这两条是推断。
- **`event_name` 不在前 6**。它是 `LowCardinality(String)`，列里只存小整数（列式存储那篇），上亿行也占不了多少。

## 第 4 题：events.raw 的配置，和脚本写的一样吗

**要查什么**：`events.raw` 有几个分区、几个副本，保留策略实际是什么。

**为什么值得查**：仓库里的脚本是「想要的样子」，broker 上的配置才是「实际的样子」。两者对不上，磁盘预算就算错了。

**提示**：`kafka-topics.sh --describe --topic events.raw`，看第一行的 `PartitionCount`、`ReplicationFactor` 和 `Configs`。

**参考答案**：

```bash
ssh <mini> docker exec -e KAFKA_HEAP_OPTS=-Xmx128m patra-kafka \
  /opt/kafka/bin/kafka-topics.sh --bootstrap-server patra-kafka:29092 --describe --topic events.raw
```

**实际结果**（整理成表）：

| 项 | 值 | 含义 |
|---|---|---|
| `PartitionCount` | 3 | 3 个分区 |
| `ReplicationFactor` | 1 | 单节点，只有一份 |
| `cleanup.policy` | delete | 过期就删（而不是按键压缩） |
| `retention.ms` | 172800000 | 2 天 |
| `retention.bytes` | 1073741824 | 每个分区 1 GiB |
| `segment.bytes` | 268435456 | 一段写满 256 MiB 就滚动 |
| `segment.ms` | 21600000 | 不满也每 6 小时滚动一段 |
| `file.delete.delay.ms` | 5000 | 段文件被判定删除后，再等 5 秒真正删 |

**怎么读**：前五项和建 topic 脚本写进去的一致：

<CodeRef at="patra-infra/docker/kafka/init-topics.sh@8140a9d9482324670b63f00ab3c62690102196c5" lines="44-46" />

```bash
  "${BIN}/kafka-configs.sh" --bootstrap-server "${BOOTSTRAP}" --alter \
    --entity-type topics --entity-name "${name}" \
    --add-config "cleanup.policy=delete,retention.ms=${TWO_DAYS_MS},retention.bytes=${retention_bytes},segment.bytes=${segment_bytes},segment.ms=${SIX_HOURS_MS}"
```

脚本每次 `up` 都会把这五项重写一遍，手工改过的值会被改回来，所以仓库里的值就是线上的值。第六项来自 broker，就是讲 Kafka 日志那篇里「清理检查 30 秒 + 删除延迟 5 秒」的后半截。有了这几项，就能按那篇的公式算出 `events.raw` 的最坏磁盘占用：3 × (1 GiB + 256 MiB) = 3.75 GiB，再加两次清理检查之间的写入量。

## 第 5 题：写到哪了，读到哪了

**要查什么**：`events.raw` 每个分区的末端偏移量；入库消费组 `patra-analytics-ingest` 每个分区读到了哪、落后多少。

**为什么值得查**：消费滞后（lag）是这条管线最重要的健康指标。它一直涨，说明入库跟不上，事件在 Kafka 里越堆越多，离保留期上限越来越近。

<Quiz
  title="先猜"
  questions={[
    {
      question: "三个分区的末端偏移量是 541,643、555,705、550,367。下面哪种理解对？",
      options: ["events.raw 现在一共存着这么多条消息，再多就要按保留期删了", "这是每个分区下一条消息要用的序号，过了保留期被删掉的也算在里面", "这是入库消费者还没处理的条数，越大说明积压越严重"],
      answer: "B",
      explain: "偏移量从 0 往上数，写进去就不变，删段文件也不会让它回退。末端偏移量是下一条要写的序号，等于这个分区有史以来写入的条数，不等于现在还留着多少条。"
    }
  ]}
/>

**提示**：末端偏移量用 `kafka-get-offsets.sh`；消费组用 `kafka-consumer-groups.sh --describe --group`。

**参考答案**：

```bash
ssh <mini> docker exec -e KAFKA_HEAP_OPTS=-Xmx128m patra-kafka \
  /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server patra-kafka:29092 --topic events.raw

ssh <mini> docker exec -e KAFKA_HEAP_OPTS=-Xmx128m patra-kafka \
  /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server patra-kafka:29092 \
  --describe --group patra-analytics-ingest
```

**实际结果**：末端偏移量（整理成表）：

| 分区 | 末端偏移量 |
|---|---|
| 0 | 541,643 |
| 1 | 555,705 |
| 2 | 550,367 |

消费组（整理成表；原输出还有 `CONSUMER-ID`、`HOST`、`CLIENT-ID` 几列，这里略去）：

| TOPIC | PARTITION | CURRENT-OFFSET | LOG-END-OFFSET | LAG |
|---|---|---|---|---|
| `events.raw` | 0 | 等于末端 | 等于末端 | 0 |
| `events.raw` | 1 | 等于末端 | 等于末端 | 0 |
| `events.raw` | 2 | 等于末端 | 等于末端 | 0 |
| `events.dlq` | 0 | `-` | 0 | — |

**怎么读**：

- **LAG = LOG-END-OFFSET − CURRENT-OFFSET**。`CURRENT-OFFSET` 是这个消费组提交过的书签。三个分区都是 0，说明入库消费者把写进来的事件全写进了 ClickHouse，实时跟上了。
- **`events.dlq` 那行是 `-`**。入库消费者同时订阅了死信 topic，但它一条消息都没有（末端 0），消费组从没在这里提交过书签。这和 ClickHouse 里 `dlq_events` 表 0 行是同一件事的两面。
- **三个分区差不多大**。消息的键是设备 ID，生产者按键算分区；设备多了，三个分区自然摊得差不多。
- **Kafka 里的数远小于 ClickHouse 里的 1 亿条**。灌 88 天历史时，模拟器直接写 ClickHouse，不经 Kafka（造流量那篇讲过两种模式）；经过 Kafka 的只有模拟器实时模式发给采集端点的那部分。
- **想知道现在还留着多少条**：`kafka-get-offsets.sh` 加 `--time -2` 取最早还在的偏移量，用末端减去它。2026-11-02 实测三个分区的最早偏移量都是 `0`：还没有任何段文件被清理（最早的消息没到 2 天保留期，每个分区也没写满 1 GiB），从第一条起都还在。

**先把 derived_at 算一遍**：

```text
sent_at − created_at    = 10:52:24.695 − 10:49:37.464 = 2 分 47.231 秒   （两个都是浏览器时钟，时钟偏差相减抵消）

```

和消息里的 `derived_at` 一位不差。注意它比 `created_at` 晚了 4.322 秒：公式把 `sent_at` 到 `received_at` 之间的差（网络传输加上两边时钟的偏差）全部当成了时钟偏差，两者分不开。这正是事件信封那篇讲的取舍：只信浏览器量出来的时间**差**，不信它报的时间**点**。这条消息在浏览器里攒了约 2 分 47 秒才发出，原因这里不展开。`10:49` UTC 是北京时间 18:49，和实测时间（约 18:50）对得上，这是刚写进来不久的消息。
