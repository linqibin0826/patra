## 像用户一样查找，不看内部实现

Testing Library 的核心主张是：**测试应该和用户使用软件的方式越像越好。** 用户不会去找某个 CSS 类名，也看不到组件里的变量。他们看到的是「一个叫有帮助的按钮」，读屏软件读出的是它的角色和名字。

所以 Patra 前端的约定是：查询优先用 `getByRole`（按角色和名字找）。看真实的测试：

<CodeRef at="patra-portal/tests/components/helpful/HelpfulButton.test.tsx@a81a667d8b65f517028d6e7305893a8d562eee26" lines="52-70" />

```tsx
it("已点时 aria-pressed", () => {
  renderButton({ helpful: true });
  expect(screen.getByRole("button", { name: /^有帮助/ })).toHaveAttribute("aria-pressed", "true");
});
```

它做了三件事：渲染组件、按「角色是按钮、名字以『有帮助』开头」找到那个按钮、断言它的 `aria-pressed` 属性是 true。

这样写的好处，用一个对比看得最清楚：

另外，`getByRole` 用起来还有个副作用：如果某个元素用 `getByRole` 找不到，常常说明它对读屏软件也不友好。测试顺便推着你把界面写得更可访问。

## 造出组件需要的环境

组件不是孤立的：它可能要读路由，要用数据请求的缓存。测试里要替它把这些环境搭好。门户把常用的搭法收进了一个小工具：

<CodeRef at="patra-portal/tests/support/render-with-query.tsx@6ead12db647bcd3e56f651af791d56e418cb79ff" lines="1-35" />

它给组件套上一个「不重试的数据缓存」和一个「不真的跳转的路由桩」。注释里说得很直白：路由桩是因为组件里的 `useRouter()` 需要 App Router 的上下文。

这就是前面讲的**测试替身**，只是换到了前端：真正会发请求或跳转的东西，都换成假的。`HelpfulButton` 的测试开头还有这样一行：

```tsx
vi.mock("@/lib/interaction/helpful-actions", () => ({ setHelpful: vi.fn() }));
```

意思是：把「真的去调后端」的 `setHelpful` 整个换成一个假函数。之后测试可以让它返回成功、失败或者一直不返回，观察按钮的反应。

## 点击、输入与时间

用户的操作用 `userEvent`：`await user.click(按钮)`，它会模拟一整套真实的鼠标事件，比直接触发「点击事件」更接近真人。

前端测试同样会碰到时间：比如「验证邮箱的提示 4 秒后消失」。这个测试没有等 4 秒，而是用假的定时器：

<CodeRef at="patra-portal/tests/components/helpful/HelpfulButton.test.tsx@a81a667d8b65f517028d6e7305893a8d562eee26" lines="120-132" />

开头 `vi.useFakeTimers(…)` 把定时器换成假的，测试里 `vi.advanceTimersByTime(4000)` 一下子拨快 4 秒。道理和后端的「注入 Clock」是一回事：让时间成为测试能控制的输入。

## 不是所有前端代码都有界面

门户里还有很多代码根本不渲染界面，比如处理请求的路由处理器（Route Handler）。它们的测试就没有 jsdom、没有 Testing Library：

<CodeRef at="patra-portal/tests/app/api/auth-me.test.ts@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="1-40" />

文件第一行 `// @vitest-environment node` 告诉 Vitest：这个文件不用假浏览器，用纯 Node 环境。测试里把全局的 `fetch` 换成假函数，模拟网关返回 200、401、503，然后断言这个处理器给浏览器的响应：状态码、响应体、Cookie 有没有被顺延或清除。

<Callout kind="lead">

一句话：组件测试看「用户看到什么」，处理器测试看「对外的响应是什么」。两者都是通过**公开的出入口**检查，不探到里面去。

</Callout>

<Callout kind="warn">

jsdom 没有真实的页面布局：它不知道一个元素有多宽、会不会把下面的按钮挤歪。靠布局才暴露的问题，单元测试看不见，要交给 Playwright 那样的真浏览器测试。

</Callout>
