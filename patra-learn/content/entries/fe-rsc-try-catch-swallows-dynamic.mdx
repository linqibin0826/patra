## 坑

服务端组件的取数函数里，`try/catch` 包住了会调 `cookies()` 或 `headers()` 的代码。Next 在静态渲染阶段用抛错（`DYNAMIC_SERVER_USAGE`）来表示「这里用到了请求信息，切到动态渲染」，这个错被 catch 当成普通失败吞掉，走了降级分支。

单元测试全绿，因为单测里没有静态渲染这一步。v0.12 用户中心那一版写门户页面时，只有跑 `pnpm build` 预渲染时才报出来，报出来的还是「网关不可用」，看上去像一次普通的取数失败。

## 为什么

Next 的不少控制流都是用抛错实现的：静态渲染时用到动态数据、`redirect()`、`notFound()`，都会抛一个框架认识的错误，一路冒泡到框架自己去处理。中间任何一层 `catch` 只要不加区分地吞掉错误，框架就收不到信号。

## 怎么避开

在 `catch` 里第一行先调 `unstable_rethrow(error)`：是框架自己的信号就原样抛出去，不是才走你的错误处理。

<CodeRef at="patra-portal/src/app/u/[username]/page.tsx@6ead12db647bcd3e56f651af791d56e418cb79ff" lines="32-43" />

```tsx
async function readProfessionalSelfOnly(): Promise<boolean> {
  try {
    const privacy = await fetchMyPrivacy();
    return privacy !== "signed-out" && privacy.professionalVisibility === "SELF";
  } catch (error) {
    // 静态渲染时 Next 用抛错切到动态渲染，这个信号必须原样抛出去
    unstable_rethrow(error);
    logRequestError("/patra-identity/me/privacy", error);
    return false;
  }
}
```

改了服务端组件的取数代码，就跑一次 `pnpm build`：这类问题只有构建时的预渲染能暴露。
