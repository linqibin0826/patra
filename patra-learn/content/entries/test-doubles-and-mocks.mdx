## 被测对象身边有一圈依赖

Patra 的用户服务里有一个类，叫 `RemoveAvatarHandler`，负责「移除头像」。它自己不存数据，要靠身边几个帮手：问「当前是谁」、查用户、改资料、删存储里的文件、开事务。

这些帮手在生产里都是「真东西」：连着数据库、连着对象存储。单元测试不想连它们，所以要在测试里把每一个帮手换成假的。

## 三种假对象：桩、Mock、Fake

统称「测试替身」。最常用的三种，区别在**它在测试里扮演什么角色**：

| 替身 | 它做什么 | 测试关心什么 |
|---|---|---|
| **Stub 桩** | 被问到什么就给固定的答案 | 让被测对象有东西可用，不检查它被问了几次 |
| **Mock** | 记录自己被谁、怎样调用过，事后让测试核对 | 「被测对象有没有叫它做某件事」 |
| **Fake** | 一个能真正工作的简化版实现 | 让被测对象按真实方式运行，但不连外面 |

看真实的测试，找出这三种：

<CodeRef at="patra-api/patra-identity/patra-identity-app/src/test/java/dev/patra/identity/app/account/usecase/avatar/RemoveAvatarHandlerTest.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="41-69" />

```java
private final AvatarStoragePort storage = mock(AvatarStoragePort.class);
private final RemoveAvatarHandler handler =
    new RemoveAvatarHandler(
        currentUserPort, users, profiles, storage, TransactionOperations.withoutTransaction());

@BeforeEach
void stubHappyPath() {
  when(currentUserPort.require())
      .thenReturn(CurrentUser.of(USER_ID, 7001L, AccountType.USER, ClientType.WEB));
  // ...
}

@Test
void should_clear_key_then_delete_objects() {
  handler.handle(RemoveAvatarCommand.of());

  InOrder order = inOrder(profiles, storage);
  order.verify(profiles).save(saved.capture());
  order.verify(storage).delete(OLD);
}
```

`mock(X.class)` 是 Mockito（Java 里最常用的造假对象的库）造出一个空壳。之后：

- `when(…).thenReturn(…)` 是在**教它怎么回答**：这是 Stub 的用法。
- `verify(…)`、`inOrder(…)` 是在**核对它被怎样调用过**：这是 Mock 的用法。
- `TransactionOperations.withoutTransaction()` 不靠 Mockito，是一个真能执行回调、只是不开事务的小实现：这是 Fake。

同一个 Mockito 造的对象，既可以当桩，也可以当 Mock，看测试用它的哪一面。

Patra 选的是第二种，`RemoveAvatarHandler` 先在事务里清引用，事务提交后才去删文件，删失败只记一条日志。测试里的 `inOrder(profiles, storage)` 就是把这个顺序**写成了会自动重跑的规矩**：以后有人改了顺序，这个测试立刻变红。

这也是 Mock 的价值：有些行为本来就是「叫了谁、按什么顺序叫」，只能靠记录调用来检查。

## Fake 什么时候比 Mock 好

Mockito 的 Mock 好用，但不是万能的。Patra 在测试工具模块里自己写了一个 Fake：

<CodeRef at="patra-tool/patra-tool-test/src/main/java/dev/patra/tool/test/transaction/RecordingTransactions.java@bacd725884150f0403f66ba921f62151e11f8e7a" lines="14-52" />

它是一个「假事务」：真的执行传进来的回调，同时把「事务开始」「事务结束」写进一个事件列表。其他协作者也往同一个列表里写事件，测试就能断言「远程调用发生在事务开始之前」。

这件事用 Mockito 的 `verify` 很难表达：它要的是**事务边界和别的调用之间的相对先后**，一个自带记录功能的小实现比一堆 `inOrder` 更直白。

<Callout kind="lead" label="怎么挑">

只要答案：用 Stub。要核对「有没有叫它、叫了几次、什么顺序」：用 Mock。需要它「真的像那么回事地工作」，又不想连外面：写一个 Fake。

</Callout>

## 什么时候不该用 Mock

Mock 用多了会出问题，有几种情形要小心：

1. **领域对象一律用真的**。这个测试里的用户、资料，都是用 `User.restore()` 这样的方法造出来的真对象，不是 Mock。Patra 的约定是 Domain 层测试不用任何 Mock：对象本身就是纯 Java，造一个真的比 Mock 更简单，也更接近真实。
2. **别把测试写成实现的复述**。如果测试里 `verify` 了每一次内部调用，生产代码改一下写法（行为没变）测试就红了，这样的测试在拖累重构，不是在保护它。只核对**对外有意义的**调用。
3. **被 Mock 的东西本身行为复杂时，Mock 会骗你**。比如一条数据库查询：Mock 里你告诉它「返回这个结果」，但真实数据库会不会返回这个结果，Mock 完全不知道。这类东西要用真的数据库来测，后面的集成测试那几篇会讲。

<Callout kind="warn">

测试里 Mock 得越多、`verify` 得越细，越可能是在检查「代码是怎么写的」，而不是「代码做了什么」。每写一个 `verify`，先问一句：这个调用，对外有意义吗？

</Callout>
