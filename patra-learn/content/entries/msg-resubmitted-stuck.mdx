## 坑

<Callout kind="lead" label="坑在哪">

补投先把登记行标成 RESUBMITTED、再去执行。进程崩在这两步之间，这一行就永远停在 RESUBMITTED，没有人会再补投它。

</Callout>

## 补投时，一行登记怎么走

## 为什么会卡住

Modulith 领走一行时执行的是这样一条 SQL（2.1.2 的 JDBC 实现）：

```sql
UPDATE event_publication
SET STATUS = 'RESUBMITTED',
    COMPLETION_ATTEMPTS = COMPLETION_ATTEMPTS + 1,
    LAST_RESUBMISSION_DATE = ?
WHERE ID = ?
  AND COMPLETION_DATE IS NULL
  AND (STATUS IS NULL OR STATUS != 'RESUBMITTED')
```

最后一个条件是为了多实例：两台机器同时补投，同一行只会被一边领走，另一边的 UPDATE 改不到行，就跳过。代价是它分不清「别人正在处理」和「处理它的进程已经死了」，两种情况都跳过。

Modulith 其实给这种情况准备了「过期检查」：配了 `spring.modulith.events.staleness.resubmitted`，就定期把停留太久的行改成 FAILED。可这个检查是靠 Spring 的定时任务机制跑的（它实现的是 `SchedulingConfigurer`），应用要开 `@EnableScheduling` 它才会动。Patra 的定时任务全交给 XXL-Job，没开 `@EnableScheduling`，配了也不会执行。

<Callout kind="insight" label="怎么认出它">

表里有 `status = 'RESUBMITTED'` 的行，`last_resubmission_date` 停在很久以前，`completion_attempts` 也不再增加。日志里没有任何报错：Modulith 只是每轮都安静地跳过它。

</Callout>

## 怎么避开

既然定时检查不会自己跑，Patra 就在每分钟的补投任务里先把检查做一遍，再补投：

<CodeRef at="patra-tool/patra-tool-events/src/main/java/dev/patra/tool/events/resubmit/EventPublicationResubmitter.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="54-76" />

```java
public int resubmit() {
  Instant now = clock.instant();
  Instant cutoff = now.minus(minAge);
  Instant inFlightCutoff = now.minus(STALE_AFTER);
  registry.markStalePublicationsFailed(
      status -> status == Status.RESUBMITTED ? STALE_AFTER : Staleness.UNCONFIGURED_DURATION);
  AtomicInteger count = new AtomicInteger();
  publications.resubmitIncompletePublications(
      publication -> {
        boolean due =
            publication.getPublicationDate().isBefore(cutoff)
                && !inFlight(publication, inFlightCutoff);
        // ……计数、尝试 10 次以上打 WARN
        return due;
      });
  // ……
}
```

两步：

1. **解卡**：调 Modulith 自己的 `markStalePublicationsFailed`，只看 RESUBMITTED 一种状态，按最后一次补投时间算，停了 10 分钟以上的改回 FAILED。这一轮接着就能把它领走。
2. **补投时跳过还在发的**：只领发布超过 1 分钟的行，并且跳过 10 分钟内还有动静的 PROCESSING 行。Modulith 的「未完成」查询不排除 PROCESSING，不加这一条，broker 卡住时每一轮都会把同一行再排一份，broker 恢复时一下冲出好几份重复消息。

<Callout kind="warn">

10 分钟要远长于一次发送最多花的时间（连接超时 5 秒加等确认 5 秒），否则正常发送中的行会被误判成卡住、被提前重发。反过来，阈值也不能太长：卡住的行要等它过去才会被补上。

</Callout>
