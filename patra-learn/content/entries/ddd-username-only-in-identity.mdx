## 背景：用户名可以改

v0.12 用户中心那一版给每个账号加了用户名，主页地址是 `/u/用户名`。产品上定了「可以改名」：改名后有 30 天冷却，旧名保留 90 天，访问旧地址会跳到新地址（v0.12 release spec 决策 L）。

可以改名，就会冒出一个担心：用户名要是被复制进很多张表（评论作者、收藏夹主人、搜索索引……），每次改名都得把这些地方一起回刷，漏掉一处，页面上就显示旧名。

拍板时（2026-10-21）核对过现状：整个仓库只有 identity 的建表脚本里有用户名列，审计字段、网关签给下游的身份断言、Redis 里的会话都只带用户 ID。这时候定规矩，没有任何历史数据要迁。

允许改名的产品（GitHub、Instagram、X、微信号）共同的做法就是第三种：用户名只是一个路由键，关联关系挂在不变的用户 ID 上。

## 选择：用户名只是路由键

<Callout kind="lead" label="选了什么">

用户名只存在 identity 的两张表：`idn_user`（当前用户名）和 `idn_user_former_username`（改名前用过的名字，用来做跳转和防抢注）。其他表、搜索索引、读模型引用用户，一律存 `user_id`，展示时按 ID 现读当前名。

</Callout>

这条规则落到几个具体地方：

- **@ 提及**：正文里存的是用户 ID 标记 `<@用户ID>`，不是 `@用户名`。用户改名后，历史评论里的 @ 自动显示新名字。
- **对象存储**：头像等文件的对象键按用户 ID 命名。
- **只有 URL 路由用用户名**：`/u/用户名` 是给人看、给人分享的地址。

## 把规则写进构建：R6

规则只写在文档里，迟早有人在新表里顺手加一个 `username` 列。所以这条规则做成了构建检查 `checkMigrationColumns`（Patra 构建规则的第 6 条，简称 R6），挂在 `./gradlew check` 上：扫描每个服务的 Flyway 迁移脚本，看到 `CREATE TABLE` 或 `ALTER TABLE ... ADD` / `RENAME ... TO` 里出现了 `username` 或 `user_name` 列，而表不是 identity 那两张，构建就失败。

<CodeRef at="build-logic/src/main/kotlin/MigrationColumnRules.kt@af8cd13c3ec367ccba78615b72e6ff19535cef90" lines="1-23" />

```kotlin
object MigrationColumnRules {
    private val FORBIDDEN_COLUMNS = setOf("username", "user_name")
    private val ALLOWED_TABLES = setOf("idn_user", "idn_user_former_username")
    // ……把 SQL 切成词，逐条语句看建表与改表
}
```

失败时的提示直接写出了规则本身：用户名只存 identity 的两张表，其他表引用用户一律存 user_id，展示时按 ID 现读当前名。

## 代价

<Callout kind="cost">

- 每次展示用户名都要按 ID 向 identity 取一次。列表页按一页里出现的 ID 批量取，不是一条一次。
- identity 不可用时，依赖它取名字的地方跟着受影响。v0.16 的提醒邮件就是在发送那一刻现查收件人信息，identity 挂了，邮件推迟到重试时再发。
- R6 只认 `username`、`user_name` 这两个列名，也只扫 Flyway 脚本。换个列名冗余用户名、或者冗余进搜索索引，它拦不住，靠的仍是写的人记得这条规则。

</Callout>
