## 背景：共享区成了杂物间

v0.10 之前，后端的共享代码分在 `linqibin-commons`、`patra-starters`、`patra-common` 几处，按「通用 / Patra 专属」划分。2026-10-13 到 10-15 盘点出的事实：

- 共享区 22 个模块、约 4 万行，其中 1.65 万行只有 ingest 一个服务在用。
- 8 条依赖声明了，源码从没引用过；一个 Redisson 的 starter 没有任何使用方。
- 自动配置的包名有 5 种写法、配置前缀 3 种，14 个 starter 只有 5 个有契约测试。
- 6 个服务都扫描整个旧包根，9 个工具 bean 靠扫描进容器，其中 6 个又被自动配置注册了一遍。
- 边界检查 `checkBoundary` 早就写好了，却一直没挂进 `check`；domain 层的纯净性用的是黑名单。

「这段代码算通用还是算专属」本身就没有答案，`commons-core` 就是这样慢慢成了杂物间。

## 决策 A：按什么分

/>

<Callout kind="lead" label="选了什么">

技术能力进 `patra-tool/`，一个能力一个模块：`core`（纯 Java 的 DDD 基类与错误类型）、`cqrs`、`web`、`jpa`、`batch`、`http-client`、`object-storage`、`observability`、`security`、`openapi`、`launch`、`test`，共 12 个。引入一个模块，只带来它那一种能力。业务代码按归属放：某服务的对外契约放该服务；只有一个服务用的留在该服务。说不出属于哪种能力的零散工具类不进 `patra-tool`，按业务代码的规则放。

</Callout>

同时立了统一写法：每个模块一个 `autoconfigure` 包、一份 imports 文件；配置类是 record，前缀 `patra.<能力>`；总开关 `patra.<能力>.enabled`；配一个同名的 `ApplicationContextRunner` 契约测试。

## 决策 C：规则写进构建

否决「规则写在文档里」的理由就是盘点出的事实：`checkBoundary` 写了半年没挂进 `check`，8 条死依赖没人发现。所以五条规则全部挂在 `./gradlew check` 上：

| 规则 | 守什么 |
|---|---|
| R1 | 工具模块不依赖 `patra-api/` 下的任何业务模块 |
| R2 | 工具之间的硬依赖（`api` / `implementation` / `runtimeOnly`）只能指向 core，白名单仅 security → web；其余协作只能 `compileOnly` 加 `@ConditionalOnClass` |
| R3 | domain 层的编译类路径用白名单 |
| R4 | 自动配置写法：和 imports 文件双向一致、在 `autoconfigure` 包里、`public final`、有同名契约测试、不许用 `@Component` 一类注解、不许裸数字 `@Order` |
| R5 | 声明了的模块依赖必须真的被 import |

<CodeRef at="build-logic/src/main/kotlin/ToolDependencyRules.kt@cfec9c9f30270dcf03f5cd7b6e54a0cd3b59296b" lines="5-40" />

```kotlin
/// 工具间允许的硬依赖白名单：security 要用 web 的 ProblemDetail 适配器。
val HARD_WHITELIST: Map<String, Set<String>> = mapOf(
    ":patra-tool:patra-tool-security" to setOf(":patra-tool:patra-tool-web"),
)

/// R2：工具间硬依赖只允许指向 core（白名单例外）；compileOnly 任意；……
fun r2Violations(project: String, declared: List<Declared>): List<String> {
    // ……
    dependency.configuration == "compileOnly" -> true
    dependency.configuration in HARD_CONFIGURATIONS -> target == CORE || target in whitelist
    // ……
}
```

规则都写成纯函数，用 JUnit 测；收尾验收时每条规则都故意违反过一次（比如给 web 加一条指向 catalog 的依赖、删掉一个契约测试），`check` 都失败并报出规则名，撤销后恢复通过。

## 代价与后来

<Callout kind="cost">

- 一次换完：改了 2,278 个文件，其中 1,983 个 Java 文件换了包根，只能放在一个版本、一个 PR 里合并，中间状态没法单独上线。
- 工具模块之间多了一层「条件生效」：`compileOnly` 加 `@ConditionalOnClass` 写法比直接依赖绕。收尾核对时还查出四处依赖 `MeterRegistry` 的组件因为自动配置顺序不对，从来没生效过，补上顺序声明才修好。

</Callout>

这套分法后来经受了两次变动：删除 ingest 时（v0.16 通知中心开工前），只剩 catalog 在用的 `patra-common` 并进了 catalog，这个模块不复存在；v0.16 又按同样的规则新增了 `patra-tool-events`（跨服务事件），工具模块变成 13 个。新模块照样只硬依赖 core，规则一条没改。
