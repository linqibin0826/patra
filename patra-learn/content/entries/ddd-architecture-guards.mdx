## 约定写下来，不如变成会失败的检查

上一篇看到，模块的依赖写在构建文件里，没声明就看不见。这是第一道防线。但还有很多事构建文件管不到：

- 在已经声明的依赖里，domain 能不能引入 Spring？
- 一个类能不能放进别的子域不公开的包里？
- 一个命令 Handler 能不能标 `@Transactional`？

这些都有专门的检查，分两种：

| 守卫 | 在哪 | 管什么 | 失败时机 |
|---|---|---|---|
| 构建规则（R1～R6） | `build-logic/` 的约定插件 | 模块依赖、域层类路径、迁移脚本 | `./gradlew check` 的构建阶段 |
| ArchUnit 架构测试 | `patra-tool-test` 的规则 + 各服务 boot 里的测试 | 类与包之间的关系 | `./gradlew check` 的测试阶段 |

R 开头的其他几条同样是构建规则：

| 规则 | 管什么 |
|---|---|
| R1、R2 | 工具模块不许依赖业务模块；工具模块之间只许依赖核心库 |
| R3 | 领域层类路径白名单（上面这条） |
| R4 | 自动配置的写法 |
| R5 | 声明了的 project 依赖必须真的被 import，不留没用的依赖 |
| R6 | Flyway 迁移脚本里，用户名列只许出现在 identity 的两张表 |

R6 很有意思，它守的是数据归属，而不是代码分层：用户名只存在 identity 里，别的服务只存用户 ID。这条约定被写成检查，扫描迁移脚本里的建表和改表语句。

## ArchUnit：检查类与包的关系

构建规则看的是模块，看不到一个类 import 了谁。这件事交给 ArchUnit，它能把已编译的类读进来，对包和依赖提问。

层依赖规则的核心几行：

<CodeRef at="patra-tool/patra-tool-test/src/main/java/dev/patra/tool/test/archunit/HexagonalArchitectureRules.java@cfec9c9f30270dcf03f5cd7b6e54a0cd3b59296b" lines="120-141" />

这段话的意思是：领域层不能访问任何别的层；应用层只能访问领域层；基础设施层只能访问领域层；适配器层只能访问应用层和领域层。除了层依赖，同一个类里还有事务规则：`@Transactional` 只能出现在 app 层（infra 层只放行 MANDATORY 守卫），命令 Handler 不得标 `@Transactional`。

## 子域边界也是规则

分包规范（子域优先）同样被 ArchUnit 守着，规则在 `SubdomainArchitectureRules`：层下面只能是已声明的子域，跨子域只能用对方的公开包，跨子域的依赖必须事先声明。

<CodeRef at="patra-tool/patra-tool-test/src/main/java/dev/patra/tool/test/archunit/SubdomainArchitectureRules.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="1-45" />

上面测试里的这两行就是「事先声明」：

```java
.allowingDependency("reaction", "discussion")
.allowingDependency("reaction", "post")
```

有帮助子域（reaction）要用讨论和投稿经验，就得明明白白写出来。没写的边，规则一跑就红。

<Callout kind="cost">

守卫有代价。规则越多，新人写第一行代码时撞墙的次数越多；新增子域、新增跨子域依赖都要先改架构测试。换来的是边界不再依赖有人记得去检查：每次 check 都会把所有规则从头跑一遍。

</Callout>
