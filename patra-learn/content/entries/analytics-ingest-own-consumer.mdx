## 背景：事件在 Kafka 里，要批量进 ClickHouse

v0.18 的行为数据管线里，采集端点把校验、富化过的事件写进 Kafka 的 `events.raw`，坏事件写进 `events.dlq`。下一步要有人把它们读出来，写进 ClickHouse 的明细表 `events`。

这一步有几条硬约束：

- **只能批量写**。ClickHouse 每写一次，就在每张受影响的表上各多一个数据片段（part）；写得太碎，后台合并跟不上，会报 `TOO_MANY_PARTS`。一条一写是不行的。
- **不能丢**。ClickHouse 停机或变慢时，事件要能在 Kafka 里等着（`events.raw` 保留 2 天），恢复后补齐。
- **出问题要看得见**。卡在哪、落后多少、哪条坏数据被拒，要能在指标和日志里查到。
- **机器小**。所有服务跑在作者家里的一台 mini 上，内存很紧。

## 选择

<Callout kind="lead" label="选了什么">

自己写批量消费者。决定性的理由是**看得见、管得住**：批次多大、失败怎么重试、坏消息去哪、落后多少，都在应用代码里，有指标、有测试；Connect 虽然能做到恰好一次，但 mini 养不起一套额外的 JVM 集群。

</Callout>

### 「恰好一次」是怎么做到的：只讲原理，不部署

Kafka Connect 的恰好一次，核心是把「写入」和「记下这批的偏移量」做成同一件事：ClickHouse 收到一批时，先看这段偏移量范围是不是已经写过，写过就跳过。

Patra 的批次去重令牌是同一个思路的轻量版：令牌就是这批的偏移量范围，ClickHouse 在去重窗口内认出同一个令牌，就丢弃这一批。区别有两条：窗口有限（记最近 1,000 次写入）；崩溃后重新拉取时，批次边界可能和上次不一样，令牌就对不上了。所以 Patra 是**至少一次 + 去重**，不是恰好一次，重复靠下游两道去重兜底（见「批量写入与块令牌去重」那篇）。

逐条看它们为什么这样设：

| 设置 | 值 | 为什么 |
|---|---|---|
| `max.poll.records` | 50,000 | 一批最多 5 万条 |
| `fetch.min.bytes` / `fetch.max.wait.ms` | 1 MiB / 1000 ms | broker 攒够 1 MiB 或等满 1 秒才返回：流量小时也是每秒一批，不会一条一批 |
| `max.partition.fetch.bytes` / `fetch.max.bytes` | 16 MiB / 64 MiB | 默认每个分区一次只拉 1 MiB，拉不到 5 万条 |
| `max.poll.interval.ms` | 600,000 | 一批的写入（包括被拒时的二分重写）要在 10 分钟内完成，否则消费组认为它死了、触发重平衡 |
| `enable.auto.commit` + `AckMode.MANUAL` | 关 + 手动 | 写成功才提交；写失败不提交，下次重来 |
| `auto.offset.reset` | `earliest` | 新的消费组从头读，Kafka 里已有的 2 天不丢 |
| 并发 | 1 | 单实例，`events.raw` 的 3 个分区由一个线程轮流拉 |
| 错误处理 | 指数退避，1 秒起、上限 30 秒、不限次数 | ClickHouse 恢复前，消费就停在原地等 |

「写成才提交」落在监听方法里，就是先交给入库用例，用例正常返回才 `acknowledge()`：

<CodeRef at="patra-api/patra-analytics/patra-analytics-adapter/src/main/java/dev/patra/analytics/adapter/ingest/mq/EventIngestListener.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="68-80" />

```java
  private void ingest(
      EventStream stream, List<ConsumerRecord<String, String>> records, Acknowledgment ack) {
    if (!records.isEmpty()) {
      String topicId = topicIds.topicId(records.getFirst().topic());
      commandBus.handle(
          IngestBatchCommand.of(
              stream,
              records.stream()
                  .map(r -> IngestRecord.of(topicId, r.partition(), r.offset(), r.value()))
                  .toList()));
    }
    ack.acknowledge();
  }
```

写入抛异常时，`acknowledge()` 根本走不到；错误处理器按退避用内存里的同一批重新调用这个方法。

### 消费滞后自己算

「落后多少」是入库最重要的指标。Kafka 客户端自带一个 `records-lag-max`，但它是在拉取时采样的：ClickHouse 宕机、消费停住不拉取的那段时间，这个值变成 NaN，正好在最需要的时候看不到。

所以 Patra 每 30 秒用 AdminClient 直接对比「消费组已提交的偏移量」和「分区末端的偏移量」：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/java/dev/patra/analytics/infra/ingest/topic/KafkaIngestLagGauge.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="87-90" />

```java
      for (TopicPartition partition : partitions) {
        OffsetAndMetadata done = committed.get(partition);
        long position = done != null ? done.offset() : earliest.getOrDefault(partition, 0L);
        long lag = Math.max(0, latest.getOrDefault(partition, position) - position);
```

已提交偏移量只在写成后才前进，所以消费停住时，末端照样往前走，差值就一直涨，面板上一眼能看出来。

## 代价

<Callout kind="cost">

- **代码要自己写、自己测**：令牌、二分定位坏行、退避重试、滞后指标，另外两种做法里，这部分活由 ClickHouse 或 Connect 插件承担。
- **只有至少一次**：崩在写成和提交之间，会写出部分重复，必须有下游去重兜底：明细表 `ReplacingMergeTree` 按 `event_id` 去重、数条数一律 `uniqExact(event_id)`、汇总表只存 `max` / `min`。
- **单实例单线程**：`events.raw` 的 3 个分区由一个线程轮流拉、一次写一批，入库的吞吐上限就由这一个线程决定。

</Callout>
