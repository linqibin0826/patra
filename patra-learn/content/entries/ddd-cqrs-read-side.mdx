## 写和读要的东西不一样

对同一条评论：

- **写的时候**，要守规则：只有作者能改、已删除不能再改、改正文要加版本。这些都在聚合里，所以写入要先把完整的聚合读出来、锁住、检查、再写回。
- **读的时候**，要的是一个页面能直接用的结果：评论本身，加上被回复者是谁、有没有回复、有帮助数是多少，可能还要分页、排序。这些字段分散在好几张表里。

用同一个模型兼顾两头，聚合就会变得又胖又乱。所以 Patra 把两条路分开：

<Callout kind="lead">

写走命令：Controller 到命令总线，再到 Handler、聚合、仓库。读走查询：Controller 到查询服务，再到读端口。读不经过聚合，也不经过命令总线。

</Callout>

这个做法叫 **CQRS**（命令查询职责分离）。Patra 里它不意味着两套数据库，而是同一个库、两条代码路径。

| QueryService | 无接口 | `app.{子域}.usecase.query` |

## 读端的自由度：可以关联别的子域

「有帮助数」在 reaction 子域的表里。讨论的读适配器直接用 SQL 读 `reaction` 的表，而不是调 reaction 子域的 Java 代码。

<Callout kind="insight">

这是有意为之。如果 discussion 的 Java 代码依赖 reaction，而 reaction 又要读 discussion（取评论），两个子域就成环了。读适配器可以用 SQL 读同一个库里的任何表，但不 import 对方的实体类，这条规则写在分包规范里，是读写分开带来的自由。

</Callout>

## 查询服务不一定经过读端口

再看一个例子，`SessionQueryService`（当前用户的登录设备列表）：

<CodeRef at="patra-api/patra-identity/patra-identity-app/src/main/java/dev/patra/identity/app/session/usecase/query/SessionQueryService.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="25-60" />

它的注释写得很明白：只读，不经命令总线，没有事务。它的数据来自 Redis 里的会话和数据库里的登录记录，用的是已有的端口，没有再单独写一个读端口。读端的形状取决于数据在哪、要什么，没有统一模板。
