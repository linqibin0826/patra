<Callout kind="lead">

CI 防的是「代码坏了」。可设施自己坏了呢：部署机上的 runner 悄悄掉线、磁盘悄悄塞满、某个容器悄悄不健康？这些事没有任何一次推送会触发检查，它们只会安静地烂下去。

Patra 的答案朴素到近乎笨：**每天定点巡一圈**。

</Callout>

## 闹钟怎么定：cron、UTC 与北京时间

GitHub Actions 的定时触发器叫 `schedule`，时间用 cron 表达式写。巡检的配置是：

<CodeRef at=".github/workflows/runner-watchdog.yml@53ec4388b912746d0fa15961b512897279bd4ae2" lines="15-18" />

```yaml
on:
  schedule:
    - cron: '0 23 * * *'   # 每日 UTC 23:00（北京 07:00）
  workflow_dispatch:
```

cron 的五个位置从左到右是「分 时 日 月 星期」。`0 23 * * *` 就是每天 23 点 0 分。

这里有个所有人都会踩一次的坑：时间按 UTC 算。想在北京时间早上 7 点跑，要把北京时间**减** 8 小时，得到前一天的 UTC 23:00。把换算结果写在行尾的注释里，是防半年后的自己看不懂。

配置里还留了 `workflow_dispatch`：刚改完设施想立刻验证，或者怀疑哪里不对，不用等明早七点，手动触发就行：

```bash
gh workflow run runner-watchdog.yml
```

关键在于第一个任务**不在部署机上跑**。如果所有检查都放在部署机上，那么部署机整个挂掉时，这些检查根本没有人认领，不会失败，不会告警，只有沉默。

为什么要有 `needs` 这一层？runner 离线时，把 canary 派给一台不在线的机器，它会一直显示排队中，比红灯更迷惑。让它依赖前一个任务，离线时直接跳过。

## 查岗怎么查：一条接口

云端那个任务只做一件事：

<CodeRef at=".github/workflows/runner-watchdog.yml@53ec4388b912746d0fa15961b512897279bd4ae2" lines="26-34" />

它调用 GitHub 的接口列出仓库里注册过的 runner，挑出名字叫 `macmini` 的，读它的状态。`online` 放行，其他情况当场失败。报错文案分两种：离线是机器掉线了；查不到则是注册记录已经被平台删除，需要重装（另一篇专门讲）。

这个接口需要凭据。工作流自带的 `GITHUB_TOKEN` 没有权限列出自托管 runner，所以用了一把 fine-grained 的个人访问令牌，保存在仓库的 secrets 里，名字是 `RUNNER_ADMIN_TOKEN`。它是最小权限的写法：只授权给这一个仓库，只勾一项只读权限。名字里虽有 Admin，拿到它也只能看 runner 在不在，改不了任何东西。

## 四项体检

canary 在部署机上依次做四项检查，每一项对着一种「悄悄坏」的死法：

<CodeRef at=".github/workflows/runner-watchdog.yml@53ec4388b912746d0fa15961b512897279bd4ae2" lines="36-65" />

| 检查 | 防的是 |
|---|---|
| Docker 引擎还活着 | 引擎停了，整台机器上的容器都没法管 |
| runner 版本没有落后 | 自更新被关掉了，GitHub 要求新版发布 30 天内手动升级，否则停止派任务 |
| 磁盘余量不少于 20G | 构建缓存、镜像、日志无声地吃磁盘，满盘时各种操作会以奇怪的姿势失败 |
| 没有 unhealthy 的容器 | 容器自查报告不健康，名单直接打在报错里 |

每项失败的提示文案都写明了该做什么，告警即行动指南。

版本检查用的是严格不等号：最新版一出就告警，不等 30 天的倒计时走完。它不是事故，只是行动信号：找个空闲时段重跑一遍安装脚本就升级完了。

## 巡检失败了，谁来知道

没有单独的通知通道。巡检失败时，GitHub 原生的通知会发邮件、推 App，和你收到构建失败的通知是一回事。每天早上七点跑完，手机没响，就是全绿。

最后一个已知的边界：GitHub 对公开仓库有一条规则，仓库长期没有活动时，定时任务会被平台自动停用。项目彻底搁置时，守夜的任务自己也会睡着。恢复也简单，回来后到 Actions 页面手动启用一下即可。
