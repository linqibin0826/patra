## 覆盖率是怎么算的

覆盖率工具（Patra 后端用的是 JaCoCo）在测试运行时盯着代码，记下：哪些行执行过、哪些分支走过。测完给出一个比例。

最常见的两种：

- **行覆盖率**：被执行过的代码行，占全部可执行代码行的比例。
- **分支覆盖率**：`if`、三元表达式这些「岔路口」里，两边的路都走过没有。

两者会不一样。拿 Patra 导出文件名的这个方法来看：

<CodeRef at="patra-api/patra-catalog/patra-catalog-adapter/src/main/java/dev/patra/catalog/adapter/portal/rest/ExportFileNames.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="29-38" />

方法里有两个岔路口：`name == null ? "" : …` 和 `if (cleaned.isEmpty())`，一共 4 个分支。它有三个测试（TDD 那一篇里看过）：正常名字、含非法字符的名字、空名字。自己开关试试，看覆盖率怎么变（只统计 `of` 这个方法）：

所以光看行覆盖率容易被糊弄：一行里有三元表达式，哪怕只走了一边，这一行也算「覆盖」。分支覆盖率更严格，更能暴露没测到的路。

## 覆盖率不会告诉你的事

覆盖率只检查「执行过」。下面这样的测试，就能把一个方法的覆盖率拉满：

```java
@Test
void just_runs() {
  ExportFileNames.of("///", ExportFormat.CSV, DATE);   // 执行了，但一个断言都没有
}
```

方法跑到了，覆盖率涨了，可如果 `of` 返回了一个错得离谱的字符串，这个测试照样是绿的。这是一个为了说明而写的反例，不是仓库里的测试。

<Callout kind="warn">

覆盖率是**下限的提醒**，不是质量的证明。低覆盖率说明有一片代码没人测；高覆盖率不说明测得对。拿它当目标去追，会鼓励大家写出没有断言、只为涨数字的测试。

</Callout>

有一种叫「变异测试」的做法，专门检查断言够不够：它故意把代码改坏一点（比如把 `>` 改成 `>=`），再看测试会不会变红。这里只作了解，Patra 目前没有使用。

## Patra 里的三件东西

Patra 里和覆盖率有关的东西，有三处，彼此**并不一致**，看清楚它们各自管什么：

**一、目标线**。后端的单元测试约定里写了期望：行覆盖率 80%，分支覆盖率 70%，关键业务逻辑 100%，DTO 的取值方法、配置类、启动类除外。

<CodeRef at=".claude/rules/testing/unit-test.md@5073ab1358404ecd989e722373cd9f7edafe238b" lines="1-30" />

**二、构建里的检查任务**。统一的构建配置里生成 JaCoCo 报告，也配了一个「覆盖率验证」任务，最低线是 0.70。但文件里明确写了：这个任务**没有挂到 `check` 上**，也就是说，即使低于它，构建也不会失败。

<CodeRef at="build-logic/src/main/kotlin/patra.java-base.gradle.kts@b6e01875bb5692356021c8a19562f557f319fc54" lines="47-76" />

**三、CI 里的汇总与上传**。后端各模块在 CI 里跑测试时，会上传 JaCoCo 的执行数据；只有「全量」运行才汇总（每晚的定时运行，或者改了构建配置、CI 流程这类牵动全仓的东西），把单元测试与集成测试的报告上传到 Codecov。这一步的上传失败会让 CI 失败；CI 里这一步只管上传成没成功，不比较数字。

<CodeRef at=".github/workflows/ci.yml@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="265-293" />

把三者放在一起看：80% 是目标，0.70 是一个没有接线的检查，Codecov 是一个展示数字的地方。**Patra 目前并不靠覆盖率数字拦合并。** 构建配置的注释写明这是一项决定：v0.3 不设阈值门禁。

<Callout kind="insight">

要设覆盖率门禁，常见做法是只卡「本次改动的代码」的覆盖率，而不是全仓的总数：全仓的数字变化太慢，卡不住具体的一次提交。

</Callout>
