## 主键：每一行的身份证号

上一篇说过，表里一行是一条记录。要在几百万行里准确找到「那一行」，就需要一列**永远不重复、永远有值**的东西来认人，这一列（或几列）叫**主键**。

数据库会替你守两条规矩：主键不能为空，也不能重复。插入一个已经存在的主键，数据库直接拒绝。

Patra 的用户表 `idn_user` 的主键就是 `id`：

<CodeRef at="patra-api/patra-identity/patra-identity-infra/src/main/resources/db/migration/account/V20261116110100__create_account.sql@1c14ff5ba53ff774c52a9ead82653c5097586a53" lines="7-26" />

```sql
CREATE TABLE idn_user
(
    id                  BIGINT          NOT NULL,
    ...
    PRIMARY KEY (id),
```

Patra 每张表都有这样一列 `id` 当主键（按用户分区的大表，主键前面还要带上分区用的 `user_id`），值是**雪花 ID**：一种在多台机器上各自生成、也不会撞号的编号方式，由应用在插入前生成好。用户表的行永久保留（表注释写着「行永久保留，注销后匿名化」），所以一个编号用过就不会再发给别人，哪怕那个用户注销了。

<Callout kind="analogy">

主键像身份证号，不是姓名。姓名可以重名、可以改名，身份证号一个人只有一个，别的系统只要记着这串号就能找到他。

</Callout>

## 外键：用「别的表的主键」表示「属于谁」

用户有一份个人资料（昵称、简介、职业）。这些放在另一张表 `idn_user_profile` 里。资料表怎么说明「这份资料是谁的」？在资料表里加一列 `user_id`，里面写用户表的主键值。这一列就是**外键**：它的值必须是另一张表里真实存在的主键。

这层关系可以**声明**给数据库，叫外键约束。标准 SQL 的写法是这样（示意，不是 Patra 的代码）：

```sql
CREATE TABLE user_profile (
    id      BIGINT NOT NULL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES app_user (id),
    ...
);
```

`REFERENCES app_user (id)` 就是外键：`user_id` 引用 `app_user` 的 `id`。声明之后，数据库会替你挡住两件事：

- 往资料表插一行 `user_id = 999`，而用户表里根本没有 999 号用户，会被拒绝；
- 删除一个还有资料指向它的用户，也会被拒绝（除非你另外声明了级联删除）。

Patra 选择不声明外键。v0.21 统一库表规范时定下「全项目不建外键，引用关系由应用保证」，identity 原来的 8 条外键、interaction 原来的 5 条都删掉了。资料表的 `user_id` 照样存用户表的主键，只是数据库不再替你检查，脚本开头写明了这一点：

<CodeRef at="patra-api/patra-identity/patra-identity-infra/src/main/resources/db/migration/account/V20261116110100__create_account.sql@1c14ff5ba53ff774c52a9ead82653c5097586a53" lines="1-2" />

```sql
-- account 子域：用户、密码凭据、资料、链接、研究兴趣、曾用用户名、邮件令牌、第三方账号
-- 引用用户的列都是 user_id，引用关系由应用保证，不建外键
```

迁移脚本里要是写了 `REFERENCES`，构建检查会直接失败。不建外键的取舍，放在本篇后面的提示框里讲。

## 一对一、一对多：差别只在那一列唯一不唯一

同样是「资料表有一列 `user_id` 指向用户表」，可以表达两种关系，区别在于这一列允许不允许重复。

- **一对一**：一个用户最多一份资料。给 `user_id` 建一个唯一索引，同一个用户就插不进第二份。

<CodeRef at="patra-api/patra-identity/patra-identity-infra/src/main/resources/db/migration/account/V20261116110100__create_account.sql@1c14ff5ba53ff774c52a9ead82653c5097586a53" lines="146" />

```sql
CREATE UNIQUE INDEX uk_idn_user_profile_user ON idn_user_profile (user_id);
```

- **一对多**：一个用户可以有好几条个人链接（博客、主页……）。链接表 `idn_user_profile_link` 里 `user_id` 不唯一，同一个用户能有多行；Patra 另外规定每人最多 5 条，用 `position` 列编号 0 到 4。

<CodeRef at="patra-api/patra-identity/patra-identity-infra/src/main/resources/db/migration/account/V20261116110100__create_account.sql@1c14ff5ba53ff774c52a9ead82653c5097586a53" lines="184-189" />

```sql
    CONSTRAINT ck_idn_user_profile_link_position CHECK (position BETWEEN 0 AND 4),
    ...
);
CREATE UNIQUE INDEX uk_idn_user_profile_link_position ON idn_user_profile_link (user_id, position);
```

注意最后一行：唯一的是 `(user_id, position)` 这个**组合**，不是 `user_id` 一列。同一个用户可以有位置 0、1、2，但不能有两条位置 0。

## 多对多：必须多一张中间表

一篇文献有好几位作者，一位作者也写过好几篇文献。这是**多对多**。如果硬把它塞进某一张表：文献表里放「作者列表」，一格里要装多个值，查「某位作者写过哪些文献」就得拆开字符串去找，数据库帮不上忙。

办法是多建一张**中间表**，一行代表「某篇文献有某位作者」。Patra 的 `cat_publication_author` 就是这样：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/resources/db/migration/publication/V20261116120100__create_publication.sql@1c14ff5ba53ff774c52a9ead82653c5097586a53" lines="613-634" />

```sql
CREATE TABLE cat_publication_author
(
    id BIGINT NOT NULL PRIMARY KEY,
    publication_id BIGINT NOT NULL,
    author_id BIGINT NULL,
    author_order INTEGER NOT NULL DEFAULT 1,
    display_name VARCHAR(200) NOT NULL,
    -- 省略若干列
    is_first_author BOOLEAN NOT NULL DEFAULT false,
    is_corresponding_author BOOLEAN NOT NULL DEFAULT false,
    ...
);
CREATE UNIQUE INDEX uk_cat_publication_author_order ON cat_publication_author (publication_id, author_order);
```

三点值得看：

- 中间表有两个指向别处的列：`publication_id`（哪篇文献）和 `author_id`（哪位作者）。多对多就这样拆成了两个一对多。
- 中间表**自己也有信息**：这位作者在这篇里排第几（`author_order`）、是不是第一作者。这类信息既不属于文献、也不属于作者，只属于「这一对」，所以正好放中间表。
- `author_id` 允许为空（`NULL`）：Patra 只在能确定是哪位已知作者时才填，其余作者只存名字。这是个设计取舍，不是中间表的必备写法。

再往下一层，作者在这篇文献里隶属哪些机构，又是一张中间表 `cat_publication_author_affiliation`，它的 `publication_author_id` 指向上面这张。于是形成一条链：文献，作者条目，机构。

<Callout kind="warn">

上面这些「指向」，建表脚本里都没有写外键。关系是由代码保证的，数据库只保存列。外键不是必须声明的：它带来「挡住脏数据」的好处，也带来每次写入多一次检查、删除要顾及引用的成本。Patra 从 v0.21 起全项目不建外键，原来交给外键的事改由代码在事务里做。例如评论的修订记录原来靠级联删除跟着评论一起删，现在是删评论时在同一个事务里显式删掉它的修订。

</Callout>
