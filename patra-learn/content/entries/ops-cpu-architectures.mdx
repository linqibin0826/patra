## CPU 说的不是同一种“语言”

CPU 只认自己那套指令。目前最常见的两种是：

- **amd64**（也叫 x86_64）：Intel 和 AMD 的芯片，云上的普通 Linux 机器几乎都是它。
- **arm64**（也叫 aarch64）：Apple Silicon 的 Mac，以及很多手机和云上的省电机型。

编译出来的原生程序是按其中一种指令集生成的，换一种芯片就读不懂。Java 的 jar 之所以能跨平台，是因为里面是字节码，由 Java 运行时翻译执行；但 **Java 运行时本身是原生程序**，镜像里的操作系统文件、工具也都是。所以：

<Callout kind="lead">

镜像和芯片架构绑定在一起。打包的机器是什么架构，镜像就是什么架构。

</Callout>

## 不匹配的时候会怎样

三种可能：

1. **直接报错**：Docker 提示镜像平台和本机不一致，容器起不来。
2. **靠转译硬跑**：Mac 上有 Rosetta 之类的转译层，能把另一种指令翻译着执行。它能跑，但是更慢、更耗资源，而且**没有任何报错**，你甚至不知道它正在转译。
3. **一个 tag 对应多种架构**：镜像仓库支持“多架构镜像”，同一个名字下放着几份，Docker 按机器自动选。这需要构建时专门准备。

第二种最危险：它不会出声。

## 部署脚本里的最后一道防线

不过 Patra 没有只靠“不会出错”。部署脚本在换新之前，仍然会**断言镜像的架构必须是 arm64**：

```bash
docker image inspect --format '{{.Architecture}}' <镜像>
```

这条命令会打印镜像的架构，部署脚本拿它和 `arm64` 比较，不一致就拒绝部署。

为什么还要多这一道？因为镜像仓库里可能还留着以前不同架构的旧镜像，回滚时要是拉回来一个，同样的问题就悄悄回来了。

<Callout kind="warn">

“能跑”不等于“对”。转译不会报错，所以架构问题往往是靠检查发现的，不是靠错误信息。检查要写成会失败的断言，而不是依赖人去留意。

</Callout>
