## PR 是一张报名表

Pull Request（PR）是你对仓库说的一句话：“我想把这条分支合并进 main，请检查并评审。”它本身不改变任何代码，但会触发整套自动流程：云端检查开始跑、AI 评审员进场、分支保护开始盯着按钮。

开发还没做完时，PR 可以先标成**草稿（draft）**，明确告诉所有人“还没准备好”。做完了再转成正式的 ready。

```bash
gh pr create --draft
```

## 合并按钮的两把锁

main 上设了**分支保护**：不是想合并就能合并。PR 页面那颗合并按钮要亮起来，两个条件都要满足：

1. **必过检查是绿的**。仓库只认一个叫 `required-check` 的检查，它汇总了所有真正会跑的检查结果（怎么汇总的，后面的篇目细讲）。
2. **评审留下的对话都处理完了**。每条意见要么改掉，要么回复清楚为什么不改，然后标记为已解决。

两把锁合起来是一句话：坏代码进不了 main，靠的是制度，不靠自觉。

注意两件事：被挡住之后，唯一的出路是**推送修复**；已经可以合并的 PR 只要再推送，也会回到“检查中”，因为检查要针对新代码重新跑。

## AI 评审员

Patra 是单人项目，没有同事帮忙看代码，评审由两位 AI 评审员替补：

- **Claude Action**：PR 打开、转 ready 或有新推送时自动触发，每个 PR 只评一次，会跳过草稿；评 bug，也核对项目规范。
- **CodeRabbit**：不自动评审，由 Claude 在评论区发 `@coderabbitai review` 才触发，只做首评。它给公开小仓库的免费额度每小时只有一次评审，复评几乎必然被限流。

对每条意见，规则很硬：**要么修掉并附上提交号，要么明确写不修的理由，不允许已读不回**。

<Callout kind="warn">

评审意见不一定都对。评审员可能误报，这时候也别直接忽略，回复清楚为什么不改，再标记已解决。沉默会让按钮一直是灰的，也让后来的人看不懂当时的判断。

## squash：把草稿装订成一页

最后是合并方式。Patra 只用 **squash merge**：PR 里不管提交了多少次——“修 typo”“再改一版”——合并时统一压成 main 上的**一条**提交。你的草稿过程仍然留在 PR 页面里，但 main 的历史永远是一行一件事。

这对后面的部署很重要。打包出来的镜像用提交号当版本号，main 上一行一件事，意味着“回滚到某个版本”就是精确指定某一次合并，不会出现“这条提交只含半个功能”。
