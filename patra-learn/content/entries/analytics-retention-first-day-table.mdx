## 背景

运营看板的留存组要一张同期群表：每一天的新增人数，以及他们恰好在第 1、7、30 天又来的人数。口径照经典 N 日留存，「人」还要先认回：登录前用设备、登录后用账号的同一个人不算两次新增。

ADS 的做法是每小时刷新一次。留存表每次重算**最近 32 个同期群**：第 30 天的留存要等一个月，认回也会改过去的首日（一台设备后来登录了，它当初那天的「新增」要挪到账号首次出现的那天）。

难点在首日。要判断一个人是不是某天的新增，得确认他在那天之前从没出现过，这要读日活表 `daily_person_activity` 的全部历史，它保留 400 天。集成测试专门守着这一点：一个 60 天前来过的人今天又来，不能算今天的新增。

约束也是硬的：ClickHouse 容器 2 GiB，每条查询上限 1 GiB；这一版明确不调高任何容器的内存，mini 已经超卖。

## 选择

<Callout kind="lead" label="选了什么">

选了增量的每人首日表。决定性的一条：它让刷新的输入量只取决于「最近两天来了多少人」，不再随历史一天天变长；另外两个选项都是读全部或接近全部的历史，日活表越攒越多，迟早超过 1 GiB。

</Callout>

表和它的刷新写在留存的迁移脚本里：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V8__ads_cohort_retention.sql@c3df651e18fcd34d66a1ece0e2cea00c78e9d881" lines="9-31" />

```sql
CREATE TABLE IF NOT EXISTS ads_person_first_day (
    person_id     String,
    is_synthetic  Bool,
    traffic       LowCardinality(String),
    first_day     SimpleAggregateFunction(min, Date)
) ENGINE = AggregatingMergeTree
ORDER BY (traffic, is_synthetic, person_id);

CREATE VIEW IF NOT EXISTS ads_person_first_day_calc AS
SELECT person_id, is_synthetic, traffic, min(day) AS first_day
FROM (
    SELECT day, person_id, is_synthetic, max(has_client) = 1 AND max(is_bot) = 0 AS human
    FROM daily_person_activity
    WHERE day BETWEEN {from:Date} AND {to:Date}
    GROUP BY day, person_id, is_synthetic
)
ARRAY JOIN ['human', 'all'] AS traffic
WHERE traffic = 'all' OR human
GROUP BY person_id, is_synthetic, traffic;

CREATE MATERIALIZED VIEW IF NOT EXISTS ads_person_first_day_rmv
REFRESH EVERY 1 HOUR OFFSET 10 MINUTE APPEND TO ads_person_first_day EMPTY AS
SELECT * FROM ads_person_first_day_calc(from = toDate(now(), 'Asia/Shanghai') - 1, to = toDate(now(), 'Asia/Shanghai'));
```

它和其他 ADS 表长得不一样：

- **引擎是 `AggregatingMergeTree`，列是 `SimpleAggregateFunction(min, Date)`**：同一个身份写了几行，合并时取最早的那天。这正是物化视图那篇说的「汇总表只存幂等的值」：每小时都把最近两天再补一遍，同一个人被补几次，`min` 的结果都一样。
- **没有 `computed_at`，也没有 `_latest`**：首日只会越来越早，不存在「新一版要替掉旧一版」。
- **按原始身份存**（`u:<账号>` 或 `d:<设备>`），认回留到算留存时再做：留存的计算先用设备与账号的对应表把 `d:` 换成账号，再取这个人所有身份里最早的首日。设备后来登录了，首日跟着变。

历史只在上线时由回填脚本建一次：从 08-06 起逐天补进来，之后交给刷新视图。

## 代价

<Callout kind="cost">

- **注销清理多删一张表**：首日表存着 `u:<账号>`，是用户数据。注销清理要删它，而且顺序在日活表之前。
- **多了先后顺序**：首日表要先于留存更新。刷新视图排在第 10 分钟，留存在第 12 分钟；回填脚本里它也排在留存前面；留存的集成测试先补首日、再算留存，照的是同一个顺序。
- **一个已知偏差**：某人某天先被算作真人、当天晚些时候才被标为爬虫，真人口径的首日不会撤回（`min` 只往早里合并，不会把一天删掉）。设计里判断量很小，写进了迁移脚本的注释。
- **什么时候重新考虑**：首日表只解决了「判首日」这一步，算留存仍要读同期群成员首日之后 30 天的日活。如果哪天同期群本身大到这一步也逼近上限，这个决策就要重新评估。

</Callout>

```java
  public void deleteUsers(List<Long> userIds) {
    if (userIds.isEmpty()) {
      return;
    }
    String ids = userIds.stream().map(String::valueOf).collect(Collectors.joining(", "));
    String persons = userIds.stream().map(id -> "'u:" + id + "'").collect(Collectors.joining(", "));
    execute("DELETE FROM events WHERE user_id IN (" + ids + ")");
    execute("DELETE FROM dlq_events WHERE user_id IN (" + ids + ")");
    execute("DELETE FROM article_session_reads WHERE person_id IN (" + persons + ")");
    execute("DELETE FROM device_user_links WHERE user_id IN (" + ids + ")");
    execute("DELETE FROM ads_person_first_day WHERE person_id IN (" + persons + ")");
    // 日活表是找用户的唯一来源，最后删：中途失败时其他表的残留次日还能再找到
    execute("DELETE FROM daily_person_activity WHERE user_id IN (" + ids + ")");
  }
```

清理任务靠日活表找出「哪些注销用户在行为数据里还有痕迹」。日活表要是先删了，中途失败时首日表里的残留就再也找不到；把它放最后，失败了下次还能从日活表找到这个人，把剩下的表补删干净。这和「行为数据的隐私与合规：告知与同意、最小化、删除、保留期」里讲的删除要求是一回事：每加一张存用户身份的表，就要同时想清楚它怎么被删掉。
