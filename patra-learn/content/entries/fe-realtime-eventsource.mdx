## 开一个连接，事件就源源不断地来

`EventSource` 是浏览器自带的对象。给它一个地址，它发一个 GET 请求，然后一直不挂断：服务器每写一条事件，浏览器就触发一次对应名字的监听函数。

门户只订阅一种事件 `unread-count`，数据是三个标签的未读数。下面是门户建连接的那段：

<CodeRef at="patra-portal/src/lib/notifications/stream.ts@4a13287485468f2c489027f1aac0bb6174643e8d" lines="104-126" />

```ts
    const connect = () => {
      disconnect();
      const next = new EventSource(STREAM_URL);
      next.addEventListener("open", () => setLive(true));
      next.addEventListener("unread-count", (event) => void onCounts(event));
      next.addEventListener("error", () => {
        setLive(false);
        if (next.readyState !== EventSource.CLOSED) {
          return;
        }
        next.close();
        source = null;
        void client
          .fetchQuery({
            queryKey: queryKeys.notificationUnread,
            queryFn: () => fetchUnread(client),
            staleTime: 0,
          })
          .catch(() => {});
        retry = setTimeout(connect, STREAM_RETRY_MS);
      });
      source = next;
    };
```

三个监听各管一件事：`open` 表示连上了；`unread-count` 是数据到了；`error` 是出事了。`error` 里先看 `readyState`，这是下面重连那节的关键。

这段代码放在一个 `useEffect` 里，挂在根布局上，整个站只连一条。effect 的清理函数会关掉连接，所以登出、组件卸载时连接都会断。

## 浏览器连的是门户，不是网关

网关要求推送请求带 `Authorization: Bearer <令牌>`，可是 `EventSource` 只能给地址，加不了请求头。门户的做法是让浏览器连门户自己的 Route Handler，由它在服务端读出 Cookie 里的令牌，再去连网关：

## 断线分两种，浏览器只管一种

这里大多数人会卡住：EventSource 的「自动重连」不是什么情况都管。

- **连着连着断了**（网络抖动、服务器到了 30 分钟的连接时长上限主动关掉）：触发 `error`，但 `readyState` 是「连接中」，浏览器 3 秒后自己再连。代码什么都不用做，所以上面那段 `error` 里直接 `return`。
- **连上时就被拒了**（回的不是 200，比如会话过期的 401、服务挂了的 502）：浏览器认为这个地址不能用，`readyState` 变成「已关闭」，从此不再重连。而且它不告诉你状态码是多少。

第二种情况门户只能自己接手：立刻用普通请求取一次未读数（普通请求能看到状态码，是 401 就让当前用户失效，页面随之登出、断开推送），再定一个 60 秒的计时器重新连。

另外，页面切到后台就主动断开，切回来再连。门户在内网直连时走的是 HTTP/1.1，同一个站点浏览器最多开 6 条连接，开着好几个后台标签页、每个都占一条，前台页面就没连接可用了。

3 秒这个间隔是通知服务在第一条事件里告诉浏览器的：

<CodeRef at="patra-api/patra-notification/patra-notification-adapter/src/main/java/dev/patra/notification/adapter/realtime/rest/SseUnreadCountStream.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="42-52" />

```java
  public void sendCounts(UnreadCounts counts) {
    SseEmitter.SseEventBuilder event =
        SseEmitter.event()
            .name(EVENT)
            .data(UnreadCountsEventResponse.from(counts), MediaType.APPLICATION_JSON);
    if (first) {
      event.reconnectTime(RECONNECT.toMillis());
      first = false;
    }
    send(event);
  }
```

## 收到一条推送之后

`onCounts` 先取消还在路上的轮询请求，再把新数写进未读数缓存。不先取消的话，一个发得早、回得晚的轮询会用旧数把推送来的新数冲掉。铃铛、菜单、提醒页的三个标签读的是同一份缓存，所以一起变。如果用户正开着提醒页，还会顺手重取当前列表，把新出现的提醒标成「新」。

推送只带「数变了」，不带提醒内容。内容仍由页面自己去取。
