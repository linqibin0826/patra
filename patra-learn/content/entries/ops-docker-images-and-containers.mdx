## 镜像：把环境一起打包

程序能不能跑，不只取决于程序本身，还取决于机器：Java 版本、系统库、字体、时区……“在我电脑上明明能跑”就是这么来的。

**Docker 镜像**把这些全部打进同一个包：程序、它需要的运行环境、一套精简的操作系统文件。任何装了 Docker 的机器，拿到这个包都能原样跑。

<Callout kind="analogy">

对 Java 程序员，最好的类比是：镜像像一个 class，容器像用它 new 出来的对象。一个镜像可以同时启动多个容器，每个容器各自独立、互不影响。

</Callout>

- **镜像（image）**：只读的模板，打包好就不变。
- **容器（container）**：从镜像启动出来的一个运行中的实例，有自己的进程、网络和文件空间。
- **Dockerfile**：写给 Docker 的“配方”，一行一行说明这个镜像怎么一步一步造出来。

## 镜像是分层的

Dockerfile 里每条指令（`COPY`、`RUN`）会生成一层。Docker 会把每一层缓存起来：**如果这一层的输入没变，下次构建就直接复用，不重新做**。

这条规则决定了 Dockerfile 怎么写才快：把很少变的放前面，经常变的放后面。Patra 的后端服务就是这么做的。Spring Boot 的可执行 jar 先被拆成几层，再依次拷进镜像：

|---|---|---|
| `dependencies` | 第三方 jar，约 80 MB | 依赖不变就几乎不变 |
| `spring-boot-loader` | 启动器类 | 很少 |
| `snapshot-dependencies` | 快照依赖 | 当前没有 |
| `application` | 你自己的代码 | 每次构建都变 |

## 镜像放哪里，叫什么

做好的镜像要有地方存，这就是**镜像仓库**。可以把它想成镜像世界的 Maven Central。Patra 用的是 GitHub 提供的 GHCR，镜像名长这样：

```text
ghcr.io/linqibin0826/patra-learn:<提交号>
```

冒号后面是 **tag**，也就是版本号。Patra 的 tag 是这次构建对应的 **commit 提交号**，同时再打一个 `latest`。这样“回滚到某一版”就是“换回某个提交号的镜像”，没有歧义。

| 命令 | 作用 |
|---|---|
| `docker build -f Dockerfile 目录` | 按配方造镜像 |
| `docker images` | 看本机有哪些镜像 |
| `docker ps` | 看有哪些容器在跑 |
| `docker logs 容器名` | 看容器输出的日志 |
