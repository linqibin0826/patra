## 背景：它对应的是另一种生意

ingest 是为「按需采集」设计的：机构客户按一个检索式跨多个数据库抓一部分数据。流程是建计划、拆任务、调外部 API、存对象存储，再经发件箱和 RocketMQ 发给 catalog 入库。

可 Patra 从 v0.4 起做的是面向个人专业用户的门户，要的是整库镜像加每日增量，这件事一直由 catalog 自己做：下载文件或调 API，解析后直接写进自己的库。

2026-10-13 做了一次业务评估，结论是 ingest 对应的生意门户用不上。那次评估之后，作者给新工作定了一个先问的问题：「有没有一个真实的人因此能做以前做不了的事」，先看业务，再看技术。到 10-30 决定删除时核对的事实：

- ingest 从没在线上跑过：调度平台上没有它的执行器，库里的表全是 0 行，全仓没有任何模块依赖它。
- 它是 RocketMQ 唯一真实的使用方，也是 `patra-object-storage` 这个服务唯一的调用方。
- 留着它的成本：v0.16 通知中心规划里有两项工作是为它白干的（让它改用新的事件模块、下线 RocketMQ 时迁它）；后端分包规范迁移只剩它没做；CI、部署各占一个单元，部署机上的容器空占内存。

分四路读代码、加一轮业界调研之后，每一块的结论：

| 部分 | 结论 |
|---|---|
| 检索式编译 | 只是把条件拼成外部 API 的查询串，种子只接了 3 个来源、4 个字段，核心编译器没有测试；门户检索要的是「用户检索式到 SQL」，它也不是 |
| 各来源客户端 | DOAJ、Crossref 是空壳；EPMC 只有半截；PubMed 那套不如 catalog 现有的解析器 |
| 编排（计划、任务、发件箱） | 运行锁、断点续采、失败重试、限流、幂等，catalog 都有且更扎实 |
| 对象存储服务 | 只有一个「上传后登记」接口，唯一调用方是 ingest；catalog 和 identity 一直经工具模块直接写 MinIO |
| `patra-common` | 删完以上几项，里面 4 个类只剩 catalog 在用，并进 catalog |

<Callout kind="lead" label="选了什么">

整块删除：ingest 的 8 个模块、`patra-object-storage` 服务、registry 里只给 ingest 用的两个子域、`patra-common` 模块、RocketMQ，以及它们在构建、CI、部署、配置和文档里的全部痕迹。registry 的字典部分保留。单独一个 PR，不挂任何版本，在 v0.16 通知中心的后端代码开工前合并。

</Callout>

## 验收：怎么证明删干净了

删除不改行为，不走 TDD，主要靠现有测试兜底；现有测试拦不住的种子缺失，由新加的回归测试补上。另外用几条全仓搜索做零命中检查（历史文档目录除外）：

```bash
git grep -niw ingest                     # -w 按整词，MeSH 里的 ingestion 这类词不算
git grep -niE 'patra_ingest|patraingest' # 库名和类名里的写法，-w 抓不到，单独查
git grep -ni rocketmq
```

部署机上：合并前先停掉旧 registry 并重建它的库（否则新代码的 Flyway 会因旧脚本校验和对不上起不来），合并后清掉孤儿容器、两个库和对象存储里的空桶，再按英文国家名解析一次（`China` 解析成 `CN`），确认那条参考标准在。

## 代价

<Callout kind="cost">

- 以后真要做按需采集或补抓某个来源，要从 git 历史里翻出来重写。为此删除说明的附录里记下了位置：catalog 还没解析的 PubMed 字段、增量窗口公式、ingest 发件箱的几个设计要点。
- 部署机上 registry 有一段停机窗口：从停旧容器到新 registry 起来之间，要避开 catalog 的导入任务。
- 删除牵动的东西远比「删一个目录」多：依赖版本、CI 镜像、测试容器类型、部署清单、配置中心、技能文档都要改。

</Callout>
