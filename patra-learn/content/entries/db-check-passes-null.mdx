## 坑

PostgreSQL 的 CHECK 约束只在表达式**结果为 false** 时拒绝这一行。结果是 NULL（「未知」）时，算通过。

条件里只要有一列可能是 NULL，整条表达式就可能变成 NULL，约束就悄悄失效了。

## 一个真实的例子

v0.14 讨论那一版，interaction 的对象登记表（`subject.registry`）要登记一种新对象：帖子（投稿经验）。帖子的规则是「来源 ID 永远有，锚就是 `post:` 加来源 ID」。最初的约束写成：

```sql
CHECK (target_type <> 3 OR natural_key = 'post:' || source_id)
```

`target_type = 3` 是帖子。看起来没毛病：不是帖子就放过，是帖子就要求锚和来源 ID 对得上。

更糟的是，表上另一条约束 `ck_registry_source_present` 本来就允许「已失效」的行没有来源 ID。一个失效状态、来源 ID 为空的帖子，两条约束**都拦不住**。

## 为什么

SQL 用三值逻辑：true、false、unknown（NULL）。NULL 表示「不知道」，和它拼接、比较，结果也是「不知道」。

`WHERE` 只留下结果为 true 的行，NULL 被当成「不要」；CHECK 正好反过来，只拒绝 false，NULL 被当成「放过」。同一个 NULL，在两个地方的待遇相反，这里大多数人会卡住。
