## 同一条规则，为什么要查两遍

注册时密码要 8 到 64 位。门户的注册页会查，后端的 identity 服务（管账号的那个后端服务）也会查。看起来重复，其实两边各防一件事：

<Callout kind="lead">

**前端校验为了体验**：填错了马上在输入框下面提示，不用等一趟网络往返。**后端校验为了安全**：请求不一定来自门户的页面——有人可以关掉脚本、改掉页面代码，或者用命令行工具直接调接口，前端的检查一条都拦不住他。只有后端那一道是真的关卡。

</Callout>

## 在门户里：规则写成 schema

门户用 **zod** 把规则写成一份「描述」（叫 schema，结构说明），再交给 **react-hook-form** 去管表单。登录和注册的规则都在一个文件里：

<CodeRef at="patra-portal/src/lib/auth/form-schemas.ts@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="17-28" />

```ts
/// 新密码：8 ~ 64 位，不去空格（注册、改密码、重设密码共用；常见密码名单只在后端判）
const newPasswordField = z
  .string()
  .min(1, FIELD_MESSAGES.passwordRequired)
  .refine((value) => codePoints(value) >= 8, FIELD_MESSAGES.passwordTooShort)
  .refine((value) => codePoints(value) <= 64, FIELD_MESSAGES.passwordTooLong);

/// 登录表单：后端的登录接口只检查密码非空，前端也只查这一条，不去空格
export const loginSchema = z.object({
  email: emailField,
  password: z.string().min(1, FIELD_MESSAGES.passwordRequired),
});
```

一条一条读：是文字；至少 1 位（否则提示「请输入密码」）；按码点数不少于 8；不多于 64。每条后面跟着出错时显示的那句话。

登录表单把这份 schema 交给 react-hook-form：

<CodeRef at="patra-portal/src/components/auth/LoginForm.tsx@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="47-54" />

```tsx
  } = useForm({
    resolver: zodResolver(loginSchema),
    // RHF 只在提交时校验；离开字段、输入时的校验由下面的 onBlur、onChange 触发。密码只查非空，
    // 空着离开又不校验，离开密码框时没有可查的，所以密码框不接 onBlur
    mode: "onSubmit",
    reValidateMode: "onSubmit",
    defaultValues: { email: handoff.email ?? "", password: "" },
  });
```

react-hook-form 替你收集各输入框的值、在该校验的时候按 schema 查一遍、把错误放进对应字段。什么时候查也是体验的一部分：门户在提交时查，另外在离开邮箱框时查一次，出错以后每输入一个字就重查，改对了错误立刻消失。

## 不是每条规则都两边都有

对照两边的代码，会发现规则分成三类：

| 规则 | 前端 | 后端 | 为什么 |
|---|---|---|---|
| 密码 8 到 64 位 | 查 | 查 | 填错马上提示，后端兜底 |
| 不能是常见密码 | 不查 | 查 | 要对照一份名单，名单在后端（`form-schemas.ts` 第 17 行注释） |
| 收藏夹不能重名 | 不查 | 查 | 要查数据库里已有的收藏夹，只有后端知道（`collection-form.ts` 第 6 行注释） |
| 两次输入的密码一致 | 查 | 不查 | 「确认密码」只为防手滑，不传给后端（`form-schemas.ts` 第 30 行注释） |

规律是：**凡是关系到数据对不对、安不安全的，后端必须查**；前端能不能也查，看它手里有没有足够的信息。只为体验存在的规则（确认密码），只放前端就够了。

## 字数怎么算：先定「一个字」是什么

「最多 100 个字」听起来很清楚，写成代码时却有好几种数法。JavaScript 里最顺手的 `value.length`，数的并不是你眼里的字：

| 输入 | `.length` | 码点数 | 字素数 | UTF-8 字节 |
|---|---|---|---|---|
| 好 | 1 | 1 | 1 | 3 |
| 😀 | 2 | 1 | 1 | 4 |
| 👨‍👩‍👧（一家三口） | 8 | 5 | 1 | 18 |
| é（e 加一个组合重音符，两个码点拼成） | 2 | 2 | 1 | 3 |

- `.length` 数的是 JavaScript 内部存储的单元（UTF-16），一个表情常常占两个。
- **码点**是 Unicode 给每个字符编的号。「一家三口」是三个人的表情，中间用两个看不见的连接符粘起来，一共 5 个码点。
- **字素**是用户眼里的「一个字」：不管几个码点拼成，看上去是一个就算一个。
- **字节**是存进数据库、在网络上传输时实际占的大小。

门户按字段选数法，原则只有一条：**和后端用同一种**。密码按码点（前端 `form-schemas.ts` 第 6 行的 `[...value].length`，后端上面的 `codePointCount`）。收藏夹名称、评论这类给人看的文字按字素，用浏览器自带的 `Intl.Segmenter`：

<CodeRef at="patra-portal/src/lib/grapheme.ts@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="1-7" />

```ts
/// 按字素（用户眼里的「一个字」）切分：汉字、组合字符、emoji 组合序列各算一个，和后端计长度的口径一致
const SEGMENTER = new Intl.Segmenter("zh", { granularity: "grapheme" });

/// 字素列表
export function graphemes(value: string): string[] {
  return Array.from(SEGMENTER.segment(value), (part) => part.segment);
}
```

后端收藏夹规则 `TextRules.java` 用 Java 的 `BreakIterator` 数同样的字素。口径不一致会怎样，做下面这道题。
