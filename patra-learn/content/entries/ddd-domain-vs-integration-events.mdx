## 两个事件，两种身份

同一件事「评论已发表」，Patra 里有两个类：

| | 领域事件 | 集成事件 |
|---|---|---|
| 类名 | `CommentPublishedEvent` | `CommentPublished` |
| 位置 | interaction 的 domain 模块 | interaction 的 api 模块 |
| 听众 | 本服务里的其他代码 | 别的服务（如 notification） |
| 字段 | 怎么方便本服务用怎么定，可用领域类型 | 只放别人需要的，用基本类型，要保持稳定 |
| 能随便改吗 | 能，重构时一起改 | 不能，改了就是改契约 |

领域事件里的 `SubjectId`、`SubjectOwner`、`SubjectType` 都是 interaction 内部的领域类型。

<CodeRef at="patra-api/patra-interaction/patra-interaction-api/src/main/java/dev/patra/interaction/api/discussion/event/CommentPublished.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="1-48" />

集成事件放在 api 模块里，实现 `IntegrationEvent`。它的 `subject` 是同在 api 模块里的 `SubjectContext`，不是领域类型。消费方依赖的是 api 模块，看不到 interaction 的领域层。

<Callout kind="lead">

领域事件是写给自己人看的账本，集成事件是写给外人看的公告。账本可以随手改，公告改了就得考虑所有看过它的人。

</Callout>

## 中间那道映射

从一个变成另一个，靠一个纯粹拷贝字段的映射类：

<CodeRef at="patra-api/patra-interaction/patra-interaction-boot/src/main/java/dev/patra/interaction/config/IntegrationEventMapper.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="19-45" />

它有三个要点，注释里写得很清楚：

1. **只拷字段**：值对象拆成基本类型，枚举转成常量名。
2. **不查库、不调转换器**：映射在每次外送（包括补投）时都会执行，查库会让补投的结果随时间变化，抛异常则会让这条事件永远发不出去。
3. **事件 ID 原样带过去**：补投时不变，消费方靠它去重。

外送哪些事件、发到哪个交换机、带什么路由键，都在一个配置类里：

<CodeRef at="patra-api/patra-interaction/patra-interaction-boot/src/main/java/dev/patra/interaction/config/InteractionEventsConfiguration.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="26-69" />

注意注释里的一句：「领域层不贴 `@Externalized`」。领域层不知道自己的事件会被发到 RabbitMQ，这件事只有 boot 模块的这个配置知道。

## 为什么要这么麻烦

<Callout kind="cost">

每个外送的事件要写两个类，外加一段映射。改集成事件的字段时，还要留意队列里没消费完的旧消息。

</Callout>

换来的是两件事：

- **领域模型能自由重构**。把 `SubjectOwner` 拆成两个类，只要改映射，不影响任何消费方。
- **契约是显式的**。api 模块里有什么，就是对外承诺了什么；没放进去的，别的服务就用不到。

还有一条小心得：不是所有领域事件都外送。

<Callout kind="insight">

「取消有帮助」这个领域事件就没有外送。配置类注释解释了原因：外送时带 `mandatory`，路由不到任何队列的消息会被退回，登记行每分钟补投一次，永远发不出去。通知服务对「取消」没有动作，没有队列订阅它，所以不外送。新增外送事件之前，通知服务要先绑定它的路由键。

</Callout>
