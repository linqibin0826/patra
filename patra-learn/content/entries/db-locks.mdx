## 为什么要锁

上一篇讲到，读已提交下两个事务"先读后写"会丢更新。办法之一是让其中一个**等一等**，或者让后到的**发现冲突、重来**。这就是锁。

Patra 里用到三种，思路各不相同：

| 锁 | 一句话 | 谁来保证 | Patra 里的例子 |
|---|---|---|---|
| 乐观锁 | 先不拦，写的时候检查「在我之后有没有人改过」，改过就报错 | 应用 + 版本号列 | 实体基类里的 `version` 列 |
| 行锁（悲观锁） | 先把这行占住，别人想改只能等 | 数据库 `SELECT ... FOR UPDATE` | 用户行：封禁与登录签发串行 |
| 咨询锁 | 随便起个名字当锁，约定谁拿到谁做 | 数据库 `pg_advisory_lock` | 导入任务同一时刻只跑一个 |

## 乐观锁：写的时候对一下版本号

给表加一列 `version`。每次修改，`UPDATE` 的条件里要带上自己读到的版本，同时把版本加 1：

```sql
UPDATE idn_user_profile SET display_name = ?, version = version + 1
 WHERE id = ? AND version = 3;
```

如果影响了 1 行，说明在你读完到现在没人改过；如果影响 **0 行**，说明有人抢先改了（版本已经不是 3），你的修改不能生效，要报错让用户刷新重来。它叫"乐观"，是因为假设大概率不会冲突，不预先拦着任何人，只在最后核对一次。

## 行锁：先占住，别人等

悲观锁的想法正相反：既然怕冲突，就在读的时候把这行**锁住**，直到事务结束。别的事务想改同一行，要排队等。

SQL 写法是 `SELECT ... FOR UPDATE`。在 Patra 里，查用户并加行锁是一个专门的方法：

<CodeRef at="patra-api/patra-identity/patra-identity-infra/src/main/java/dev/patra/identity/infra/account/persistence/dao/UserDao.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="17-23" />

```java
  /// 按 ID 加行锁查（`SELECT … FOR UPDATE`），只能在事务里调。
  @Lock(LockModeType.PESSIMISTIC_WRITE)
  @Query("select u from UserEntity u where u.id = :id")
  Optional<UserEntity> findByIdForUpdate(@Param("id") Long id);
```

为什么要用？Patra 的规范里写了一个具体理由：**会话的签发和用户封禁，靠同一把用户行锁串行化**。如果不串行，可能出现"管理员刚封禁了账号，同一时刻一个新登录又成功签发了会话"，封禁就被绕过去了。两边都先锁住这个用户的行，一个做完另一个才能开始，顺序就确定了。

<CodeRef at=".claude/rules/tech/transaction.md@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="26" />

行锁要点：

- 锁**只在事务里有效**，事务结束（提交或回滚）自动释放，所以 `findByIdForUpdate` 注释写着"只能在事务里调"。
- 锁的是行，不同用户的行互不影响。
- 持锁时间越短越好，别在持锁期间做慢操作。

## 咨询锁：给"一件事"上锁

有时要保证的不是"别人别改这一行"，而是"这件事同一时刻只有一个人在做"。比如 catalog 的 PubMed 导入任务，一个做完了才能开下一个；多个服务实例同时跑，不能有两个同时导入。

这件事没有对应的"行"可锁。PostgreSQL 提供了**咨询锁**：你随便起一个名字（实际是一个 64 位整数），谁拿到这个"锁号"谁就独占，别人取不到。数据库不关心这个锁代表什么，约定由你的代码遵守，所以叫"咨询"。

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/java/dev/patra/catalog/infra/kernel/lock/PgAdvisoryRunLockAdapter.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="39-54" />

```java
  public <T> Optional<T> runExclusively(String lockName, Supplier<T> work) {
    long key = lockKey(lockName);
    return jdbcTemplate.execute(
        (ConnectionCallback<Optional<T>>)
            connection -> {
              if (!queryBoolean(connection, "SELECT pg_try_advisory_lock(?)", key)) {
                log.info("任务锁 {} 已被其他实例持有，本次跳过", lockName);
                return Optional.empty();
              }
              try {
                return Optional.ofNullable(work.get());
              } finally {
                queryBoolean(connection, "SELECT pg_advisory_unlock(?)", key);
              }
            });
  }
```

读法：`pg_try_advisory_lock` 是"试着拿，拿不到立刻返回 false，不等"。拿不到就说明别的实例在跑，这次直接跳过；拿到了就干活，干完（`finally`）释放。两个细节：

- 这是**会话级**咨询锁，绑在数据库连接上，所以整个运行期间都占着同一条连接（连接池那一篇提过）。进程崩了连接断开，锁自动释放，不会"死锁"在那里。
- "有帮助"功能里用的是另一种：**事务级**咨询锁 `pg_advisory_xact_lock`，对每个被点的目标上锁，随事务结束自动释放。拿不到时它会等，不是跳过：

<CodeRef at="patra-api/patra-interaction/patra-interaction-infra/src/main/java/dev/patra/interaction/infra/reaction/persistence/HelpfulRepositoryAdapter.java@b554d996121f219ca9dc8a6ea08baf4f93648f5a" lines="35-40" />

```java
  public void lockTarget(HelpfulTarget target) {
    jdbc.sql("SELECT pg_advisory_xact_lock(hashtextextended(:lockKey, 0))")
        .param("lockKey", LOCK_PREFIX + target.type().name() + ":" + target.id())
        .query((rs, rowNum) -> 1)
        .single();
  }
```

目标是"评论或帖子加它的 ID"，把它拼成一个字符串再哈希成锁号。这样"删评论的同时有人点有帮助"会排好队，不会留下指向已删评论的孤儿明细。

## 多把锁：死锁

```java
  ...
            SELECT id, 1 FROM unnest(CAST(:ids AS bigint[])) AS t(id) ORDER BY id
  ...
  /// 先按 `subject_id` 升序锁住统计行（多行 `UPDATE` 不保证加锁顺序），再减；
```

两个批量操作，不管传进来的顺序如何，一律按 `subject_id` 从小到大处理，加锁顺序就固定了。规范里对不同种类的锁也有统一顺序：**配额锁，业务对象锁，行锁**。
