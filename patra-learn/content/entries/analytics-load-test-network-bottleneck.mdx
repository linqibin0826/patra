## 坑

<Callout kind="lead" label="坑在哪">

压测机到被测系统之间的网络本身慢，客户端的超时又比中间网关的超时短、还会重试：放弃的请求在网关上继续占着连接，重试再来一份，连接池很快打满，开环的压力在中间越积越多。测出来的是这段网络和网关的连接池，不是你想测的服务。

</Callout>

## 一次真实的压测：服务很闲，结果很差

v0.18 的验收要求以每秒不少于 1,000 条事件持续打采集端点 30 分钟。第一次正式压测（模拟器第 2 次运行）在作者的笔记本上跑，经网关打 mini 上的采集端点，目标每秒 1,200 条。结果：

| 看哪里 | 数字 |
|---|---|
| 30 分钟送达的事件 | 361,192 条 |
| 模拟器看到的延迟中位数 | 100 秒 |
| 采集服务处理一个请求 | 平均 16～74 毫秒 |
| 采集服务 30 分钟一共收到的请求 | 181,917 个 |
| 模拟器的在线会话 | 从约 5 千涨到 6.2 万 |

服务端处理得很快，收到的请求却很少；客户端那边延迟高到离谱，在线会话还在不停变多。两端的数字对不上，说明请求卡在了中间。

后来查明的原因有两层：

1. **网络绕路**：笔记本和 mini 之间没有建立点对点直连，流量经一个中转节点绕行（作者用组网工具连这两台机器，这次没打通直连），一次往返 40～60 毫秒。
2. **超时错配加重试**：模拟器照门户的设定，一个请求 6 秒没响应就放弃，按退避再发，最多 5 次；网关到采集服务的读超时却是 60 秒，连续 60 秒收不到下游任何字节才断，所以一个被模拟器放弃的请求，在网关那边要 45～60 秒才放手。网关到采集服务用的 Reactor Netty 连接池是默认大小：500 条连接、1,000 个排队名额，就这样被打满了。

```java
  /// 门户调采集端点的超时（采集设计 §4.5）
  private static final Duration REQUEST_TIMEOUT = Duration.ofSeconds(6);
  private static final int MAX_ATTEMPTS = 5;
```

<CodeRef at="patra-api/patra-gateway-boot/src/main/resources/application.yml@8140a9d9482324670b63f00ab3c62690102196c5" lines="33-43" />

```yaml
  # 网关唯一的 HTTP 客户端：显式用 Reactor Netty，不靠 classpath 自动探测。
  # 读超时是空闲超时：连续这么久收不到下游任何字节才断，不限总时长，大文件慢速下载不被掐断（设计第 6 节）。
  # factory、redirects 写枚举常量原名：配置刷新时 Gateway 用默认转换服务读这两项，不认 reactor、dont-follow
  http:
    clients:
      imperative:
        factory: REACTOR
      connect-timeout: 5s
      read-timeout: 60s
      # 网关不替客户端跟随下游的 3xx
      redirects: DONT_FOLLOW
```

网关这个 60 秒是为大文件慢速下载定的，本身没错；错在压测链路上，外层（模拟器）的耐心比内层（网关）短得多。

这正是开环压测的本意：真实的读者不会因为你慢就晚点来，所以问题会被放大出来。只是这一次放大出来的，不是被测的服务，而是压测机到服务之间的路。

<Callout kind="insight" label="怎么认出它">

- 服务端每个请求处理得很快，收到的请求数却远少于客户端发出的数。
- 客户端延迟高得不合理（这次中位数 100 秒），在途请求和在线会话持续上涨，不回落。
- 把客户端、网关、服务三处各自看到的请求数和耗时摆在一起，差距出现在哪两层之间，瓶颈就在哪。

</Callout>

## 怎么避开

**先测压测机到被测系统的那段路。** 正式压测前，单独量一下往返时延和能不能直连；压测机和被测系统放在同一个局域网或同一个机房，是业界的常规做法。Patra 后来改在 mini 本机上跑模拟器（第 3、4 次运行），这段网络就不存在了。

**外层的超时要比内层长，重试要有限度。** 一条调用链从外往里，每一层的超时应该越来越短：外层放弃之前，内层先放弃，资源才会及时释放。外层超时比内层短、还会重试，等于主动制造重复的在途请求。这条和「下游慢了怎么办」那篇讲的超时预算是同一个道理。

**看两端，不只看一端。** 只看模拟器的报告，会以为采集服务扛不住；只看服务的指标，会以为一切正常。两边对照才看得出压力卡在哪。

<Callout kind="warn">

把压测器挪到被测机器上，又会碰到另一个问题：它和被测系统抢 CPU 与内存，测出来的瓶颈可能是压测器自己造成的。Patra 在 mini 上跑时给模拟器的容器限了 2 个 CPU，正式那次又把它的内存降到 1 GiB。即使这样，下一次压测还是撞上了单机内存超卖，见「单机内存超卖：Kafka 一次 GC 停了 3 秒，被自己的控制器踢下线」那篇。

</Callout>
