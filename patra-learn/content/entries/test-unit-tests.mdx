## 单元测试检查「一个小零件」

造自行车时，不会等整辆车组装好才发现链条断了，而是先把链条单独拉一拉、刹车单独捏一捏。

**单元测试**也是这样：每次只检查程序里的一个小零件（通常是一个类里的一个方法），而且**不碰外面的世界**——不连数据库、不发网络请求、不读文件。零件的输入给定，输出就应该固定，所以它又快又稳：一个测试通常是几毫秒。

Patra 的构建配置里给单元测试设了一个很松的上限：单个测试超过 15 秒就判失败。

## 每个测试三步：准备、执行、断言

几乎所有测试都是同一个形状：

1. **准备**（Arrange / Given）：造出被测的对象，摆好输入。
2. **执行**（Act / When）：做那一个动作。
3. **断言**（Assert / Then）：说出你期望的结果，让电脑去核对。

看 Patra 里一个真实的测试，再对号入座。被测的是一个手动拨动的时钟：

<CodeRef at="patra-tool/patra-tool-test/src/test/java/dev/patra/tool/test/clock/MutableClockTest.java@af8cd13c3ec367ccba78615b72e6ff19535cef90" lines="18-26" />

```java
@Test
@DisplayName("从指定时刻开始，固定 UTC，换时区返回自己")
void should_start_at_given_instant_in_utc() {
  MutableClock clock = MutableClock.startingAt(START);   // 准备

  assertThat(clock.instant()).isEqualTo(START);          // 断言
  assertThat(clock.getZone()).isEqualTo(ZoneOffset.UTC); // 断言
  assertThat(clock.withZone(ZoneId.of("Asia/Shanghai"))).isSameAs(clock);
}
```

这个例子很简单：「准备」就是造时钟，「执行」就是读它的状态，几行断言放在一起。更常见的是三步各占一块、中间空一行，读的人一眼看出分界。

`@Test` 告诉 JUnit（Java 最常用的测试框架）：这是一个要跑的测试。`@DisplayName` 是给人看的中文名，测试报告里显示它。

## 断言：用 AssertJ 把期望写成一句话

断言就是「我期望是这样，请核对」。Patra 用 AssertJ 写断言，它的写法读起来像英语：

```java
assertThat(实际值).isEqualTo(期望值);
```

失败时它会把两边都打印出来，大致是：

```text
Expecting actual:
  2026-10-20T08:00:00Z
to be equal to:
  2026-11-19T08:00:00Z
```

看一眼就知道哪边错了，不用再自己加打印。

想检查「应该抛出异常」，也有对应写法，例如 `assertThatThrownBy(...).isInstanceOf(...)`。

## 一个测试只测一件事

回到开头那道题：断言失败，方法立刻结束。看看把三件事塞进一个测试会怎样。

这就是「一个测试只测一件事」的理由：失败时，它的名字就是诊断书。

一件事不等于一行断言。检查「时钟从指定时刻开始、时区固定」这类同一个结论的几个侧面，放在一起没问题。判断标准是：**这个测试失败时，你能不能只看名字就知道哪个行为坏了。**

## 名字要读得通

Patra 对测试方法的命名有明确约定，写在 `.claude/rules/testing/conventions.md` 里：

<CodeRef at=".claude/rules/testing/conventions.md@cfec9c9f30270dcf03f5cd7b6e54a0cd3b59296b" lines="1-30" />

几条最常用的：

| 维度 | 约定 |
|---|---|
| 位置 | `src/test/java/`，包路径与生产代码一一镜像 |
| 类名 | `{被测类}Test`，如 `MutableClock` 对应 `MutableClockTest` |
| 方法名 | snake_case，`should_期望行为` 或 `行为_when_条件`，直接读得通 |
| 工具 | JUnit 5（`@Test`）+ AssertJ（`assertThat`）+ Mockito（下一篇讲） |

对比一下：`test1` 失败时你要打开代码才知道在测什么；`should_advance_and_set` 失败时，名字已经告诉你是「往前拨与直接设置」出了问题。

测试多了之后，同一个类可以用 `@Nested` 按场景分组，每组一个内部类，报告里就是一棵树：

<CodeRef at="patra-tool/patra-tool-web/src/test/java/dev/patra/tool/web/error/engine/DefaultErrorResolutionEngineTest.java@b6e01875bb5692356021c8a19562f557f319fc54" lines="86-90" />

<Callout kind="warn">

不要为了让测试通过去改生产代码里的访问权限、加只给测试用的 `setXxx()`，也不要用反射去摸私有方法。测试只通过对象公开的方法检查它，这样内部怎么重构都不会让测试无故变红。

</Callout>
