## 代理：替别人跑腿

**代理**是站在中间转发请求的程序。按站的位置分两种：

- **正向代理**站在客户端这边，替客户端去访问外面（科学上网的那类）。服务器不知道真正的客户端是谁。
- **反向代理**站在服务器这边，替服务器接收外面的请求。客户端不知道后面是哪台服务器。

**API 网关**就是一种反向代理，在转发之外还做一些所有服务共同的事。

<Callout kind="analogy">

公司前台。访客只和前台说话，说「找财务」，前台就把人带到财务部，访客不用知道财务在几楼。前台还顺便核对访客证件、限制每天来的人数，这些事不用每个部门各做一遍。

</Callout>

## 在 Patra 里：路径前缀就是路由

网关用 Spring Cloud Gateway 实现，路由写在配置里：每条路由有 `Path` 条件（匹配哪些路径）、`uri`（转给谁）和 `filters`（转发前做什么）。

<CodeRef at="patra-api/patra-gateway-boot/src/main/resources/application.yml@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="54-109" />

以 catalog 为例：

- `Path=/patra-catalog/**`：路径以 `/patra-catalog/` 开头的都归它。
- `StripPrefix=1`：转发时去掉第一段，所以 `/patra-catalog/venues` 到了 catalog 变成 `/venues`。
- `uri: lb://patra-catalog`：`lb` 表示负载均衡，网关从注册中心查到名叫 patra-catalog 的服务有哪些实例，选一个转过去。服务发现的细节在后面讲。

## 路由的顺序有讲究

配置里的路由**从上往下依次匹配，先匹配到的先用**。Patra 里有一个很能说明问题的例子：通知服务有两条路由。

- 推送路由（长连接事件流）：`Path=/patra-notification/me/notifications/stream`，走专用的连接池。
- 通用路由：`Path=/patra-notification/**`。

配置文件里的注释特意写明了：推送路由**必须排在通用路由之前**。

## 门口还做什么

路由只是网关的一半。其余共同的事也在门口做：

| 事情 | Patra 的做法 |
|---|---|
| 认证 | 带令牌的请求，网关向 identity 查会话，确认是谁，再给下游一份身份断言。网关自己不连 Redis。 |
| 超时 | 连接下游最多 5 秒，读下游连续 60 秒收不到数据就断开。 |
| 客户端地址 | 只采信自己人（门户）加的 `X-Forwarded-For`，其他来源带的一律剥掉。 |
| 推送长连接 | 单独的连接池，上限 500，满了立刻 503，不挤占普通请求。 |

限流、超时与失败分类是后面两篇的主题。
