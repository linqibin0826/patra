<Callout kind="lead">

非敏感的配置，以仓库里 `patra-infra/nacos/dev/` 下的 YAML 文件为**唯一来源**。合并进 main 后，CD 在部署之前先把它们同步到 Nacos。Nacos 控制台只在应急时用，改在那里的内容，下一次推送就会被覆盖。

</Callout>

## 推送脚本做了什么

同步由一个幂等脚本 `nacos-push.sh` 完成。目录名就是 Nacos 的命名空间，目录里的每个 `*.yaml` 是一份配置，文件名就是配置的名字。

<CodeRef at="patra-infra/scripts/nacos-push.sh@25d6e781ce2078a892d1b7f89231de4a0b157f68" lines="1-14" />

对比 Nacos 里已有的内容，脚本按四种情况处理：

| 情况 | 动作 |
|---|---|
| Nacos 里没有 | 新增 |
| 内容不同 | 更新 |
| 内容逐字节相同 | 跳过，打印「未变化」 |
| Nacos 里有、目录里没有 | 删除 |

所以多跑几次没有副作用，这就是「幂等」。脚本还有一个 `--check` 模式：只对比不写入，退出码 0 表示一致，2 表示有差异，1 表示出错。

推送前先做一次本地预检，不联网：必须有 `patra-common.yaml`，每个文件的第一行必须是对应的「签到行」。签到行是一行形如 `patra.config-source.service: patra-catalog.yaml` 的配置，服务启动时靠它确认确实读到了 Nacos 里的配置，而不是悄悄回退到了 jar 包里的默认值。

## 在流水线里的位置

CD 的任务顺序是：判断改了什么，然后推送配置，然后构建部署。推送在部署**之前**，因为新代码可能依赖新配置。推送失败，本次就不部署。

<CodeRef at=".github/workflows/cd.yml@b6e01875bb5692356021c8a19562f557f319fc54" lines="90-109" />

这里有两个设计值得停下来想：

1. **推送任务在每次 push main 时都跑**，不看这次到底改没改配置。原因是排队中的运行会被更新的一次替换，被替换那次的配置修改，不在新运行的 diff 里，只看 diff 会漏推。脚本会跳过没变化的文件，多跑一次只花几秒。
2. **推送前再查一次配置文件**。CD 不等 CI，直接推 main 时 CI 的检查可能还没跑完，所以推送前在部署机上再跑一次 `NacosConfigFilesTest`。它检查：签到行、重复的键、以及不许写密钥。

关于密钥：仓库是公开的，名字以 `password`、`secret`、`token`、`api-key` 之类结尾的键，值只能写 `${变量}` 引用（或者带公开的 dev 默认值的引用）。真正的密钥放在部署机上仓库之外的目录，由容器启动时注入。

改了配置之后，对应的服务也要重新部署，因为库地址、对象存储这类配置是启动时读取的：`patra-<服务名>.yaml` 改了就重部署那个服务；公共配置 `patra-common.yaml` 改了，六个后端服务全部重部署。

当时没有为这件事做推送前的完整校验，也没有做部署失败后的 Nacos 自动恢复。理由是单人开发，revert 一次几分钟就能恢复，写一套自动恢复机制得不偿失。
