## 坑

<Callout kind="lead" label="坑在哪">

按名字理解超时，会把它们设错：`connectTimeout` 不止管 TCP，还包含 TLS 握手；`JdkClientHttpRequestFactory` 的 `readTimeout` 不是读超时，是从发出请求到读完响应的总上限。

</Callout>

## 为什么

| 参数 | 望文生义 | 实际 | 到点报什么 |
|---|---|---|---|
| JDK `HttpClient.Builder.connectTimeout` | TCP 建连 | 包含 TLS 握手：TCP 连上、握手不完成，照样到点 | `HttpConnectTimeoutException` |
| Spring `JdkClientHttpRequestFactory.setReadTimeout` | 两次收到数据之间的空闲 | `JdkClientHttpRequest` 在 `sendAsync` 之后就起计时器，算到响应流关闭，建连也在里面 | `HttpTimeoutException: Request cancelled` |
| JDK `HttpRequest.Builder.timeout` | 等响应的时间 | 同样从建连算起，建连阶段到点也报连接超时 | `HttpConnectTimeoutException` |

以上是 JDK 25、spring-web 7.0.10 下的实测结果。

这和 Patra 网关的读超时不一样：网关的 `read-timeout` 是空闲超时，只要还在收到数据就不会断。同样叫读超时，含义取决于用的是哪个客户端。`patra-tool-http-client` 用的是 Apache HttpClient 5，也不适用这里的结论。

<Callout kind="insight" label="怎么认出它">

看到 `HttpTimeoutException: Request cancelled`，先查总上限，别当成下游主动断开。看到 `HttpConnectTimeoutException`，别只想到 TCP 不通，还要量一下 TLS 握手。

</Callout>

## 怎么避开

总上限必须大于建连上限，否则建连上限不起作用。Patra 把它做成启动时的校验，配错了起不来：

<CodeRef at="patra-api/patra-identity/patra-identity-boot/src/main/java/dev/patra/identity/config/IdentityProperties.java@eb45ccde6f359692196b4b874ddaead6b9ffe0c2" lines="57-71" />

```java
    public record Outbound(
        @DefaultValue("10s") Duration connectTimeout,
        @DefaultValue("15s") Duration requestTimeout) {

      /// 总上限必须大于建连上限。
      public Outbound {
        if (requestTimeout.compareTo(connectTimeout) <= 0) {
          throw new IllegalArgumentException(
              "request-timeout 必须大于 connect-timeout，实际: "
                  + requestTimeout
                  + " <= "
                  + connectTimeout);
        }
      }
    }
```

配置项也不再叫读超时，改叫 `request-timeout`，名字说的就是它实际做的事。

<Callout kind="warn">

放宽超时也有代价：平台真的卡住时，请求线程要多占这么久。调用链上的上游也要跟着算，否则上游先放弃。Patra 的门户等回调从 20 秒放宽到 35 秒，就是因为一次回调最坏要 30 秒。

</Callout>
