## 坑

Spring Data 的派生删除方法（`deleteByUserId` 这种按方法名生成的）不是一条 `DELETE` 语句。它先把要删的实体查出来，再逐个 `remove`。`remove` 只是在持久化上下文里登记「这个要删」，真正的 `DELETE` 要等 flush。

而 Hibernate flush 时执行 SQL 的顺序是固定的：**插入在前，更新居中，删除在后**，和你在代码里调用的先后无关。

## 为什么

Hibernate 把一次 flush 要做的事放进一个动作队列，按类型分组执行：先插入，再更新，再删集合元素，最后删实体。这样排的初衷是保证外键顺序（先有父行再有子行），代价是你无法靠「调用顺序」控制删和插的先后。

这个坑在 Patra 里踩过两次。v0.11 全文阅读那一版，同一个 URL 的资源先删旧行再插新行，撞了唯一约束。v0.12 用户中心那一版，个人资料里的「链接」和「关注领域」两张子表每次保存都整组替换，表上有 `(user_id, position)` 唯一约束：只要新旧两组里有相同的 position（几乎每次保存都是），派生删除的写法就会撞上。
