## 应用层回答的问题：先做什么，再做什么

领域层告诉你「规则是什么」，基础设施层告诉你「怎么存」。把它们串成一个完整的用户操作，是应用层的事：**一个用例就是一个 Handler**。

<Callout kind="lead">

应用层管流程，不管规则。它的工作是排顺序：取当前用户、把输入变成值对象、划事务边界、调用仓库和聚合的方法。

</Callout>

## 命令与处理器

Patra 用命令（Command）和处理器（Handler）一对一表达用例：

- `CreateCollectionCommand`：一个只装数据的 record，写明「要做什么、带什么参数」。
- `CreateCollectionHandler`：实现 `CommandHandler`，真正做事。

Controller 不直接调 Handler，而是交给命令总线：

<CodeRef at="patra-api/patra-interaction/patra-interaction-adapter/src/main/java/dev/patra/interaction/adapter/collection/rest/MyCollectionController.java@3cf6fa5757b3be54c3b030e4cace871f53e2599c" lines="48-53" />

`SimpleCommandBus` 启动时收集所有 Handler，按命令的类型找到对应的那一个。一个命令只能有一个 Handler，重复注册会直接报错。

<CodeRef at="patra-tool/patra-tool-cqrs/src/main/java/dev/patra/tool/cqrs/SimpleCommandBus.java@b6e01875bb5692356021c8a19562f557f319fc54" lines="55-72" />

这样 Controller 和 Handler 互相不认识，中间还能挂拦截器（统一日志等），后面加功能不用改 Controller。

## Handler 里看得到什么

回到新建收藏夹的 Handler，按行读：

<CodeRef at="patra-api/patra-interaction/patra-interaction-app/src/main/java/dev/patra/interaction/app/collection/usecase/collection/CreateCollectionHandler.java@3cf6fa5757b3be54c3b030e4cace871f53e2599c" lines="34-53" />

| 行为 | 属于什么 |
|---|---|
| `currentUser.require().userId()` 取当前用户 | 编排：拿到调用者 |
| `CollectionName.parse(...)` | 编排：调用领域层的值对象，规则在它里面 |
| `transactions.execute(...)` | 编排：划事务边界 |
| `library.lockOwner`、`countCollections`、`nameTaken`、`create` | 编排：按顺序调用仓库接口 |
| `throw new CollectionLimitReachedException()` | 用领域层定义的异常表达拒绝 |

没有出现 SQL，没有出现名称怎么算合法。那些都在别的层。

## 事务边界放在这里

应用层决定事务从哪开始、到哪结束。Patra 的做法有点特别：**不在 `handle()` 上加 `@Transactional`**，而是注入 `TransactionOperations`，只把「锁、复核、写库」那一段包起来。

<CodeRef at="patra-tool/patra-tool-cqrs/src/main/java/dev/patra/tool/cqrs/CommandHandler.java@26ce40c846dc18aec3688e27e3a54caf20b64b26" lines="1-20" />

原因是总原则：事务里只放数据库操作，越短越好。远程调用、发消息、Redis、文件这些都不放进去，因为事务一直开着，数据库连接和行锁就一直占着。这条规则由构建里的架构测试守住：命令 Handler 一旦标了 `@Transactional`，`check` 就失败。
