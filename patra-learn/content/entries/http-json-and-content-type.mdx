## 为什么需要 Content-Type

正文只是一串字节。同样一串字节，可以是文本、图片、JSON、PDF。发送方必须在头里声明「这是什么」，接收方才知道该怎么读。这个头就叫 **Content-Type**，值是一个「类型/子类型」，叫媒体类型：

| Content-Type | 正文是 |
|---|---|
| `application/json` | JSON 数据 |
| `application/problem+json` | 一种有约定字段的 JSON，专门描述错误 |
| `text/html` | 网页 |
| `image/webp` | WebP 图片 |
| `application/pdf` | PDF 文件 |

请求和响应都用同一个头。反过来，请求里的 `Accept` 头说「我希望收到什么类型」。

## JSON：接口的通用语言

JSON 是一种纯文本的数据写法，只有几种东西：对象（花括号，键值对）、数组（方括号）、字符串、数字、布尔、null。浏览器、手机、各种语言都能读写，所以成了接口的事实标准。

```json
{
  "id": "1001",
  "name": "我的综述",
  "itemCount": 12,
  "public": false
}
```

<Callout kind="warn">

JSON 里的数字在 JavaScript 里是 64 位浮点数，大整数会丢精度。Patra 的数据库 ID 是很大的整数，所以后端统一把它们输出成字符串（上面 `id` 带引号的原因）。细节在讲 Jackson 的那一篇。

</Callout>

## 出错的时候：统一的 ProblemDetail

最糟的接口是每个出错的接口各用各的格式：有的返回一句话，有的返回 `{msg: ...}`，有的返回 HTML 错误页。调用方没法统一处理。

有一份公开的标准（RFC 7807 / 9457）约定了错误的 JSON 长什么样，Content-Type 是 `application/problem+json`。Patra 的后端服务出错时都用它。下面是一个示意（具体字段随情况而变）：

```json
{
  "type": "https://errors.example.com/cat-0404",
  "title": "CAT-0404",
  "status": 404,
  "detail": "找不到这个期刊",
  "code": "CAT-0404",
  "path": "/venues/123",
  "timestamp": "2026-10-31T08:00:00Z",
  "traceId": "..."
}
```

<Callout kind="insight">

调用方遇到错误，先看 `status` 判断大类，再看 `code` 做精确分支，最后才把 `detail` 展示给人。顺序反了，改一句文案就会让程序出错。
