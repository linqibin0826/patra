<Callout kind="lead" label="坑在哪">

先查出 N 个实体，再在循环里读它们 `LAZY` 的关联，每读一个实体的一个关联，Hibernate 就单独补一条 SQL。查询本身只有 1 条，循环让它变成 1 + N 条。

</Callout>

## 坑：一条查询，循环里长出一串

Patra 导入 PubMed 作者时，要按 ORCID 找出库里已有的作者，再转成领域对象 `AuthorAggregate`。转换在 `AuthorJpaMapper.toAggregate` 里，它会读实体的 `nameVariants` 和 `orcids` 两个集合。

下面假设查询没做任何处理，看 SQL 怎么一条条长出来。

## 为什么：懒加载等到「第一次读」才查

`AuthorEntity` 的两个集合都写着 `fetch = FetchType.LAZY`。查作者时 Hibernate 不去碰子表，只在集合位置放一个代理。代码第一次读这个集合，代理才发 SQL 把它填满。

单看一个实体，这很划算：不用的集合就不查。问题出在循环。每个实体的代理各管各的，Hibernate 不知道你接下来要把 100 个都读一遍，只能一个一个补。

这个坑难发现，是因为代码里看不到 SQL。`entity.getNameVariants()` 看起来只是取一个字段，背后却是一次数据库往返。

<Callout kind="insight" label="怎么认出它">

把 Hibernate 的 SQL 日志打开（`org.hibernate.SQL` 调到 DEBUG），跑一次批量操作，看日志里是不是同一条 `select … where author_id=?` 换着参数刷屏。条数随数据量线性增长，就是 N+1。

</Callout>

## 怎么避开：让主查询顺手把集合带回来

Patra 的做法是在查询里写 `JOIN FETCH`：告诉 Hibernate 这次查作者时，把两个集合也一起 JOIN 进来，填好再交出去。

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/java/dev/patra/catalog/infra/author/persistence/dao/AuthorDao.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="144-153" />

```java
  @Query(
      """
      SELECT DISTINCT a FROM AuthorEntity a
      JOIN FETCH a.orcids
      LEFT JOIN FETCH a.nameVariants
      WHERE a.id IN (
          SELECT DISTINCT ao.author.id FROM AuthorOrcidEntity ao WHERE ao.orcid IN :orcids
      )
      """)
  List<AuthorEntity> findByOrcidIn(@Param("orcids") Collection<String> orcids);
```

这里有三个细节：

- `orcids` 用 `JOIN FETCH`，`nameVariants` 用 `LEFT JOIN FETCH`：能按 ORCID 查到的作者一定有 ORCID，名字变体却可能为空，用左连接才不会把没有变体的作者漏掉。
- 一个作者有 2 个 ORCID、3 个名字变体，JOIN 出来是 6 行。`DISTINCT` 把它们合回一个实体。
- 作者的筛选放在子查询里，外层的 FETCH 不带条件。顺带避开一个常见陷阱：要是直接在被 FETCH 的集合上写 `WHERE o.orcid IN …`，装进实体的 `orcids` 只剩匹配上的那几个，实体就是残缺的。

查回来以后，适配器照常循环调用 `toAggregate`，这时集合已经填好，读它们不再发 SQL。

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/java/dev/patra/catalog/infra/author/persistence/AuthorRepositoryAdapter.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="230-246" />

<Callout kind="warn">

同时 FETCH 两个集合有个前提：它们得是 `Set`。两个 `List` 一起 FETCH，Hibernate 会直接报 `MultipleBagFetchException`，因为它没法从笛卡尔积里分清哪几行属于哪个列表。`AuthorEntity` 的注释专门写了「使用 Set 而非 List 的原因」。

</Callout>

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/java/dev/patra/catalog/infra/author/persistence/entity/AuthorEntity.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="105-133" />

不想手写 JPQL 时，Spring Data 还提供 `@EntityGraph(attributePaths = …)` 注解，在派生查询方法上声明要一起加载哪些关联，效果和 `JOIN FETCH` 一样。Patra 目前的查询都写成显式的 `JOIN FETCH`，一眼能看出 SQL 长什么样。
