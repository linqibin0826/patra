## 背景：用户自己的数据，和统计不是一回事

v0.18 给登录用户加了「阅读历史」：打开过哪些文献、最近一次是什么时候、有没有读过全文。产品规则（release spec 2.1）：

- 只记登录用户的文献详情浏览与全文阅读（下载 PDF 也算读过全文）。
- **默认开启**，隐私政策里写明；关闭后不再记录，已有的保留。
- 可以单条删除、一键清空；12 个月后自动清理；注销账号时清空。

同一次浏览，ClickHouse 里也有一条事件，用来算「N 人看过」。这两者是**两层数据**：个人历史是这个用户自己的，匿名统计是全站的。关闭记录、删除、清空只动前者，浏览量照常累计。

这个拆法是业界通行的（YouTube 的「暂停观看记录」也只停个人记录）。但它要求两套数据**各存各的、各删各的**，于是有两个问题要回答：历史存哪；什么时候写。

## 存哪：PostgreSQL，不从 ClickHouse 查

阅读历史要按人倒序翻页、按（用户，文献）删一行、按人清空，全是按行修改和点查。这正是 PostgreSQL 擅长、ClickHouse 不擅长的（「列式存储：为什么行为数据放 ClickHouse」讲过原因）。而且两边的保留期也不一样：ClickHouse 的事件明细留 90 天，历史留 12 个月。

所以 `patra-analytics` 有自己的 PostgreSQL 库，历史单独一个 schema。代价是同一次浏览在两边各存一份，删除也各管各的；好处是「清空历史不影响浏览量」自然成立。

<Callout kind="lead" label="选了什么">

存 PostgreSQL，采集时同步写（release spec 决策 B，用户 11/02 定）。阅读历史是用户自己看、自己删的东西，「清空了就真的空了」比拆出一个独立消费者更重要。

代码上，采集和历史是两个子域，采集用例不直接调历史的代码：它在 Kafka 写成之后发一个进程内事件 `ArticlesReadEvent`，历史子域用同步的 `@EventListener` 接住。同步监听和发布方在同一个线程里执行，效果等同于直接调用，写完历史才返回 202。

事件里的用户 ID 能信，是因为采集端点只在内网可达：公网的浏览器事件先到门户，门户按服务端会话补上用户 ID，浏览器发来的批次里不允许带任何身份字段。采集端点以后若要对公网开放，写历史前必须先改成从可信来源取用户。

## 晚到的事件：清空时刻与删除记录

同步写消掉了队列的延迟，但事件晚到还有别的来源：浏览器每隔几秒才把「读了全文」攒成一批发出；客户端失败后会重试（比如流量模拟器）。所以第二个选项的那套比对，第三个选项最后也要做，只是要挡的窗口短得多。

规则落在两张小表上：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/db/migration/history/V20261102100000__create_history_schema.sql@8140a9d9482324670b63f00ab3c62690102196c5" lines="18-32" />

```sql
-- 改过开关或清空过历史的人才有一行；没有行 = 开着、没清空过
CREATE TABLE history.recording_setting (
    user_id            BIGINT      PRIMARY KEY,
    recording_enabled  BOOLEAN     NOT NULL,
    cleared_at         TIMESTAMPTZ,              -- 最近一次清空的时刻；没清空过为 NULL
    updated_at         TIMESTAMPTZ NOT NULL
);

-- 单条删除的记录：挡住删除之前发生、删除之后才到的事件；2 天后由过期清理删掉
CREATE TABLE history.deleted_entry (
    user_id     BIGINT      NOT NULL,
    article_id  BIGINT      NOT NULL,
    deleted_at  TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (user_id, article_id)
);
```

- **清空**记 `cleared_at`（服务端时钟），存在设置表里，不过期。
- **单条删除**在删掉那一行的同一个事务里写一条删除记录。之后这一篇事件时间不晚于 `deleted_at` 的丢掉；之后真的再打开（时间更晚），照常记、重新出现在最上面。
- **删除记录只留 2 天**：采集端点会校正事件时间，比收到时刻早 24 小时以上的按收到时刻算，那就是一次「新」的打开。所以 2 天后删除记录不再起作用，由每天的清理任务删掉。

没有设置行的人用 `RecordingSetting.defaults`：开着、没清空过。`accepts` 要求事件时间严格晚于 `cleared_at`。

这套比对有一个已知的漏洞：事件时间最多能比收到时刻晚 5 分钟，客户端时钟严重偏快时，极少数清空前的打开可能漏网，不另处理。

## 其他几处取舍

| 取舍 | 做法 | 为什么 |
|---|---|---|
| 默认开，关掉只停后续 | 设置表只存改过开关或清空过的人；关掉写 `false`，已有的历史保留 | 照 YouTube「暂停观看记录」的做法；隐私政策写明默认开启 |
| 记哪些事件 | 只记登录、非合成的文献浏览、全文阅读、PDF 下载；被判为爬虫的照记 | 那是这个账号自己的历史，爬虫标记只用在对外数字上；模拟器的用户在 identity 里不存在，注销清理永远删不掉它们 |
| 每人每篇一行 | 同一批里先在 Java 里按（用户，文献）合并，再按键排序后一条 `INSERT ... ON CONFLICT DO UPDATE` 写入，时间取 `GREATEST`、全文取「或」 | 一条语句里同一个键出现两次 PostgreSQL 会报错；排序让并发请求按同一顺序加锁、不死锁；`GREATEST` 让晚到的旧事件不把时间往回改 |
| 慢也算失败 | 拿连接、每条语句、锁等待各限 500 毫秒，超时跳过这批 | 写历史不能把采集拖过门户的 6 秒超时；代价是那次打开没进历史，再打开一次就补上 |
| 保留 12 个月 | 每天 06:40 删 12 个日历月以前的行，每批 1 万行一个短事务；接口再按时间过滤一次 | 不会长时间锁表；跑清理之前的那一天也不会多出来 |
| 注销清空 | 接入注销清理流程，一个事务里删掉这批用户在三张表里的行 | identity 确认已注销的才删 |
| 不存用户名 | 表里只有 `user_id` 和文献 ID，标题、刊名由门户按 ID 向 catalog 批量取 | 项目规则：用户名只存 identity；改名不用回刷，catalog 改标题也不用回刷 |
| 不存 IP | 分析事件只存省级地区，IP 用完即丢；历史表里没有任何地址信息 | 个保法的最小必要；医生的阅读轨迹可能暴露科研方向，按接近敏感处理（规划时的保守解读，不是法律意见） |

## 代价

<Callout kind="cost">

- **采集端点多了一次数据库写入**：最坏情况下写历史占 1 秒多（拿连接加两次查询加写入），只在 Kafka 和 PostgreSQL 同时很慢时才会碰到门户的 6 秒超时，那时门户本来就会丢掉这一批。
- **写失败就丢**：历史写失败不重试，这次打开不进历史。对个人历史可以接受，换成要求不丢的数据就不行了。
- **同一次浏览存两份**：ClickHouse 和 PostgreSQL 的删除各管各的，注销时两边都要清。
- **开关的毫秒级窗口**：用户关掉记录的那一刻正好有一批在写，这一批可能还会写进去，不另加锁。
- **什么时候该重新考虑**：采集量大到同步写数据库成了瓶颈，或者采集端点要对公网开放、用户 ID 不再可信时。

</Callout>
