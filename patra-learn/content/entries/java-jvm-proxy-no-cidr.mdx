<Callout kind="lead" label="坑在哪">

macOS 上的 JDK 启动时会把系统代理读成 `http.proxyHost` / `https.proxyHost` / `socksProxyHost`，把系统的例外列表照抄进 `http.nonProxyHosts`。可 Java 的 `nonProxyHosts` 只认 `*` 通配符，不认 `100.64.0.0/10`、`192.168.0.0/16` 这种网段写法，抄过来的例外全部失效：去内网的请求一律进了代理。

</Callout>

## 当时看到什么

v0.8 做本机与部署机的对照测试时，本机起的服务要连部署机上的 Nacos 和其他服务（部署机在 VPN 的地址段里，Nacos 注册的实例在局域网段里）。结果：

- JDK `HttpClient`、Spring 的 `RestClient` 发出去的请求，全部拿回一个**空正文的 503**，响应头带 `Proxy-Connection: close`；
- Nacos 3 的客户端（底层是 grpc-java）一直停在 `Client not connected, current status:STARTING`；
- 同一台机器上，curl 访问这些地址全都正常。

花了近一个小时才把注意力从「部署机上的服务坏了」挪到「Java 的请求走了哪条路」上。

## 为什么

两件事叠在一起：

1. **JVM 会自动继承系统代理**。没在命令行写任何 `-Dhttp.proxyHost`，macOS 上的 JDK 也会从系统网络设置里读出代理地址和例外列表，填进这几个系统属性。你以为程序没配代理，其实已经配上了。
2. **两种例外列表的语法不一样**。系统设置和 curl 的 `no_proxy` 都认网段；Java 的 `nonProxyHosts` 是一串用 `|` 隔开的主机名模式，只认开头或结尾的 `*`：

| 写法 | 系统设置 / curl | Java `nonProxyHosts` |
|---|---|---|
| `192.168.0.0/16` | 认，整个网段直连 | 不认，当成一个叫这个名字的主机 |
| `192.168.*` | 看具体程序 | 认，以 `192.168.` 开头的都直连 |
| `localhost` | 认 | 认 |

于是例外列表抄过来了，却一条都没生效。代理收到去内网地址的请求，连不上，回了个空的 503。gRPC 那边则是连接一直建不起来。

## 怎么避开

起要连内网的 JVM（本地跑服务、跑测试）之前，用 `JAVA_TOOL_OPTIONS` 把三个例外列表都改成通配符写法。JVM 启动时会自动读这个环境变量：

```bash
NO_PROXY_HOSTS='localhost|127.*|100.*|192.168.*|172.*|10.*'
export JAVA_TOOL_OPTIONS="-Dhttp.nonProxyHosts=${NO_PROXY_HOSTS} -Dhttps.nonProxyHosts=${NO_PROXY_HOSTS} -DsocksNonProxyHosts=${NO_PROXY_HOSTS}"
```

两点要留意：

- 写进 shell 的启动文件也不一定够。作者自己的 shell 配置里早就有这一行，可 Agent 执行命令用的 shell 不加载那份配置，起出来的 JVM 照样踩坑。
- 认出它的信号：**JVM 请求内网地址，拿到空的 503，响应头带 `Proxy-Connection`**。看到这个先想代理，别先去查目标服务。

<Callout kind="warn">

第三项的名字没有点：JDK 认的是 `socksNonProxyHosts`。当初写成 `socks.nonProxyHosts`，后来在部署机上查实它不生效，SOCKS 那条路照样进代理。详见另一篇：代理拨号超时被 JVM 报成 TLS 握手被断。

</Callout>
