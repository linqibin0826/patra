## 隔离性要解决什么

上一篇的 ACID 里有个 I，隔离性。现实里数据库同时有很多事务在跑。**隔离级别**回答的是：一个事务运行期间，能看到别的事务的哪些修改？

隔离得越严，越不容易出现怪现象，但并发能力也越低。所以数据库提供几档，让你按需选择。

## 三种怪现象

并发事务可能碰到下面这些问题：

| 现象 | 通俗说 |
|---|---|
| **脏读** | 读到别人**还没提交**的修改。人家一回滚，你读到的东西就根本不存在 |
| **不可重复读** | 同一个事务里，**同一行**读两次，结果不一样（中途别人改了并提交） |
| **幻读** | 同一个事务里，用同样的条件查两次，**多了或少了几行**（中途别人插入或删除并提交） |

还有一种更常出事故的：**丢更新**，两个事务都基于旧值算出新值再写回去，后写的覆盖先写的。这不在三种之内，但和隔离级别关系密切，后面专门讲。

## 四档隔离级别

SQL 标准定义了四档，PostgreSQL 的实际行为如下：

| 级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---|---|---|---|---|
| 读未提交 | 不会 | 会 | 会 | PostgreSQL 里等同读已提交，从不允许脏读 |
| **读已提交（默认）** | 不会 | 会 | 会 | 每条语句看到的是它开始时已提交的数据 |
| 可重复读 | 不会 | 不会 | 不会 | 整个事务看一份快照；PG 比标准更严，连幻读也没有 |
| 串行化 | 不会 | 不会 | 不会 | 效果和一个个排队执行一样，冲突时报错让你重试 |

Patra 的各个服务没有改过这个设置，都跑在 PostgreSQL 默认的**读已提交**上。所以下面重点看它。

## 真正要小心的：先读后写，会丢更新

不可重复读本身很少直接出事故，出事故的是**读了再写**。看 Patra 里统计收藏人数的场景：两个人几乎同时收藏同一篇文献，都要把这篇的收藏人数加 1，当前是 5。

解法有两种思路，Patra 用的是第一种：**别在程序里算，让数据库在一条语句里算**。

```sql
UPDATE collection.subject_stats
   SET collector_count = collector_count + 1
 WHERE subject_id = :id;
```

这是示意写法；Patra 加计数时实际用 upsert 版本（`INSERT ... ON CONFLICT DO UPDATE SET c = c + 1`，没有统计行就先建出来），原理一样。这条语句在读已提交下是安全的：如果这一行正被另一个事务修改且还没提交，你的 `UPDATE` 会**等**；对方提交后，它会基于**最新提交的值**重新计算，所以 5 加 1 得 6，下一个等着的再基于 6 加 1 得 7，不会丢。

Patra 的 v0.15 决策 A 把这个道理写进了设计：计数用 `c = c + 1` 原子加减，**不**用"按明细重数一遍再覆盖"。理由正是读已提交下，重数的子查询用的是语句开始时的快照，两个事务同时重数可能少算一次。

锁住之后再发起的那条 `count(*)`，是一条新语句，它的快照在拿到锁之后才生成，所以能看到在这之前提交的所有写入。这个细节正是"读已提交是按语句取快照"的直接后果。

<Callout kind="insight" label="可重复读不是万能药">

升到可重复读也能防丢更新：第二个写的事务发现这一行已被别人改过，数据库直接报「无法串行化」错误。代价是你必须在代码里捕获并重试。Patra 选的是留在读已提交，用原子 `UPDATE` 和显式加锁（下一篇）来解决具体问题，不是整体提高隔离级别。

</Callout>
