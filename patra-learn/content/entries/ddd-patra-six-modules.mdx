## 为什么要拆成独立模块

上一篇讲了端口和适配器：核心定义接口，外面实现。要让这条规则不被悄悄破坏，光靠约定不行。Patra 的做法是把每一层拆成一个独立的 Gradle 模块，用构建文件决定谁能看见谁。

所有服务都是同一个结构。以 interaction 为例：

```
patra-interaction/
├── patra-interaction-domain    业务规则
├── patra-interaction-app       用例编排
├── patra-interaction-infra     出站适配器：存储、调别的服务
├── patra-interaction-adapter   入站适配器：REST、定时任务
├── patra-interaction-api       给别的服务看的契约
└── patra-interaction-boot      启动与装配
```

## 每个模块放什么

| 模块 | 放什么 | interaction 里的例子 |
|---|---|---|
| domain | 聚合、值对象、领域服务、仓库和端口接口、领域事件、领域异常 | `CommentAggregate`、`CollectionRepository`、`CollectionLimits` |
| app | 命令与处理器、查询服务、各种 Gateway 的实现 | `CreateCollectionHandler`、`DiscussionQueryService` |
| infra | 仓库与端口的实现（SQL、Redis、HTTP 调用） | `CollectionRepositoryAdapter`、`UserDirectoryAdapter` |
| adapter | Controller、定时任务、内部接口的实现 | `MyCollectionController`、`SubjectEndpointImpl` |
| api | 对外的契约：DTO、接口定义、集成事件 | `CommentPublished`（给通知服务消费的事件） |
| boot | `@SpringBootApplication`、配置装配、架构测试 | `InteractionEventsConfiguration` |

<Callout kind="insight">

运行时的调用路径是 adapter → app → domain → infra，但编译时的依赖方向是 adapter → app → domain ← infra。最后一步看起来「app 调到了 infra」，实际上 app 调的是 domain 里的接口，接口的实现由 boot 在启动时接上。

</Callout>

## 为什么有 api 和 boot

**api** 是服务间的契约，单独成模块是为了让别的服务能只依赖契约，不依赖你的业务代码。例如通知服务消费 interaction 的事件时，依赖的是 interaction 的 api 模块里的 `CommentPublished`，而不是它的 domain。
