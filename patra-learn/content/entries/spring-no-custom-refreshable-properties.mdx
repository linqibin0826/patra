## 背景

v0.9 配置中心那一版，把各服务的配置搬进 Nacos，有几个参数要能在线调（比如登录失败上限）。当时项目里 28 个配置类有 5 个是 record。

Spring Cloud 自带的刷新有三个缺口，都是真实存在的：

1. record（构造器绑定）刷新不了。
2. 原地重新绑定时先把字段重置成默认值、再绑新值，这期间并发的读者可能读到默认值。
3. 新值不合法时，校验在写入之后才跑，坏值已经进了对象，旧值回不来。

原计划是自研 `RefreshableProperties<T>`：配置保持 record，刷新时校验通过才原子替换整个快照，校验失败保留旧值。三个缺口一次补齐。

选可变配置类加 Spring Cloud 重新绑定，2026-10-14 改定，原定的自研任务取消。

调研了 Spring Cloud、Spring Cloud Alibaba、Apollo、Micronaut、Archaius：业界普遍用可变类自动重新绑定，或者 `@RefreshScope`，没有广泛采用的「不可变快照 + 原子替换 + 校验失败保留旧值」方案。

缺口逐个看：Patra 是单人项目，当时还没有真实用户，要在线调的只是几个互相独立的参数，读到一瞬间的默认值、坏值进对象，都可以接受；而 Nacos 配置文件放在 git 里、改动要过评审，坏值进来的机会本来就少。

为此定下几条写法：

- 需要在线刷新的配置写成带默认值的可变类，使用方**每次用时再读**，不缓存到字段或构造器里。
- 默认值写在字段上，jar 的 `application.yml` 里不写这些键；要调就在 Nacos 文件里加。
- 加 `@Validated`：不合法的值让刷新报错、健康检查转 DOWN。
- 不需要刷新的配置（数据源、端口、密钥）继续用 record，Spring Cloud 刷新时会跳过它们。

## 代价

<Callout kind="cost">

- **重新绑定期间可能读到默认值**：字段先被重置再绑新值，那一瞬间的并发读者看到的是字段上的默认值。
- **坏值进得来，旧值回不去**：校验失败只让健康检查转 DOWN。恢复靠 git revert 后重新推送（还有一个坑，见「配置推回原文，服务却不刷新」）。
- **一个配置类刷新失败，会中断它后面配置类的重新绑定**：`ConfigurationPropertiesRebinder` 不吞异常。

</Callout>

什么时候该重新考虑：有了真实用户，某个参数调错一瞬间就会造成实际损失；或者要在线刷新的参数多到互相有约束、必须一起生效。
