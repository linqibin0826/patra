## 把启动参数写进文件

`docker run` 要把镜像名、端口映射、环境变量、重启策略……全写在命令行上。参数一多，既难读，也难复现。

**Docker Compose** 的做法是：把这些写成一份 yml 文件，每个服务一个小节，然后用 `docker compose up -d` 照着文件启动。

<Callout kind="analogy">

compose 文件像是整套服务的 application.yml：你声明想要的状态，由工具负责把现实调整到那个状态。

</Callout>

看一个真实的小节。这是学习站自己的：

```yaml
  learn:
    image: ghcr.io/linqibin0826/patra-learn:${LEARN_IMAGE_TAG:-latest}
    container_name: patra-learn
    restart: unless-stopped
    ports: [ "4001:4001" ]
    env_file:
      - .env.learn
    healthcheck:
      test: [ "CMD", "wget", "-q", "-O", "-", "http://127.0.0.1:4001/api/health" ]
      <<: *app-healthcheck
```

<CodeRef at="patra-infra/docker/docker-compose.apps.yaml@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="202-214" />

逐行读：

| 字段 | 含义 |
|---|---|
| `image` | 用哪个镜像。tag 是个变量，默认 `latest`；部署时由流水线传入本次的提交号 |
| `container_name` | 容器叫什么名字，方便 `docker logs` 和脚本引用 |
| `restart: unless-stopped` | 容器挂了或机器重启后自动拉起，除非你手动停掉 |
| `ports` | `宿主机端口:容器端口`，让外面能访问到容器里的服务 |
| `env_file` | 从文件读取环境变量，密钥就靠它注入（见“密钥不进仓库”） |
| `healthcheck` | 怎么判断这个容器“真的活着”：定时执行一条命令 |

## 健康标准也是声明出来的

容器进程在跑，不等于服务可用。所以每个服务都声明了自己的**健康检查**：定时请求一次健康接口，连续失败多次就把容器标成不健康。

几个应用共用同一套参数，用 YAML 的锚点复写：

<CodeRef at="patra-infra/docker/docker-compose.apps.yaml@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="26-30" />

- `interval: 10s`：每 10 秒检查一次
- `timeout: 5s`：单次检查最多等 5 秒
- `retries: 15`：连续失败 15 次才判定不健康
- `start_period: 60s`：启动后的头 60 秒宽限期，这期间失败不算数（Java 服务启动慢）

## 内存也要声明

在后端服务的小节里还能看到：

```yaml
    deploy:
      resources:
        limits:
          memory: 1g
```

这是 2026 年 10 月加的。镜像用 `-XX:MaxRAMPercentage=75` 启动，如果不设上限，每个 JVM 的堆最大能涨到整个虚拟机内存的 75%。一次 catalog 回填，堆膨胀把虚拟机撑满，被系统直接杀掉进程。设了上限之后，堆是上限的 75%，一个服务再贪心也撑不满全局。

## 栈：按职责分几份文件

Patra 不是把所有服务塞进一份文件，而是**按职责拆成几份**：基础设施（数据库、缓存、消息队列）、应用、定时任务、监控……它们各自是独立的 compose 项目，共享同一个外部网络 `patra-net`，所以彼此用容器名就能互相访问。
