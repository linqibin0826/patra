## 同步监听器的另一面

上一篇的同步 `@EventListener` 在发布时立刻执行，和发布方同成同败。但有些事你**不希望**在提交之前做。

Patra 通知服务有一个实时推送：收到新提醒后，通过 SSE（服务器推送）告诉浏览器「你的未读数变了」。浏览器收到通知，会立刻来拉最新数据。如果在事务提交**之前**就推了：

- 浏览器来拉数据，可能读不到那条还没提交的提醒；
- 事务如果随后回滚，推出去的通知指向的是一件根本没发生的事。

所以推送要等**事务提交之后**。

## @TransactionalEventListener

Spring 用 `@TransactionalEventListener` 表达这个意思，并通过 `phase` 指定时机，最常用的是 `AFTER_COMMIT`：

- 事务提交了，才调用监听器。
- 事务回滚了，不调用。

Patra 的实时推送监听器：

<CodeRef at="patra-api/patra-notification/patra-notification-app/src/main/java/dev/patra/notification/app/realtime/listener/UnreadCountPushListener.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="11-33" />

```java
@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void on(UnreadCountsChangedEvent event) {
  registry.push(event.recipientIds());
}
```

它还加了 `@Async`：换一条线程去推。类注释解释了：提交事务的是 RabbitMQ 消费线程或请求线程，推送的慢和错不应该落到它们头上；提交后的回调里事务资源还挂在原线程上，换线程读库是干净的上下文。

## 提交后，事务已经结束了

这是最容易踩的地方。`AFTER_COMMIT` 的监听器执行时，**原来的事务已经提交了，回不了滚**：

- 监听器抛异常，不会撤销已经提交的数据，只会记一条日志。
- 监听器里要写库，原事务已经结束，得自己新开事务（Patra 的事务规范写成 `REQUIRES_NEW`）。

所以它只适合「**提交后可丢的副作用**」，比如推一个通知：丢了一次，浏览器 60 秒一次的轮询会补上。

最后一种就是**不该用**提交后监听器的例子。Patra 里负责这件事的监听器，类注释写得很明白：同步 `@EventListener`，不能用 `@TransactionalEventListener`，因为提交后才执行，标记会丢。

<CodeRef at="patra-api/patra-catalog/patra-catalog-app/src/main/java/dev/patra/catalog/app/publication/listener/PmcOpenAccessListener.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="10-31" />

<Callout kind="lead">

怎么选：这件事**必须和主事务同成同败**，用同步 `@EventListener`；这件事**要等提交后才有意义，丢一次也能补回来**，用 `@TransactionalEventListener(AFTER_COMMIT)`。

</Callout>

## 提交后，崩了怎么办

再看上面第二种写法的失败那一栏：提交了，进程却在推送之前崩了。对「推一次通知」来说无所谓。

可如果这个提交后的动作是「给别的服务发一条消息」，而且那条消息**不能丢**呢？
