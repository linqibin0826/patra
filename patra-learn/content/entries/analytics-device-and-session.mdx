<Callout kind="lead">

行为数据里的「一个人」：登录用户按账号 ID 认，没登录的访客按设备 ID 认；设备 ID 是服务器在访客第一次来时下发、存在浏览器 Cookie 里的一个随机串。

</Callout>

## 为什么要认人

上一篇定了「看过人数」按人去重：同一个人看多少次只算 1。还有更多指标离不开「同一个人」：今天新来了多少人、第一天来的人第 7 天还有多少回来（7 日留存）、看过这篇的人还看了什么。这些都要求能把跨请求、跨天的事件串到同一个人身上。

登录用户好办，账号 ID 就是现成的身份。难的是没登录的访客，而公开站点上他们往往是大多数。

## 两种认访客的做法

业界认匿名访客主要有两条路：

| 做法 | 怎么做 | 能认出什么 | 谁在用 |
|---|---|---|---|
| 持久匿名 ID | 访客第一次来就下发一个随机 ID，存在 Cookie 里，之后每个请求都带着；登录后把这个 ID 和账号关联起来 | 跨天、跨会话的同一台设备 | 神策、PostHog |
| 每日轮换的哈希 | 用「每天换一次的盐 + IP + UA」算一个哈希当访客标识，不存任何 Cookie | 只能认出当天的同一个人 | Plausible |

第二种更隐私，代价是第二天就认不出来了，「7 日留存」这类跨天指标根本算不了。Patra 要做留存和长期去重的「N 人看过」，选了持久匿名 ID，同时只存 ID、不存用户名，并在隐私政策里写明。

## 设备 ID：第一次请求就下发

规划时核对现状发现，Patra 的设备 Cookie 只在登录或注册时写入：从没登录过的访客没有任何标识，按设备认人无从谈起。所以 v0.18 的埋点方案把它改成：

- 每个访客**第一次请求门户的任意页面**时，门户下发设备 Cookie；已经有合法值就沿用。
- 有效期 400 天，`httpOnly`（浏览器里的脚本读不到）。登录、登出都不换。
- 名字沿用门户原来的约定：开着 Secure 时叫 `__Host-patra_device`，关着时叫 `patra_device`。

设备 ID 是 43 位的 URL 安全字符（`^[A-Za-z0-9_-]{43}`），采集端点的 schema 按这个格式校验。

<Callout kind="insight">

设备 Cookie 是 `httpOnly` 的，浏览器里的埋点脚本读不到它。所以浏览器发出的事件里根本没有设备 ID，是门户服务端收到这批事件时，从请求带来的 Cookie 里取出来补上的。身份字段只由服务端填，浏览器既拿不到，也没法自报。这一点在「事件信封三形态与 JSON Schema」那篇展开。

</Callout>

## 会话：30 分钟没动静就换一个

除了「人」，还有一个更小的单位：**会话**，一个人一段连续的访问。热读要「每人每天每篇只算一次」，面板的 COUNTER 指标要「一个会话里同一篇只算一次」，判断一段访问是不是真人也按会话判（「爬虫识别」那篇讲）。

切会话的业界通用规则是：**30 分钟没有任何活动，就开始一个新会话**。Patra 的做法：

- 会话 Cookie 里存会话 ID 和最后活动时间。它不设过期时间，浏览器关掉就失效；命名同设备 Cookie：`__Host-patra_sid` / `patra_sid`。
- 门户每处理一个页面请求或一批浏览器事件：没有会话 Cookie，或者距最后活动超过 30 分钟，就生成新的会话 ID；否则沿用，并把最后活动时间更新为现在。

## `person_id`：把两种身份写成一列

「登录按账号、访客按设备」落到数据库里，Patra 在 ClickHouse 明细表上用一个计算列把它写成一个字符串：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V1__events.sql@8140a9d9482324670b63f00ab3c62690102196c5" lines="13-15" />

```sql
    device_id       String,
    session_id      UUID,
    user_id         UInt64,
```

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V1__events.sql@8140a9d9482324670b63f00ab3c62690102196c5" lines="29-29" />

```sql
    person_id       String MATERIALIZED if(user_id != 0, concat('u:', toString(user_id)), concat('d:', device_id))
```

明细表里未登录的 `user_id` 存成 0。有账号就是 `u:` 加用户 ID，没有就是 `d:` 加设备 ID。加前缀是为了两种 ID 永远不会撞在一起：哪怕某个设备 ID 恰好和某个用户 ID 写法相同，`u:5` 和 `d:5` 也是两个人。之后所有「按人去重」的查询都直接 `uniqExact(person_id)`，不用每次再写一遍「有账号用账号、没有用设备」。流量模拟器造数据时也按同一个写法生成「人」，模拟器的真值和线上的计数才对得上。

## 已知会数错的地方

这套认法不完美，埋点方案里明写了已知偏差：

- **先当访客、后登录，算两个人。** 登录前的事件 `person_id` 是 `d:…`，登录后是 `u:…`。identity 的登录记录里存着设备和账号的对应关系，可以把之前的记录认回同一个人，但这一版只在面板的「新增 / 留存」里用到，门户上的「N 人看过」不做这一步。
- **同一个人两台设备都没登录，也算两个人。** 设备 ID 认的是设备，不是人。
- **清了 Cookie、换了浏览器，就是新访客。** 这是所有持久匿名 ID 的共同局限。

量很小，这一版接受。真正麻烦的是另一种：**不保存 Cookie 的爬虫**。它每次请求都拿到一个新设备 ID、新会话，按设备去重对它完全无效，一个爬虫能变成几千个「人」。这要靠下一篇「爬虫识别」里的真人会话规则拦。
