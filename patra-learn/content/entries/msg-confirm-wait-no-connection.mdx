## 背景：评审的担心

v0.16 接入 identity 的事件外送时（PAP-104），一次独立评审提出：外送在 Modulith 的 `REQUIRES_NEW` 事务里同步等 broker 确认；broker 卡住（端口通、就是不回确认）时，每个外送都拿着一条连接等满超时。Spring Boot 默认的异步线程池有 8 个线程，identity 的连接池只有 10 条，8 个外送一起等，就能占掉 8 条，登录、注册这些和事件毫不相干的请求跟着排队、超时。

identity 当时的应对是在自己的配置里把异步并发压到 2（`spring.task.execution.pool.core-size: 2`）。

<Callout kind="analogy">

连接池像一叠号码牌。请求要查库就领一张，用完还回去；牌发完了，后来的只能排队，排到超时就报错。所以有一条铁律：拿着号码牌的时候不要去等网络。

</Callout>

担心本身没错，可它建立在一个前提上：外送真的在事务里。PAP-104 的修复没有直接加限制，而是先把这个前提查清楚。

## 选项

前提查清了：外送线程本来就不拿连接。剩下的问题是，还要不要限制它们。

## 选择

<Callout kind="lead" label="选了什么">

不加并发上限，加两道护栏。identity 的 `core-size: 2` 和它的配置测试删掉，interaction 也不用配。

</Callout>

第一道是运行时的：等确认的发送模板在发送前先看一眼线程上有没有挂着事务资源，有就直接报错，不发也不等。

<CodeRef at="patra-tool/patra-tool-events/src/main/java/dev/patra/tool/events/publisher/ConfirmingRabbitMessagingTemplate.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="83-92" />

```java
/// 等确认会阻塞几秒到更久，期间线程上挂着的事务资源（数据库连接、EntityManager 等）一直不还，broker 一卡住
/// 就能把连接池占光。Modulith 的外送器跑在 `SUPPORTS` 作用域里，本身不绑资源；外送路径上的选择、路由、映射、
/// 消息转换只要查一次库，连接就会绑到线程上，这里直接拒绝，让问题在测试里暴露，而不是线上饿死连接池。
private static void assertNoTransactionalResources() {
  if (!TransactionSynchronizationManager.getResourceMap().isEmpty()) {
    throw new IllegalStateException(
        "线程上挂着事务资源（数据库连接或 EntityManager）时不能等 broker 确认：外送路径（选择、路由、映射、"
            + "消息转换）不能查库，也不要在事务里经 RabbitMessageOperations 发送");
  }
}
```

报错时事件不会丢：外送失败，登记行留在表里，修好代码后由补投发出去。

第二道是测试：上面那个集成测试留在仓库里。哪天升级 Modulith，外送器被改回在事务里跑，它会变红。

## 代价

<Callout kind="cost">

- **外送路径不能查库**。外送配置里的选择、路由（包括表达式里引用的 bean）、映射、消息转换，都只能用事件自己带的数据。
- **broker 卡住时线程照样被占**。每个外送至少等满确认超时（5 秒）；真卡住时可能到分钟级，因为等不到确认的信道不回缓存，新开信道的那次调用只受 `channel-rpc-timeout` 限制（Spring Boot 默认 10 分钟）。只占线程、不占连接；补投会把排太久的行再派一次，恢复后多出来的重复消息由消费端去重兜住。
- **线程池的排队不设上限**。长时间卡住时，排队的外送任务堆在内存里（每个只带一个事件对象，现在的量可以忽略）。哪天要给它配队列容量，拒绝策略不能用 `CallerRunsPolicy`：提交后监听在业务事务的收尾阶段执行，那时请求线程还拿着业务连接，队列满了让请求线程自己跑外送，原来的问题就回来了。

</Callout>
