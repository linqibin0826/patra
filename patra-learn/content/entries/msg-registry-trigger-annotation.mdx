## 背景：登记表里该放什么

Modulith 的事件登记是这样工作的：事务里调 `publishEvent(事件)` 时，它找出所有会在提交后处理这个事件的监听器，**每个监听器写一行**登记（行里记着监听器的 ID）。监听器执行成功，那一行才算完成；没成功的留在表里，补投任务会再调一次那个监听器。

v0.16 Patra 第一次跨服务发事件，登记表只想放一种东西：**要外送到 RabbitMQ 的事件**。理由有两条：

- 服务内部还有「提交后做一下、丢了也无所谓」的副作用。通知服务（v0.16 新建）要用普通的提交后监听器给浏览器推实时消息，推不到，用户下次刷新页面照样看得到提醒。这类事要是进了登记表，失败后会被补投，过几分钟又推一遍，反而奇怪。
- Patra 把发成功的登记行设成「发完即删」，表里只剩没发出去的。只放外送的事件，「表不空」就等于「有事件卡住了」，排查一眼就看出来。

要分清这两类监听器，先得认识 Modulith 自己的注解。`@ApplicationModuleListener` 只是三个 Spring 注解的组合：

```java
// Spring Modulith 2.1.2 源码：org.springframework.modulith.events.ApplicationModuleListener
@Async
@Transactional(propagation = Propagation.REQUIRES_NEW)
@TransactionalEventListener
public @interface ApplicationModuleListener {
```

提交后、换一条线程、在新事务里处理。Modulith 外送事件的那个监听器（`EventExternalizerModuleListener` 的 `externalize` 方法）就贴着它，只是把传播方式改成了 `SUPPORTS`（为什么改，后面「等确认时占不占连接」那篇讲）。

## 选择

<Callout kind="lead" label="选了什么">

升到 Modulith 2.1.2，由事件工具模块出一个默认值：`registry-trigger-annotation` 填 `@ApplicationModuleListener` 的全类名。登记表里从此只有外送器的行。

## 代价

<Callout kind="cost">

- **服务代码里不写 `@ApplicationModuleListener`**。写了它就会进登记表，失败后被补投；而且它默认是 `REQUIRES_NEW`，在新事务里跑。服务内部的提交后副作用一律用普通的 `@TransactionalEventListener`，接受「崩了就丢」。
- **只消费、不外送的服务也得建 `event_publication` 表**。通知服务不会写登记行，但 Modulith 关机时会查一遍未完成的行，没有这张表会报 SQL 错。
- 服务内部哪天出现一个「提交后必须做成」的副作用，这条约定就要重新想：要么把它变成外送事件，要么单独为它设计可靠的做法。

</Callout>
