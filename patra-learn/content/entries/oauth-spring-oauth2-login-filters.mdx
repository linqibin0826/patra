<Callout kind="lead">

`oauth2Login` 是往过滤器链上加两个过滤器：`OAuth2AuthorizationRequestRedirectFilter` 负责发起授权，`OAuth2LoginAuthenticationFilter` 负责处理回调。`state`、`nonce`、PKCE、换令牌、验签都由它们完成，应用只提供配置和几个可替换的零件。

</Callout>

## 差点手写

这一版最初打算自己写协议流程，理由有两条：这是学习项目，手写学得多；Patra 的门户是 BFF（浏览器只和门户打交道，门户转发给后端），以为 `oauth2Login` 不适合这种架构。

对照官方扩展点核对之后，两条都不成立。协议的安全细节恰恰最不该自己写，而 BFF 也完全够用。关键是这一点：`redirect-uri` 写门户的公网地址，框架把它原样放进授权请求，换令牌时也从存下的授权请求里取，并不比较它和当前请求的地址。所以 identity 处理回调时看到的是内网地址也没有关系。

于是改用官方的 `spring-boot-starter-security-oauth2-client`，这也是企业里的常规做法。

## Patra 换了哪些零件

配置全在这条链上，只匹配发起和回调两组路径，其余请求仍走默认链：

```java

    StatelessSecurityDefaults.apply(http, problemWriter);
    http.oauth2Login(
            login ->
                login
                    .authorizationEndpoint(
                        endpoint ->
                            endpoint
                                .authorizationRequestRepository(repository)
                                .authorizationRequestResolver(resolver))
                    .tokenEndpoint(endpoint -> endpoint.accessTokenResponseClient(tokenClient))
                    .userInfoEndpoint(endpoint -> endpoint.userService(userService))
                    .authorizedClientRepository(authorizedClients)
                    .successHandler(successHandler)
                    .failureHandler(failureHandler))
```

| 扩展点 | 框架默认 | Patra 的做法 | 为什么 |
|---|---|---|---|
| 授权请求仓库 | 存 `HttpSession` | 存 Redis，取出即删 | identity 不建会话，保持无状态 |
| 换令牌、取资料的客户端 | 没有超时 | 带超时的客户端 | 平台卡住时不能一直占着请求线程 |
| 验 `id_token` 的解码器工厂 | 没有设置 HTTP 客户端的口子 | 自己声明一个，做一样的事，只多了超时 | 取公钥也要有超时 |
| 已授权客户端仓库 | 把令牌留在内存 | 什么都不存 | 只做登录，不留令牌 |
| 成功、失败处理器 | 回跳转 | 写 JSON 或错误响应 | 调用方是门户，由门户决定跳去哪 |
| 注册信息 | Boot 的配置属性 | 自己建 `ClientRegistration` | 见下面第二个默认行为 |

## 三个默认行为要主动改

这三处不改也能跑通，所以更要留意。

<Callout kind="warn" label="默认留存 access token">

回调过滤器认证成功后，会把带令牌的「已授权客户端」存进仓库。Boot 的默认实现存在内存里。Patra 不需要替用户调平台接口，就声明一个什么都不存的实现，声明成 Bean 后 Boot 的默认实现随之让位。`TokenNotRetainedIT` 走完流程后检查 Redis 和外部身份表里都没有令牌的字面量，已授权客户端也读不出来。

</Callout>

<Callout kind="warn" label="issuer-uri 让启动时联网">

配 `issuer-uri` 最省事，代价是 Spring Boot 启动时要联网读发现文档，服务能不能启动就依赖外部平台。Boot 的 `spring.security.oauth2.client.registration` 属性还要求客户端 ID 非空，一家没配整个应用起不来。Patra 把三家的端点都写明确，自己建 `ClientRegistration`：没配的平台不注册，入口回 404，其余照常。`issuerUri` 这个字段仍然填，但只用来比较 `id_token` 里的 `iss`，不会触发联网。集成测试断言启动期间模拟平台收到 0 个请求。

</Callout>

<Callout kind="warn" label="`{baseUrl}` 解析成内网地址">

`redirect-uri` 的默认写法带占位符 `{baseUrl}`，按当前请求解析。identity 在内网，解析出来就是内网地址，平台不认。所以要按环境写完整地址。

</Callout>

## 还有两个留意的地方

**处理器里的异常到不了全局异常处理器。** 回调的成功处理器在过滤器里运行，抛出的业务异常进不了 MVC 的 `GlobalRestExceptionHandler`，所以 Patra 的处理器要自己写错误响应。成功响应同样绕开了 MVC，雪花 ID 转字符串也要用那个转换器写。

**绑定不走发起过滤器。** 发起绑定要先判断再认证，结果要以 JSON 回给门户的弹框。框架的发起过滤器会捕获解析器抛出的所有异常并回 500，业务错误传不出来。所以绑定走自己的接口，只复用官方的解析器造授权请求。
