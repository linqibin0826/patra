<Callout kind="lead">

埋点工具按管的那一段分三类：**分析平台**从 SDK、存储到报表一条龙；**采集管线**负责把校验、富化过的事件送进你自己的数仓或数据湖；**客户数据平台（CDP）**负责把各处的数据收齐，再分发给其他工具。

</Callout>

同一家厂商可能同时有几类产品，所以下面说的是「这个产品的主业是哪一段」，依据是各家官方文档对自己的介绍。

## 分析平台：从 SDK 到报表一条龙

这类工具给你 SDK，事件发到它们那里存，打开网页就能看漏斗和留存。差别主要在部署方式、数据存在哪、开不开源。

- **神策分析**：神策数据的分析产品。官方手册里有 Web 全埋点、可视化全埋点、数据质量校验、测试项目与正式项目分开等完整文档（见 [神策分析手册](https://manual.sensorsdata.cn/sa/docs/)）。官网首页称自己是「大数据分析与营销科技解决方案服务商」，并展示等级保护和国产软硬件的适配认证。部署方式本文没在官方页面查到明确说法，不写。
- **GrowingIO**：官网称自己是「面向企业的数据智能增长平台」，核心是「GrowingIO 分析云」，产品分增长分析和客户数据平台两块，常见问题里写明提供 SaaS 与私有化部署两种方式（据 [GrowingIO 官网](https://www.growingio.com/)）。它的采集 SDK 在 GitHub 上公开，Android 无埋点 SDK 用 Apache 2.0 许可，开源的是 SDK，不是整个平台。
- **GA4（Google Analytics 4）**：Google 官网说它免费提供（「free of charge」），另有进阶版 Analytics 360（据 [Google Analytics 官网](https://marketingplatform.google.com/about/analytics/)）。原始事件可以导出到 BigQuery，标准版每天导出上限 100 万条事件，360 版每天最多 200 亿条（据 [GA4 BigQuery 导出说明](https://support.google.com/analytics/answer/9358801?hl=en)）。用户级数据的保留期标准版只能选 2 个月或 14 个月，只影响探索和漏斗报告，不影响标准的汇总报告（据 [GA4 数据保留](https://support.google.com/analytics/answer/7667196?hl=en)）。
- **Mixpanel**：官方文档称自己是产品分析，建立在事件、用户、属性三个概念上（据 [What is Mixpanel](https://docs.mixpanel.com/docs/what-is-mixpanel)）。数据默认存在它在 Google Cloud 上的美国服务器，可以在建项目时选欧盟数据驻留；选错了只能新建项目迁移（据 [Mixpanel EU 数据驻留](https://docs.mixpanel.com/docs/privacy/eu-residency)）。
- **Amplitude**：官方文档称自己是「基于事件的分析工具」（据 [What is Amplitude](https://amplitude.com/docs/get-started/what-is-amplitude)），同时提供自动采集和精确埋点两种方式。
- **PostHog**：开源，任何人都可以自己部署；免费的自部署版用 Docker Compose、MIT 许可，但官方不为自部署提供支持，付费功能只在它的云服务上（据 [PostHog 自部署文档](https://posthog.com/docs/self-host)）。它公开了自己的架构：采集服务把事件写进 Kafka，处理后再写进 ClickHouse（据 [How PostHog works](https://posthog.com/docs/how-posthog-works)）。这和 Patra 选的 Kafka + ClickHouse 是同一个骨架。

## 采集管线：把干净的事件送进你自己的仓库

**Snowplow** 不以报表界面为主业。它的文档开头一句话是把校验、富化过的事件级数据实时送到你的数仓、数据湖或消息流（据 [Snowplow 文档首页](https://docs.snowplow.io/docs/)），可以部署在你自己的云上或它的云上。管线里每个事件都按 JSON Schema 校验，schema 放在叫 Iglu 的 schema 注册中心里；校验没过的事件不进主表，单独存放（据 [Snowplow schemas](https://docs.snowplow.io/docs/fundamentals/schemas/) 与 [Snowplow failed events](https://docs.snowplow.io/docs/fundamentals/failed-events/)）。

说它「开源」要加限定：Snowplow 已把新版管线组件改成「源码可得」（source-available）的 Snowplow Limited Use License，测试或合成数据、个人学习研究可以用，**在生产环境处理真实数据要买商业许可**（据 [Snowplow 许可 FAQ](https://docs.snowplow.io/docs/resources/limited-use-license-faq/)）。

## CDP：收齐，再分发

**Segment**（现属 Twilio）的官方文档称自己是客户数据平台（CDP），负责收集、清洗、激活客户数据（据 [Segment 文档](https://www.twilio.com/docs/segment)）：从网站、App、服务端收第一方数据，再发给你用的各种业务工具。它的 Protocols 功能用 JSON Schema 写埋点方案，不符合方案的事件会产生违规记录，可以选择拦下来，转进单独的隔离来源（据 [Segment Protocols](https://www.twilio.com/docs/segment/protocols)）。这一点和 Snowplow 的 Iglu 一样，都是「格式写成机器能校验的规格」，在「埋点治理」那篇细讲。

## Patra 对应哪一类

Patra 不用上面任何一个，每一段都自己搭（为什么这么选，在「自建还是买 SaaS」那篇讲）。拿上面的分类对照，Patra 的各段分别像：

- **采集**：门户按埋点方案代码埋点，服务端事件由门户发、浏览器事件经门户自己的路径转发。对应各家 SDK 做的事。
- **管线**：采集端点按 JSON Schema 校验、补地区和设备信息、判爬虫，坏事件进 `events.dlq`。这一段的思路最接近 Snowplow：schema 校验加坏数据单独存放。
- **存储**：Kafka 缓冲，ClickHouse 存明细和物化视图汇总。骨架和 PostHog 公开的架构一样。
- **分析**：给作者看的运营面板（PAP-172）这一版还没做；面向读者的计数、热读、看过还看了，是 Patra 自己的应用层，这是现成分析平台不直接提供的部分。
