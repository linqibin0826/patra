## 背景：采集端点是唯一同步的一环

门户每处理一个页面请求，都可能顺手发一批事件给采集端点（`POST /patra-analytics/events`）。采集端点后面的入库、汇总、去重，都隔着 Kafka 异步进行；只有它，是门户要等着回话的。它慢一点，门户就跟着慢；它挂了，不能连累门户。

业界的采集服务（PostHog 的 capture、Snowplow 的 collector）因此都只做三件事：**校验格式、补上只有服务端知道的字段、写进消息队列，然后立刻返回**。重活全在队列后面做，ClickHouse 停机或变慢时采集照收，事件在 Kafka 里等着。Patra 的采集端点也是这样：逐条校验、富化、判爬虫，合格的写 `events.raw`、不合格的写 `events.dlq`，等这一批全部确认后返回 202 和「合格几条、不合格几条」。

剩下要决定的是：**Kafka 本身不可用时怎么办。**

## 选择

<Callout kind="lead" label="选了什么">

Kafka 写不进时返回 503，门户直接丢弃这一批、不重试；只有流量模拟器重试。决定性的理由是代价不对称：行为数据丢一小段只是计数少几条，而为了不丢它去做磁盘缓冲或门户重试，复杂度和拖慢页面的风险都远超这一版的价值。

</Callout>

模拟器为什么要重试：它是用来测吞吐和去重的，丢了事件真值就对不上；而且它不是用户在等的页面，重试多慢都没关系。它对 503、其他 5xx、超时和连接错误按指数退避重试同一个请求体，4xx 不重试：

        LOG.log(System.Logger.Level.ERROR, "采集端点拒收（{0}），不重试：{1}", status, response);

4xx 是请求本身有问题（格式不对、太大），重发一万次也一样；5xx 和超时可能是暂时的，等一等再试才有意义。这是重试策略的通用分界。

## 「写进 Kafka」怎样才算写成功

返回 202 之前要等 Kafka 确认，「确认」到什么程度由生产者设置决定。采集端点的设置集中在一个类里，运行时和测试用同一份：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/java/dev/patra/analytics/infra/collect/publish/KafkaProducerSettings.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="15-34" />

```java

      Map.of(

          "zstd",

          ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
          StringSerializer.class);
```

逐个看：

| 设置 | 取值 | 为什么 |
|---|---|---|
| `acks` | `all` | 所有同步副本都写了才算成功。Patra 是单节点，等同于 `1`，但以后换成多节点不用改配置 |
| `enable.idempotence` | `true` | 生产者给消息编号，网络抖动导致内部重试时，broker 认得出重复、只留一条 |
| `delivery.timeout.ms` | 5000 | 一条消息从交出到放弃的总时限，含内部重试 |
| `request.timeout.ms` | 4000 | 单次请求等 broker 回话的上限。Kafka 要求总时限不小于它加上 `linger.ms`，所以比 5 秒略小 |
| `max.block.ms` | 2000 | 连不上 Kafka 时，`send()` 调用最多卡 2 秒就抛异常 |
| `linger.ms` / `compression.type` | 10 / `zstd` | 攒 10 毫秒凑一批再发、整批压缩，减少请求数和网络字节 |

消息的键是设备 ID，同一设备的事件落进同一个分区、保持先后顺序；值是富化事件的 JSON 文本。

## 整批一个总截止时间：5 秒

所以采集端点没有把超时只交给生产者设置，而是给整批加了一个总截止时间：从开始发送起 5 秒。

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/java/dev/patra/analytics/infra/collect/publish/KafkaEventPublishAdapter.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="70-88" />

```java
  private void sendAll(List<OutboundMessage> messages) {
    Instant deadline = clock.instant().plus(properties.batchDeadline());
    List<CompletableFuture<SendResult<String, String>>> pending = new ArrayList<>(messages.size());
    for (OutboundMessage message : messages) {
      CompletableFuture<SendResult<String, String>> future;
      try {
        future = kafka.send(topicOf(message.stream()), message.key(), message.payload());
      } catch (RuntimeException e) {
        throw new EventPublishUnavailableException("写 Kafka 失败：" + e.getMessage(), e);
      }
      if (future.isCompletedExceptionally() || clock.instant().isAfter(deadline)) {
        throw new EventPublishUnavailableException("写 Kafka 失败或超过整批截止时间，放弃本批");
      }
      pending.add(future);
    }
    for (CompletableFuture<SendResult<String, String>> future : pending) {
      awaitUntil(future, deadline);
    }
  }
```

分两段：

1. **先全部交出去。** 逐条 `send()`，它只是把消息放进生产者的发送缓冲、立刻返回一个 future。任何一次 `send()` 抛异常、已经失败、或者过了截止时间，立刻放弃剩下的，整批失败。
2. **再统一等确认。** 每个 future 只等到截止时间为止，有一条没等到也整批失败。

整批失败抛出的异常被映射成 503。于是 Kafka 不可用时，一次请求最长约 2～5 秒就有结论：连不上的话第一次 `send()` 卡 2 秒就失败，连得上但不回话就等满 5 秒。门户调采集端点的超时设 6 秒，正好盖住它。集成测试里专门造了 Kafka 不可用的场景，断言 6 秒内拿到 503。

## 已经写进去一半怎么办

整批 503 时，前面已经交出去的消息可能有一部分其实写进了 Kafka，只是没等到全部确认。门户丢弃不重试，这部分照常入库，正好不丢；模拟器重试整批时，这部分会再写一次。

这不会导致重复计数：重试时每条事件的 `event_id` 不变，入库时按 `event_id` 去重。采集端点只保证「至少一次」，去重交给下游，这和发件箱「保证不丢、不保证不重」是同一个思路。

## 代价

<Callout kind="cost">

- **Kafka 停机期间的真实浏览会丢。** 门户不重试，这段时间的计数会少。行为数据可以接受，业务数据不行。
- **采集端点要等 Kafka 确认才返回。** 正常时很快，但它让采集端点的延迟直接挂在 Kafka 上；门户那边是「发出去不等结果」，读者感觉不到。
- **整批共进退。** 一批里只要有一条没确认，整批都报 503，已经写成的那部分只能靠下游去重兜住。
- **什么时候该重新考虑**：事件开始承载不能丢的东西（比如按量计费），或者 Kafka 变得经常不可用。那时该换成门户重试或采集端点本地缓冲，并接受随之而来的复杂度。

</Callout>
