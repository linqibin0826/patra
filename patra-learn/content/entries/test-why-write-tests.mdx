## 手工检查：每改一次，全部重做一遍

先想一个小场景：你做了一个记账小程序，有「记一笔」「看本月合计」「删除」三个功能。

每次改完代码，要确认没弄坏东西，只能自己打开程序，把三个功能依次点一遍。三个功能，点一遍两分钟，还能忍。

可是功能会变多。十个功能要点十分钟，一百个功能要点一个多小时。更糟的是：你改的是「记一笔」，却可能弄坏「看本月合计」，所以不能只点你改的那个，要全部重点。

<Callout kind="analogy">

手工检查像每次出门都把家里所有的门窗、煤气、电器挨个摸一遍。头几次你很认真，一个月后你就只看大门了。不是你偷懒，是这件事本来就不适合靠人记性来做。

</Callout>

这里有两个成本，都会随功能数量增长：时间越来越长，人越来越容易漏。

## 测试：把「点一遍」写成会自动重跑的代码

测试就是一小段代码，它自己去调用你的程序，再自己判断结果对不对。写好之后，电脑可以随时、不知疲倦地重跑，一百个测试几秒钟就跑完。

看一个 Patra 里真实的测试。被测的是一个「可以手动拨动的时钟」（后面的文章会讲它为什么存在），这个测试检查「往前拨 30 天」这件事：

<CodeRef at="patra-tool/patra-tool-test/src/test/java/dev/patra/tool/test/clock/MutableClockTest.java@af8cd13c3ec367ccba78615b72e6ff19535cef90" lines="28-38" />

```java
@Test
void should_advance_and_set() {
  MutableClock clock = MutableClock.startingAt(START);

  clock.advance(Duration.ofDays(30));
  assertThat(clock.instant()).isEqualTo(START.plus(Duration.ofDays(30)));

  clock.set(START);
  assertThat(clock.instant()).isEqualTo(START);
}
```

不用懂每个词，看它的三个动作就够了：

1. 造一个从 `START` 开始的时钟。
2. 让它往前拨 30 天。
3. 断言（`assertThat`）：现在的时刻应该等于 `START` 再加 30 天。

如果有人以后改坏了「往前拨」，这一行断言就会失败，测试变红，改的人当场就知道。

测试还有一个副作用：它是一份**不会过期的说明书**。文档会写旧，但只要测试还在跑、还是绿的，它描述的行为就一定还成立。

## 测试在 Patra 里什么时候跑

Patra 不靠人记得去跑测试。每个合并到 `main` 的 Pull Request（一次「请把我的改动合进去」的申请）都会触发 CI（持续集成：一台云上的机器自动把测试跑一遍）。

<CodeRef at=".github/workflows/ci.yml@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="1-12" />

读开头几行注释就能看出：CI 先判断这次改了哪部分（`detect-changes`），再只跑受影响的那部分测试，最后汇总成一个叫 `required-check` 的检查。它是分支保护唯一要求必须通过的检查：红了，就合并不了。

另外每天 UTC 18 点会定时全量跑一次兜底。

<Callout kind="warn">

测试变绿，只能说明「测到的那些情况没问题」，不能说明「一个 bug 都没有」。没写测试的地方，绿灯什么也没保证。

</Callout>

## 测试要花时间，值不值

写测试要花时间，测试本身也要随代码一起维护，这是真实的代价。

<Callout kind="cost">

写一个测试通常比手工点一遍慢。它赚回来的方式是：同一个检查以后会被重跑成百上千次，每次都不花你的时间。

</Callout>

所以越是「会反复改动、出错代价大」的地方，越值得写测试；一次性的小脚本，可以不写。
