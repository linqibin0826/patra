## 坑

<Callout kind="lead" label="坑在哪">

后端在 HTTP 层做的 Long 转字符串，只管经过后端的数据。Grafana 这类直接读数据库的工具绕过了这一层，超过 2^53 的 ID 到了浏览器里会悄悄变成另一个数。

</Callout>

运营看板「文献使用（COUNTER）」组有一张表：时间范围内被读全文最多的 20 篇，点文献 ID 打开门户的文献页。文献 ID 是雪花 ID，一个按时间加机器号拼出来的 64 位整数，远超 2^53。全分支终审指出：这一列原样交给 Grafana，链接会打开错的文献。问题在合并前修掉了。

## 为什么

「对象和 JSON 怎么互转：Jackson」那篇讲过：浏览器里的 JavaScript 只有一种数字类型，能精确表示的整数最大是 2 的 53 次方减 1。更大的整数不会报错，而是被舍入到最接近的、能表示的那个数，后几位就变了。

所以 Patra 在 Spring MVC 写响应时把 `Long` 写成字符串，门户拿到的 ID 一直是准的。可这条规则只装在那一处。看板走的是另一条路：

看板这条路上没有任何 Patra 的代码。这正是 ADS 层想要的（面板只读预先算好的表，不经过任何服务），也正是坑的来源：后端替前端兜住的那些事，Grafana 一样都没有。

<Callout kind="insight" label="怎么认出它">

- 链接打开的是别的文献，或者是 404；把表里显示的 ID 和数据库里的对比，前面十几位一样，后几位不一样。
- JavaScript 打印这种被舍入的大整数时，常常是末尾几位变成 0。
- 只有大 ID 出问题：测试里用 `1001` 这种小 ID 永远测不出来。

</Callout>

## 怎么避开

在交给 Grafana 之前，就在 SQL 里把 ID 转成字符串：

<CodeRef at="patra-infra/docker/grafana/provisioning/dashboards/patra/analytics-ops.json@df36467c9dc87e765c1a8687a7eb238513d5f932" lines="1095" />

```json
          "rawSql": "SELECT toString(article_id) AS article_id, sum(unique_requests) AS `Unique Item Requests`,\n       sum(unique_investigations) AS `Unique Item Investigations`,\n       sum(total_requests) AS `Total Item Requests`\nFROM ads_daily_counter_items_latest\nWHERE day BETWEEN toDate($__fromTime, 'Asia/Shanghai') AND toDate($__toTime, 'Asia/Shanghai') AND traffic = '${traffic}' AND is_synthetic IN (${synthetic:raw})\nGROUP BY article_id ORDER BY `Unique Item Requests` DESC LIMIT 20",
```

`toString(article_id) AS article_id` 让这一列从一开始就是字符串，Grafana 和浏览器只是原样搬运。链接里用 `${__value.raw}` 取这一格的原始值，拼进门户的地址：

<CodeRef at="patra-infra/docker/grafana/provisioning/dashboards/patra/analytics-ops.json@df36467c9dc87e765c1a8687a7eb238513d5f932" lines="1104-1125" />

```json
          {
            "matcher": {
              "id": "byName",
              "options": "article_id"
            },
            "properties": [
              {
                "id": "unit",
                "value": "string"
              },
              {
                "id": "links",
                "value": [
                  {
                    "title": "打开文献页",
                    "url": "${portal}/papers/${__value.raw}",
                    "targetBlank": true
                  }
                ]
              }
            ]
          }
```

`${portal}` 是看板的一个常量变量，写的是门户的地址，这里不展开。

看板 JSON 放在仓库里，集成测试会把每个面板的 SQL 替换掉宏、在测试库上执行。这张表另有一条断言：结果里 `article_id` 的类型必须是 `String`。

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/integrationTest/java/dev/patra/analytics/infra/ads/AnalyticsOpsDashboardIT.java@c3df651e18fcd34d66a1ece0e2cea00c78e9d881" lines="124-134" />

```java
  @Test
  void top_article_ids_are_strings() {
    String top = queries().get("Unique Item Requests 前 20 篇");

    assertThat(
            rows(client, "SELECT toTypeName(article_id) AS t FROM (" + resolve(top, "0,1") + ")")
                .getFirst()
                .getString("t"))
        .as("雪花 ID 超过 2^53，交给 Grafana 前端前要转成字符串")
        .isEqualTo("String");
  }
```

它断言的是类型，不是具体的值：测试库里的 ID 再小，只要有人把 `toString` 删了，类型就会变回 `UInt64`，测试就红。上面说过小 ID 测不出舍入，所以测类型比测值更可靠。

<Callout kind="warn">

转成字符串之后，这一列就不能再按数字排序或做加减了。Patra 这张表按 `Unique Item Requests` 排序，ID 只用来显示和拼链接，没有这个问题；要按 ID 排序的场景，排序要在 SQL 里先按原始数字做完，最后一步再转字符串。

</Callout>
