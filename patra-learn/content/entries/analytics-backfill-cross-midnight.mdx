## 坑

<Callout kind="lead" label="坑在哪">

按「第一条事件的日期」归天的会话，在按天回填时会被切开：算第二天时读不到前一天的前半段，后半段被当成第二天的新会话又算一次。读明细的范围要往前多读一天。

</Callout>

这个坑同样是 PR 合并前的全分支终审指出的。实施计划里写的读取范围是 `[from, to + 1 天]`，注明「为了看到跨午夜的后半段」：右边想到了，左边漏了。

## 为什么

会话表的计算分两层：里层按 `session_id` 聚合出每个会话的首日、页数、漏斗级，外层只留首日落在 `[from, to]` 里的会话。首日是 `toDate(min(derived_at))`，取的是**读进来的事件里**最早的那一条。读的范围从哪开始，决定了 `min` 能看到什么。

还有一个让它藏住的原因：**一次算两天就没事**。区间内部的午夜，两边的事件都在读取范围里，会话被看成完整的一个。所以一次回填 `[10-01, 10-02]` 的测试是绿的，按天一次一天地回填才暴露。

<Callout kind="insight" label="怎么认出它">

- 同一段日期，「一次算完」和「一天一天算」结果不一样，就是区间边界在切东西。这是最便宜的检查：两种回填方式各跑一遍，对比结果。
- 回填出来的历史里，每天都多出一批凌晨开始的单页会话，跳出率偏高。

</Callout>

## 怎么避开

读取范围往前也多读一天，外层的「首日在区间里」照旧：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V9__ads_daily_sessions.sql@c3df651e18fcd34d66a1ece0e2cea00c78e9d881" lines="22-44" />

```sql
CREATE VIEW IF NOT EXISTS ads_daily_sessions_calc AS
SELECT day, is_synthetic, session_kind, funnel_level, single_page, count() AS sessions, now64(3) AS computed_at
FROM (
    SELECT session_id,
           toDate(min(derived_at), 'Asia/Shanghai') AS day,
           any(is_synthetic) AS is_synthetic,
           multiIf(max(is_bot), 'bot', max(source = 'client'), 'human', 'no_script') AS session_kind,
           countIf(event_name = 'page_viewed') AS page_views,
           page_views = 1 AS single_page,
           toUInt8(if(page_views = 0, 0,
               1 + windowFunnel(1800)(toDateTime(derived_at),
                   event_name = 'search_performed',
                   event_name = 'article_clicked' AND JSONExtractString(properties, 'list_type') = 'search',
                   event_name = 'article_viewed',
                   event_name IN ('fulltext_read', 'pdf_downloaded')))) AS funnel_level
    FROM events
    -- 前后各多读一天：跨午夜的会话要看到整个会话才能定它的首日，后半段不能在次日被当成新会话
    WHERE derived_at >= toDateTime({from:Date} - 1, 'Asia/Shanghai')
      AND derived_at < toDateTime({to:Date} + 2, 'Asia/Shanghai')
    GROUP BY session_id
)
WHERE day BETWEEN {from:Date} AND {to:Date}
GROUP BY day, is_synthetic, session_kind, funnel_level, single_page;
```

两头各多一天，各管一件事：

- **往前多读（`from - 1`）**：前一天开始的会话，能看到它真正的第一条事件，首日算对，外层把它滤掉，不会在区间第一天重复出现。
- **往后多读（`to + 2` 之前，即读完 `to` 的后一天）**：区间最后一天开始的会话，能看到它午夜之后的后半段，页数和漏斗级算全。

刷新视图每次算「昨天到今天」，它的区间也有左边界，就是昨天 00:00，往前多读的那一天对它同样生效。

修好后补的测试照搬回填脚本的用法，一天一天地算，断言第二天没有这个会话：

同一个文件里原先就有一个跨午夜的测试 `session_crossing_midnight_counts_on_start_day`，它一次回填两天，只能证明往后多读那一天，证明不了往前那一天。

<Callout kind="warn">

多读进来的那一天只能用来「看清楚」，不能被算进结果。外层的 `WHERE day BETWEEN {from:Date} AND {to:Date}` 必须保留；去掉它，每次都会把前一天、后一天的会话也写进来。

</Callout>

## 顺带：双击过滤也有跨午夜的问题，方向相反

COUNTER 的 Total 指标做双击过滤：同一个人对同一篇，两条事件相隔 30 秒以内只算后一条。判断一条事件算不算，要看它的**下一条**。文献使用表的计算视图读明细只读区间内：

```sql
views AS (
    SELECT toDate(derived_at, 'Asia/Shanghai') AS day, article_id, is_synthetic, person_id, derived_at,
           event_name IN ('fulltext_read', 'pdf_downloaded') AS is_request,
           session_id IN human_sessions AS human
    FROM events
    WHERE event_name IN ('article_viewed', 'fulltext_read', 'pdf_downloaded', 'article_collected')
      AND article_id != 0
      AND derived_at >= toDateTime({from:Date}, 'Asia/Shanghai')
      AND derived_at < toDateTime({to:Date} + 1, 'Asia/Shanghai')
    LIMIT 1 BY event_id
),
```
