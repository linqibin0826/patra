## 坑

<Callout kind="lead" label="坑在哪">

刷新视图把每次的结果追加进按版本去重的目标表时，上一版有、这一版没有的键会一直留在表里，`FINAL` 也去不掉；面板按天求和，就把旧行和新行一起算了，数字翻倍。

</Callout>

这个坑是 PR 合并前的全分支终审指出的，没有到 mini 上才暴露。实施计划最初的约定是「读时一律 `FINAL`」，也写了一个「同一天算两次不翻倍」的测试，测试是绿的。问题出在那个测试碰巧测不到它。

## 为什么

`ReplacingMergeTree(computed_at)` 的规则是：**排序键完全相同**的几行，合并后（或查询加 `FINAL` 时）只留 `computed_at` 最大的那行。它不知道「10-01 单页的那一行」和「10-01 多页的那一行」说的是同一个会话，在它眼里这是两个不同的键，各留各的。

会话表的键里有漏斗级、是否单页、会话类别。一个会话还没结束时，这三样都可能变：多看一页，从单页挪到多页；做了检索，漏斗级往上走；后面来了一条爬虫事件，从真人挪到爬虫。每挪一次，下一次刷新就在新的键上写一行，旧键上的那一行原样留着。

<Callout kind="insight" label="怎么认出它">

- 只有**键里带着「会变的分类」**的表才会中招：同一个对象在两次计算之间能从一个键挪到另一个键（单页 → 多页、真人 → 爬虫；留存表里，认回之后某个首日下的一种口径组合整组消失，而那天的其他行还在）。
- 症状是按天求和偏大，偏多的恰好是「早先的分类」：跳出率偏高、低漏斗级的会话偏多。
- 键集合稳定的表测不出来。活跃表的键是（天, 合成, 口径），同一天算几次都还是那几个键，`FINAL` 完全够用，计划里那个测试就是在它上面写的。

</Callout>

这就是那个绿着的测试：同一天回填两次，读 `FINAL`，数字不变。

## 怎么避开

不靠键去重，改成按「哪一次计算」取：每张带 `_latest` 的 ADS 表都加一个读取视图，面板只读它。

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V9__ads_daily_sessions.sql@c3df651e18fcd34d66a1ece0e2cea00c78e9d881" lines="16-20" />

```sql
-- 面板读这个视图：每天只取最近一次计算的结果。刷新只追加这一次算出的键，上一版有、这一版没有的键
-- （例如会话后来多看了一页，从「单页」挪到「多页」）FINAL 去不掉，按天取 computed_at 最大的那一版才对。
CREATE VIEW IF NOT EXISTS ads_daily_sessions_latest AS
SELECT * FROM ads_daily_sessions
WHERE (day, computed_at) IN (SELECT day, max(computed_at) FROM ads_daily_sessions GROUP BY day);
```

它成立靠两个前提：

1. **一次计算的所有行共用一个 `computed_at`**：计算视图输出 `now64(3)`，同一条查询里它是常量。所以「`computed_at` 最大」等于「最近一次计算」。
2. **每次计算都把那一天的全部键重新写一遍**：计算视图对区间里的每一天给出完整结果，而不是只写变了的键。所以取最近一次计算，就拿到了那一天完整、自洽的一套数字。

修好后补的测试，就是开头那个场景：先回填一次，会话再长大，再回填一次，`_latest` 里只剩一行，而且是新的那一行。

看板 JSON 里所有面板也随之改读 `_latest`，白名单测试对 ADS 表只放行 `_latest` 视图（重复率表除外，见下面的小测）。

<Callout kind="warn">

`_latest` 是按天取最近一次计算。从那条 SQL 也能看出它的边界：如果某次计算对某一天一行都没写出来，这一天没有更新的 `computed_at`，读到的仍是上一版。所以计算视图要保证「区间里的每一天都给出完整结果」，不能为了省事只写有变化的行。

</Callout>
