## 现象

`patra-tool-jpa` 的 `JpaAutoConfigurationTest` 里，用例 `should_skip_error_mapping_without_web_on_classpath` 报 `TimeoutException`。2026-10-29 一个 PR（#311）在本地和 CI 上各撞了一次，两次都是重跑就过。同一天本机还撞过 `patra-tool-batch` 里 `BatchAutoConfigurationTest` 的同类超时。

最容易把人带偏的方向，是以为 JPA 的自动配置被改坏了。

## 根因

首次初始化的开销集中在第一个用例上，本来就离超时线不远；机器一忙，它就越线。这和代码对不对无关。

单元测试的默认超时写在构建插件里：

```kotlin
maxParallelForks = (Runtime.getRuntime().availableProcessors() / 2).coerceAtLeast(1)
forkEvery = 50
systemProperty("junit.jupiter.execution.timeout.testable.method.default", "15s")
```

这个类的每次上下文启动都要 mock 一个 Spring Data JPA 的类；第一次 mock 时 Mockito 要做字节码增强，这笔开销落在最先执行的那个用例上：

## 修法

没有改代码。以后再碰到这两个用例单独超时、所在模块又没改动时：

1. 先看负载：macOS 上 `sysctl -n vm.loadavg`，Linux 上 `uptime`。负载远高于核数，就是它。
2. CI 上只重跑那一个任务：`gh run rerun --job <任务 ID>`，不用整条流水线重来。
3. 只有在没有负载时也稳定复现，才去根治首次 mock 的开销。

<Callout kind="warn">

不要顺手把超时调大。超时是用来发现「测试卡住了」的，调大以后真卡住的测试也要等更久才报。

</Callout>
