## 背景：网关看到的「客户端」其实是门户

v0.12 用户中心那一版要做登录记录、登录设备列表和「新设备登录」提醒邮件，这些都要知道用户的真实 IP 和浏览器信息（User-Agent）。

可浏览器并不直接连网关。门户（Next.js 写的 BFF）替浏览器调网关，网关在 TCP 连接上看到的对端地址是门户自己。真实 IP 只能由门户写进转发头 `X-Forwarded-For` 带过来。

在这之前，网关的做法是**剥掉一切入站转发头**（v0.8 账号那一版定的）。这本身是对的，问题是它也剥掉了门户带来的真实 IP。

选第三种，而且不写自研过滤器，用 Spring Boot 接 Tomcat `RemoteIpValve` 的标准方式。

为什么门户要自己丢：Next.js 16 对入站请求做的是「浏览器没带 `x-forwarded-for` 才用连接地址填上」，浏览器带了就原样保留。

## 代价

<Callout kind="cost">

- **阀门对受信连接还会改写协议、主机和端口**（按 `X-Forwarded-Proto` / `-Host` / `-Port`），后面的剥头过滤器只藏头、不还原。Patra 接受这一点：受信的只有门户，门户是自己的代码，只构造 `X-Forwarded-For` 和 `User-Agent` 两个头，这一条写成了门户与网关之间的契约。
- **受信地址是启动时读的**，改了要重启网关。门户在容器网络里配了固定地址，受信列表只写这一个地址，不写整个网段：信任网段等于信任经端口转发、VPN 进来的所有人。
- **部署在家里那台 Mac mini 上时，记下的多半是内网地址**：浏览器经端口转发进来，门户看到的就是网桥地址。真实公网 IP 要等门户前面有一层会覆盖该头的反向代理时才看得到。

</Callout>

两条集成测试把规则钉住：受信来源的值被采用、取最右边的非代理值、受信来源带的其他转发头照样被剥；非受信来源的值被忽略。
