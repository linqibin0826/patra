<Callout kind="lead" label="结论先说">

2026 年 6 月 9 日，CD 把构建挪到了云端 x86 的 `ubuntu-latest`，但构建命令里没有指定目标芯片，产出的镜像是 x86 格式。Apple 芯片的部署机拉取时报错 no matching manifest。这条流水线自那天起**一次都没有成功部署过**，直到 8 月 27 日要把整套集群拉起来，才第一次真的去拉镜像，问题才暴露。

- **怎么修的**：先在构建命令里补上 QEMU 和 `--platform linux/arm64`；随后又把构建整个搬回部署机原生进行
- **值得记住**：错误不是被发现的，是被撞上的。再加一道部署前的格式断言，把它变成能被发现的

</Callout>

## 现象

2026 年 8 月 27 日，要把整套服务拉起来，部署机拉镜像时报：

```
no matching manifest for linux/arm64/v8
```

镜像在 GHCR 上，名字、版本号都对。最容易把人带偏的方向是网络：看到拉取失败，第一反应往往是代理、DNS、超时。可这句报错说的不是连不上，而是**连上了，找不到合适的那一份**。

## 根因

根因只有一行没写的东西。构建机是 x86 的云端机器，构建命令里没有告诉它「请为 arm64 打包」，它就按自己的芯片默认打出 x86 格式。修复提交的说明，意思是这样：构建任务移到了 x86 的云端机器，没有指定 `--platform`，产出的是 x86 镜像，arm64 的部署机拉取时报 no matching manifest。

门户和学习站的情况类似：它们的镜像同样是 x86 构建出来的，工作流文件的注释里记着，那种镜像在 Apple 芯片上要靠转译层才能运行。

## 为什么近三个月没人发现

这一条是整个事故里最值得停下来想的。

三个月里，流水线没有一次成功把后端服务部署上去过。可没有人看到过这个问题，直到 8 月 27 日要拉起整套集群，才第一次真的去拉镜像。

<Callout kind="insight" label="怎么认出这类问题">

错误一直存在，但没有任何东西在替你**看**它。构建成功了，镜像推上去了，一切看起来正常；只有走到「在目标机器上真的拉一次、跑一次」，才会撞上。

</Callout>

## 修法：两层

**第一层，让这次不再错。** 8 月 27 日的修复在构建里加了 QEMU 并指定 `--platform linux/arm64`。随后，构建整个搬回部署机本机原生进行（那一篇讲了为什么），格式从物理上不可能再错。

**第二层，让将来的错能被发现。** 部署脚本拿到镜像之后，先核对它的芯片架构，不是 arm64 就拒绝部署：

<CodeRef at="patra-infra/cd/deploy.sh@2197850b5a624ed4dbaa97df71e144c343e28baa" lines="56-59" />

```bash
assert_arm64() { # $1=img:tag
  local arch; arch="$($DOCKER image inspect --format '{{.Architecture}}' "$1")"
  [ "$arch" = "arm64" ] || { echo "✗ $1 架构为 ${arch}（期望 arm64）"; return 1; }
}
```

它在主流程里紧跟在「镜像就位」后面，不过就不会往下 `compose up`：

<CodeRef at="patra-infra/cd/deploy.sh@2197850b5a624ed4dbaa97df71e144c343e28baa" lines="116-118" />

为什么本机原生构建之后还要这道断言？因为镜像不一定是刚刚本机打的。回滚时，如果本地没有旧镜像，会从 GHCR 把历史归档拉回来，而那里面躺着修复之前打的 x86 镜像。没有断言，回滚就可能把这次事故的主角重新请回来。

这条规则还有一个单元测试守着：用假的 Docker 把架构伪装成 amd64，断言部署脚本不执行 `up`。
