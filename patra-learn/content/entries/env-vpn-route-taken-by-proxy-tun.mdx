<Callout kind="lead" label="结论先说">

Tailscale 的 `100.64.0.0/10` 路由有时会被装成「绑定到指定网卡」（interface-scoped）的形式。普通流量查路由表时不看这种条目，于是去 VPN 网段的包落进了代理软件虚拟网卡（TUN）铺的大网段路由，被代理接走。代理对 ping 直接在本机代答，所以快得离谱；SSH 在密钥交换阶段就被断。

- **怎么修**：手动补一条不绑定网卡的 `100.64.0.0/10` 路由指向 Tailscale 的网卡；长期用一个定时任务每分钟检查并补上
- **值得记住**：延迟低得不合理，说明包没出本机

</Callout>

背景：2026-08-27，作者把两台 Mac 上的 Tailscale 换成官方图形客户端之后，笔记本上的代理软件也开着 TUN 模式。只有这种组合会碰到，但「看延迟判断包出没出本机」「查路由表里谁接走了流量」到处适用。

## 现象

- ping VPN 里的部署机只要约 0.5 毫秒；
- SSH 连部署机，在密钥交换（kex）阶段被断开；
- 正常时的延迟应该是：直连几十毫秒，经自建中继 20～130 毫秒，经官方境外中继几百毫秒到 1 秒。

## 根因

macOS 的路由表里，一条路由可以带「只对某块网卡生效」的标记（`netstat -rn` 里标志列带 `I`）。普通流量查表时不看这种条目。

代理软件开 TUN 模式时，会铺一组很大的网段路由（比如 `64.0.0.0/2` 这一类）把流量都引进自己的虚拟网卡。Tailscale 的 `100.64.0.0/10` 本来更具体、应该优先；可它一旦被装成绑定网卡的形式，普通流量就看不到它，落进了代理那条大网段路由。

<Callout kind="warn">

代理软件自带的「TUN 旁路路由」设置实测不会在内核里产生旁路，流量仍然先进它的用户态程序，替代不了下面的修法。

</Callout>

## 修法

**应急**（重启后失效）：手动补一条不绑定网卡的路由，指向 Tailscale 的那块虚拟网卡：

```bash
sudo route add -net 100.64.0.0/10 -interface <Tailscale 的 utun 网卡>
```

**长期**：在笔记本上装一个 root 权限的定时任务（LaunchDaemon），每 60 秒检查一次：找出持有 Tailscale 地址的那块 utun 网卡，确认存在一条不绑定网卡的 `100.64.0.0/10` 路由指向它，没有就补上，补的动作记日志。检查是幂等的，重复跑没有副作用。

<Callout kind="insight" label="顺带想通的">

清路由时还踩过一个小坑：笔记本上另有一个常驻的 SSH 端口转发任务，断了会自动重连，它不停地撞目标地址，把虚拟网卡上的一条单地址克隆路由一直顶着不过期。要先停掉这个任务，再清路由。

</Callout>
