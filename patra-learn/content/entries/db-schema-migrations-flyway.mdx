## 表结构是会变的，变更要像代码一样管理

上线后表结构还会不断变：加列、加索引、加约束、新建表。这些变更和代码要对得上：新版代码用了新列，数据库就得有这一列。

如果靠人手工在各个环境执行 SQL，会遇到三个问题：漏了某个环境、执行顺序错了、没人说得清"现在这个库到底改到哪一步了"。

**Flyway** 的做法是：每次表结构变更写成一个**迁移脚本**，放进代码仓库，文件名带版本号。服务启动时，Flyway 检查数据库里已经执行过哪些脚本，把**没执行过的**按版本号从小到大依次执行。

## 它怎么记账

Flyway 在你的数据库里建一张表 `flyway_schema_history`，每执行一个脚本就记一行：版本号、描述、**校验和**（脚本内容算出的一个指纹）、执行时间、是否成功。

看 Patra 的 catalog 服务，它的迁移目录里是这样一组文件：

```
V1__create_venue.sql
V2__create_publication.sql
...
V12__add_venue_nlm_unique.sql
V13__add_venue_instance_unique_key.sql
R__cat_organization_alias_seed.sql
```

文件名的规则：`V` + 版本号 + 两个下划线 + 描述。版本号决定执行顺序。

看一个具体的脚本，它给期刊表加一条唯一约束：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/resources/db/migration/V12__add_venue_nlm_unique.sql@6d96ac9d6c2b8463cddf24d8b3461215b4ff8f4c" lines="8-15" />

```sql
-- 主 NLM：覆盖软删行；允许为空（多个 NULL 互不冲突）
ALTER TABLE cat_venue
    ADD CONSTRAINT uk_venue_nlm_id UNIQUE (nlm_id);

-- 标识符表里 NLM 类型的值全表唯一：主 NLM、副 NLM 都只属于一个期刊
CREATE UNIQUE INDEX uk_venue_identifier_nlm
    ON cat_venue_identifier (identifier_value)
    WHERE identifier_type = 'NLM';
```

脚本里只写"这一版要做的变更"，不是整张表重来。V1 建了 `cat_venue`，V12 就用 `ALTER TABLE` 在原表上加东西。

## 关键规矩：执行过的脚本，不能改

这是用 Flyway 最重要的一条。已经在某个环境执行过的脚本，**内容一个字符都不要改**。

原因是校验和：Flyway 每次启动都会拿"现在文件的校验和"和"记账表里当时记的校验和"比。对不上就说明有人改了历史，Flyway 认为这个库的状态不可信，**拒绝启动**。

Patra 的上线手册里记着这个坑发生过的样子：开发期间本机连着 mini（作者家里常驻的 Mac mini 部署机，上面跑着开发环境的库）时，最容易发生：已经在 mini 的库上执行过的脚本被改了，服务起不来，日志里是 `Migration checksum mismatch` / `Validate failed`。

当时给出的处理办法是：开发库的数据可以丢，确认没有要留的数据就删库重建；改动无害时也可以用 `flyway repair` 把记账表里的校验和更新成新的。更重要的是以后的纪律：**在 mini 上执行过的脚本不再改，有改动就新增脚本**。

比如 interaction 服务给评论加版本号这件事，就是新增了一个脚本，没去动原来建表的脚本：

<CodeRef at="patra-api/patra-interaction/patra-interaction-infra/src/main/resources/db/migration/discussion/V20261031015300__add_comment_version.sql@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="8-12" />

```sql
ALTER TABLE discussion.comment
    ADD COLUMN version INTEGER NOT NULL DEFAULT 1;

ALTER TABLE discussion.comment
    ADD CONSTRAINT ck_comment_version CHECK (version > 0);
```

注意 `NOT NULL DEFAULT 1`：表里已经有评论了，新加的 `NOT NULL` 列必须给已有的行一个值，`DEFAULT 1` 让"已有的评论都算版本 1"。给已有数据的表加约束，永远要想一想存量数据怎么办。前面的 V12 也是这样：它加的是唯一约束，开头的注释就写着「上线前须在 mini 核对没有重复」，因为库里要是已经有重复的 NLM 编号，这个脚本执行时会失败。

## 版本号怎么排

Patra 里能看到两种版本号风格：

- catalog：`V1`、`V2`……`V13`，顺序编号。
- interaction：`V20261031015300__add_comment_version.sql`，用时间戳当版本号，并且按子域放在 `db/migration/discussion/`、`db/migration/reaction/` 这样的子目录里。配置里是 `locations: classpath:db/migration`，Flyway **递归扫描**子目录，整个服务仍然是一份历史、一张记账表。

顺序编号很直观，但两个人同时在各自的分支上新增脚本，容易都取到 `V14`，合并时撞号。时间戳版本号一般不会撞，这是它的好处之一。

除了 `V` 开头的版本化脚本，还有 `R__` 开头的**可重复迁移**，比如 catalog 的 `R__cat_organization_alias_seed.sql`：它没有版本号，**每次内容变了（校验和变了）就重新执行一遍**，并且总在所有版本化脚本之后。适合放"可以反复重新生成"的东西，比如种子数据。脚本开头先删再插，所以改这个文件就是改线上数据。

<Callout kind="warn">

只有 `R__` 脚本允许"改了内容重新执行"。`V` 开头的脚本一旦执行过就是历史，改它等于改写账本。

</Callout>
