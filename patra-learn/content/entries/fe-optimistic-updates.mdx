## 等结果再改，用户会觉得卡

一次点击要经过门户、网关、interaction，再原路回来。网络好时几百毫秒，差时一两秒。如果等结果回来再改数字，用户点完要盯着一个没反应的按钮，常常会再点一下。

乐观更新换了个顺序：先按「应该会成功」改界面，再发请求。两种写法在顺利时都是对的，区别出在失败的时候：

乐观更新的难点全在最后那一步：退回去，而且要退得准。

## 回滚靠的是不动原值

最直接的写法是把数字改成 4，失败了再改回 3。问题是：请求在路上的时候，原来的 3 可能已经被别的东西更新过了，「改回去」改的是哪个值说不准。

门户的做法是不碰原值。服务端给的值（组件的 props）原样留着，乐观值另放在一个单独的状态 `pending` 里：

<CodeRef at="patra-portal/src/lib/helpful/use-helpful-toggle.ts@a81a667d8b65f517028d6e7305893a8d562eee26" lines="60-61" />

```ts
  /// 请求中的乐观值
  const [pending, setPending] = useState<HelpfulValue | null>(null);
```

按钮显示哪个，按顺序挑：有乐观值显示乐观值；没有就显示上一次请求成功时服务端返回的值；都没有就是 props。

<CodeRef at="patra-portal/src/lib/helpful/use-helpful-toggle.ts@a81a667d8b65f517028d6e7305893a8d562eee26" lines="79-83" />

```ts
  const shown: HelpfulValue =
    pending ??
    (settled && settled.viewer === viewer && sameValue(settled.base, server)
      ? settled.value
      : server);
```

点击时设好乐观值，再发请求（`setHelpful` 是一个 Server Action）：

```ts

    const base = server;
    const clickedBy = viewer;
    inFlight.current = true;
    setHint(null);
    setPending({ helpful: on, count: Math.max(0, shown.count + (on ? 1 : -1)) });
    void orUnavailable(setHelpful(target, on)).then((result) => {
      inFlight.current = false;
      setPending(null);
```

注意最后一行：结果一回来，不论成败，先把乐观值清掉。失败时什么都不用「改回去」，`shown` 自然落回原来的值，再显示一条提示就完了。这就是回滚。

成功时也不是留着自己算的 4，而是用服务端返回的数：

<CodeRef at="patra-portal/src/lib/helpful/use-helpful-toggle.ts@a81a667d8b65f517028d6e7305893a8d562eee26" lines="139-145" />

```ts
      if (result.ok) {
        const { helpful: marked, helpfulCount } = result.result;
        setSettled({ base, value: { helpful: marked, count: helpfulCount }, viewer: clickedBy });
        patchHelpful(client, target, result.result);
        markHelpfulStale(client, target);
        return;
      }
```

你点的这几百毫秒里，别人可能也点了，服务端回的可能是 5。以服务端为准，按钮就和真实情况对上了。`patchHelpful` 把新数写进页面上所有缓存了这条内容的列表，`markHelpfulStale` 把它们标成过期但不立刻重取，免得列表在你眼前重新排序。

几个顺带的防护：

- `inFlight` 是一个 ref，请求在路上时再点直接忽略，不会连发两次。
- 点的时候记下是谁点的（`clickedBy`）。请求在路上时如果换了账号（另一个标签页退出了），结果属于上一位，直接丢掉。
- 登录状态还没取回来时，按钮不响应：这时判断不了你有没有登录、邮箱验证没有。

## 什么样的操作适合乐观更新

v0.15 定下「有帮助」用乐观更新，理由是：它是高频的轻操作，等服务端返回会显得卡；计数晚几秒对上也不影响使用。拆开来看，适合的操作有几个共同点：

| 条件 | 有帮助 | 注册账号 |
|---|---|---|
| 几乎总会成功 | 是，失败只有次数用完、内容被删等少数情况 | 否，邮箱被占、格式不对都常见 |
| 成功后的样子能提前算出来 | 是，加一或减一 | 否，要等服务端分配 |
| 猜错了代价小、退得回去 | 是，数字退回去就好 | 否，用户会以为已经注册成功、关掉页面 |

不满足这些条件的，老老实实等结果，按钮上显示「提交中」。

同样的思路也用在不改数据的地方。门户的文献检索页切筛选条件时，地址栏才是真正的状态，可页面跳转要等服务端渲染。`BrowseQueryProvider` 先把新的查询条件当乐观值显示出来，服务端的查询一变就清掉它：

<CodeRef at="patra-portal/src/components/portal/browse/BrowseQueryProvider.tsx@f7ac9f60e8ef610772128b294c8845488f97f33c" lines="67-75" />

```tsx
  const serverKey = serialize(query);
  const [optimistic, setOptimistic] = useState<Q | null>(null);
  const [seenServerKey, setSeenServerKey] = useState(serverKey);
  // 服务端查询变化：渲染期清空乐观值（派生状态写法，本次渲染即用服务端查询）
  if (serverKey !== seenServerKey) {
    setSeenServerKey(serverKey);
    setOptimistic(null);
  }
  const current = optimistic !== null && serverKey === seenServerKey ? optimistic : query;
```

两处是同一个模式：真实值不动，乐观值另放，真实值一来乐观值就让位。
