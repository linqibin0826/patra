Patra 的集成测试约定里写明：用 TestContainers 模拟真实中间件，避免使用内存数据库。

## Testcontainers 是什么

**Testcontainers** 是一个库：在测试代码里写一句「我要一个 PostgreSQL 17」，它就通过 Docker 拉起一个真容器，测试结束后把容器清掉。容器里是真正的 PostgreSQL，和线上用的是同一个镜像。

一次集成测试的生命周期，可以点着走一遍。其中有一步很容易想错。

## Patra 怎么管这个容器

每个测试类各启一个容器太慢，Patra 在测试工具模块里写了一个统一的初始化器：

<CodeRef at="patra-tool/patra-tool-test/src/main/java/dev/patra/tool/test/container/initializer/PostgreSQLContainerInitializer.java@b6e01875bb5692356021c8a19562f557f319fc54" lines="62-125" />

读这段代码，抓住四点：

1. **镜像钉死**：`postgres:17`，和线上的大版本一致。
2. **一个 JVM 只起一次**：用「单例 + 双重检查锁」保证，同一个测试进程里所有测试共用一个容器。注释写着首次启动约 10 到 20 秒，后面复用就没有成本了。
3. **不跨进程复用**：`withReuse(false)`，下一次跑测试一定是干净的新容器，避免旧状态污染。
4. **动态注入连接配置**：容器起来后，用 `TestPropertyValues` 把 `spring.datasource.url` 等写进 Spring 的环境。

每个服务只需要写几行，指定自己的库名：

<CodeRef at="patra-api/patra-catalog/patra-catalog-boot/src/e2eTest/java/dev/patra/catalog/integration/config/CatalogE2EPostgreSQLContainerInitializer.java@b6e01875bb5692356021c8a19562f557f319fc54" lines="12-18" />

然后在测试类上声明用它。下面是真实的机构建议测试头部：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/integrationTest/java/dev/patra/catalog/infra/organization/persistence/OrganizationReadAdapterIT.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="36-42" />

```java
@DataJpaTest
@ContextConfiguration(initializers = CatalogITPostgreSQLContainerInitializer.class)
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
```

注意第三行。`@DataJpaTest` 默认会**尝试把你的数据库换成内存库**；`replace = NONE` 就是在说「不许换，用我给的这个真的」。漏写它，上面整套努力都白费。

<Callout kind="warn">

容器是整个测试进程共享的，所以测试之间要自己清场。比如那个全文抓取的端到端测试，每次开始前先把相关表清空。`@DataJpaTest` 默认每个测试结束后回滚事务，是另一种清场办法。

</Callout>

测试用的镜像版本和线上不一致，就失去了「用真的」的意义。CI 有一步专门核对，常量和 workflow 里声明的版本必须相同，对不上就让 CI 失败：

CI 还会提前把 PostgreSQL、Redis、RabbitMQ 的镜像并行拉好，免得测试一个个等下载。

<Callout kind="cost">

真实容器的代价：需要 Docker、启动要时间、比内存测试慢。所以集成测试只占约 20%，只测「单元测试没法说清」的那一类：SQL、事务、迁移脚本、与中间件的交互。

</Callout>
