<Callout kind="lead" label="坑在哪">

IDE（这里是 IntelliJ IDEA）的编译输出和 Gradle 是同一个 `build/` 目录。IDE 在后台编译的同时你在命令行跑 `./gradlew`，两个进程同时删写 class 文件，命令行这边就报：

- javac：`bad class file … java.nio.file.NoSuchFileException`，或者 `package … does not exist`（包明明在）
- SpotBugs：`java.io.IOException: No files to analyze could be opened`

</Callout>

## 谁在后台编译

Patra 先后撞上过两种情况：

1. **IDE 自己的编译器写进了 `build/classes`**。当时 IDEA 开着「自动构建项目」，又没有单独的 `out/` 目录，它自带的编译器（JPS，进程参数里带 `-Djps.*`）直接写 Gradle 的 `build/classes`。2026-09-24 升级依赖时，命令行的 `check` 和它撞在一起，报的就是上面那几种错。换到 IDEA 不监视的另一个 git worktree 里重跑，全绿。
2. **构建脚本被「外部」改了，IDE 自动重新同步**。后来 IDEA 改成委托 Gradle 构建，JPS 不再写 `build/classes`，可「构建脚本有外部更改时自动重新加载」还开着。Agent 用编辑工具改 `build.gradle.kts`，对 IDEA 来说就是外部更改，它立刻起一次 Gradle 同步、编译 `build-logic`，和紧接着的命令行 `./gradlew` 抢同一个 `build-logic/build/`。症状一样。

后一种更隐蔽：你自己什么都没在 IDE 里点，是改文件这个动作把它叫起来的。

## 怎么避开

- 看到上面的症状，先 `ps` 查有没有 JPS 进程或者第二个 Gradle 进程，别急着改代码或依赖。
- 让 IDE 委托 Gradle 构建，关掉「自动构建项目」和「构建脚本外部更改后自动重新加载」；改完构建脚本，自己在 IDE 里手动点一次加载。
- 关掉之后主检出里还能复现，就在一个 IDE 不监视的临时 worktree 里跑一次全量验证，用完删掉。

<Callout kind="warn">

也有不是抢目录的孤例：一次全量 check 里某个模块报找不到另一个模块的类，那段时间只有这一个构建在跑，单独重编就过，原因没查明。再遇到先按孤例重跑一次；复现了再加 `--info` 看 javac 的 classpath。另一种「源码里有、class 文件里没有」的情况，先 clean 那个模块再查。

</Callout>
