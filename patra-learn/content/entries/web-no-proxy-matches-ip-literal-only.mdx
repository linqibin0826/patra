<Callout kind="lead" label="坑在哪">

两件事常被想当然：一是以为在代理软件里配了「这个网段直连」，命令行工具也会照办；二是以为 `no_proxy` 写了网段，用主机名访问那个网段里的机器也会直连。两个都不成立。

</Callout>

## 命令行工具只看环境变量

curl、wget 这类工具不知道系统里跑着什么代理软件。它们决定走不走代理，只看 `http_proxy` / `https_proxy` / `no_proxy`（大小写两种都认）。代理软件里写的「跳过代理」「按网段直连」，管的是交给它的流量；curl 已经按环境变量把请求交给代理了，代理软件再怎么配也追不回来。

作者的 shell 配置里曾经写着一句注释：「不在 shell 层维护 no_proxy，规则交给代理软件」。这句话是错的，后来改掉了。

认出它的办法是 `curl -v`：如果输出里有 `Uses proxy env variable http_proxy`，就是环境变量在起作用，和代理软件的规则无关。

## 网段只和 IP 字面量比

`no_proxy` 里写网段（`100.64.0.0/10`）要 curl 7.86 以上才支持，而且只和网址里**直接写出来的 IP** 比。网址写的是主机名时，curl 不会先查 DNS 再看那个 IP 在不在网段里：

| 网址 | `no_proxy=100.64.0.0/10` 时 |
|---|---|
| `http://<mini 的地址>:8080/`（直接写 IP） | 直连 |
| `http://mini:8080/`（写主机名） | 走代理 |
| `curl --noproxy '*' http://mini:8080/` | 直连，这一条命令不用任何代理 |

## 它怎么误导了排查

作者有一次排查浏览器访问部署机很慢，用 curl 带主机名去测「直连有多快」，结果也慢，于是一度以为是 VPN 的中继或网络本身坏了。其实那条 curl 也进了代理，测的根本不是直连。换成 `--noproxy '*'` 或直接写 IP，直连只要几十毫秒，问题这才回到正确的方向上（那次的根因见个人环境里的「代理软件把内网主机名解析成假地址」一篇）。

## 怎么避开

- 测「直连快不快」时，用 `curl --noproxy '*'`，或网址里直接写 IP，别让测量本身带上代理。
- 用主机名访问的内网机器，把主机名或域名后缀写进 `no_proxy`。
- 记住这一套只对命令行工具有效。Java 程序另有一套例外列表，语法还不一样，见「JVM 的代理例外列表不认 CIDR」。
