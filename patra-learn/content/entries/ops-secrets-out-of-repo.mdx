## 为什么不能“先提交，回头再删”

Patra 的仓库是公开的。任何提交（包括历史）都全网可读，并且被各种爬虫长期抓取。所以仓库里有一条硬规则：

<Callout kind="warn">

一旦发现密钥被提交，先轮换作废，再清理跟踪。“反正服务连不上”不是不轮换的理由。

</Callout>

顺序不能反：清理历史再快，也快不过爬虫。密钥作废了，被人拿走的那份才真正没用。

## 三种东西，三种放法

不是所有“看起来像密码”的东西都要保密。判断标准只有一个：**泄漏之后坏人能做什么**。

| 种类 | 例子 | 怎么放 |
|---|---|---|
| 公开的开发默认值 | 本地开发库的默认账号密码，只在内网可达 | 可以直接写进配置或随仓库的 `.env`，有意为之 |
| 真正的密钥 | Redis 密码、网关签身份断言的私钥、外部数据源的 API key | 值只放在仓库之外，配置里只写变量引用 |
| CI 要用的凭据 | 缓存加密密钥、覆盖率上传令牌、巡检用的只读令牌 | 存进 GitHub 仓库的 secrets，workflow 里引用 |

第一类有一个例外要看清：Nacos 的令牌签名密钥和各账号密码**不在**这个宽松范围里，它们只放在仓库外。

## 配置里只放引用，值在仓库外

以 Redis 密码为例。服务的配置在仓库里（会被推送到配置中心），里面是这样写的：

```yaml
spring:
  data:
    redis:
      password: ${REDIS_PASSWORD}
```

`${REDIS_PASSWORD}` 是一个**占位符**，没有默认值。真正的值在 `~/.patra/secrets/redis.env` 这个文件里，目录在仓库之外，权限只有自己能读。

这样，仓库、PR、配置中心里都**没有**密码本身。别人读到的只是“这里要一个叫 REDIS_PASSWORD 的值”。

<Callout kind="insight">

代价也要认：密钥换了，要在每台用到它的机器上各改一份。Patra 的取舍是：密钥很少、只涉及几个文件，换这点麻烦，换仓库不可能泄漏。

</Callout>

## CI 里的凭据：secrets

流水线也要用凭据，比如覆盖率上传、缓存加密。它们存在 GitHub 仓库的 **secrets** 里，workflow 里这样引用：

```yaml
cache-encryption-key: ${{ secrets.GRADLE_ENCRYPTION_KEY }}
```

secrets 有两个性质：写进去之后只能覆盖、不能再读出来；一旦出现在日志里，GitHub 会自动打码成星号。它们也不会传给来自别人 fork 的 PR。

权限也只给够用的。Patra 的每日巡检要查 runner 是否在线，用的是一把只有“读管理信息”权限的令牌，叫 `RUNNER_ADMIN_TOKEN`，不是账号的万能令牌。

## 两道门，一起守

| 门 | 在哪 | 拦什么 |
|---|---|---|
| 本地钩子 | 你执行 git commit 时（gitleaks） | 在密钥进入历史之前就拦住 |
| 评审工具 | PR 上的云端扫描 | 钩子被绕过时的兜底 |

两道都不是万能的，所以第一道防线仍是习惯：密钥从不进文件，进文件的只有占位符。
