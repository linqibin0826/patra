## 同一个词，三种意思

先看 Patra 里「用户」这个词。

**在 identity 里**，用户是一个有生命周期的账号：邮箱、验证状态、用户名、一个四态状态机（正常 / 封禁 / 注销冷静期 / 已注销）。

<CodeRef at="patra-api/patra-identity/patra-identity-domain/src/main/java/dev/patra/identity/domain/account/model/aggregate/User.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="19-38" />

**在 interaction 里**，用户只是评论作者、收藏夹主人的一张名片：昵称、头像色号、账号是否正常、主页对这位访客是否可见。

<CodeRef at="patra-api/patra-interaction/patra-interaction-domain/src/main/java/dev/patra/interaction/domain/subject/model/read/UserCard.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="1-27" />

**在 notification 里**，用户是一个收件人：邮箱、邮箱是否验证、账号状态、用户名。它在发送的那一刻向 identity 现查，不存副本。

<Callout kind="lead">

**限界上下文**：一个业务术语只有一种精确含义的范围。出了这个范围，同一个词可以指向完全不同的模型。

</Callout>

## 不只是「用户」

再看一个例子。interaction 和 notification 各有一个叫 `SubjectType` 的枚举，表示被评论的对象的种类，但它们并不相同：

<CodeRef at="patra-api/patra-interaction/patra-interaction-domain/src/main/java/dev/patra/interaction/domain/subject/model/enums/SubjectType.java@6d96ac9d6c2b8463cddf24d8b3461215b4ff8f4c" lines="1-45" />

interaction 里有三种（文献、期刊、投稿经验），每一种带着「能收藏吗、能讨论吗」这样的能力。

<CodeRef at="patra-api/patra-notification/patra-notification-domain/src/main/java/dev/patra/notification/domain/kernel/model/enums/SubjectType.java@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="1-22" />

notification 里只有两种，因为提醒只涉及文献和投稿经验。它的 `parse` 遇到不认识的值不抛异常，因为对方以后可能新增种类，它要能容忍。

同名但不是同一个类，这是有意的。每个上下文用自己的词、自己的模型，在边界处翻译。

## 为什么不共用一个类

共用一个类看起来省事，实际是把两个上下文焊在一起：

- identity 给 User 加一个字段，所有用到 User 的服务都得重新编译、重新发布。
- 一个服务为了自己的需要改了共享类，会不知不觉改变别人的含义。
- 每个服务本来只要几个字段，却背着整个模型。

分开的代价是翻译：两边的模型之间要有一道转换。Patra 的做法是通过 HTTP 接口取数据，在自己这边转成自己的模型（见后面的跨服务调用篇）。

## Patra 的服务就是上下文

Patra 的四个业务服务，大致对应四个上下文：

| 服务 | 它是什么上下文 | 核心的词 |
|---|---|---|
| catalog | 文献目录 | 文献、期刊、作者、MeSH、机构 |
| identity | 身份与账号 | 用户、会话、登录记录 |
| interaction | 社区互动 | 对象、收藏夹、评论、有帮助 |
| notification | 通知送达 | 提醒、偏好、邮件、实时推送 |

它们的往来，用箭头表示谁依赖谁的数据：

箭头方向总是「谁需要谁的数据」，而且每次只带走对方愿意给的那一部分。notification 还会回头向 interaction 查对象的显示信息，也是走内部接口，不是直接读对方的库。

<Callout kind="insight">

「用户名只存在 identity」就是边界的一个具体体现。其他服务的表里只存用户 ID，要显示名字时向 identity 现查；改名只改 identity 的一行，别处不用回刷。构建里还有检查（R6）守着这条边界。

</Callout>

## 子域和限界上下文的区别

两个词容易混：

- **子域**是在拆「业务问题」：这个生意由哪几块组成。
- **限界上下文**是在划「模型边界」：一套术语和模型的适用范围。

Patra 里两者大致对齐：一个服务是一个上下文，服务里再分子域。但这是实践上的对齐，不是定律。有的团队一个上下文里跨好几个子域，也有的一个子域被拆进几个上下文。
