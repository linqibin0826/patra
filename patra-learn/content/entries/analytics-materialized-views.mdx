<Callout kind="lead">

ClickHouse 的物化视图是一个**插入触发器**：每当一批数据写进源表，它就对这一批跑一次 `SELECT`，把结果追加进另一张目标表。

</Callout>

## 它不是定时刷新的视图

很多数据库里的物化视图是「把一条查询的结果存下来，定时或手动刷新」，例如 PostgreSQL 要执行 `REFRESH MATERIALIZED VIEW` 才会重算整张结果。

ClickHouse 的不一样：它从不重算，也从不回头看源表里已有的数据。它只在写入那一刻，拿**刚写进来的这一批**算一次。所以计数接口查汇总表时，数据已经是写入时就汇总好的，不用每次扫明细。

Patra 的明细表 `events` 上挂了三个物化视图，各自写一张汇总表：

| 汇总表 | 一行代表 | 用来 |
|---|---|---|
| `article_session_reads` | 一篇文献 × 一个会话 × 一个人 × 一天 | 「N 人看过」「N 人读过全文」、热读、看过还看了 |
| `session_quality` | 一个会话 | 判断这个会话是不是真人会话 |
| `daily_person_activity` | 一个人 × 一天 | 日活、留存 |

## 目标表：只存「有没有过」

以文献 × 会话这张为例，表和物化视图写在同一个建表脚本里：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V3__article_session_reads.sql@8140a9d9482324670b63f00ab3c62690102196c5" lines="3-27" />

```sql
CREATE TABLE IF NOT EXISTS article_session_reads (
    article_id    UInt64,
    session_id    UUID,
    person_id     String,
    day           Date,
    is_synthetic  Bool,
    viewed        SimpleAggregateFunction(max, UInt8),
    fulltext      SimpleAggregateFunction(max, UInt8)
) ENGINE = AggregatingMergeTree
ORDER BY (article_id, session_id, person_id, day, is_synthetic)
SETTINGS non_replicated_deduplication_window = 1000;

-- 查看类事件（埋点方案 §6.8）；全文 = 全文阅读或下载 PDF。列名写明：SELECT * 不含计算列
CREATE MATERIALIZED VIEW IF NOT EXISTS article_session_reads_mv TO article_session_reads AS
SELECT
    article_id,
    session_id,
    person_id,
    toDate(derived_at, 'Asia/Shanghai') AS day,
    is_synthetic,
    1 AS viewed,
    event_name IN ('fulltext_read', 'pdf_downloaded') AS fulltext
FROM events
WHERE article_id != 0
  AND event_name IN ('article_viewed', 'fulltext_read', 'pdf_downloaded', 'article_collected');
```

- **`AggregatingMergeTree`**：后台合并时，把排序键相同的多行聚合成一行。合并之前，同一个键可能有好几行，所以查询时还要再按键聚合一次（`max(viewed)`）。
- **`SimpleAggregateFunction(max, UInt8)`**：告诉引擎，合并时这一列取最大值。`viewed` 只有 0 和 1，取最大值就是「这个会话里看过没有」。
- **`SELECT` 里列名写明**：`article_id`、`person_id` 是 `events` 上的计算列（`MATERIALIZED`），`SELECT *` 不会带上它们。

`daily_person_activity` 里连 `user_id` 都写成了 `SimpleAggregateFunction(max, UInt64)`：ClickHouse 26.x 不允许 `AggregatingMergeTree` 有既不在排序键里、也不是聚合函数的列。同一个 `person_id` 的 `user_id` 不变，取最大值不改变它。这一处和设计文档里的写法不同，以代码为准。

<Callout kind="insight" label="怎么认出它">

源表的去重发生在**合并时**，物化视图的汇总发生在**写入时**，写入永远在合并之前。凡是「源表靠合并去重 + 物化视图做汇总」的组合，都要先问一句：同一条数据来两次，汇总列算出来一样吗？

</Callout>

所以 Patra 两头堵：

1. **重复尽量在批次层面拦住**：重试同一批时，块令牌让整批被丢弃，明细表和三张汇总表都不会多出一份。
2. **漏过去的，让它算两次也无所谓**：三张汇总表的列全是 `max` / `min`（「有没有过」「最早一次」），同一事件来几次结果都一样；对外的数字都是按人去重的人数。汇总表里**不放** `sum`、`count` 这类会被重复放大的列，日活表也没有「当天事件条数」。

## 重试时还有一个坑：明细写成了，汇总没写成

```java
  public static InsertSettings settings(String token) {
    return new InsertSettings()
        .setDeduplicationToken(token)
        .serverSetting("deduplicate_blocks_in_dependent_materialized_views", "1")
        .serverSetting("input_format_null_as_default", "1")
        .serverSetting("date_time_input_format", "best_effort")
        .serverSetting("input_format_json_read_objects_as_strings", "1");
  }
```

这就是为什么三张汇总表也都设了 `non_replicated_deduplication_window = 1000`：它们要能自己记住令牌。集成测试专门造过这个场景：先删掉 `article_session_reads` 让写入失败，重建表后带同一令牌重试，断言四张表各有一行。

## 物化视图只看得到这一批：跨批的判断留给查询

「看过人数」只数**真人会话**：会话里至少有一条浏览器事件，并且没有一条被判为爬虫。可一个会话的事件会分散在很多批里，爬虫标记可能在第十批才出现。物化视图每次只看到一批，没法回答「整个会话里有没有爬虫事件」。

做法是把判断拆成两半：物化视图只记每个会话的特征，每批各记一行，合并时取最大值；判断留到查询时做。

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V4__session_quality.sql@8140a9d9482324670b63f00ab3c62690102196c5" lines="11-17" />

```sql
CREATE MATERIALIZED VIEW IF NOT EXISTS session_quality_mv TO session_quality AS
SELECT
    session_id,
    source = 'client' AS has_client,
    toUInt8(is_bot) AS has_bot,
    toDate(derived_at, 'Asia/Shanghai') AS first_day
FROM events;
```

查询时按 `session_id` 分组，`HAVING max(has_client) = 1 AND max(has_bot) = 0` 就是真人会话，再和 `article_session_reads` 连起来数人。爬虫事件照样写进文献 × 会话表，排除放在查询里：口径哪天改了，只改查询，不用重算汇总。

## 放在数据分层里看

业界常把数据仓库分成几层，Patra 这一版用的是同样的思路：

| 层 | 业界叫法 | Patra 里是 |
|---|---|---|
| 明细层 | ODS + DWD | `events`：一行一条富化事件，按天分区，90 天后整个分区丢掉 |
| 汇总层 | DWS | 三张物化视图汇总表，写入时生成；两张文献 / 会话表长期保留，日活表 400 天 |
| 应用层 | ADS | 计数接口查汇总表、外面套 Redis 60 秒缓存；热读与看过还看了由定时任务算好写进 PG 快照 |

物化视图就是明细层到汇总层的那根管子。它省掉了每次查询扫明细，代价是这篇讲的两条：汇总列必须幂等，跨批的判断做不了。
