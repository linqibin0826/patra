<Callout kind="lead">

服务发现就是：每个服务启动时把「我叫什么、在哪个地址」报到注册中心；调用方只记服务名，真要发请求时再去注册中心查这个名字下有哪些实例，挑一个发过去。Patra 的注册中心是 Nacos。

</Callout>

## 为什么不把地址写死

把 registry 的地址写进 catalog 的配置，看起来最简单。但地址是会变的：

- 容器重建后可能拿到新地址；
- 同一个服务可能同时跑两个实例，写死只能打到一个；
- 一个实例挂了，调用方得知道别再往那儿发。

<Callout kind="analogy">

像医院的叫号台。医生（服务实例）上班时在台上登记「我在 3 号诊室」，下班就划掉。病人（调用方）不用记哪位医生在哪间，只说「看内科」，叫号台给出一间现在有人的诊室。

</Callout>

## 第一步：服务启动时报到

Patra 的服务都由工具模块 `patra-tool-launch` 接入 Nacos。它在 Spring Boot 加载配置之前，先补上一组服务发现的默认值：

<CodeRef at="patra-tool/patra-tool-launch/src/main/java/dev/patra/tool/launch/NacosDefaultsPostProcessor.java@b6e01875bb5692356021c8a19562f557f319fc54" lines="58-74" />

```java
  private static final Map<String, Object> DEFAULTS =
      Map.of(
          "spring.cloud.nacos.server-addr",
          "${PATRA_NACOS_ADDR:${PATRA_INFRA_HOST:127.0.0.1}:8848}",
          "spring.cloud.nacos.username",
          "${NACOS_USERNAME}",
          "spring.cloud.nacos.password",
          "${NACOS_PASSWORD}",
          "spring.cloud.nacos.discovery.service",
          "${spring.application.name}",
          "spring.cloud.nacos.discovery.ip",
          "${PATRA_ADVERTISE_IP:}",
          // nacos 3.x gRPC 握手未完成时同步注册会失败，fail-fast 会让整个应用启动失败
          "spring.cloud.nacos.discovery.fail-fast",
          "false");
```

和服务发现有关的是两行：

- `discovery.service` 取 `spring.application.name`：服务在注册中心里的名字就是它的应用名，比如 `patra-registry`。调用方写的 `lb://patra-registry` 对的就是这个名字。
- `discovery.ip` 取环境变量 `PATRA_ADVERTISE_IP`，没设时留空，由客户端自己探测本机地址。

<Callout kind="warn">

自动探测的地址不一定是别人能连到的地址。一台机器开着代理软件时会多出一块虚拟网卡，探测可能挑中它，注册上去的地址别的机器根本路由不到。Patra 吃过这个亏（当时是 XXL-Job 执行器自动探测地址，道理相同），所以凡是要对外登记自己地址的组件，都显式读 `PATRA_ADVERTISE_IP`。

</Callout>

## 第二步：发请求那一刻换成真实地址

catalog 这边，基础地址只写服务名：

<CodeRef at="patra-api/patra-catalog/patra-catalog-boot/src/main/resources/application.yml@3cf6fa5757b3be54c3b030e4cace871f53e2599c" lines="72-78" />

```yaml
    http-interface:
      connect-timeout: 2s
      read-timeout: 5s
      groups:
        registry:
          base-url: lb://patra-registry
          read-timeout: 10s
```

客户端用的是工具模块提供的 `httpInterfaceLoadBalancedRestClientBuilder`，它带着 Spring Cloud 的 `@LoadBalanced` 注解：

<CodeRef at="patra-tool/patra-tool-http-client/src/main/java/dev/patra/tool/httpclient/autoconfigure/HttpClientInterfaceAutoConfiguration.java@b6e01875bb5692356021c8a19562f557f319fc54" lines="152-163" />

<CodeRef at="patra-api/patra-catalog/patra-catalog-boot/src/main/java/dev/patra/catalog/config/HttpClientConfiguration.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="51-57" />

`@LoadBalanced` 让 Spring Cloud 给这个 Builder 建出的客户端挂一个拦截器。每次请求发出前，拦截器看到 `lb://patra-registry`，就去服务发现客户端（这里是 Nacos 的）要 `patra-registry` 的实例列表，挑一个，把服务名换成那个实例的真实地址和端口，再真正发出去。

## 「客户端」负载均衡

传统做法是在服务前面放一台负载均衡器（比如 Nginx），所有请求先到它，再由它分给后面的机器。Spring Cloud LoadBalancer 是另一种：**挑哪个实例由调用方自己决定**，请求不经过任何中间节点。好处是少一跳，坏处是每个调用方都要拿到一份实例列表。
