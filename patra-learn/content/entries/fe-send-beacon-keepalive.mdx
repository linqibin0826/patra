<Callout kind="lead">

`fetch` 加上 `keepalive: true`，请求就能比发起它的页面活得久；`navigator.sendBeacon` 是专为上报做的「只管发、不管回」的 POST，内部用的是同一个机制。两者共用一份整页约 64 KiB 的在途额度。

</Callout>

## 普通请求为什么会丢

上一篇「门户怎么埋点」讲过，浏览器事件先进队列、攒一批再发。攒批省请求，但也意味着任何时刻队列里都可能有几条还没发。读者如果这时关掉标签页、跳到别的网站、或者在手机上切到别的 App，这几条就面临丢失。

浏览器的规矩是：页面卸载时，它发起的、还没完成的普通请求一并中止。早年的做法是在 `unload` 里发一个同步请求，强行让浏览器等它发完，结果是关页、跳转都被拖慢。现在的标准做法是下面两个工具。

## 两个工具

| | `navigator.sendBeacon(url, data)` | `fetch(url, { keepalive: true, ... })` |
|---|---|---|
| 方法 | 只能 POST | 任意方法 |
| 请求头 | 不能自定义（只能借 `Blob` 的类型设 `Content-Type`） | 随便设 |
| 能拿到响应吗 | 不能 | 能，和普通 fetch 一样拿 Promise |
| 返回什么 | 布尔值：`true` 只表示浏览器把它排进了发送队列，不表示服务器收到了 | Promise |
| 页面关了还发吗 | 发 | 发 |
| Cookie | 带（同源请求，凭据模式是 include） | 按 fetch 的凭据设置 |

MDN 的建议：只是上报数据、不关心回应，用 `sendBeacon`；要换方法、改请求属性、或者要看响应，用 `fetch` 加 `keepalive`。

<Callout kind="warn">

`sendBeacon` 返回 `true` 只是「浏览器接下了」。服务器有没有收到、回了什么，页面永远不知道。所以它只适合「丢几条也无所谓」的数据，埋点正好是这种。

</Callout>

## 什么时候算「最后时刻」

直觉是在 `unload`、`beforeunload` 里发。可这几个事件在很多情况下不触发，手机上尤其不可靠：读者切到别的 App，浏览器可能直接把页面冻结或回收，`unload` 根本不来。`unload` 还会让页面进不了浏览器的往返缓存（点「后退」秒回的那个缓存）。`pagehide` 不影响往返缓存，可可靠性问题一样。

MDN 给的答案是 `visibilitychange`：页面变成 `hidden` 是页面能可靠观察到的最后一个事件。切标签、关标签、最小化浏览器、手机上切到别的 App 都会触发它，应当把它当作这次访问的可能终点。

这里大多数人会卡住的一点：**`hidden` 不等于读者走了**。读者可能只是切出去看一眼又回来。所以在 `hidden` 时发的是「到目前为止攒下的」，读者回来后继续攒、继续发，不会因此多算或少算。

定时和攒满 20 条走的是 `post`：

<CodeRef at="patra-portal/src/lib/analytics/client/queue.ts@ffc25c0bf848b54ae29bb08571a5c491c1f5089d" lines="87-100" />

```ts
  function post(body: string): void {
    try {
      deps
        .fetch("/api/reading-signals", {
          method: "POST",
          keepalive: true,
          headers: { "Content-Type": "application/json" },
          body,
        })
        .catch(() => {});
    } catch {
      // fetch 同步抛错（如 keepalive 超出在途上限）同样丢弃
    }
  }
```

平时也带 `keepalive`，是因为一批发出去之后读者随时可能关页，带上它这批就不会半路被中止。页面隐藏时走 `flushWithBeacon`：

<CodeRef at="patra-portal/src/lib/analytics/client/queue.ts@ffc25c0bf848b54ae29bb08571a5c491c1f5089d" lines="126-139" />

```ts
    flushWithBeacon() {
      for (const batch of take()) {
        const body = bodyOf(batch);
        if (deps.sendBeacon) {
          try {
            deps.sendBeacon(ENDPOINT, new Blob([body], { type: "application/json" }));
          } catch {
            // 丢弃
          }
        } else {
          post(body);
        }
      }
    },
```

浏览器不支持 `sendBeacon` 时退回 `fetch keepalive`。谁来调 `flushWithBeacon`？挂在根布局里的 `AnalyticsRoot`：

<CodeRef at="patra-portal/src/components/analytics/AnalyticsRoot.tsx@ffc25c0bf848b54ae29bb08571a5c491c1f5089d" lines="31-49" />

```tsx
  useEffect(() => {
    const onVisibilityChange = () => {
      if (document.visibilityState !== "visible") {
        flushWithBeacon();
        return;
      }
      if (pending.current !== null) {
        sent.current = pending.current;
        pending.current = null;
        track("page_viewed", {});
      }
    };
    document.addEventListener("visibilitychange", onVisibilityChange);
    window.addEventListener("pagehide", flushWithBeacon);
    return () => {
      document.removeEventListener("visibilitychange", onVisibilityChange);
      window.removeEventListener("pagehide", flushWithBeacon);
    };
  }, []);
```

`visibilitychange` 是主路，`pagehide` 是兜底，代码注释给的理由是「有的浏览器关标签页时不触发 visibilitychange」。两个事件都来也没关系：第一次已经把队列清空，第二次什么都不发。

站内跳转（点链接进另一篇文献）不会卸载页面，队列还在，点击事件入队后照常跟下一批一起发，不用特别处理。

## 64 KiB 是整页共用的在途额度

keepalive 请求能活过页面，浏览器就得防着它被滥用。Fetch 规范的做法：发一个带 keepalive 的请求时，把**这个页面所有还没完成的 keepalive 请求**的请求体大小加起来，再加上这一个，超过 64 KiB 就直接返回网络错误。Beacon 规范写明 `sendBeacon` 用的就是带 keepalive 标记的请求，和 fetch keepalive 共用这份额度，超了就返回 `false`。

所以埋点方案给每批定了上限：**最多 50 条、序列化后不超过 48 KiB**，给额度留出余量（队列按条数和字节顺序切批，单条就超过上限的直接丢，正常用法碰不到）。门户的 `/api/reading-signals` 对应地按 64 KiB 拒收，回 413。

超额时两个工具的表现不一样：`sendBeacon` 返回 `false`；fetch keepalive 按规范是返回网络错误，也就是 Promise 被拒绝。门户的 `post` 两条路都接住了：外面的 `try` 接同步抛错（注释里写的就是超额的情况），`.catch(() => {})` 接 Promise 被拒绝。不管哪种，结果都是丢弃这一批、不往控制台报错。

<Callout kind="insight">

额度是按「在途」算的。平时 5 秒一批、一批几 KiB，前一批早就回来了，碰不到上限。真正会挤的是页面隐藏那一刻：定时发的那一批可能还没回来，`sendBeacon` 又要把剩下的全塞进去。每批卡在 48 KiB，就是为了这时候还有空间。

</Callout>
