<Callout kind="lead" label="选了什么">

CD 和巡检失败时，只用 GitHub 自带的通知（App 推送加邮件），不设自建的通知通道。2026 年 8 月 27 日 Patra 曾接入一个自建推送服务，8 月 28 日就整个拆掉了。

</Callout>

## 背景：曾经有一条专线

重做 CD 的时候，同时做了一条失败通知通道：一个自建的推送服务（ntfy），配上手机应用，流水线出事就推一条到手机。听上去很专业：生产系统不都该有独立的告警通道吗？

第二天它就被拆了。拆除的理由，用一句话说：这是单人 dev 环境。自己发布，自己看结果，要通知的人有且只有一个。

## 选择：通知条数没少，设施少了一整套

决定性的一条是：**它能送到的消息，GitHub 本来就送得到。** 在单人项目里，触发者、定时任务的维护者、收通知的人，是同一个人。自建通道没有让你多知道任何一件事，只是多了一个可能自己出问题的环节。

这次决定还被写进了案发地：CD 工作流的头注释里连日期一起记着，巡检工作流的头注释里也留着一句「不设自建通知通道」。防的是几个月后的自己手痒，又想把它建回来。

现在出事了去哪看，就两个地方：手机上收到通知，点进去就是那次运行的日志；或者主动打开仓库的 Actions 页，每一次运行的绿红都列在那里。平时的默认状态是**无声即安好**：每天早上的巡检跑完，手机没响，就是全绿。

## 一条更一般的原则

拆通知通道不是抠门，是一条原则：**不给单人 dev 环境套生产级的运维模板。**

值班表、告警分级、独立通知通道、冗余备份链，这些东西在多人的生产团队里每一件都有受众。受众不存在时，它们不会提供安全感，只会提供维护负担，以及「通知系统自己坏了没人通知」这种套娃问题。

同一条原则在别处也用过：配置中心的数据备份，在 v0.9 的版本范围里明确写成了「不做」，理由是 dev 数据可丢弃，生产环境才需要。

克制不等于什么都不做。**有用的检查保留了下来**：每天查 runner 在不在、版本有没有过期这类检查，防的是「隔一阵回来干活时，发现设施早就悄悄坏了」，受众是未来的自己，所以留着。多余的是「主动推到手机」这一层。

## 代价与何时重新考虑

<Callout kind="cost">

- 你得自己保证平台的通知设置是开着的。关了，失败就真的沉默了。
- 如果项目以后有了其他维护者，或者有了需要保证可用性的线上用户，「要通知的人只有自己」这个前提就不成立了，这时该重新评估要不要独立的告警通道、值班和备份。

</Callout>
