## 普通唯一的盲区：它管整张表

上一篇讲过，`UNIQUE (email)` 保证整个 `email` 列没有重复值。但现实里的规则常常带条件：

- 「活着的」用户邮箱不能重复，已注销的不算；
- 「类型是 NLM」的标识符不能重复，别的类型的重复也无所谓；
- 「中文名」的主标签，每家机构只能有一条，别的语言、别的标签类型不受限。

规则里都有"在满足某个条件的行里"这个前提。

## 局部唯一索引：给唯一索引加 WHERE

PostgreSQL 允许在 `CREATE UNIQUE INDEX` 后面加 `WHERE`，写成"只有满足条件的行才进这个索引，也只有它们参与唯一性检查"。这就是**局部（部分）唯一索引**。

```sql
-- 示意：活着的用户邮箱唯一，已软删除的行不参与
CREATE UNIQUE INDEX uk_user_email_alive
    ON users (email)
    WHERE deleted_at IS NULL;
```

被软删除的行（`deleted_at` 不为空）压根不在这个索引里，所以新用户可以复用它的邮箱。

## Patra 里的真实例子

catalog 为机构维护了一张别名表 `cat_organization_alias`，补 ROR 里缺的中文名和简称。每条别名有类型：`LABEL` 是可作显示名的全名，`ALIAS` 是简称、旧名这类只参与搜索匹配的。显示中文名时取"中文的 LABEL"，如果同一家机构有两条中文 LABEL，取哪个就说不清了。于是有这条规则：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/resources/db/migration/V9__add_suggest_trigram_indexes.sql@af8cd13c3ec367ccba78615b72e6ff19535cef90" lines="64-68" />

```sql
-- 一家机构只能有一条中文 LABEL：zhName 取 zh LABEL，两条文字不同的 LABEL 会让「最短者胜出」压掉审过的名字。
-- 种子（R__cat_organization_alias_seed.sql）按此规则生成：某机构已有手工 LABEL 时，Wikidata 的 LABEL 生成为 ALIAS。
CREATE UNIQUE INDEX uk_org_alias_zh_label
    ON cat_organization_alias (ror_id)
    WHERE alias_type = 'LABEL' AND lang = 'zh';
```

读法：只有"类型是 LABEL 且语言是 zh"的行才进这个索引；在这些行里 `ror_id` 不许重复。同一家机构可以有任意多条 `ALIAS`，也可以有英文的 `LABEL`，只是不能有第二条中文 `LABEL`。

这张表还有一个普通唯一约束 `uk_org_alias (ror_id, alias)`：同一家机构同样的别名文字不能出现两次。两条规矩各管各的：

## 一个容易误会的写法：WHERE ... IS NOT NULL

catalog 的作者表和 interaction 的对象登记表里各有一条这样写的：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/resources/db/migration/V3__create_author.sql@da049982156cfbb1f3c7bd753948df3a5b9bc06c" lines="132-134" />

```sql
-- 软关联部分唯一索引：仅 author_id 非空时约束同篇不重复关联同一已消歧作者
CREATE UNIQUE INDEX uk_pub_author ON cat_publication_author (publication_id, author_id)
    WHERE author_id IS NOT NULL;
```

`author_id` 允许为空（作者暂时没匹配上已知作者）。这条索引的 `WHERE author_id IS NOT NULL` 表达了意图："只在 `author_id` 有值时检查"。

细看一下就会发现一个事实：PostgreSQL 的唯一约束本来就不认为两个 NULL 相等（上一篇讲过），所以哪怕去掉这个 `WHERE`，`author_id` 为空的多行也不会互相冲突。这里的 `WHERE` 对**唯一性的结果没有改变**，它的作用是让索引里不存没意义的 NULL 行、少占空间，同时把意图写在了定义里。

对比前面两个例子：中文 LABEL、NLM 类型的 `WHERE` 是真正**改变了规则**——去掉它们就会把不该管的行也管进来。判断一个局部唯一索引的 `WHERE` 是不是真的有用，就问："去掉它，规则还成立吗？"

## 软删除的三种做法

回到开头的问题，软删除后怎么处理唯一性，Patra 里能看到三种思路：

| 做法 | 怎么做 | Patra 里的例子 |
|---|---|---|
| 局部唯一 | `UNIQUE ... WHERE deleted_at IS NULL`，已删的行不参与 | 示意（上面的 users 例子） |
| 清空唯一的那一列 | 注销时把邮箱设成 NULL，NULL 不冲突 | 用户表：`ck_idn_user_email_deleted` 规定已注销用户的邮箱必须为空 |
| 干脆不放开 | 软删行仍占着名额 | 期刊 NLM 编号 `uk_venue_nlm_id` 的注释写明「覆盖软删行」；用户名「never released」，不再发给别人 |

没有哪种一定对，要看业务想不想让名字被复用。

<Callout kind="warn">

用 `INSERT ... ON CONFLICT` 去配合局部唯一索引时，要在冲突目标后面把同样的条件写出来：`ON CONFLICT (列) WHERE 条件 DO NOTHING`，数据库才能认出你说的是哪个局部索引。

</Callout>
