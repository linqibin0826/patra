## 对方的错误，是对方的语言

interaction 调 identity，靠的是一个 HTTP Interface 客户端（`UserEndpoint`）。调用失败时，客户端抛出的是 `RemoteCallException`，里面装着对方的东西：HTTP 状态码、对方的业务错误码、跟踪 ID，如果对方带了语义特征，还有特征。

<CodeRef at="patra-tool/patra-tool-core/src/main/java/dev/patra/tool/core/error/remote/RemoteCallException.java@cfec9c9f30270dcf03f5cd7b6e54a0cd3b59296b" lines="28-70" />

这些都是 identity 那边的语言。如果让它一路冒泡到 interaction 的业务代码，会出两个问题：

- **业务代码得认识对方的细节**：Handler 为了处理「identity 挂了」，要去判断状态码是不是 503、错误码是不是某个字符串。
- **含义可能被误导**：identity 回 404，意思是「这个用户不存在」；原样冒泡成 interaction 的 404，前端会以为是「你访问的评论不存在」。

所以项目规则写明：`RemoteCallException` 只在适配器层出现，应用层和领域层只看到本服务的异常。

<CodeRef at=".claude/rules/tech/error-handling.md@cfec9c9f30270dcf03f5cd7b6e54a0cd3b59296b" lines="21-25" />

<Callout kind="lead">

防腐层：在自己和别人之间放一层翻译，对方的概念、错误、状态码走进来之前，先变成自己的。适配器就是这层翻译。

</Callout>

三种失败，调用方看到的是一个异常。它们对调用方的意义一样：现在拿不到用户信息，请稍后再试。

<Callout kind="insight">

这两个适配器（用户名片、catalog 解析）选择「所有失败都变成不可用」，是有原因的。注释里写：回了错误响应时，4xx 是本服务的程序错误，要在日志里看得出来，对用户而言仍然只是「暂时无法获取」。状态码和错误码只写进日志，不流到业务层。

</Callout>

## 什么时候要按含义翻译

「全部变成不可用」只是一种选择。有些场景对方的错误本身有业务含义，要区别对待。`RemoteCallException` 带着对方的语义特征，适配器可以据此翻译。类的注释里给了写法：

```java
try {
    return dictionaryEndpoint.resolve(request);
} catch (RemoteCallException ex) {
    if (RemoteErrorHelper.isNotFound(ex)) {
        throw new DictionaryTypeNotFoundException(request.typeCode());
    }
    throw ex;
}
```

这是注释里的示例：对方说「找不到」，在本服务里翻成本服务的「字典类型不存在」。项目规则规定判断方式优先看特征，其次才看状态码：

1. 捕获 `RemoteCallException`，用 `ex.getErrorTraits()` 基于语义特征判断。
2. 备选：`RemoteErrorHelper` 工具类基于 HTTP 状态码判断。
3. 禁止直接捕获 `RestClientException`，统一处理 `RemoteCallException`。
