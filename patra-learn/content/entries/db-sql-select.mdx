## 一句 SELECT 回答三个问题

SQL 查询的基本形状只有一个：

```sql
SELECT id, title
FROM cat_venue
WHERE venue_type = 'JOURNAL' AND deleted_at IS NULL
ORDER BY title
LIMIT 20;
```

（示意查询，列名取自 catalog 的期刊表。）逐行读，每一行回答一个问题：

| 子句 | 回答的问题 | 上面这句的意思 |
|---|---|---|
| `SELECT` | 要哪几列？ | 只要 `id` 和 `title` |
| `FROM` | 从哪张表？ | 从 `cat_venue` |
| `WHERE` | 要哪些行？ | 类型是期刊，并且没有被软删除 |
| `ORDER BY` | 怎么排？ | 按标题 |
| `LIMIT` | 要多少行？ | 前 20 行 |

几个新手常踩的细节：

- **只取要用的列**。`SELECT *` 会把一行所有的列都带回来。`cat_venue` 有二十多列，其中还有 JSON 大字段，页面只要标题时全带上是浪费。
- **判断空值要写 `IS NULL`，不能写 `= NULL`**。`deleted_at = NULL` 永远查不到任何行，原因在「约束与 NULL」那一篇讲。
- **字符串用单引号**。`'JOURNAL'` 是字符串，双引号在 SQL 里是用来括列名、表名的。

`WHERE` 里常用的条件：

| 写法 | 意思 |
|---|---|
| `a = 1`、`a <> 1`、`a >= 10` | 比较 |
| `a = 1 AND b = 2`、`a = 1 OR b = 2` | 且、或（混着用时加括号） |
| `a IN (1, 2, 3)` | 值在列表里 |
| `title LIKE '协和%'` | 以「协和」开头，`%` 代表任意多个字符 |
| `deleted_at IS NULL` | 这一格是空的 |

## 一句查询是按什么顺序做的

写的时候 `SELECT` 在最前面，但数据库的处理顺序并不是从上到下。先后顺序是：取表，过滤（`WHERE`），排序（`ORDER BY`），取一页（`LIMIT`）。

看一个真实场景：Patra 的文献库（`collection.library_item`）里每一行是「某个用户收藏了某个对象」。要给用户 7 看收藏的第一页，每页 2 条。

<CodeRef at="patra-api/patra-interaction/patra-interaction-infra/src/main/java/dev/patra/interaction/infra/collection/persistence/LibraryReadAdapter.java@3cf6fa5757b3be54c3b030e4cace871f53e2599c" lines="265-270" />

```java
  private static String librarySql(LibraryView view) {
    return "SELECT li.subject_id, li.collected_at FROM collection.library_item li"
        + " WHERE li.user_id = :userId"
        + filter(view)
        + " ORDER BY li.collected_at DESC, li.subject_id DESC";
  }
```

分页时再接上 `LIMIT :limit OFFSET :offset`。

## 翻页为什么要写第二个排序键

注意上面真实查询的最后一行写了**两个**排序键：先按 `collected_at DESC`，再按 `subject_id DESC`。

为什么要第二个？因为收藏时间可能相同（一次批量收藏几篇，时间戳一样）。只按时间排，时间相同的几行谁先谁后数据库不保证，翻页时它们可能一次出现在第一页、下一次又出现在第二页。加上 `subject_id` 这个**不会重复**的列做第二个排序键，每一行的位置就是唯一确定的。

<Callout kind="warn">

分页的 `ORDER BY` 必须能把每一行排出唯一的位置。排序键不唯一时，在最后补上主键（或别的唯一列）。

</Callout>
