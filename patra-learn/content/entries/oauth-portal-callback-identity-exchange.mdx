## 背景

Patra 的门户是 BFF：浏览器的请求先到门户，门户再经网关调后端，登录会话的 Cookie 也只由门户写。接第三方登录时，这个结构碰上两个约束：

- 平台会把用户的浏览器跳到回调地址，这个地址必须是浏览器能到的公网地址。
- 换令牌要用 `client_secret`，它只应该放在后端。

所以要决定回调落在哪里，协议在哪里跑。

## 选择

<Callout kind="lead" label="选了什么">

门户收回调，identity 换令牌。决定性的理由是两条约束都不用破：密钥留在后端，Cookie 仍只由门户写。

## state 为什么要查两次

identity 不建 `HttpSession`，框架默认把授权请求存在会话里的办法用不了，改存 Redis。这解决了存储问题，却带来一个缺口：Redis 记录不认浏览器。

门户这一半的代码。查询串里的 `state` 必须恰好一个，且等于 Cookie 的值，否则不转发：

<CodeRef at="patra-portal/src/lib/identity/oauth-login.ts@eb45ccde6f359692196b4b874ddaead6b9ffe0c2" lines="94-105" />

```ts
export async function finishProviderCallback(provider: Provider, search: string): Promise<string> {
  const { state, ret } = await readOAuthFlow();
  await clearOAuthFlowCookies();
  const back = originHref(ret);
  const notice = (kind: OAuthNoticeKind) => oauthNoticeHref(back, { kind, provider });
  const given = new URLSearchParams(search).getAll("state");
  if (!state || given.length !== 1 || given[0] !== state) {
    return notice("rejected");
  }
```

<Callout kind="insight" label="顺带想通的">

这个 Cookie 用 `SameSite=Lax`，不能用 `Strict`。平台跳回门户是一次从别的站点来的顶层导航，`Strict` 的 Cookie 不会随它发送，回调就永远对不上。`Lax` 在这种顶层 GET 跳转上会带上，而攻击者从别的页面发起的跨站子请求仍然带不上。

</Callout>

## 代价

<Callout kind="cost">

- 门户多两个转发路由，要手动处理跳转（`redirect: manual`），而且门户要等 identity 跑完协议，它的回调超时必须比 identity 调平台的最坏耗时更长。
- identity 不把 `ticket` 绑定到浏览器。把攻击者的 `ticket` 塞进受害者的浏览器也是一种预劫持，这一层只靠门户的 HttpOnly Cookie 和 `state` 核对来防，门户要有防 `ticket` 注入的端到端测试。
- 这个决策建立在「所有客户端都经门户」上。以后如果有不经门户的客户端，比如手机 App，这条路走不通，要另外设计。

</Callout>
