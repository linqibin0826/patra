## 子域：按业务切，而不是按技术切

上一篇把服务按技术层切成六个模块。但一个服务里往往不止一件事。interaction 的业务就能再切成五块：

| 子域 | 管什么 |
|---|---|
| `subject` | 对象底座：每个被互动过的对象（文献、期刊、投稿经验）登记一行，其他子域都引用它 |
| `collection` | 文献库与收藏夹 |
| `discussion` | 评论与回复 |
| `post` | 投稿经验 |
| `reaction` | 「有帮助」 |

通知服务同样有自己的子域：`kernel`（底座）、`inbox`（站内信箱）、`preference`（提醒偏好）、`mail`（邮件）、`realtime`（实时推送）。

<Callout kind="analogy">

一家医院有内科、外科、药房、挂号处。它们在同一栋楼里，共用一个后勤，但各有各的业务，科室之间转诊要走固定流程，不会随便闯进对方的手术室。子域就是服务内部的科室。

</Callout>

## 先按子域分包，再按技术分

子域和六层不冲突，而是交叉：**每一层里面先按子域分，再按组件类型分**。

```
dev.patra.interaction.{domain|app|infra|adapter|api}.{subject|collection|discussion|post|reaction}
```

所以「新建收藏夹」相关的类，在每一层都能在 `collection` 这个目录下找到：domain 里的 `collection`，app 里的 `collection`，infra、adapter 里的 `collection`。

数据库也跟着切：同一个库，每个子域一个 schema，schema 名就是子域名（`collection.collection`、`discussion.comment`）。

## 子域之间怎么往来

规则很简单，都由架构测试守住：

1. **每个子域只公开三个包**：`port.read`（读端口）、`model.read`（读模型）、`event`（事件）。别的包，聚合、仓库、app、infra 的类，别的子域看不见。
2. **底座例外**：它对其他子域完全公开，所有子域都可以用。代价是底座只能放真正被两个以上子域共用的东西，而且它自己不能反过来依赖任何子域。
3. **其他的跨子域依赖要先声明**：在架构测试里写一行。
4. **子域之间不许成环**。
5. **跨子域写，不调对方的仓库**：发本子域的事件，对方订阅。

虚线是默认就允许的（任何子域都可以用底座），实线是在测试里事先写明的。要新增一条实线，必须去改架构测试，这个动作本身就是一次「我要让这两块业务产生联系」的决定。

## 跨子域写：发事件，别伸手

最容易越界的是写。比如投稿经验被删了，有帮助里点在它上面的记录也要清掉。post 子域不能自己去调 reaction 的仓库删数据，规矩是：post 发布自己的事件，reaction 订阅。

<CodeRef at=".claude/rules/tech/package-layout.md@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="47-53" />

真实情况正是如此：投稿经验删除时发布 `PostDeletedEvent`，reaction 订阅它，在同一个事务里清掉被删目标的有帮助。post 不知道 reaction 的存在，reaction 要不要接这个事件，只有 reaction 自己决定。

## 子域为什么值得

<Callout kind="insight">

读 interaction 的架构测试，就能知道哪些业务块之间有联系：只有 reaction 依赖 discussion 和 post，其余互相无关。哪天要把 discussion 拆成独立服务，只需处理这两条声明过的边，不需要在代码里到处找谁偷偷引用了它。

</Callout>

## 业界的说法：核心、支撑、通用

DDD 的原著把子域按「对业务有多重要」分成三类：

| 类别 | 意思 | 一般怎么对待 |
|---|---|---|
| 核心子域 | 让产品与众不同的部分 | 最好的人、最多的设计投入 |
| 支撑子域 | 业务必需，但不是差异所在 | 够用就行 |
| 通用子域 | 哪家都一样，如登录、发邮件 | 能买现成的就买现成的 |

这是业界通用的分类。Patra 自己在服务内部用的是另一种区分：**底座**与**普通子域**，看的是依赖关系（谁被所有人用），不是业务重要性。两种分法回答不同的问题，不必强行对上。
