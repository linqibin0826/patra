<Callout kind="lead">

事件信封是一条事件在链路上传递时的完整外壳：事件本身的名字、时间、属性，加上「谁、在哪、用什么设备」这些上下文。Patra 按链路上每一跳的信任程度，把它定成三种形态，每种一份 JSON Schema。

</Callout>

## 为什么不是一种格式走到底

最省事的设计是浏览器直接发一个完整的事件，包括设备 ID、账号 ID，采集端点收下入库。问题出在信任上：浏览器发来的东西谁都能伪造。如果身份字段由浏览器自报，任何人都能冒充任何账号刷浏览量。

另一头是隐私：判爬虫要 UA，查地区要 IP，可 Patra 的决策是分析事件不存 IP（个保法讲「最小必要」，医生的阅读轨迹按接近敏感处理）。IP 必须进到采集端点，又不能落盘。

所以一条事件在不同位置该带的字段不一样，Patra 把它拆成三种形态：

| 形态 | 谁写 | 有什么 | 没有什么 |
|---|---|---|---|
| ① 浏览器批次 `browser-batch` | 门户前端脚本 | 事件 ID、事件名、版本、浏览器时间、页面、事件属性 | 设备、会话、账号、IP、UA |
| ② 采集信封 `collect-envelope` | 门户服务端 | ① 的全部，加设备 ID、会话 ID、账号 ID、来源、IP、UA、是否合成 | — |
| ③ 富化事件 `enriched-event` | 采集端点 | ② 去掉 IP 和原始 UA，加接收时间、校正时间、地区、UA 解析结果、爬虫标记 | IP、原始 UA、用户名 |

还有一个前提让这套分法成立：采集端点只经网关、只给门户服务端和模拟器调，浏览器只能打门户自己域名下的路径。所以采集端点可以信任 ② 里的账号 ID，和 Segment、PostHog 的服务端 SDK 直接上报 `userId` 是同一个道理。

## JSON Schema：把格式写成机器能查的规格

JSON Schema 是用 JSON 描述 JSON 应该长什么样的标准：有哪些字段、什么类型、必填哪些、取值范围。校验器拿一份 schema 和一段 JSON，告诉你合格不合格、哪里不合格。Snowplow（Iglu）、Segment（Protocols）都用它防「埋点越埋越乱」。

Patra 每个事件一份属性 schema，`article_viewed` 的最简单：

<CodeRef at="patra-api/patra-analytics/patra-analytics-api/src/main/resources/analytics/schema/events/article_viewed.schema.json@8140a9d9482324670b63f00ab3c62690102196c5" lines="1-16" />

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://patra.linqibin.dev/schemas/analytics/events/article_viewed.schema.json",
  "title": "Article Viewed",
  "x-patra-version": "1-0-0",
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "article_id": {
      "$ref": "../defs.schema.json#/$defs/article_id"
    }
  },
  "required": [
    "article_id"
  ]
}
```

关键是 `additionalProperties: false`：属性里多一个 schema 没登记的键，这条事件就不合格。上一篇说的「字段不能随手加」在这里落地：想加字段，必须先改 schema。三个信封 schema 用的是 2020-12 草案里更严的 `unevaluatedProperties: false`，它把 `oneOf`、`$ref` 引进来的子 schema 里声明的字段也算进「已知字段」，效果同样是多一个顶层字段就不合格。

几个写法上的细节，也是从这份 schema 里学到的：

- **不靠 `format` 关键字。** 2020-12 草案默认不校验 `format`，时间、UUID 一律写 `pattern`：时间必须是 UTC、带毫秒，UUID 必须小写。
- **正则结尾不用 `$`。** 不少正则引擎的 `$` 会放过末尾的换行，`"123\n"` 会被当成合法 ID；Patra 写成各引擎都认的 `(?![\s\S])`。
- **一份定义，三处使用。** 采集端点按它校验，模拟器按它造事件，门户的 TypeScript 类型由它生成，CI 检查两边一致。

## 来源和事件名绑在 schema 里

事件目录 schema 把 10 个事件分成两组：服务端事件只能配 `source = server`，浏览器事件只能配 `source = client`。这就是上面那条伪造的 `article_viewed` 被拦下的原因。

实现时有一个坑：这种绑定在 schema 里是用 `oneOf` 写的，`oneOf` 校验失败时校验器只会报「没有分支匹配」，分不出是事件名不认识、来源不对，还是版本不收。所以采集端点在跑完整 schema 之前，先按顺序做三道预检：

```java
    JsonNode node = parsed.get();
    String wireName = text(node, "event_name");
    Optional<EventName> eventName = EventName.fromWire(wireName);
    if (eventName.isEmpty()) {
      return new EnvelopeCheck.Invalid(
          RejectionReason.UNKNOWN_EVENT, "event_name 不在事件字典里：" + wireName, wireName);
    }
    if (!eventName.get().source().wire().equals(text(node, "source"))) {
      return new EnvelopeCheck.Invalid(
          RejectionReason.SOURCE_MISMATCH,
          wireName + " 只能由 " + eventName.get().source().wire() + " 发出",
          wireName);
    }
    Optional<SchemaVersion> version = SchemaVersion.parse(text(node, "schema_version"));
    if (version.isPresent() && !version.get().accepted()) {
      return new EnvelopeCheck.Invalid(
          RejectionReason.VERSION_REJECTED,
          "schema_version 的 MODEL 不是 " + SchemaVersion.CURRENT_MODEL,
          wireName);
    }
    List<Error> errors = envelopeSchema.validate(node);
    if (!errors.isEmpty()) {
      return new EnvelopeCheck.Invalid(
          RejectionReason.SCHEMA_INVALID, describe(errors.getFirst()), wireName);

```

事件名在不在字典里 → 来源对不对 → 版本收不收，前三道各给一个明确的原因码；都过了再跑完整 schema，不过就是 `schema_invalid`，带上校验器给的第一条错误。原因码分得清，运营面板上才看得出坏数据是哪一类。

## 坏事件进死信，不拖累同批

一批里有一条坏事件，整批都拒掉吗？Patra 把「批次外壳」和「单条事件」分开校验：

- **整批拒收（400）**：请求体不是合法 JSON、条数为 0 或超过 500、外壳上多了字段；请求体超过 1 MiB 返回 413。这些情况不进任何 topic。
- **单条进死信**：外壳合格，就逐条预检、校验。不合格的那条写进 `events.dlq`，同批其余合格的照常写进 `events.raw`，响应是 202 加「合格几条、不合格几条」。

死信（dead letter）是业界对「处理不了、但留着排查」的消息的叫法。死信记录也有自己的 schema：收到时刻、原因码、第一条错误、原事件名，以及原事件的 JSON 原文。原文**先删掉 `client_ip` 和 `user_agent` 两个键再存**：死信也在 Kafka 里落盘、保留 2 天，同样不能有 IP。

浏览器那一跳同理：门户只校验浏览器批次的外壳（1～50 条、序列化后不超过 48 KiB，给 `sendBeacon` 约 64 KiB 的上限留余量），不逐条校验，每条都原样组装成 ② 转发，交给采集端点逐条判。所以一条坏事件只会让它自己进死信。

## 版本号：MODEL-REVISION-ADDITION

格式总会改。Patra 用 Snowplow 的 SchemaVer，每个 schema 带一个三段版本号 `MODEL-REVISION-ADDITION`：

- 加了一个**可选**属性：`ADDITION` +1（`1-0-0` → `1-0-1`）。
- 改了属性含义或取值范围，旧数据还能读：`REVISION` +1。
- 删属性、改类型、加必填属性，旧事件会不合格：`MODEL` +1。

采集端点**接受 `MODEL` 相同的任意版本**。原因是门户和 `patra-analytics` 分开部署，读者已经打开的标签页也还跑着旧脚本，总有一段时间会同时收到新旧两版事件；只改了 `ADDITION` / `REVISION` 的，按定义兼容旧事件，照收。`MODEL` 变了的旧事件进死信，原因 `version_rejected`。仓库里每个事件只留当前版本的 schema，已入库的旧数据靠每行的 `schema_version` 追溯。改 schema 的顺序也定死了：先改 schema，再改采集端点，最后改产生方。

## 发生时间：客户端的钟不可信

事件带着产生方写的 `created_at`（发生时刻）和 `sent_at`（这一批发出的时刻），可浏览器所在电脑的时钟可能快几个小时，也可能慢一天。直接用 `created_at` 排时间，热读、会话都会算错。

Snowplow 的做法（`derived_tstamp`）是：客户端时钟的**绝对值**不可信，但同一个钟量出来的**时间差**可信。`sent_at − created_at` 是「这件事发生后多久才发出来」，用服务端收到的时刻往回减这么久，就得到校正后的发生时间：

`derived_at = received_at − (sent_at − created_at)`

<CodeRef at="patra-api/patra-analytics/patra-analytics-domain/src/main/java/dev/patra/analytics/domain/collect/policy/EventTimeCorrection.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="26-31" />

```java
  public static Instant derive(Instant createdAt, Instant sentAt, Instant receivedAt) {
    Instant derived = receivedAt.minus(Duration.between(createdAt, sentAt));
    boolean tooEarly = derived.isBefore(receivedAt.minus(MAX_EARLY));
    boolean tooLate = derived.isAfter(receivedAt.plus(MAX_LATE));
    return tooEarly || tooLate ? receivedAt : derived;
  }
```

算出来比收到时刻早 24 小时以上、或晚 5 分钟以上，说明时钟严重错乱，取 `received_at`，不丢事件。之后所有分析一律用 `derived_at`，ClickHouse 明细表也按它分区。
