## 搜"含有某个词"，普通索引没办法

Patra 的机构联想要做到：用户输入「北京大学」，下拉框里立刻出现名字里带这几个字的机构。这种"词出现在名字任意位置"的匹配，在 SQL 里是 `LIKE '%北京大学%'`（或不区分大小写的 `ILIKE`）。

两头都有 `%` 时，B 树索引完全没用：它是按整个值从头到尾排序的，没有"包含某段文字"的捷径。对二十多万行就是全表扫描，边打字边搜时每敲一个键都要扫一遍。

## pg_trgm：把文字切成三个字符一组

PostgreSQL 有一个扩展 `pg_trgm`（trigram，三元组）。它的想法是：**把每个字符串切成所有连续的三个字符的片段**，用这些片段当索引的键。

以"北京大学"为例，它含有的三字片段是：`北京大`、`京大学`（两端还会补空格，凑出更多片段，细节从略）。

查 `LIKE '%北京大学%'` 时，把查询词也同样切成片段（`北京大`、`京大学`），然后问："哪些行同时含有这两个片段？"

存"片段到行号"的这种索引叫**倒排索引**，PostgreSQL 里叫 **GIN 索引**。它像书末的关键词索引：每个关键词（这里是片段）后面跟着一串出现过它的页码（这里是行号）。

这就是文章开头问题的答案：用了 pg_trgm 的 GIN 索引，`LIKE '%词%'` 不用扫全表，只读索引缩小到几行候选再复查。

## 在 Patra 里怎么建

建索引只有一行：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/resources/db/migration/V9__add_suggest_trigram_indexes.sql@af8cd13c3ec367ccba78615b72e6ff19535cef90" lines="13-14" />

```sql
CREATE INDEX idx_org_name_value_trgm
    ON cat_organization_name USING gin (name_value gin_trgm_ops);
```

`USING gin` 指定索引类型，`gin_trgm_ops` 告诉它"用三元组切分文字"。这个迁移脚本最前面还要先启用扩展：`CREATE EXTENSION IF NOT EXISTS pg_trgm;`。

脚本里另外两个索引更有意思，它们带了 `WHERE`：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/resources/db/migration/V9__add_suggest_trigram_indexes.sql@af8cd13c3ec367ccba78615b72e6ff19535cef90" lines="20-30" />

```sql
CREATE INDEX idx_mesh_desc_name_trgm
    ON cat_mesh_descriptor USING gin (name gin_trgm_ops)
    WHERE descriptor_class = '1' AND active_status;

CREATE INDEX idx_entry_term_term_trgm
    ON cat_mesh_entry_term USING gin (term gin_trgm_ops)
    WHERE record_type = 'DESCRIPTOR' AND is_permuted_term = false;
```

这是「局部索引」（只给满足条件的行建索引）的思路用在 GIN 上：MeSH 词表里很多行（非主题类、已停用、排列入口词）搜索根本不会用到，不把它们放进索引，索引更小、写得更快。代价是**查询的 WHERE 必须包含同样的条件**才能用上这个索引，所以脚本注释写明了"谓词与建议查询的 WHERE 逐字相同"。

## 最大的局限：词太短就凑不出片段

三字片段意味着：查询词里至少要有三个字符，才能切出一个完整片段。只有两个字的词，切不出片段，GIN 索引无从下手，数据库只能退回全表扫描。

Patra 为此专门做了取舍：两个汉字的联想查询（如「协和」「华西」）接受全表扫，实测约 30 多毫秒，在可接受范围内，所以没有为它们再引入别的方案。这个决定写在设计文档里，用实测的数字作依据，不是拍脑袋。

<Callout kind="insight" label="还有一个更隐蔽的坑">

短关键词的故事还有后续：在数据库驱动把查询转成预编译语句、并改用"通用计划"之后，两个汉字的查询反而会被规划器引向 GIN 索引，变成「扫完整个索引再回表复查几十万行」，比直接全表扫还慢好几倍。这个问题在 Patra 的设计评审中被发现并绕开，过程会在专门的排查文章里细讲。

</Callout>

## GIN 索引的代价

和 B 树一样，GIN 也要为读的快付出代价：

- **体积**：机构名称的这个索引大约 22 MB，对应二十多万行名称。
- **写入更慢**：每插入一行，要把它切出的所有片段都登记进索引。批量导入大量机构名称之前，要把这个成本算进去。
- **只适合"含有"类的匹配**：`=`、范围比较、排序它都不管，那些还是 B 树的事。
