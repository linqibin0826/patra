## 坑

<Callout kind="lead" label="坑在哪">

对一张「同一个键有好几行部分结果」的聚合表，在 GROUP BY 之前用 WHERE 按聚合列过滤，会把同一个键的一部分行先扔掉，聚合出来的是残缺的结果。

</Callout>

## 一个真实的例子

v0.18 在 mini 上灌完 1 亿条后对账，读过全文人数误差 0，看过人数误差 0.001%：有 26 行对不上。原因是对账查询的 bug，不是管线算错了。

事情是这样的：一个伪装成浏览器的爬虫 23:58 开始访问。它用普通 Chrome UA、跑脚本，前 30 篇和真人没有区别；要等 5 分钟内超过 30 篇，采集端点的频率规则才开始给它的事件标 `rate`，而那已经过了零点。于是这个会话的事件分成了两段：零点前的没有爬虫标记，零点后的有。

「真人会话」靠 `session_quality` 判定。它是物化视图写的一张聚合表，每批写入的事件各自汇成一行：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V4__session_quality.sql@8140a9d9482324670b63f00ab3c62690102196c5" lines="1-17" />

```sql
-- 会话特征（入库设计 §5.4）：真人会话 = 有浏览器事件且没有爬虫事件，在查询时判定；长期保留。
CREATE TABLE IF NOT EXISTS session_quality (
    session_id    UUID,
    has_client    SimpleAggregateFunction(max, UInt8),
    has_bot       SimpleAggregateFunction(max, UInt8),
    first_day     SimpleAggregateFunction(min, Date)
) ENGINE = AggregatingMergeTree
ORDER BY session_id
SETTINGS non_replicated_deduplication_window = 1000;

CREATE MATERIALIZED VIEW IF NOT EXISTS session_quality_mv TO session_quality AS
SELECT
    session_id,
    source = 'client' AS has_client,
    toUInt8(is_bot) AS has_bot,
    toDate(derived_at, 'Asia/Shanghai') AS first_day
FROM events;
```

这个爬虫会话在表里就有了两类行：零点前的事件写出 `first_day = D`、`has_bot = 0`，零点后的事件写出 `first_day = D+1`、`has_bot = 1`。对账查询按天跑，查 D 日时是这样写的：

<CodeRef at="patra-api/patra-analytics/patra-analytics-simulator/src/main/java/dev/patra/analytics/simulator/truth/Reconciler.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="26-42" />

```java
  private static final String ACTUAL_SQL =
      """
      SELECT article_id,
             toUInt32(uniqExactIf(person_id, v = 1)) AS viewers,
             toUInt32(uniqExactIf(person_id, ft = 1)) AS fulltext_readers
      FROM (
          SELECT article_id, session_id, person_id, max(viewed) AS v, max(fulltext) AS ft
          FROM article_session_reads
          WHERE day = {d:Date} AND is_synthetic = 1 AND {run}
          GROUP BY article_id, session_id, person_id)
      WHERE session_id IN (
          SELECT session_id FROM session_quality
          WHERE first_day BETWEEN {d:Date} - 1 AND {d:Date}
          GROUP BY session_id HAVING max(has_client) = 1 AND max(has_bot) = 0)
      GROUP BY article_id
      HAVING viewers > 0
      """;
```

`WHERE first_day BETWEEN {d:Date} - 1 AND {d:Date}` 只查前一天到当天的行，而且在 `GROUP BY` 之前生效。D+1 那行爬虫标记被滤掉，分组时这个会话只剩 `has_bot = 0` 的行，于是被当成了真人会话。真值那边按整个会话套规则，会话里有 `rate` 事件，整个不算，两边就差出了这几行。照这个机制推：它零点前打开过的每篇文献，在 D 日都会多算 1 个人；模拟器里的伪装爬虫只打开文献页、不读全文，所以只有「看过」受影响，这也和读过全文误差为 0 对得上。

## 为什么

`AggregatingMergeTree` 不在写入时把同一个键的行合成一行。每批写入各自落成一个数据片段，片段里每个会话一行部分结果；后台合并片段时，才按列上声明的函数把同一个 `session_id` 的行合起来：`has_bot` 取 max，`first_day` 取 min。合并之前，一个会话有几行、每行的 `first_day` 各是多少，取决于它的事件分在了几批里。

所以 `first_day` 这一列在合并前不是「会话的第一天」，只是「这一批里这个会话的第一天」。WHERE 按这个部分值逐行筛，筛掉的可能正是带着关键信息的那一行。合并之后反而没事：两行合成 `first_day = D`、`has_bot = 1`，落在范围内，会话被正确排除。查询对不对取决于后台有没有合并完，这是最难发现的那种 bug。

<Callout kind="insight" label="怎么认出它">

按上面的机制，这类 bug 的样子是：不一致的行很少、误差极小（这次是 0.001%），ClickHouse 只会比真值多、不会少，只出现在爬虫会碰到的口径上（这次只有「看过」）。碰到这种「方向一致、量极小」的差，先怀疑「某个会话本该被排除却没被排除」，把多出来的那几行对应的会话找出来，看它们是不是跨过了午夜。

</Callout>

## 线上查询为什么不受影响

同样的 `session_quality` 也被线上用来判真人会话，可线上的查询没有踩这个坑：

- **计数接口**（「N 人看过」）根本不按日期过滤 `session_quality`，只按会话 ID 取这几篇文献涉及的会话，同一个会话的所有行都参与分组。
- **热读与看过还看了**按 `first_day` 只设下限（窗口起点再往前一天），不设上限。会话的爬虫标记只会出现在它后来的事件里，晚于窗口起点的行全都保留，标记丢不了。

对账查询之所以会踩，是它为了按天控制内存加了上限，正好切掉了会话「后面」的那一行。

## 怎么避开

对聚合表做判定，要先把同一个键的行聚合完，再按聚合后的值筛。WHERE 里只放对一个键的所有行都成立的条件，最常见的就是按键本身筛：

- **按会话 ID 限定范围**：像计数接口那样，先从当天的 `article_session_reads` 取出涉及的会话 ID，`session_quality` 只按 `session_id IN (…)` 过滤再分组。范围照样收窄，同一个会话的所有行都在。
- **日期条件挪到聚合之后**：写成 `HAVING min(first_day) BETWEEN {d:Date} - 1 AND {d:Date} AND max(has_client) = 1 AND max(has_bot) = 0`。结果对，但 WHERE 里没了范围，要分组的会话变多，对账这种有 1 GiB 上限的查询要和上一条配合用。
- **只设下限**：像热读那样只写 `first_day >=`，会话后面的行都参与分组。

<Callout kind="warn">

`FINAL` 也能在查询时把同一个键的行先合并再筛，结果是对的，可它要在查询时现做合并，大表上很慢、很吃内存；对账这种按天跑、每条查询有 1 GiB 上限的场景，先按会话 ID 收窄范围更合适。另外，改查询时要顺带构造一个跨午夜才被标记的会话写成测试，这种情况靠随机数据很难稳定碰到。

</Callout>
