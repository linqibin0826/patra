<Callout kind="lead">

块令牌（`insert_deduplication_token`）是写入时附带的一个字符串：ClickHouse 记住最近若干次写入的令牌，同一个令牌再来，整批数据直接丢弃，就像没写过。

</Callout>

## 为什么一定要批量写

MergeTree 那篇讲过：ClickHouse 每写一次，就在表上新建一个数据片段，后台再慢慢合并。Patra 的明细表 `events` 挂着三个物化视图，一次写入会在 `events` 和三张汇总表上**各**多一个片段，也就是 4 个；而合并线程只有 2 个。一秒写几百次，片段数很快超过上限，写入被拒（`TOO_MANY_PARTS`）。

所以入库消费者攒批：一批最多 5 万条，流量小时最多等 1 秒，**一批只写一次**。连按分区拆开分别写都不做：`events.raw` 有 3 个分区，拆开就是 3 倍的片段。

## 至少一次，重复从哪来

入库是「写成功才提交偏移量」，这保证了不丢，代价是会重复。重复有三个来源：

- **写成了，响应没回来**：ClickHouse 已经写进去，响应在路上超时，消费者以为失败，重试同一批。
- **写成了，提交偏移量前进程崩溃**：重启后从上次提交处重新拉取。
- **故意的**：流量模拟器每条事件以 1% 的概率再发一次，专门用来验证去重。

第一种最常见，块令牌就是给它准备的。

## 令牌长什么样

令牌由这一批里每个分区的偏移量范围拼成，前面加上 topic ID：

<CodeRef at="patra-api/patra-analytics/patra-analytics-app/src/main/java/dev/patra/analytics/app/ingest/usecase/ingest/IngestBatchHandler.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="166-182" />

```java
  /// 批次去重令牌：`{topic ID}|p{分区}:{首}-{尾}|…`，按分区号排序（入库设计 §4.3）。
  ///
  /// @param records 这一批（同一 topic）
  /// @return 令牌
  private static String token(List<IngestRecord> records) {
    Map<Integer, long[]> ranges = new TreeMap<>();
    for (IngestRecord record : records) {
      ranges.merge(
          record.partition(),
          new long[] {record.offset(), record.offset()},
          (a, b) -> new long[] {Math.min(a[0], b[0]), Math.max(a[1], b[1])});
    }
    return records.getFirst().topicId()
        + ranges.entrySet().stream()
            .map(e -> "|p" + e.getKey() + ":" + e.getValue()[0] + "-" + e.getValue()[1])
            .collect(Collectors.joining());
  }
```

几个细节：

- **为什么带 topic ID**：topic ID 是 Kafka 给每个 topic 的 UUID，启动时用 AdminClient 取一次。删掉 topic 重建、重置消费组、集成测试复用同一个 ClickHouse 容器时，偏移量都会从 0 重来；令牌只有偏移量的话，新数据会和旧令牌撞上，被当成重复**静默丢掉**。topic ID 一换，令牌就不会撞。
- **记多少个**：明细表和三张汇总表都设了 `non_replicated_deduplication_window = 1000`，记住最近 1,000 次写入的令牌。重试期间消费者卡在这一批上，不会写别的批次，窗口不会被挤掉。
- **重试时边界不变**：监听方法写失败时抛普通异常，spring-kafka 的错误处理器用**内存里的同一批**重新调用它，不重新拉取，所以这一批的偏移量范围、也就是令牌，和上次一模一样。监听方法刻意不抛 `BatchListenerFailedException`：那会让容器重新定位偏移量、重新拉取，批次边界就变了。

<Callout kind="warn">

令牌只挡「同一批重试」。提交偏移量前崩溃、模拟器故意把副本放进另一次写入，令牌都对不上。所以令牌之后还有两道：明细表 `ReplacingMergeTree` 按 `event_id` 合并、数条数一律 `uniqExact(event_id)`；汇总表只存 `max` / `min` 这类重复来几次结果都一样的值。详见「重复行怎么数：ReplacingMergeTree 只在合并时去重，数条数一律 uniqExact」和「物化视图：写入时就汇总，所以汇总表只能存幂等的值」两篇。

</Callout>

## 一批里有一条坏数据怎么办

ClickHouse 写入是整批的：5 万条里有一条解析不了，整批被拒。可数据里有坏行，重试多少次都不会好，也不能因为一条坏行卡住整个管线。

入库用例先把空消息和不以 `{` 开头的消息挑出来，直接转进 dlq 表（JSONEachRow 会静默跳过空行，这类最常见的垃圾也不值得去找）。剩下的整批写；被拒了，就**对半拆开**分别写：

<CodeRef at="patra-api/patra-analytics/patra-analytics-app/src/main/java/dev/patra/analytics/app/ingest/usecase/ingest/IngestBatchHandler.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="106-118" />

```java
    boolean whole = from == 0 && to == records.size() - 1;
    List<String> lines = records.subList(from, to + 1).stream().map(IngestRecord::value).toList();
    try {
      insert(stream, lines, whole ? token : token + "#" + from + "-" + to);
    } catch (IngestRejectedException e) {
      if (from == to) {
        rejected.add(new Rejection(records.get(from), e.getMessage()));
        return;
      }
      int middle = (from + to) >>> 1;
      write(stream, records, from, middle, token, rejected);
      write(stream, records, middle + 1, to, token, rejected);
    }
```

写成的那半就算写成，写不进的那半继续对半拆，到单条还写不进，就转成 dlq 记录（原因 `ingest_rejected`）。几个要点：

- **子批也有令牌**：在批次令牌后面加 `#起-止`（批内序号）。重试整批时拆法一样、子批令牌一样，已经写成的那半会被认出来丢弃。
- **哪些算「坏」**：只有 ClickHouse 返回解析、类型转换这一类错误码才拆；连不上、超时、磁盘不够都当成「重试会好」，整批停住等。
- **为什么 `max.poll.interval.ms` 设到 10 分钟**：二分重写也算这一批的处理时间，超时了消费组会判它死掉、触发重平衡。
