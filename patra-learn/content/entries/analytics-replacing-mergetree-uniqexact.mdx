<Callout kind="lead">

`ReplacingMergeTree` 在后台合并数据片段时，把排序键相同的行只留一行；合并之前，重复的行都还在表里，查询照样看得见。

</Callout>

## 去重发生在合并时，不在写入时

Patra 的明细表 `events` 用的就是它，排序键最后一列是 `event_id`：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/resources/clickhouse/V1__events.sql@8140a9d9482324670b63f00ab3c62690102196c5" lines="30-34" />

```sql
) ENGINE = ReplacingMergeTree
PARTITION BY toYYYYMMDD(derived_at, 'Asia/Shanghai')
ORDER BY (event_name, toDate(derived_at, 'Asia/Shanghai'), article_id, person_id, event_id)
TTL toDateTime(derived_at) + INTERVAL 90 DAY DELETE
SETTINGS non_replicated_deduplication_window = 1000, ttl_only_drop_parts = 1;
```

一条重发的事件内容完全一样，所以它和原件落在同一天的分区里、排序键也完全相同，合并时会被合成一行。可这里大多数人会卡住：**合并什么时候发生，ClickHouse 不保证**。它按片段大小和后台线程的空闲情况自己决定，可能几秒后，可能很久以后；而且它只合并同一个分区里的片段。在那之前，两行都在。

### 那加 FINAL 行不行

ClickHouse 提供 `SELECT ... FINAL`：查询时先把待合并的行就地合并一遍，再返回结果。它能让 `count()` 数对，但一般说来代价不小：查询要多读、多合并，表大的时候明显变慢、更费内存。Patra 没有用 `FINAL`，选的是另一条路：查询本身对重复不敏感。

## 规矩：数条数用 uniqExact(event_id)

入库设计定了一条规矩：凡是数「条数」的查询（检索次数、零结果词、曝光等），一律 `uniqExact(event_id)`，不用 `count()`。同一个事件不管在表里有几行，按 ID 去重只算一次，结果和合并进度无关。

数人也是同一个道理，按人去重：`uniqExact(person_id)`。

### uniq 和 uniqExact 选哪个

ClickHouse 有两个常用的去重计数函数：

| 函数 | 结果 | 内存 |
|---|---|---|
| `uniq` | 近似值：用采样和哈希估算，大基数时有小幅误差 | 有上限，基数再大也不怎么涨 |
| `uniqExact` | 精确值 | 要把见过的每个值都记下来，基数越大越费 |

Patra 的生产查询全部用 `uniqExact`：门户上展示的「N 人看过」是一篇文献的读者，基数小，精确没有负担；对账要逐行比对真值，近似值没法比。

费内存的一面在对账时碰到了。一次性对 1 亿个 UUID 做 `uniqExact` 要几 GB 内存，而 ClickHouse 的 `patra` 账号每条查询上限 1 GiB。所以模拟器的对账按天算、再求和：

<CodeRef at="patra-api/patra-analytics/patra-analytics-simulator/src/main/java/dev/patra/analytics/simulator/truth/Reconciler.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="44-49" />

```java
  private static final String UNIQUE_SQL =
      """
      SELECT uniqExact(event_id) AS n FROM events
      WHERE derived_at >= {from:DateTime64(3, 'UTC')} AND derived_at < {to:DateTime64(3, 'UTC')}
        AND is_synthetic AND {run}
      """;
```

按天拆开不会算错：每天一个分区，同一事件的重发内容一样、`derived_at` 一样，落在同一天，不会跨天各算一次。

## 「N 人看过」是怎么数的

文献页的计数查的是汇总表 `article_session_reads`。它用的是 `AggregatingMergeTree`，同样有「合并前同一个键有多行」的问题，所以查询分三层：

<CodeRef at="patra-api/patra-analytics/patra-analytics-infra/src/main/java/dev/patra/analytics/infra/insight/stats/ClickHouseReaderStatsAdapter.java@8140a9d9482324670b63f00ab3c62690102196c5" lines="24-40" />

```java
  private static final String SQL =
      """
      SELECT article_id,
             uniqExactIf(person_id, viewed = 1) AS viewers,
             uniqExactIf(person_id, fulltext = 1) AS fulltext_readers
      FROM (
          SELECT article_id, session_id, person_id, max(viewed) AS viewed, max(fulltext) AS fulltext
          FROM article_session_reads
          WHERE article_id IN ({ids}){synthetic}
          GROUP BY article_id, session_id, person_id)
      WHERE session_id IN (
          SELECT session_id FROM session_quality
          WHERE session_id IN (SELECT session_id FROM article_session_reads WHERE article_id IN ({ids}))
          GROUP BY session_id
          HAVING max(has_client) = 1 AND max(has_bot) = 0)
      GROUP BY article_id
      """;
```

1. **里层**：按（文献，会话，人）分组取 `max`，把还没合并的多行先手动合成一行。
2. **会话过滤**：只留真人会话，会话里有浏览器事件、没有爬虫事件。
3. **外层**：`uniqExactIf(person_id, ...)` 按人去重。同一个人在几个会话里看同一篇，也只算一个读者。

每一层都对重复不敏感：同一事件来两次，里层的 `max` 不变；同一个人来两次，外层的 `uniqExact` 不变。

## 对账为什么不用 count() − uniqExact

流量模拟器会故意把 1% 的事件再发一次，而且把副本放进**另一次写入**（令牌不同），专门绕过块令牌、考验 `event_id` 这一层。验证时，最直觉的做法是看 `count() − uniqExact(event_id)`：多出来的行就是被去重的重复。

所以模拟器的对账换了一种证明方式：

- **写入了多少行**：取模拟器自己记的已确认写入数（含 1% 重发），不问 ClickHouse。
- **去重后多少条**：按天 `uniqExact(event_id)` 再求和。
- **去重有效的证据**：写入行数比去重后多约 1%，而「看过人数」的对账误差仍在 1% 以内。

2026-11-02 在 mini 上灌入 1.0232 亿条的实测：写入 103,342,637 行，去重后 102,320,830 条，故意重发的 1% 全部被去重；看过人数误差 0.001%，读过全文人数误差 0。
