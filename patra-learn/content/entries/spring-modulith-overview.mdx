## 痛点：一个应用里的几块业务，越写越缠

拿 Patra 里一件很普通的事当例子：**有人回复了你的评论，系统要给你写一条提醒。**「评论」和「提醒」是两块业务。最省事的写法是在发评论的代码里，顺手调一下写提醒的方法。刚开始这样没问题，日子久了会冒出三类麻烦：

1. **一块出错，连累另一块。** 两件事在同一个事务里，开头那道题就是这个情况：提醒的 bug 让评论也发不出去。想把提醒挪到事务提交之后、换一条线程去做，又会出现新问题：评论提交了，写提醒之前进程恰好被重启，这条提醒就再也没人记得。
2. **谁都认识谁。** 发评论的代码要认识提醒；以后加邮件、加实时推送，还得回来改发评论的代码。测评论时，提醒、邮件、推送要一起拉起来。业务越多，牵一发动全身。
3. **边界说不清，也守不住。** 大家口头约定「提醒的内部类别人别碰」，可 Java 的 `public` 类谁都能引用，编译器不拦。某天有人图方便直接用了提醒的内部类，没人发现。

这三类麻烦在任何「一个应用里有好几块业务」的项目里都会出现，不管它最后是单体还是微服务。

## 以前怎么做，哪里不够

| 做法 | 能做到 | 不够的地方 |
|---|---|---|
| 拆成多个 Gradle / Maven 模块 | 编译期就拦住不该有的引用 | 模块一多构建配置膨胀；一个模块里还是分不出「对外的类」和「内部的类」；不管事件怎么可靠 |
| 自己写 ArchUnit 规则 | 想守什么规则都能写成测试 | 「模块」是什么、哪些包算对外，都要自己定义、自己维护 |
| 直接拆成微服务 | 进程级隔离，谁也碰不到谁的代码 | 过早背上网络、分布式一致性和部署的成本；边界划错了代价很高 |
| Spring 的事件加 `@Async` | 发布方不再认识订阅方，提交后再处理不连累主事务 | 订阅方失败、或进程在处理前崩了，事件就丢了，没有记录可以重来 |

每种做法都只解决一部分，第四种还引出了新问题。

## Spring Modulith 是什么

<Callout kind="lead">

Spring Modulith 是一组按需取用的库：帮你在一个 Spring Boot 应用里把代码按业务分成模块，在测试里检查模块边界，并让模块之间靠事件可靠地协作。

它不是微服务框架，也不是消息队列：模块还是在同一个应用、同一个进程里运行，事件记在你自己的业务数据库里。

</Callout>

Spring Boot 对技术结构有主张（控制器、服务、仓库怎么写），对业务结构以前只有口头建议；Modulith 补的就是业务结构这一块。它把一个应用叫作**模块化单体**：只部署一个应用，里面按业务切成边界清楚的模块。

## 核心思路

两个想法，各对付上面的一部分麻烦：

- **把包当模块，在测试里检查边界。** 启动类所在包下的每个子包就是一个模块，子包下面再套的包算内部实现。写一个测试让 Modulith 扫一遍代码，有人引用了别的模块的内部类、或者模块之间互相依赖成环，测试就失败。这对付「边界守不住」。
- **模块之间发事件，不直接调用；事件先记一笔再处理。** 评论模块只发布「评论已发表」，不认识提醒。Modulith 在评论的事务里顺手记一行「这个事件还欠提醒模块处理一次」，提交后再换一条线程处理，处理成功才把这一行划掉。处理失败、进程崩了，这一行都还在，可以重来。这对付「互相连累」和「谁都认识谁」。

<Callout kind="analogy">

像一家公司的几个部门。部门之间只走正式窗口，不进别人办公室翻文件（模块只用对方对外的类）；要通知别的部门，就发一份内部函件，收发室的登记簿记着每份函件谁还没签收（事件发布登记）。函件丢了，照着登记簿再送一次。

</Callout>

| 概念 | 一句话 | 在 Patra 里 |
|---|---|---|
| 应用模块 | 包即模块，顶层包对外、子包对内 | 没用：Patra 的子域散在好几个 Gradle 模块里，认不成一个模块 |
| `verify()` | 在测试里检查模块边界 | 没用：Patra 用自己写的 ArchUnit 规则检查子域边界 |
| 模块间事件 | 发布事件代替直接调用 | 用：服务里的子域之间用同步事件，跨服务靠外送 |
| `@ApplicationModuleListener` | 提交后、异步、新事务里处理 | 服务代码不写，只有 Modulith 的外送器带着它 |
| 事件发布登记 | 处理之前先在业务事务里记一行 | 用：当发件箱，发不出去的每分钟补投 |
| 外送 | 把事件发到消息中间件 | 用：发到 RabbitMQ，并等 broker 确认 |

除了这六个，Modulith 还有模块级集成测试（`@ApplicationModuleTest`）、从代码生成模块关系图、模块级的链路追踪、「过了一小时 / 一天」这类时间事件。它们都建立在「应用模块」之上，Patra 没用到，路线最后会给出去处。

## 常见误解

- **以为它是微服务的替代品**：名字里有「模块」，又常和微服务放在一起比较。实际上它管的是代码结构，和怎么部署无关：模块化单体里的模块不能单独扩容，一个模块把内存吃光，整个应用一起倒。Patra 本身是微服务，照样用了它的事件那一半。
- **以为事件发布登记就是消息队列**：都能「先存下来、稍后处理」。实际上登记表只是你业务库里的一张表，没有消费组，不保证顺序；失败的行也不会自己重试，要有人定时调补投。
- **以为 `@ApplicationModuleListener` 只是语法糖**：它确实只是三个注解的组合，但每一个都改变行为：提交后才执行（发布方回滚就不执行）、换一条线程、在新事务里跑（处理失败不会回滚发布方）。
- **以为登记行标了完成，消息就一定到了 broker**：Modulith 的 RabbitMQ 外送默认发完就算成功，不等 broker 回确认。Patra 为此自己补了「等确认」这一步。
- **以为有了登记就「恰好一次」**：确认在路上丢了、补投时重发，同一个事件都可能到两次。它保证的是不丢，不保证不重，收消息的一方要能去重。

## 什么时候用，代价是什么

<Callout kind="cost">

**适合**：一个 Spring Boot 应用里有好几块业务，想守住它们之间的边界；模块之间有「提交后必须做成」的事，想有记录、能重来；以后可能把某块拆成独立服务。

**代价**：

- 结构那一半要求包结构服从它的约定（一个模块就是一个基包）。Patra 的分包是「先按层分 Gradle 模块、层里再按子域分包」，套不上，所以只用了事件那一半。
- 事件那一半要多建一张表，定时补投，选好发成功的行怎么清理。
- 事件序列化后存进表里，改事件的类名或字段、升级 Modulith，都要先确认表里没有积压的旧行。
- 只保证至少一次，所有收事件的一方都要能去重。

</Callout>

## Patra 用了哪一半

Patra 的事件工具模块只按构件引了事件相关的几块，没用 Modulith 的 starter，因为 starter 会顺带引进结构那一半的校验：

<CodeRef at="patra-tool/patra-tool-events/build.gradle.kts@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="23-28" />

```kotlin
// Modulith 事件：只要事件相关构件，不要 starter（会带进模块结构校验 spring-modulith-core）
api("org.springframework.modulith:spring-modulith-events-api")
implementation("org.springframework.modulith:spring-modulith-events-core")
runtimeOnly("org.springframework.modulith:spring-modulith-events-jdbc")
runtimeOnly("org.springframework.modulith:spring-modulith-events-jackson")
runtimeOnly("org.springframework.modulith:spring-modulith-events-amqp")
```

`events-core` 是登记本身，`events-jdbc` 把登记行存进数据库，`events-jackson` 负责事件和 JSON 互转，`events-amqp` 负责外送到 RabbitMQ。

## 学习路线

「Spring Modulith」路线按下面的顺序排好了，从这篇往下读：

| 档 | 学什么 | 篇目 |

| 结构 | 模块怎么认、`verify()` 查什么、Patra 为什么用自己的规则 | 应用模块与 verify() |
| 事件基础 | Spring 自己的事件、提交后监听为什么会丢、为什么要先记一笔 | 进程内事件；提交后再处理；双写问题；发件箱 |
