## 第一层：输入是数据，不是代码

`${{ … }}` 看起来像变量，其实是**模板展开**：GitHub 在运行脚本之前，把这个位置换成对应的文字，再把整份脚本交给 shell。如果这段文字是人填的，就等于把代码的一部分交给了他写。

对比两种写法，输入都是 a; echo 已被注入：

Patra 的 cd.yml 就是第二种写法，并且注释里写明了原因：

<CodeRef at=".github/workflows/cd.yml@b6e01875bb5692356021c8a19562f557f319fc54" lines="69-90" />

规则可以记成一句话：**凡是人能控制的内容——手动输入、PR 标题、分支名、提交说明——一律先放进 `env`，在脚本里用 `"$变量"` 读取，不要直接写 `${{ … }}`。** 提交号、运行编号这类系统自己生成的值，风险低得多。

脚本里还有第二层校验：`deploy.sh` 在入口处检查服务名必须在清单里，不认识的直接拒绝执行。输入既要被当作数据，也要被检查合不合理。

## 第二层：谁有资格触发

部署流水线跑在家里的机器上（自托管 runner，下一篇会讲）。这就带来一个问题：Patra 的仓库是**公开**的，任何人都能 fork 一份、提一个 PR。如果 PR 里的代码能在这台机器上运行，等于任何陌生人都能在你家里执行脚本。

所以 cd.yml 在触发器上就划了线：

<CodeRef at=".github/workflows/cd.yml@b6e01875bb5692356021c8a19562f557f319fc54" lines="19-52" />

它只订阅两种事件：

- `push` 到 main：代码已经通过检查和评审，合并进来了。
- `workflow_dispatch`：手动点按钮，而这个按钮只有对仓库有写权限的人才能点。

**不订阅 `pull_request`**。陌生人的代码想上这台机器，唯一的路是先通过检查和评审并合并进 main，而检查它的是一次性的云端机器，用完就销毁。

<Callout kind="lead">

自托管的机器只执行两种代码：已经合并进 main 的，和有写权限的人亲手指定的。

</Callout>

## 第三层：权限、凭据与第三方

三个更细的习惯：

1. **权限最小化**：workflow 顶部写 `permissions: contents: read`，只给读代码的权限；需要更多的 job 单独申请，比如推送镜像需要 `packages: write`。
2. **检出时不留凭据**：`actions/checkout` 加 `persist-credentials: false`，防止仓库令牌留在这台机器的 git 配置里，被后面的步骤顺手拿走。
3. **第三方 action 钉在提交号上**：前面提过的 40 位字符。版本标签（如 `@v4`）可以被作者重新指向另一份代码，一旦作者账号被盗，所有引用标签的人都中招；提交号不可变。

还有一个只在自托管机器上才有的问题：**工作区是持久的**，上一次运行的残留会留给下一次。所以部署流水线要写入一份镜像仓库凭据时，会在最后一步用 `if: always()` 无论成败都删掉它。
