## 看起来是调函数，其实是发了一个 POST

在一个文件的第一行写 `"use server"`，这个文件导出的所有 async 函数就成了 Server Function。Next 把它们用在提交表单、改数据这类场合时，叫 Server Action。

门户的登录、注册、登出都写在这样一个文件里：

<CodeRef at="patra-portal/src/lib/auth/actions.ts@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="148-159" />

```ts
/// 登录：成功（200）时写入 Cookie、返回用户。422 返回字段错误，401 是邮箱或密码不对，
/// 403 是账号被封禁，429 是尝试次数过多；其余状态码、超时和网络错误都是 `unavailable`。
export async function login(input: Credentials): Promise<LoginResult> {
  const reply = await submitCredentials(LOGIN_ENDPOINT, credentialsSchema, input);
  if (!reply) {
    return UNAVAILABLE;
  }
  const { status } = reply.res;
  if (status === 200) {
    const user = await signIn(LOGIN_ENDPOINT, reply);
    return user ? { ok: true, user } : UNAVAILABLE;
  }
```

构建时，Next 把客户端打包里的 `login` 换成一个替身：一个加密过的动作 ID，加一段「把参数发回服务器」的代码。函数体从来不会发到浏览器。

客户端组件这边就是普通的 import 和调用。登录表单把 `login` 交给提交逻辑，提交时 `await` 它：

<CodeRef at="patra-portal/src/components/auth/LoginForm.tsx@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="56-59" />

```tsx
  const { submitting, submit } = useAuthSubmit({
    next,
    action: login,
    successToast: TOAST_MESSAGES.loggedIn,
```

最后一步很关键：在 Next 里，`cookies().set` 只能在 Server Function 或 Route Handler 里调用，服务端组件渲染页面时不能写 Cookie。登录要写 Cookie，所以登录天然适合做成 Server Action。

Next 文档推荐的写法是 `<form action={login}>`，这样脚本还没加载完、表单也能提交。门户没有这样写：它要先用表单库在浏览器里校验一遍、再按返回的 `reason` 决定提示哪条文案，所以在 `onSubmit` 里自己调。表单上另写了 `method="post"`，只是为了脚本没加载完时邮箱和密码不会跑进地址栏。

## 任何人都能直接 POST 它

替身发的是一个普通的 POST。打开浏览器开发者工具就能看到它，复制下来就能自己重发，改掉参数也行。所以每个 Server Action 都得当成一个公开的接口来写：

<CodeRef at="patra-portal/src/lib/auth/actions.ts@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="36-38" />

```ts
/// 入参只校验形状，多余的字段被剥掉；长度和格式由后端校验，失败时回 422 并带原因码
const credentialsSchema = z.object({ email: z.string(), password: z.string() });
const registrationSchema = credentialsSchema.extend({ username: z.string() });
```

TypeScript 的类型只在写代码时有效，请求里实际来的是什么谁也说不准，所以门户在服务端用 zod 再查一遍形状，形状不对就不请求网关。要登录才能做的动作，也要在函数里自己读会话，不能因为「只有登录后的页面才显示这个按钮」就不查。

Next 自己替你做了一道检查：请求的 `Origin` 必须和 `Host` 对得上，别的网站骗你的浏览器发过来的请求会被拒掉。Route Handler 没有这道检查，门户的写操作 Route Handler 都要自己补（`src/lib/same-origin.ts` 的注释写的就是这件事）。

返回值也会原样发给浏览器。门户的 Action 只返回 `ok`、`reason` 和界面要显示的字段，不把网关的原始响应往外传。

## 它适合做什么，不适合做什么

| 场合 | 用不用 Server Action | 原因 |
|---|---|---|
| 登录、注册、保存资料、点有帮助 | 用 | 改数据，常要写 Cookie；不用为每个动作单独写接口 |
| 列表取数、轮询未读数 | 不用 | 浏览器一次只派发一个 Action，取数会排队；取数用服务端组件或 Route Handler |
| 推送事件流、文件下载 | 不用 | 它返回的是一个值，不是一条可以一直流的响应 |
| 给别的程序调的接口 | 不用 | 动作 ID 由构建生成、加密过，不是一个稳定的公开地址 |
