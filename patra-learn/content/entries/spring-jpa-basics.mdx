<Callout kind="lead">

JPA 是 Java 访问关系数据库的一套标准，Patra 用的实现是 Hibernate。你写一个带 `@Entity` 的类对应一张表，Hibernate 负责把「读对象、改对象」翻译成 SQL；Spring Data JPA 再进一步，你只写一个接口，增删改查的实现由它生成。

</Callout>

## 一个类对应一张表

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/java/dev/patra/catalog/infra/author/persistence/entity/AuthorEntity.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="48-72" />

```java
@Entity
@Table(
    name = "cat_author",
    indexes = {
      @Index(name = "idx_normalized_key", columnList = "normalized_key"),
      @Index(name = "idx_status", columnList = "status"),
      @Index(name = "idx_provenance", columnList = "provenance_code"),
      @Index(name = "idx_display_name", columnList = "display_name")
    })
public class AuthorEntity extends SoftDeletableJpaEntity {

  // ========== 核心属性 ==========

  /// 姓名规范化格式，对应 PubMed Computed Authors 的 name 字段。
  ///
  /// 格式如 "SMITH+R"（姓 Smith + 首字母 R），用于分组查询。
  /// **非唯一标识**：同一格式下可能有多个不同的已消歧作者。
  @Column(name = "normalized_key", length = 100, nullable = false)
  private String normalizedKey;

  /// 展示名称（从首个名字变体派生）。
  ///
  /// 格式如 "Zhiyong Lu"，用于界面显示和搜索。
  @Column(name = "display_name", length = 200)
  private String displayName;
```

- `@Entity`：告诉 Hibernate 这个类要和表对应，它的对象叫「实体」。
- `@Table(name = "cat_author")`：对应哪张表。
- `@Column(name = "normalized_key")`：字段对应哪一列。字段叫 `normalizedKey`，列叫 `normalized_key`，靠这个注解对上。
- 主键 `id`、乐观锁版本号 `version`、创建时间这些每张表都有的列，写在父类 `BaseJpaEntity` 里；父类 `SoftDeletableJpaEntity` 再加上软删除：删除时不真删这一行，而是填上 `deleted_at`，之后的查询自动跳过它。

表结构本身由 Flyway 的迁移脚本建，不让 Hibernate 自动建表。实体只描述「类和表怎么对应」。

## 一对多：注解照着外键写

诊断题里那个关系，在实体里是两头各写一句。ORCID 实体这边，外键列 `author_id` 对应一个 `AuthorEntity` 字段：

```java
  @JoinColumn(name = "author_id", nullable = false)
  @ToString.Exclude

```

作者实体那边，用 `mappedBy = "author"` 说「这个集合由对面的 `author` 字段管着，外键不在我这」：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/java/dev/patra/catalog/infra/author/persistence/entity/AuthorEntity.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="127-133" />

```java
  @OneToMany(
      mappedBy = "author",
      cascade = CascadeType.ALL,
      orphanRemoval = true,
      fetch = FetchType.LAZY)
  @Builder.Default
  private Set<AuthorOrcidEntity> orcids = new HashSet<>();
```

另外三个参数：

- `cascade = CascadeType.ALL`：保存、删除作者时，它的 ORCID 跟着一起保存、删除。
- `orphanRemoval = true`：从集合里拿掉一个 ORCID，提交时这一行就被删掉。
- `fetch = FetchType.LAZY`：读作者时先不查 ORCID 表，等代码真用到 `orcids` 时再查。这个「用到才查」在循环里会变成一个经典的坑，后面 N+1 那篇专门讲。

## Repository：只写接口，不写实现

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/java/dev/patra/catalog/infra/author/persistence/dao/AuthorDao.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="29-39" />

```java
public interface AuthorDao extends JpaRepository<AuthorEntity, Long> {

  // ========== 姓名规范化格式查询 ==========

  /// 根据姓名规范化格式查询作者。
  ///
  /// 同一格式下可能有多个不同的已消歧作者。
  ///
  /// @param normalizedKey 姓名规范化格式（如 "SMITH+R"）
  /// @return 匹配的作者列表（可能为空）
  List<AuthorEntity> findByNormalizedKey(String normalizedKey);
```

`AuthorDao` 只是一个接口，项目里没有它的实现类。Spring Data JPA 启动时替它生成一个：

- 继承 `JpaRepository<AuthorEntity, Long>`，就白得 `save`、`findById`、`findAllById`、`deleteById` 这些通用方法（`Long` 是主键类型）。
- 按方法名生成查询：`findByNormalizedKey` 拆开是「找，按 normalizedKey 等于参数」，生成 `where normalized_key = ?`。`countByStatus`、`existsByNormalizedKey` 同理。
- 方法名说不清的，用 `@Query` 手写 JPQL（一种按实体和字段名写的查询语言，不是直接写表名列名）。比如按 ORCID 找作者：`SELECT a FROM AuthorEntity a JOIN a.orcids o WHERE o.orcid = :orcid`。

<Callout kind="warn">

名字容易混。Spring Data 管这种接口叫 Repository，可在 Patra 里，**领域层的 `AuthorRepository` 是一个端口**（领域层定义、不知道 JPA），JPA 的这个接口叫 `AuthorDao`，放在 infra 层。两者之间隔着一个 `AuthorRepositoryAdapter`。

</Callout>

## 持久化上下文：被管着的对象

这是 JPA 最容易让人糊涂的地方。用 JPA 读出来的实体，不是一份普通的拷贝，而是**被管着的**（managed）：在当前事务结束前，Hibernate 记着它读出来时的样子。你改了它的字段，哪怕没调 `save`，事务提交时 Hibernate 也会发现「变了」，自动发一条 `UPDATE`。这个「记着所有被管着的对象」的地方叫**持久化上下文**。

而 SQL 也不是你一改字段就立刻发出去的。Hibernate 把要做的改动攒着，到某个时刻一次性发给数据库，这一步叫 **flush**。默认在事务提交前、以及执行一条可能受这些改动影响的查询前会 flush；也可以调 `entityManager.flush()` 手动让它马上发。

catalog 批量导入作者时，更新已有作者正是这样做的：

<CodeRef at="patra-api/patra-catalog/patra-catalog-infra/src/main/java/dev/patra/catalog/infra/author/persistence/AuthorRepositoryAdapter.java@5073ab1358404ecd989e722373cd9f7edafe238b" lines="101-131" />

```java
    // 处理更新：批量加载现有 Entity，然后更新
    if (!existingAuthors.isEmpty()) {
      List<Long> ids = existingAuthors.stream().map(a -> a.getId().value()).toList();

      // 批量加载 managed entities
      List<AuthorEntity> loadedEntities = authorDao.findAllById(ids);
      Map<Long, AuthorEntity> entityMap =
          loadedEntities.stream()
              .collect(java.util.stream.Collectors.toMap(AuthorEntity::getId, e -> e));

      for (AuthorAggregate aggregate : existingAuthors) {
        AuthorEntity entity = entityMap.get(aggregate.getId().value());
        if (entity == null) {
          log.warn("跨批次更新失败：作者不存在，ID={}", aggregate.getId().value());
          continue;
        }

        // 更新核心属性
        updateEntityFromAggregate(entity, aggregate);

        // 更新子实体（orphanRemoval 会自动删除旧的）
        entity.getNameVariants().clear();
        entity.getOrcids().clear();

        allEntities.add(entity);
      }

      // 先 flush 删除操作，避免 INSERT 和 DELETE 顺序问题导致唯一约束冲突
      // Hibernate 默认顺序：INSERT → UPDATE → DELETE
      // 需要先执行 DELETE，才能 INSERT 具有相同唯一键的新记录
      entityManager.flush();
```

为什么这里非要在中途手动 flush，和 Hibernate 发 SQL 的先后顺序有关，是另一篇坑的内容。在这篇里只要记住：**改对象不等于写库，flush 才是 SQL 真正发出去的时刻，提交才是生效的时刻。**
