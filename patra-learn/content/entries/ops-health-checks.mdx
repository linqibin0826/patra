<Callout kind="lead">

上线不算数，验货才算数。Patra 的部署脚本在换上新容器之后，要过两道检查才认这次部署成功：

- **门外追问**：部署脚本从宿主机这一侧，亲自去敲服务的门
- **对版**：确认跑起来的就是这次要上的那个版本

另外还有一层**容器自查**：容器在里面定期问自己「我还好吗」。它不是部署脚本的门槛，结果写在容器的健康状态上，给 Docker 和每日巡检看。

</Callout>

## 容器起来了，服务还没醒

<Callout kind="analogy">

饭店开了门，不等于能点菜。灯亮了、人到了，后厨的灶还没点着，菜单还没印好，客人进来也吃不上饭。

</Callout>

后端服务也一样。Spring Boot 启动时要连 PostgreSQL、连 Redis、注册进 Nacos，把整个应用上下文初始化完。这些任何一步出错，容器照样显示「已启动」，里面的服务却不能用。

所以「部署」这一步之后，必须有一步专门验货。

## 先看另一层：容器自己的体检表

每个应用容器在 compose 文件里都声明了 `healthcheck`：容器**从内部**定期自查。六个后端服务和门户、学习站共用同一组节奏参数，用 YAML 锚点写在文件开头：

<CodeRef at="patra-infra/docker/docker-compose.apps.yaml@26cdec9df840016230344598ab7ff109775c49f9" lines="26-30" />

```yaml
x-app-healthcheck: &app-healthcheck
  interval: 10s
  timeout: 5s
  retries: 15
  start_period: 60s
```

| 参数 | 意思 |
|---|---|
| `interval` | 每 10 秒查一次 |
| `timeout` | 一次检查最多等 5 秒 |
| `retries` | 连续失败 15 次，才判成「不健康」 |
| `start_period` | 启动后 60 秒内的失败不计数 |

最后一个参数很关键：Spring Boot 冷启动要一阵子，给它一段不计失败的宽限期，免得刚起来就被判了死刑。

检查本身是在容器里发一个 HTTP 请求：后端服务用 `curl` 访问自己的 `/actuator/health`，门户和学习站的镜像里没有 `curl`，用自带的 `wget` 访问 `/api/health`。结果写在容器的 health 状态上，用 `docker ps` 能看到。

这道检查是 Docker 层面的「自我感觉」。它有一个盲区：自己说自己好，不等于从外面真能连上。所以部署脚本不读这个状态，`up -d` 之后自己再去问一遍。

## 第一道：部署脚本站在门外追问

换上新容器之后，部署脚本 `deploy.sh` 要**从宿主机这一侧**去问：服务，你好了吗？

<CodeRef at="patra-infra/cd/deploy.sh@2197850b5a624ed4dbaa97df71e144c343e28baa" lines="67-81" />

```bash
health_ok() { # $1=svc
  local port path match out
  port="$(meta "$1" port)"; path="$(meta "$1" healthPath)"; match="$(meta "$1" healthMatch)"
  out="$($CURL -fs "http://127.0.0.1:${port}${path}")" || return 1
  [ -z "$match" ] || echo "$out" | grep -q "$match"
}
```

端口、路径、期望的返回内容都不写死在脚本里，而是从 `services.json` 这份花名册按服务名查。这里有三个细节：

1. **`curl -f`**：服务器回 4xx、5xx 时，`curl` 以非零状态退出。服务返回 503，就算没过。
2. **`healthMatch`**：后端服务的条目里写了 `"status":"UP"`，返回内容里必须真的出现这几个字才算过。门户和学习站没写，HTTP 成功就行。
3. **地址写 `127.0.0.1`**，不写 `localhost`。为什么，有一篇专门讲这个坑。

## 第二道：确认跑的是这一版

最阴险的失败长这样：`up -d` 悄悄落在了旧镜像上，比如版本变量没传对。旧版本照样健康，容器自查和门外追问全绿，可你要上线的新代码根本没上去。表面成功，实际什么都没发生。

所以部署脚本还有第二道：用 `docker inspect` 掏出容器正在跑的镜像，和期望的「镜像名:版本号」逐字比对。

<CodeRef at="patra-infra/cd/deploy.sh@2197850b5a624ed4dbaa97df71e144c343e28baa" lines="83-86" />

版本号是提交的 SHA，所以这一步等于把「跑的就是这次提交」变成了可以验证的事实。

两道都过，脚本才在服务器上记下这个服务的「上一个好版本」，用于以后回滚。

容器自查的结果不会白费：每天早上的巡检会去看有没有 `unhealthy` 的容器。部署脚本的轮询则只在部署那几分钟里起作用。两者互补，谁也替代不了谁。
