## 令牌只在浏览器和门户服务端之间

用户登录成功后，identity 发给门户一个会话令牌。会话本身存在后端，归 identity 一家管，令牌只是一张「凭它来查会话」的号码牌。门户要做的，是让浏览器替它保管这张号码牌，又不让页面上的任何脚本碰到它。

<CodeRef at="patra-portal/src/lib/auth/session-cookie.ts@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="21-33" />

```ts
/// 会话 Cookie 的名称和固定属性。`Secure` 开时名字带 `__Host-` 前缀：浏览器只接受本站经 HTTPS 写入、
/// `Path=/`、不带 `Domain` 的那一份，同一域名下的其他子站点没法种入或覆盖它。这个前缀要求必须带
/// `Secure`，所以 HTTP 环境只能用不带前缀的名字。
function sessionCookie() {
  const secure = secureEnabled();
  return {
    name: secure ? "__Host-patra_session" : "patra_session",
    httpOnly: true,
    sameSite: "lax",
    path: "/",
    secure,
  } as const;
}
```

每个属性挡一类问题：

| 属性 | 挡住什么 |
|---|---|
| `httpOnly` | 页面脚本读不到。就算页面被注入了一段恶意脚本，它也偷不走令牌 |
| `sameSite: "lax"` | 别的网站发起的跨站请求（除了点链接跳过来）不带这个 Cookie |
| `secure` + `__Host-` 前缀 | 只走 HTTPS；同域名下别的子站点没法种一个同名 Cookie 来顶替它 |

这个文件第一行是 `import "server-only"`。门户里所有读写会话 Cookie 的代码都在服务端，浏览器端要知道「我是谁」，只能问门户。

## 谁在读，谁在写

在 Next 里，`cookies()` 在服务端组件里只能读；要写，必须在 Server Function 或 Route Handler 里。门户各处的分工正好照着这条规则来：

| 位置 | 做什么 |
|---|---|
| 登录、注册的 Server Action | 成功后写入令牌，有效期 30 天 |
| `/api/auth/me`（Route Handler） | 导航栏来问「我是谁」：读到用户就把 Cookie 有效期顺延回 30 天；网关说令牌无效就清掉 |
| 登出的 Server Action | 请求网关删会话，不管成败最后都清 Cookie |
| 服务端渲染的页面 | 只读：拿令牌问网关当前用户是谁 |
| `proxy.ts`（请求入口） | 只读，而且从不写 |

清 Cookie 有个细节：门户不用 `cookies().delete()`，而是写一个空值、`Max-Age=0`。因为 `delete` 发出去的指令不带 `Secure`，浏览器会拒绝用它删 `__Host-` 开头的 Cookie。

<CodeRef at="patra-portal/src/lib/auth/session-cookie.ts@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="60-64" />

```ts
/// 清除：写入空值，属性和写入时相同，`Max-Age=0`。不用 `cookies().delete()`：它不带 `Secure`，
/// 浏览器会拒绝用它删除 `__Host-` 开头的 Cookie。
export async function clearSessionCookie(): Promise<void> {
  (await cookies()).set({ ...sessionCookie(), value: "", maxAge: 0 });
}
```

## 请求入口：proxy.ts 先看一眼

Next 16 里，项目根（或 `src/`）下的 `proxy.ts` 会在每个请求到达页面之前先跑一遍。它以前叫 middleware，功能一样。门户的入口长这样：

<CodeRef at="patra-portal/src/proxy.ts@d0ca49caf72d9d9aacd7459c1054cf9131b3759e" lines="82-87" />

```ts
export async function proxy(req: NextRequest) {
  if (AUTH_PAGES.includes(req.nextUrl.pathname)) {
    return leaveAuthPage(req);
  }
  // 冷静期查询先发出去；详情页的存在检查与它并行，结果出来后冷静期跳转优先
  const pending = pendingDeletionRedirect(req);
```

它管所有页面，但不管 `/api/` 和静态文件：

<CodeRef at="patra-portal/src/proxy.ts@d0ca49caf72d9d9aacd7459c1054cf9131b3759e" lines="127-130" />

```ts
/// 全部页面（冷静期跳转要覆盖任何页面），不含 `/api/`、`/_next/` 与带扩展名的静态文件
export const config = {
  matcher: ["/((?!api/|_next/|.*\\.[^/]+$).*)"],
};
```

和登录态有关的事它只做两件，都是「顺路把人送到该去的地方」：

1. 已经登录的人打开登录页或注册页，直接送回他原本要去的页面。
2. 账号在注销冷静期的人整页打开任何页面，送到取消注销页。

它不负责「没登录就不许看」。Next 的文档也说得明白：proxy 每个请求都跑，包括预取，只适合做这种乐观的检查，不该当成完整的权限判断。

## 真正的门在页面里

要登录才能看的页面（设置、文献库、提醒），在页面代码里自己调 `requireUser`：

<CodeRef at="patra-portal/src/lib/auth/require-user.ts@fe4c6bb68c591a9c9b5fe80f76bbfbbbc6aeae75" lines="10-22" />

```ts
export async function requireUser(path: string): Promise<CurrentUser> {
  const session = await lookupSession();
  if (session.status === "authenticated") {
    if (session.user.status === "PENDING_DELETION") {
      redirect(deletionPendingHref(path));
    }
    return session.user;
  }
  if (session.status === "unavailable") {
    throw new Error("登录状态暂时不可用");
  }
  redirect(authPageHref("/login", path));
}
```

proxy 和 `requireUser` 都是「读 Cookie、问网关我是谁」，平时看不出区别。差别在网关出问题的时候。切到「问网关时网关挂了」看看：
