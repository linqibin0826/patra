## 现象

部署用的那台 Mac mini 上，PostgreSQL 隔一段时间就报：

```text
FATAL: sorry, too many clients already
```

连 `psql` 用超级用户都进不去。原因是所有服务都用 `postgres` 超级用户连库，PostgreSQL 给超级用户留的几个保留槽也被它们占完了。这个问题出现过不止一次。

最容易带偏的方向是「负载大了」或「连接池配太大」，接着就去调 `max_connections` 或各服务的池子。

确诊用的就是这两条命令（库跑在容器里）：

```bash
docker restart patra-postgres
docker exec patra-postgres psql -U postgres -t -c \
  "SELECT count(*) FROM pg_stat_activity WHERE backend_type = 'client backend';"
```

满到连不上时，先停掉在崩溃重启的容器腾出几个槽；还是满就直接重启 PostgreSQL。进得去以后，按 `datname`、`state`、`client_addr` 把 `pg_stat_activity` 拆开看分布，能看出孤儿连接来自哪一类客户端。

## 根因

客户端异常断开时，告别的那个 TCP 包（FIN）没有一路传到 PostgreSQL。这台库的连接要经过 VPN 隧道和容器的端口转发（NAT），客户端这头的进程没了，中间环节不会替它通知服务端。

PostgreSQL 这边看到的是一条一直空闲、从不说话的连接。它没法区分「对方还在、只是闲着」和「对方早没了」，只能等操作系统的 TCP keepalive 探测出来。Linux 默认的 keepalive 要空闲约 2 小时才开始探。

哪些客户端会这样断开：开发机上热重载的服务、被强杀的工具进程、崩溃重启的容器。开发工具里配的数据库插件会给每个工作会话各起一套连接，开的会话一多，堆积就更快。一天下来攒够 100 条并不难。

## 修法

**恢复**：重启 PostgreSQL 就清空孤儿连接。会短暂断开所有连接，各服务的连接池会自动重连。

**长效**：让 PostgreSQL 自己更早地探测死连接：

```sql
ALTER SYSTEM SET tcp_keepalives_idle = 900;
ALTER SYSTEM SET tcp_keepalives_interval = 60;
ALTER SYSTEM SET tcp_keepalives_count = 10;
SELECT pg_reload_conf();
```

死连接在约 25 分钟内被回收。只会断掉对端已经消失的连接：活着的连接会被对方的内核自动回应，正在跑的长查询也不受影响。`ALTER SYSTEM` 写进数据目录里的 `postgresql.auto.conf`，数据目录挂在宿主机上，重建容器也还在。

<Callout kind="warn">

两个容易误判的地方：

- 新设置**只对之后建立的 TCP 连接生效**，reload 之前的旧连接还是老样子。
- 用 unix socket 连进去执行 `SHOW tcp_keepalives_idle`，永远显示 0，这是正常的：socket 连接没有 TCP。要验证得用 `psql -h 127.0.0.1` 走 TCP 再看。

</Callout>
