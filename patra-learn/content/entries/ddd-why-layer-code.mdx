## 先看不分层的写法会怎样

假设要做「新建收藏夹」。最直接的写法是把所有事塞进一个方法里：

```java
// 假想的写法，用来对比，不是 Patra 的代码
@PostMapping("/me/collections")
public Map<String, Object> create(@RequestBody Map<String, String> body, HttpSession session) {
  long userId = (long) session.getAttribute("userId");
  String name = body.get("name").trim();
  int count = jdbc.queryForObject("SELECT count(*) FROM collection WHERE user_id = ?", Integer.class, userId);
  if (count >= 200) throw new RuntimeException("最多 200 个");
  // 再查重名、再 INSERT、再把数据库行拼成 JSON 返回……
}
```

它能跑。问题在于，一个方法同时懂四件事：怎么从 HTTP 里取数据、先做什么后做什么、「200」这条规则、SQL 怎么写。

<Callout kind="analogy">

像一家小餐馆里，同一个人又收银、又点菜、又炒菜、又洗碗。人少的时候没问题。想换一种收银方式，他得连炒菜的流程一起重新想一遍，因为所有事缠在他一个人的脑子里。

</Callout>

## 分层：每层只回答一个问题

分层就是把这四件事分开放。Patra 里「新建收藏夹」是这样分的：

| 层 | 只回答的问题 | 新建收藏夹里对应的东西 |
|---|---|---|
| adapter（适配器） | 谁在敲门？数据怎么进来、怎么出去？ | `MyCollectionController` 收 JSON，交给命令总线 |
| app（应用） | 先做什么，再做什么？ | `CreateCollectionHandler` 排顺序：锁用户、数个数、查重名、创建 |
| domain（领域） | 业务规则是什么？ | `CollectionLimits` 放数字 200，`CollectionName` 管名称怎么算合法 |
| infra（基础设施） | 具体怎么存？ | `CollectionRepositoryAdapter` 里才有 SQL |

先别急着记这四个名字。后面的篇目会一层一层展开。这篇只要看清一点：每一层只管一类变化。

## 分层是有代价的

<Callout kind="cost">

文件变多了。新建一个收藏夹，要打开 Controller、Handler、Repository 接口、适配器至少四个文件才能看全。Patra 愿意付这个代价，是因为项目会长期改下去，而且改的是互相独立的东西：规则、流程、存储。几十行的小脚本不需要分层。

</Callout>
