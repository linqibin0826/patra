<Callout kind="lead">

事件发布登记：发布事件时，在发布方的业务事务里，为每个要在提交后处理它的监听器记一行；监听器处理成功，这一行才算完成，没完成的留在表里，可以补投。

</Callout>

## 先看监听器：@ApplicationModuleListener 改了三件事

Modulith 推荐的监听写法是 `@ApplicationModuleListener`。它本身只是三个 Spring 注解的组合：

```java
// Spring Modulith 2.1.2 源码：org.springframework.modulith.events.ApplicationModuleListener
@Async
@Transactional(propagation = Propagation.REQUIRES_NEW)
@TransactionalEventListener
public @interface ApplicationModuleListener {
```

可每一个都改变了监听器的行为：

| 注解 | 改变了什么 | 带来的后果 |
|---|---|---|
| `@TransactionalEventListener` | 等发布方的事务提交后才执行 | 发布方回滚，监听器根本不执行，不会处理一件没发生的事 |
| `@Async` | 换一条线程执行 | 请求线程不用等它，监听器慢不拖慢用户 |
| `@Transactional(REQUIRES_NEW)` | 在自己的新事务里执行 | 监听器失败只回滚它自己，不影响已经提交的发布方 |

三个加起来，正好是全景篇里那个「提交后、换线程处理」的写法。它的老问题也还在：监听器在内存里排着，进程一崩，事件就没了。事件发布登记就是来补这个洞的。

## 登记什么时候写、写了什么

事务里调 `publishEvent(事件)` 的那一刻，Modulith 找出所有会在提交后处理这个事件的监听器，**在当前这个业务事务里**，每个监听器写一行。这一行和业务数据一起提交、一起回滚：业务回滚了，登记行也没了，监听器也不会执行。

表结构是 Modulith 定死的，Patra 用 Flyway 照着建：

<CodeRef at="patra-tool/patra-tool-events/src/integrationTest/resources/db/migration/V1__create_event_publication.sql@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="3-14" />

```sql
CREATE TABLE event_publication
(
    id                     UUID                     NOT NULL PRIMARY KEY,
    listener_id            TEXT                     NOT NULL,
    event_type             TEXT                     NOT NULL,
    serialized_event       TEXT                     NOT NULL,
    publication_date       TIMESTAMP WITH TIME ZONE NOT NULL,
    completion_date        TIMESTAMP WITH TIME ZONE,
    status                 TEXT,
    completion_attempts    INT,
    last_resubmission_date TIMESTAMP WITH TIME ZONE
);
```

| 列 | 记什么 |
|---|---|
| `listener_id` | 欠的是哪个监听器（默认是监听方法的完整签名） |
| `event_type`、`serialized_event` | 事件的类型和序列化后的内容，补投时要靠它们把事件还原出来 |
| `publication_date` | 什么时候发布的 |
| `status`、`completion_date` | 处理到哪一步了、什么时候完成的 |
| `completion_attempts`、`last_resubmission_date` | 试过几次、最后一次补投是什么时候 |

<Callout kind="warn">

事件是序列化后存进表里的，补投时再反序列化回来。改了事件的类名或字段、或者升级 Modulith 改了监听器的名字，表里的旧行就可能还原不了、找不到监听器。改之前先确认表里没有积压。

</Callout>

## 完成了的行怎么办：三种完成模式

监听器成功之后，这一行怎么处理，由 `spring.modulith.events.completion-mode` 决定：

| 模式 | 做什么 | 要注意 |
|---|---|---|
| `UPDATE`（默认） | 标成完成，行留在表里 | 表会一直长，要自己定期清理已完成的行，否则越来越慢 |
| `DELETE` | 直接删掉 | 表里只剩没完成的；想查历史就查不到了 |
| `ARCHIVE` | 挪进同结构的归档表 | 要多建一张 `event_publication_archive` |

Patra 选了 `DELETE`，由事件工具模块出成默认值。理由有两条：表里只剩没发出去的事件，「表不空」就等于「有积压」，一眼看得出来；identity 外送的安全邮件事件里带着一次性的令牌链接，发完就不该在库里久留。

## 没完成的行谁来管

这是最容易想当然的地方：**登记表不会自己重试**。失败的行只是躺在表里，Modulith 给了三种把它们捡起来的办法，都要你自己决定用不用：

| 办法 | 怎么工作 | 默认 |
|---|---|---|
| 补投接口 | 代码里调 `IncompleteEventPublications.resubmitIncompletePublications(过滤条件)`，把符合条件的未完成行重新交给监听器 | 要自己找地方定时调 |
| 过期检查 | 定时把停在某个状态太久的行改成失败，好让补投捡起来 | 不配时长就不查；还要应用开着 Spring 的定时任务 |
| 重启时重发 | 应用启动时把所有未完成的行重发一遍 | 关；多实例部署时不推荐 |

Patra 的做法是 XXL-Job 每分钟跑一次补投，只捡发布超过 1 分钟、又不在发送中的行；重启时重发不开，反正一分钟内补投就会捡起来。

## 哪些监听器会被登记

默认情况下，**每一个**在提交后执行的监听器（贴了 `@TransactionalEventListener` 的，包括 `@ApplicationModuleListener`）都会被登记。Modulith 2.1.2 起可以用 `spring.modulith.events.registry-trigger-annotation` 只登记带某个注解的监听器。Patra 只登记带 `@ApplicationModuleListener` 的，也就是外送器，为什么这样选，「只让要外送的事件进登记表」那篇讲。
