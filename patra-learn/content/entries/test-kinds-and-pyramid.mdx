## 三层：测的范围一层比一层大

按「一次测多少个零件」，测试大致分三层：

| 层 | 测什么 | 靠什么跑 |
|---|---|---|
| 单元测试 | 一个类、一个方法，不碰外面 | 纯内存 |
| 集成测试 | 几个零件接在一起，其中一两个是真的（真数据库、真 HTTP 层） | 真实的中间件容器，或 Spring 的一小块 |
| 端到端测试 | 整个服务（或整个系统）从入口走到出口 | 真实数据库、对象存储等全套 |

Patra 后端把这三层放在三个不同的目录里，名字、位置、超时都不一样。点一点下面的方块：

## 为什么是金字塔，不是倒过来

既然端到端最接近真实，为什么不全写端到端？

金字塔的底座是便宜的，所以什么事能在底层说清楚，就别往上放。上层测试只负责底层测不到的那一类问题：零件之间的接口对不对、真实数据库和我们的 SQL 合不合、配置有没有装配对。

## 一个功能，在三层里各被测什么

用「用户改名」来感受分工：

- **单元层**：名字格式合法不合法、冷却期怎么算。纯逻辑，几毫秒。
- **集成层**：改名的 HTTP 接口收到请求，转成命令，返回正确的状态码；或者仓储在真实数据库里能存取。
- **端到端层**：注册、验证邮箱、改名、再改被拒、30 天后能改回、旧名被占用……整条流程串起来。

后两层各用一篇单独讲。

分层不是死规矩。Patra 里「改名」这条完整流程，实际由 `UsernameChangeFlowIT` 覆盖：它起了真实的 PostgreSQL、Redis、RabbitMQ 容器，走完整条流程，却放在 identity 服务 boot 模块的 `integrationTest` 套件里。划分的依据是「用什么跑、跑多重」，名字和目录只是照这个归类。

## CI 里怎么分别点名

Patra 的 CI 不是对每个模块都跑三样。每个 Gradle 模块在构建时被登记它「需要跑哪些任务」，结果存成 `module-graph.json`：

<CodeRef at="patra-infra/cd/module-graph.json@5b1d855a5da18806b91a52f24253e64d40d743a8" lines="12-62" />

看这份文件里 catalog 服务的几个模块：`catalog-domain` 只有 `check`（也就是单元测试加各类检查）；`catalog-adapter` 在 `check` 之外还要跑 `integrationTest`；`catalog-boot` 在 `check` 之外跑 `e2eTest`。

整个文件 44 个模块里，22 个带 `integrationTest`，21 个只有 `check`，只有 1 个带 `e2eTest`：端到端测试在 Patra 里确实是「极少」。

CI 把这些任务点名交给 Gradle，示意如下：

```text
./gradlew <该模块的 check>  <该模块的 integrationTest>  <该模块的 e2eTest>
```

<Callout kind="insight">

`check`、`integrationTest`、`e2eTest` 是三个独立的任务，所以 CI 里要逐个点名。本地想只跑某一层：`./gradlew :模块名:test`、`:模块名:integrationTest`、`:模块名:e2eTest`。

</Callout>
