## 为什么云端机器不够用

上一篇讲过，CI 的 job 跑在 GitHub 租来的云端机器上，用完即销毁。这很适合做检查，但部署做不了：

- 云端机器在远处，**摸不到家里 Mac mini 上的容器**。
- 要把新版本换上去，命令必须在容器所在的那台机器上执行。

解决办法是在 Mac mini 上装一个常驻程序，把这台机器注册给 GitHub，当作“自己的 runner”。这就是 **self-hosted runner（自托管 runner）**。

| | 云端 runner | 自托管 runner |
|---|---|---|
| 谁的机器 | GitHub 的 | 你自己的 |
| 生命周期 | 每个 job 一台全新的，用完销毁 | 常驻，一直守着 |
| 环境 | 干净，每次从零开始 | 持久，上次的东西可能还在 |
| 能否摸到你的服务 | 不能 | 能，它就在服务旁边 |
| Patra 用它做 | 合并前检查 | 打包、部署、推送配置 |

## 领活：不是 GitHub 找上门，是机器主动去问

最容易误解的地方：GitHub 怎么连进你的家庭网络？答案是**不连**。

这带来一个很好的性质：**家里的防火墙不用为它开任何口子**。不需要公网 IP，不需要端口转发。

## 标签：这份活该谁接

仓库可以有很多 runner，任务靠**标签**路由。Patra 的 runner 注册时带了自定义标签 `macmini`，加上内置的 `self-hosted`。部署的 job 这样声明需求：

<CodeRef at=".github/workflows/cd.yml@b6e01875bb5692356021c8a19562f557f319fc54" lines="112-121" />

`runs-on: [self-hosted, macmini]` 的意思是：两个标签都对得上的 runner 才能接。CI 里那些写着 `ubuntu-latest` 的 job，永远轮不到它。

## 安全边界：陌生代码上不了这台机器

仓库是公开的，任何人都能提 PR。如果 PR 的代码能跑在 Mac mini 上，就等于任何陌生人都能在你家里执行脚本。所以部署类 workflow 只订阅 `push` 到 main 和手动触发，**不订阅 `pull_request`**。

再加上上面的“零入站”：陌生代码进不来，陌生连接也进不来。这台家用机器能当部署机，靠的就是这两道墙。（细节见“流水线安全”一篇。）

## 常驻程序的生存环境

runner 是 macOS 的 launchd 服务，在后台常驻。这带来一个隐蔽的差异：

<Callout kind="insight">

后台服务不会继承你终端里的任何环境变量。你在终端里能用的 JAVA_HOME、PATH，对 runner 统统不存在。

</Callout>

所以安装脚本要把必需的环境显式固化下来：

- 一份 `.env` 文件：写入 JAVA_HOME 等变量，runner 启动时读取。
- 一份 `.path` 文件：补上 docker 所在的目录，否则 runner 连 docker 命令都找不到。

<CodeRef at="patra-infra/scripts/install-github-runner.sh@53ec4388b912746d0fa15961b512897279bd4ae2" lines="88-100" />

另一个有意的选择是注册时加了 `--disableupdate`，关掉 runner 的自动更新。代价是升级要人工做：**闲时不带参数重新跑一次安装脚本**，它会比较版本、只更新程序本体，注册信息不动。

还有两条运维红线：

1. **任务执行期间不能重启 runner**，否则正在执行的任务会被当场杀掉，表现成莫名其妙的 cancelled。重启前先确认没有进行中的运行。
2. **工作区是持久的**。每次运行前 `actions/checkout` 会清掉被 git 忽略的文件，所以密钥这类文件不能放在仓库目录里，要放在仓库之外的固定位置。
