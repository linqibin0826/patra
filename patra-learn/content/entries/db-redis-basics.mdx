## Redis 是什么

上一篇讲的 PostgreSQL 是**关系型数据库**：数据放表里，有列有类型，靠 SQL 查询，存在磁盘上。

**Redis** 是另一类：**键值库**。数据没有表，只有一个个「键 → 值」：

```
session:abc123  →  { user_id: 7, last_active_at: ... }
login-fail:7    →  3
```

你给它一个键，它返回对应的值。因为数据放在**内存**里，读写极快（通常比查磁盘上的数据库快一两个数量级）。

代价也来自内存：容量比磁盘小得多，也更贵；机器重启数据可能丢（可以配置持久化，但不是它的强项）。

所以 Redis 的定位是**快而不求永远**：存那些丢了可以重新来、或者本来就该过期的东西。账号、文献这类"丢了就是事故"的数据，仍然放在 PostgreSQL 里。

## 值不止是字符串

一个键下面的值有几种形状：

| 类型 | 长什么样 | 典型用途 |
|---|---|---|
| 字符串（string） | 一段文字或数字，可以直接加 1 | 计数器 |
| 哈希（hash） | 一个键下面有多个字段，像一行小表 | 一个会话的各项信息 |
| 有序集合（sorted set） | 每个成员带一个分数，按分数排好 | 排行榜、「到期时间」排序 |
| 列表、集合 | 顺序列表、不重复集合 | 队列、去重 |

## 过期时间：数据自己消失

Redis 里每个键都可以设置**过期时间（TTL）**，到点自动删除。

Patra 登录会话就靠它。建会话时，除了把各项信息写成一个哈希，还会给这个键设上过期时间：

<CodeRef at="patra-api/patra-identity/patra-identity-infra/src/main/resources/redis/session-create.lua@8a1deacc881d2260bb5802caf0ad974aff0d6072" lines="60-61" />

```lua
redis.call('HSET', sessionKey, unpack(fields))
redis.call('PEXPIRE', sessionKey, math.min(idle, expiresAt - now))
```

`PEXPIRE` 设的是毫秒级过期。取"不活跃过期时间"和"距离绝对过期还剩多久"中较小的那个：用户太久不动会过期，用得再勤也有一个总上限。没有任何清理程序，到点 Redis 自己删。

用户每次操作要"续期"，也是重设一次过期时间：

<CodeRef at="patra-api/patra-identity/patra-identity-infra/src/main/resources/redis/session-touch.lua@8a1deacc881d2260bb5802caf0ad974aff0d6072" lines="19-21" />

```lua
if now - tonumber(session['last_active_at']) >= tonumber(ARGV[2]) then
  redis.call('HSET', KEYS[1], 'last_active_at', ARGV[1])
  redis.call('PEXPIRE', KEYS[1], math.min(tonumber(session['idle_timeout_ms']), expiresAt - now))
```

## 命令是原子的，但「读再写」两步不是

Redis 处理命令是**一条一条排队执行**的：每条命令执行时，不会被别的命令打断。所以 `INCR`（计数加 1）这种单条命令是原子的，十个人同时 `INCR`，结果就是准确加了 10。

但如果你把"读出来，加 1，再写回去"拆成两条命令，中间就有空子可钻：

对于简单的计数，用一条原子的 `INCR` 就解决。但很多场景要把好几步捆在一起：先看有没有被锁、再数失败次数、再决定放不放行、放行了还要登记……这就轮到 **Lua 脚本**。

## Lua 脚本：把几步捆成一个整体

Redis 允许你把一段 Lua 脚本交给它执行。**整段脚本执行期间，别的命令都得等着**，所以脚本等价于"一个不可分割的操作"。

Patra 登录限次的核心就是一段脚本：

<CodeRef at="patra-api/patra-identity/patra-identity-infra/src/main/resources/redis/login-throttle-begin.lua@2c72f64fa87141c8e1f23d4ba583c052e6800212" lines="5-20" />

```lua
local lockTtl = redis.call('PTTL', KEYS[3])
if lockTtl > 0 then
  return lockTtl
end
local time = redis.call('TIME')
local now = tonumber(time[1]) * 1000 + math.floor(tonumber(time[2]) / 1000)
redis.call('ZREMRANGEBYSCORE', KEYS[2], '-inf', now)
local failures = tonumber(redis.call('GET', KEYS[1]) or '0')
local inflight = redis.call('ZCARD', KEYS[2])
if failures + inflight >= tonumber(ARGV[1]) then
  return -1
end
local ttl = tonumber(ARGV[3])
redis.call('ZADD', KEYS[2], now + ttl, ARGV[2])
redis.call('PEXPIRE', KEYS[2], ttl)
return 0
```

读法：先看账号有没有被临时锁住；没有的话，数一下"已失败的次数 + 正在验证中的次数"，到了上限就拒绝；没到，就登记一条"正在验证中"并返回放行。判断和登记在同一段脚本里，两个并发的登录尝试不可能同时看到"还差一次"然后都放行。

这里还用到了一个有序集合（`ZADD`）：成员是每次正在进行的尝试，分数是它的过期时间。每次先把过期的清掉（`ZREMRANGEBYSCORE`）再数，不需要另外的清理程序。

<Callout kind="warn">

Lua 脚本期间别的命令都在等，所以脚本要短、不能做耗时的事。把脚本当作"一小段不可分割的数据库操作"，不要往里塞业务逻辑。

</Callout>

## 什么该放 Redis，什么不该

| 适合 | 不适合 |
|---|---|
| 会过期的状态：登录会话、验证码 | 不能丢的业务数据：账号、文献、评论 |
| 高频读写的计数与限流 | 需要复杂查询、多表连接的数据 |
| 可以重新生成的缓存 | 要靠它永久保存的唯一副本 |

Patra 的分工很清楚：**账号信息在 PostgreSQL，登录会话在 Redis**。会话丢了用户重新登录即可，账号丢了就是事故。
